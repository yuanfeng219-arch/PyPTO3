## 开场：一个真实的下午

**发生在 pypto-lib 的一次调试**

一位算子开发者在改 DeepSeek 的 attention kernel。改完，跑起来，**输出有 7% 的值是错的——而且每次跑，错的位置都不一样**。没有报错，没有警告，程序正常退出，返回码为 0。

他往下挖。翻开生成的 orchestration C++，发现同一块 KV cache 被两个 reshape 视图分别标成了 `add_input` 和 `add_output`。**于是他直接动手改了这两行生成的 C++**，改成 `add_inout`，重跑——过了。假设被证实：自动依赖分析按 SSA 值追踪读写，而这两个视图指向同一块 buffer，它没看出这里需要一条 WAR 边。

但他不能把手改的 C++ 提交进去。**于是他往 kernel 里插了一句什么都不做的自我拷贝**——`t[i:i+1] = t[i:i+1]`——只为了骗依赖分析器把这个张量标成 inout。这段代码至今还在主干里。

> **这一个下午里藏着这份报告的全部主题：错误是沉默的；抽象只能向下、不能向上；用户最终靠的是民间偏方，而这个偏方永远不会变成产品知识。**

出处 `pypto-lib#481`。同类还有 `pypto-lib#419`（手改生成 C++ 来验证假设）、`simpler#1012`（自己 fork 一个 patch 才能拿到计时）。

## 全景：五类人，五种失败方式

这条栈上有五种截然不同的工作。他们用不同的工具、在不同的层出错、对"好"的定义也不一样。把他们笼统当作"开发者"，是设计资源上最大的浪费。

| 角色 | 一天在做什么 | 失败长什么样 | 最痛的一件事 |
| --- | --- | --- | --- |
| **算子开发者** | 用 `pl.*` 写 attention / matmul kernel，追精度和性能 | 编译通过，结果全零或部分错 | 没有任何东西告诉他哪里错了 |
| **编译器 Pass 开发者** | 写和修 IR 变换、codegen、verifier | 改 A 处，B 处在三周后炸 | Pass 之间的契约是隐性的 |
| **后端 & ISA 工程师** | MLIR lowering、自动插同步、指令语义 | 自动化生成了能跑但错、或慢 10% 的代码 | 自动化无法被检查 |
| **运行时 & 系统工程师** | AICPU 调度器、依赖图、DFX 观测能力 | 死锁、超时、竞态 | 诊断工具自己也会失灵 |
| **服务 & 部署工程师** | 把模型跑成真实的推理服务 | 跑到第 89 个 token 之后开始胡言乱语 | 底层错误码直接穿透到终端用户面前 |

### 产品分层参考

| 层 | 仓库 | 职责 |
| --- | --- | --- |
| L1 | `pypto-serving` | 推理服务：OpenAI 风格 API、连续批处理、KV Cache 管理 |
| L2 | `pypto-lib` | 模型算子库：Qwen3 / DeepSeek-V4 的 kernel 实现 |
| L3 | `pypto` | 前端 DSL（`pl.*`）+ IR + 数十个编译 Pass + 代码生成 |
| L4 | `PTOAS` | 汇编器：MLIR 方言、自动插同步、lowering 到 C++ |
| L5 | `pto-isa` | 指令集定义 + CPU 仿真器（a2a3sim / a5sim） |
| L6 | `simpler` | 运行时：AICPU 调度器、任务依赖图、ring buffer、DFX |
| L7 | 硬件 / CANN | 昇腾 A2/A3/A5 芯片、驱动、bisheng——不在仓库内，但错误从这里返回 |

## 角色 01 · 算子开发者

> **核心用户。**他要把一个 attention 或 MoE 层，写成能在昇腾芯片上又对又快的 kernel。他懂模型、懂一些硬件，但**他不是编译器专家**——他写的是 Python，他期待的反馈也应该是 Python 层面的。这条栈上所有其他角色，最终都是在为他服务。

主要活动区域：`pypto-lib` / `pypto` · 写 `pl.*` DSL · 日常目标：精度对 + 性能达标

### 他的一次迭代要走完这条路

| # | 阶段 | 卡点 | 痛感 |
| --- | --- | --- | --- |
| 01 | 写 kernel | 手写三层切分循环；怕 UB 溢出反复调结构；换并行方式要整段重新缩进 | 中 |
| 02 | 编译 | 报错来自 MLIR / C++；不告诉你是哪一行 Python；首次编译可能直接超时 | **高** |
| 03 | CPU 仿真 | 过了不代表真机能过；仿真与硬件语义有已知分歧 | 低 |
| 04 | 上真机 | 要先 export 一串环境变量；挂死时只有一个错误码 | **高** |
| 05 | 比精度 | 只知道"不对"，不知道哪一步开始不对；**精度一挂，泳道图就不生成了** | **高** |
| 06 | 看性能 | 能测量，不能归因；看得到慢，看不出为什么慢 | 中 |
| 07 | 调优 | 没有系统化的优化语汇；靠口传心授和试错 | 中 |

### 关键痛点

#### 痛点 1 · 系统主动告诉他"一切正常"，然后给出错误答案

这是这个角色最贵的痛，因为它**攻击的是判断力本身**：他无法信任"编译通过"这四个字，于是每一次改动之后都要用全套 golden 比对来自证清白。他的迭代速度因此被锁死在最慢的验证环节上。

失败的形态五花八门，但共同点是*没有任何一处界面提示过异常*：

- `pl.concat` 因为缺少一个 not-inplace 标记，被内存复用把目标别名到了源上，返回错数据 — `pypto#2007`
- `pl.matmul(..., b_trans=True)` 在 Tile 路径上参数被静默丢弃，编译出错误的数学 — `pypto#2264`
- 把算子结果赋给 `pl.Out` 参数，什么都没写进去 — `pypto#2352`
- 写在 incore 块外面的语句被编译器直接忽略，不给警告 — `pypto#919`
- `pl.split(UP_DOWN)` 静默误编译含行归约的 scope，数值错误无报错 — `pypto#1864`

> 用户自己已经指出了正确的产品形态——他把 issue 标题写成：**"pypto 静默输出全零……*本应是一个编译期诊断*"**。他不是在报 bug，他是在指定这件事应该以什么形式被暴露。
>
> — `pypto#1525`，标题以 `[DX]` 开头

#### 痛点 2 · 出了事，他要靠考古才能知道是哪一步坏的

编译流水线有数十个 Pass。当结果不对，他面对的是一堆 IR 快照文件和一个问题：**哪一个 Pass 第一次把我的意图改错了？** 今天这个问题完全由人力回答——打开几十个文件，肉眼 diff，未改动的 Pass 还在制造噪声。

更麻烦的是，Pass 的名字对他来说是完全陌生的词汇。`ConvertTensorToTileOps`、`ExpandMixedKernel`、`LegalizePTOBufferReuse`——这些是编译器团队的语言，不是算子开发者的语言。**即使他找到了那个 Pass，他也不知道那意味着他该改哪一行代码。**

而快照本身还不完整：Pass dump 会省略隐式的 tile layout，恰恰让 layout 类问题最难定位 — `pypto#2088`。

#### 痛点 3 · 工具偏偏在最需要的时刻缺席

这一条最值得设计师记住，因为它是纯粹的产品决策失误，与技术难度无关。

**当精度比对失败时，泳道图不生成。**原因是执行流程被一个 try/except 整体包住，精度不过就走异常分支，可视化产物一起没了 — `pypto#1042`。也就是说——*出问题的时候，你恰好失去了用来看问题的那个工具*。

同一模式反复出现：

- 依赖图在图变大时把父进程拖到被系统杀掉 — `pypto#1517`
- 卡死诊断对几乎所有卡住的任务都打印 `kernel_id=-1`，等于什么都没说 — `simpler#731`

**观测工具在正常情况下工作良好，在异常情况下失效——而它存在的意义正是为了异常情况。**

#### 痛点 4 · 抽象层次退步了，他被迫回到硬件细节里

一位开发者写了一整篇讨论：PTO 2.0 时他只需声明 tile shape，框架自动生成切分循环；PTO 3.0 取消了这个接口，他必须手写三层嵌套循环来切 m/k/n，RMSNorm 的大 h 维也要自己写内层循环。为了避免 tile 溢出 UB，**他还得反复重构代码结构、增加循环层级** — `pypto#628` / `#630`。

他的原话是在问设计意图：*"PTO 3.0 取消 tile shape 设置的初衷是什么？是否考虑过上述易用性问题？"* 这是一个用户在替产品追问它自己的抽象边界。

类似的摩擦还有：`pl.spmd` 和 `pl.parallel + pl.at` 之间切换需要把整段代码重新缩进 — `pypto#1647`。两种表达同一件事的方式，在语法上却不兼容，让"试一下另一种并行方式"变成一次成本不小的重构。

#### 痛点 5 · 优化是门手艺，不是产品能力

最有力的证据不是抱怨，而是**一位用户自己做出来的产品**：他写了一份自包含 HTML"性能优化语法图鉴"，把 15 类 PyPTO 优化语法按算法 / 核内 / 调度三层整理；又写了一份记录 20 组调优实验的泳道图实录，每组给出改动前后代码、原因、性能数据、精度结果、泳道截图，*以及失败的尝试* — `pypto-lib#828`。

他甚至在 issue 里附上了阅读说明和方法论骨架——*"现象 → 假设 → 实验 → 归因 → 精度验证"*，还提醒读者后面的章节会修正前面的结论。

> 当用户开始自建知识产品、并为它写使用说明时，说明产品侧存在一个明确的、未被满足的一级需求。**这份图鉴本该是产品的一部分。**

### 他真正期望的

- **反馈要说我的语言。**我写的是 Python，请用我那一行 Python 回答我——不是 MLIR，不是六位错误码，不是 `<string>:15`。
- **不要让我在无声中犯错。**宁可给我一个可以关掉的警告，也不要给我一个正常退出的错误结果。
- **帮我回答"从哪一步开始不对"。**这是我每次调试都要问的唯一问题，而它今天完全由我人工回答。
- **出问题时工具要还在。**失败恰恰是我最需要观测的时刻。
- **抽象要能双向。**让我在需要时下沉到细节，但不要强迫我一直待在那里。
- **告诉我为什么慢，而不只是多慢。**测量我已经有了，我缺的是归因和建议。

### 设计机会点

**A1 · 编译置信度报告：让"编译通过"变成一句有内容的话**
把二元的成功／失败，换成一份说得清楚的产出：哪些部分被完整校验、哪些走了启发式路径、哪些模式历史上与静默错误相关、这份产物在什么环境下有效。产品内部已有两个方向相近的提案——警告验证系统 `pypto#808` 与低于 warning 的性能提示通道 `pypto#1180`——**但它们是分别提的、没有共同的呈现层。把它们收敛成一个用户读得懂的产出，正是 UX 的工作。**

**A2 · 首次偏离定位：把"哪一步坏的"从人的活变成系统的活**
用户给出"这个张量本该是什么"，系统回答"在第 17 个 Pass 之后不再成立"，并同时给出 IR 变化、对应的源码行、以及历史上相关的 issue。交互规格已经有人写全了 `pypto#2134`——缺的是把它从一个工具请求，提升为遇到数值问题时的默认入口。**关键设计动作是那层翻译：Pass 名必须被翻译成算子开发者听得懂的话。**

**A3 · 诊断产物与失败解耦**
最低成本、最高确定性的一项。凡是用于诊断的产出（泳道图、依赖图、张量快照），都不应该被任何"成功"条件所门控——失败路径反而应该*加大*采集力度。这一条改完，用户在最痛的时刻手里就有牌了。

**A4 · 把民间偏方收编成产品语汇**
那句骗过依赖分析的自我拷贝、那份自制的优化图鉴，都是用户在产品之外自行发育出来的知识。设计上的做法是**给它们一个官方的表达方式**——比如显式的依赖声明语法、比如产品内的优化手册——让偏方变成 API，让经验变成文档。

## 角色 02 · 编译器 Pass 开发者

> 他维护数十个 IR 变换、代码生成器和验证器。他的敌人不是难题，而是**看不见的耦合**——他改一个 Pass，另一个 Pass 在几周后以完全无关的形态崩掉。

主要活动区域：`pypto` · C++ / Python 混合 · 日常目标：改动不破坏别人

### 关键痛点

#### 痛点 1 · Pass 之间的契约是隐性的，靠口头和惯例维持

最典型的一族问题：**变量的"身份"到底是什么。**一部分代码用指针判断同一性，另一部分用变量的显示名 `name_hint_` 判断——于是两个碰巧同名的变量被当成同一个，或者同一个变量在改名后被当成两个。

这个模式在至少六个独立 issue 里以不同面貌出现（`pypto#616` / `#648` / `#649` / `#650` / `#666` / `#1244`），最后不得不专门开一个 issue 来清点"还有哪些地方在这么干"。

这不是某个人写错了。**这是因为"变量身份"这个契约从来没有被显式表达过**，每个人只能按自己的理解实现。

#### 痛点 2 · IR 的打印和解析不可逆，破坏了最基本的自检手段

"打印出来再读回去，应该得到同一个东西"——这是编译器最朴素的自检。但这条性质在这个栈里反复被破坏：类型信息在打印时丢失、常量的 dtype 分辨不出来、某些字段打印后解析器不认（`pypto#1259` / `#1260` / `#1261` / `#1278` / `#1498`）。

后果不只是不整洁：**它让"用 IR 快照来定位问题"这条路本身变得不可靠**——而这正是角色 01 唯一的调试手段。

#### 痛点 3 · Pass 的知识只存在于人脑和代码里

有一批 issue 是同一个人一次性开的：为 Simplify、OutlineHierarchyScopes、InferTileMemorySpace、ResolveTransposeLayout、SplitVectorKernel 等十来个 Pass 补文档（`pypto#1161` → `#1171`）。

另外还有一条独立 issue 指出：**文档里 Pass 的排列顺序，和实际执行顺序对不上** — `pypto#375`。换句话说，即便有文档，它描述的也不是正在跑的那条流水线。

### 他真正期望的

- **把隐性契约变成显式的、机器可检查的东西。**而不是靠"你应该知道"。
- **让我在提交前就知道我破坏了什么**，而不是等下游同事三周后来找我。
- **Pass 文档要和流水线本身同源**，否则它只是又一处会漂移的信息。

### 设计机会点

**B1 · Pass 契约的可视化**
每个 Pass 声明它需要什么前置性质、保证什么后置性质。产品里已经有 `PassProperties` 这样的机制雏形——**UX 的价值在于把它做成一张人能看懂的流水线图**：谁依赖谁、在哪一步某个性质开始成立、我这次改动动了哪几条边。

**B2 · 从代码生成流水线文档**
彻底消除"文档顺序与执行顺序不符"这类问题的唯一办法，是让文档不再是手写的。这与角色 01 的 A2（首次偏离定位）共用同一套数据，两者应该一起设计。

## 角色 03 · 后端 & ISA 工程师

> 他负责把 IR 落到真实指令上，包括这条栈上最受欢迎、也最令人不安的能力：**自动插入同步**。这个角色的痛点非常集中，几乎全部围绕一件事——自动化做了决定，但没人能检查它做得对不对。

主要活动区域：`PTOAS` / `pto-isa` · MLIR / C++ / 硬件手册 · 日常目标：生成又对又快的指令

### 关键痛点

#### 痛点 1 · 同一个自动化功能，同时是卖点、是 bug 源、也是性能损失

围绕 `--enable-insert-sync` 这一个开关，issue 呈现出一个完整的**信任崩塌曲线**：

| 阶段 | 证据 |
| --- | --- |
| **生成得不对** | set / wait 配对错误 `#10`；漏掉必要的同步导致结果错 `#194`；循环零迭代时漏 MTE2→V `#533`；追踪不到子视图的别名 `#536` |
| **生成得会死锁** | 在示例上直接生成死锁 kernel `#112`；FlashAttention 编得出来但跑起来死锁 `#622`；**同一份输入，v0.17 正常、v0.22 挂死** `#450` |
| **生成得慢** | 动态 GEMM 比手工同步慢 10% `#226`；向量 kernel 同样慢 10% `#233`；比 torch_npu 和手工版都慢 `#643`；**删掉自动插的一道屏障，正确性不变、吞吐提升到 165 TFLOP/s** `#646` |

这条曲线的终点很清楚：**用户会退回到手工同步。**而那正是这个功能本来要替他省掉的事。

#### 痛点 2 · 同样的输入，不保证同样的输出

最极端的一例：同一份 MLIR 输入，多次运行产生不同的 C++ 输出，**其中一部分计算结果是错的** — `PTOAS#541`。这直接摧毁了"复现"这个概念——用户无法确定他看到的问题是自己代码的问题，还是这一次编译的问题。

叠加上版本漂移：

- 零算术指令变更，结果却从一个版本回归到另一个版本 — `PTOAS#1111`
- 编译时间从 1–2 分钟涨到 8 分钟 — `PTOAS#586`
- 某个 kernel 的编译慢了 160 倍 — `PTOAS#950`

*"我的环境和上周一样吗"成了一个需要认真回答的问题。*

#### 痛点 3 · 文档描述的是另一个版本的产品

这个角色被文档误导的频率很高，因为他必须依赖规格文档而不能靠读源码：

- 解析器不接受文档里写的语法 — `PTOAS#106`
- 文档里有的算子实现里不存在 — `PTOAS#107`
- 文档写的参数名和实现要求的不一致 — `PTOAS#108`
- 两条排序指令在手册里被写错 — `PTOAS#326`（同一问题在另一个仓库被重复提了一次 `pypto#664`）

### 他真正期望的

- **自动化要能解释自己。**告诉我你为什么插了这道屏障，我才可能相信它、或者有依据地删掉它。
- **自动化要能被局部关掉。**全开或全关是个太粗的开关——我需要在一个区域里接管它。
- **结果要可复现。**同样的输入必须给同样的输出，否则一切调试都失去地基。
- **规格文档要有权威性**，否则我只能读实现，那文档就等于不存在。

### 设计机会点

**C1 · 可解释的自动化：每个自动决策都能追问"为什么"**
插同步、复用缓冲、选择切分——这些自动决策今天都是无声发生的。让每一个都携带理由，并允许用户在局部覆盖它。**这不是把控制权还给用户，而是把"理解"还给用户**——理解之后，他才会重新信任自动化。

**C2 · 自动 vs 手工的并排对照**
既然"比手工慢 10%"是反复出现的话题，就把这个对比做成产品能力：同一个 kernel，自动同步与手工同步的产物、时序、性能并排呈现。**把一个反复出现的争论，变成一个可以随时自己回答的问题。**

## 角色 04 · 运行时 & 系统工程师

> 他造的是别人用来看问题的东西——调度器、依赖图、泳道图、张量快照。这个角色的处境有一种特殊的讽刺：**他建设了整条栈的观测能力，而他自己的问题最难被观测。**

主要活动区域：`simpler` · C++ / AICPU / 设备侧 · 日常目标：不死锁、看得见

### 关键痛点

#### 痛点 1 · 系统只肯说数字，不肯说人话

当驱动调用失败，日志里只有一个裸整数。他自己写下的诊断是：用户拿到一个 `507018`，然后**得去找一个知道 CANN 码表的人** — `simpler#1350`。

这个 issue 里最值得注意的是它的取证过程——他把这些错误码的含义在仓库里找到了至少四个存放处：一段注释块、一个 pytest 常量集、一份人工排查表格、若干散落的代码注释。**知识一直都在，只是从来没有出现在用户看到的那一行日志上。**

而正确的做法就在同一个代码库里：运行时已经有一处会打印 `S1:running-stalled` 而不是裸的 `1`。*缺的不是能力，是把它定为全局规范的那个决定。*

#### 痛点 2 · 观测能力是五个各自独立的工具，不是一个体验

他自己整理的清单很说明问题：五个 DFX 特性（张量快照、泳道图、硬件计数器、依赖图、作用域统计），**各有独立开关、独立输出目录、独立查看脚本，其中两个还标注着"要你自己去跑 viewer"** — `simpler#995`。

看一次泳道图的完整路径是：跑测试 → 生成 JSON → 转成 Perfetto 格式 → 下载文件 → 打开网页。有人直接把这段路称为"繁琐且非 IDE 原生"，并指出 Perfetto 的依赖边渲染受时间戳约束，**根本画不出用户真正想看的关系** — `simpler#512`。

配置面同样碎：issue 正文里出现过 110 个不同的运行时环境变量名。一份逐条列举的提案总结道：*"全集、有效范围、2 的幂约束只能靠读 C++ 源码才看得到；无效值被静默忽略。"* — `simpler#834`

#### 痛点 3 · 观测能力本身会成为故障源

这是最需要设计介入的一类：诊断在压力下反噬系统。

- 张量快照的主机端来不及消费，反而成了 kernel 挂死的根因 — `simpler#860`
- 依赖池在全量快照的背压下死锁 — `simpler#959`
- 用于诊断的插桩本身把满负载的同步搞超时 — `pypto#1931`

**用户因此学会了一件很糟糕的事：出问题时不要开诊断——因为诊断会改变问题。**

### 他真正期望的

- **诊断信息要自带含义**，永远不要只给一个数字。
- **观测要有一个入口，而不是五个开关。**
- **观测必须是可信的、低干扰的**——它不能成为它要观测的那个问题的一部分。
- **配置要可发现、可校验**，而不是散落在源码里的环境变量。

### 设计机会点

**D1 · 症状驱动的诊断工作台**
今天用户必须先知道每个工具叫什么、干什么，才能开始排查。反过来设计：**入口是四个症状**——结果不对 / 跑不动 / 太慢 / 挂死——由系统决定采什么数据、并排哪几个视图。三个独立的 issue（IDE 内泳道预览、文本版依赖图、作用域统计可读性）指向的其实是同一个缺失的产品。这是**本报告中投入产出比最高的一项**：底层数据全部齐备且已文档化，缺的纯粹是信息架构。

**D2 · 错误码的一生：从数字到下一步动作**
码 → 含义 → 常见成因 → 建议动作 → 历史上相似的 issue。成本极低，因为这些知识已经在仓库里写过四遍了；**它只是从来没有走到用户面前。**

**D3 · 把"观测的代价"变成可见的、可选的**
用户需要在开启诊断前就知道它会带来多少干扰。设计上表现为分级采集与明确的代价标注——让"开不开诊断"从一次赌博，变成一次知情选择。

## 角色 05 · 服务 & 部署工程师

> 他站在最上层，也离真实用户最近。他关心的东西和下面四个角色完全不同——他关心首字延迟、每字延迟、长时间跑会不会崩。而这条栈目前**还没有为他准备好语言**。

主要活动区域：`pypto-serving` · 对标 vLLM · 日常目标：稳定、可预期、指标可信

### 关键痛点

#### 痛点 1 · 指标口径不对，导致对产品的判断也不对

性能报告把预填充和解码混成一个端到端吞吐数字。结果：**报告上写着 3.19 tok/s，而稳态解码的真实吞吐是约 22 tok/s——低估了七倍** — `pypto-serving#28`。原因是一次性的首次派发预热（约 6 秒）被算进了每次请求的成本里。

这是一个纯粹的信息设计问题，但它的杀伤力是战略级的：*如果团队照着这个数字做决策，他们会去优化根本不是瓶颈的东西。*

#### 痛点 2 · 长时间运行才暴露的问题，现有验证根本覆盖不到

一次真实的部署验证：请求 130 个 token，API 返回 200，报告说 130 个 token 全部生成完毕。但**前 89 个 token 是一段连贯的介绍，第 90 到 130 个 token 退化成了重复的 JSON 片段** — `pypto-serving#131`。

这个 issue 自己点破了要害：*"现有的精度守卫只生成 10 个 token，所以它覆盖不到这种长生成的失败。"* 验证的时间尺度，和故障的时间尺度不匹配。

#### 痛点 3 · 底层的错误码，直接穿透到了服务层

离线批量生成缺少 token 级的分块预填充，长提示词直接把任务环堆死锁——**而它在服务层报出来的，仍然是那个 `507018`** — `pypto-serving#91`。同样的还有多卡 8 张的性能验证、前缀缓存冷热命中序列导致的预填充崩溃 — `pypto-serving#41`。

抽象层在这里彻底失效：*一个做推理服务的人，被迫理解 AICPU 调度器的环形缓冲区。*

### 他真正期望的

- **指标要用部署领域的语言**——首字延迟、每字延迟、输出吞吐，而不是混合出来的端到端数字。
- **验证的尺度要匹配真实使用的尺度。**10 个 token 的守卫保护不了 130 个 token 的生成。
- **下层的失败要在到达我之前被翻译。**我不应该需要理解调度器。

### 设计机会点

**E1 · 面向部署的指标语言**
采用这个领域已经形成共识的口径（对标 vLLM），并明确区分一次性成本与稳态成本。**指标定义是产品对世界的表态**——它决定了团队会去优化什么。

**E2 · 分层的错误翻译**
每一层都有责任把下层的失败翻译成本层的语言。服务层应该说"上下文过长导致资源耗尽"，而不是把一个设备错误码原样抛给调用者。这与 D2 是同一套机制在不同层的应用。

## 横切 · 新人与外部贡献者

> 这个群体在数据里声音最小——因为**被劝退的人不会留下 issue**。但仅有的几条已经足够说明第一天的样子。

### 四道门，一道比一道靠前

**装不上**——四个组件要分别安装配置，版本不匹配是"难以调试的失败"的常见来源 `pypto#1024`；conda 环境下装不上 `simpler#474`；跨仓库安装留下的陈旧产物导致导入失败 `simpler#531`。

**跑不起来**——有人开的第一个 issue 就是：*"我没法照 README 说的跑测试，报 ModuleNotFoundError。"* `pypto#63`。另一条：全新安装后的第一次编译总是超时 `PTOAS#380` / `pypto-lib#50`。**第一次编译超时——这是一个新用户能遇到的最糟糕的第一印象。**

**看不到**——一次审计发现：前端 DSL 的 **216 个公开符号全部写了 docstring，一个不缺，其中不乏数千字的详细说明——但没有任何工具把它们发布出来**，用户只能靠 IDE 悬停才能读到 `pypto#2120`。同时手写指南在持续漂移。

**问不着**——外部贡献者的 issue 里"怎么做"类问题占比明显更高，而他们通常只能靠开 issue 来问，因为没有别的入口。

### 设计机会点

**F1 · 让 216 个已写好的 docstring 见天日**
全报告中成本最低、确定性最高的一项。内容已经存在且质量很好，缺的只是发布通道和一条防止再次漂移的 CI 约束。

**F2 · 一条被守护的首日路径**
从安装到跑通第一个例子，定义为一条**被自动化守护的路径**——任何一步坏掉都应该像功能回归一样被对待。今天它是靠新人撞墙才被发现的。

## 贯穿：把五个角色串起来的三条主线

上面五个角色看起来痛在不同的地方。但把他们叠在一起看，会发现是同三个机制在不同层反复上演。这三条主线，才是设计真正的着力点。

### 主线一 · 自动化的信任赤字

这条栈的每一层都有一个引以为傲的"自动"能力。而**每一层的自动，都是它上一层的恐惧来源**：

| 自动化能力 | 它承诺的 → 它带来的 |
| --- | --- |
| 自动内存复用 | 节省缓冲区 → 也会把目标别名到源上，**静默给出错数据** |
| 自动依赖分析 | 省去手写依赖 → 也会漏掉 WAR 边，**逼用户插入假的空操作** |
| 自动插入同步 | 省去手工同步 → 也会漏同步、造死锁、**比手工慢 10%** |
| 自动切分与调度 | 省去手工切分 → 也会做出坏决策，**而且不解释为什么** |

注意这不是"自动化做得不够好"。任何自动化都会有做不对的时候。**真正的缺口是：当自动化做了一个决定，用户没有任何办法知道它做了什么决定、为什么这么决定、以及如何在局部推翻它。**

> **设计命题不是"要不要自动"，而是"自动化如何向人交代"。这是这个产品最核心、也最有想象空间的设计问题。**

### 主线二 · 抽象是一道单向门

抽象向下工作得很好：你写几十行 Python，产出几千行 C++ 和设备指令。但**抽象向上完全失效**：当下面出了问题，没有任何机制把它翻译回你写的那几十行 Python。

于是用户被迫穿透抽象，去他本不该去的地方：算子开发者读生成的 C++、手改 `add_inout`；服务工程师去理解 AICPU 的环形缓冲区；每个人都在读不属于自己那一层的错误信息。

**抽象承诺了"你不需要知道下面"，但在失败时收回了这个承诺——而失败恰恰是最需要这个承诺的时刻。**

好消息是，这条主线对应的解法非常明确，也几乎全是信息设计工作：源码回溯、错误翻译、术语翻译、分层诊断。*它不需要编译器能力的突破。*

### 主线三 · 工具在最需要的时候失效

这条主线在五个角色里都出现过，而且形态惊人地一致：

- 精度比对失败 → **泳道图不生成**（你恰好失去了看问题的工具）
- 依赖图变大 → **渲染器把进程拖到被杀掉**（复杂场景才需要看图，而它只在简单场景能用）
- 任务卡死 → **诊断打印 `kernel_id=-1`**（等于什么都没说）
- 开启全量快照 → **反而把系统压死锁**（观测改变了被观测的对象）

这四件事在工程上互不相关，但在体验上是同一件事：**这些工具是按"正常路径"设计的，而它们存在的全部意义是异常路径。**

> **一条可以直接采纳的设计原则：凡是用于诊断的能力，都必须在失败路径上比在成功路径上更强。**

## 收敛：如果只做三件事

按"能影响多少角色 × 需要多少新能力"排序。第一梯队的共同特征是：**底层数据全部已经存在，缺的只是把它组织成人能用的形态。**

| 优先 | 做什么 | 受益角色 | 需要新能力吗 |
| --- | --- | --- | --- |
| **第一** | **症状驱动的诊断工作台**<br>按"哪里不对"而不是按工具名组织；一次采集、一处查看、多视图联动；失败路径优先 | 算子开发者 · 运行时 · 服务 | 否——五类数据齐备 |
| **第一** | **让每条诊断都能回到用户那一行**<br>源码回溯 + 错误码翻译 + 术语翻译；跨层统一为一条规范 | 全部五个角色 | 部分——Span 机制已有雏形 |
| **第二** | **自动化的可解释与局部接管**<br>每个自动决策携带理由，并允许在局部覆盖 | 算子开发者 · 后端 · 编译器 | 是——但价值最高 |
| 随手 | **诊断产物与失败解耦**；**发布已写好的 216 个 docstring**；**部署指标口径修正** | 各自对应角色 | 否——纯粹是决策 |

关于第三行值得多说一句。前两项是"补齐"——把已经缺失的体验补上；**第三项才是"超越"**。在编译器工具这个品类里，"自动化如何向人交代"还没有成熟范式；如果这个产品把它想清楚了，那会是一个别人短期内学不走的差异点。

而它的门槛并不在技术：编译器内部当然知道自己为什么插了那道屏障、为什么复用了那块缓冲区。**缺的是有人决定把这件事说出来，并且决定用什么形式说。**那正是这个岗位的工作。

### 一个用来对齐讨论的靶子

把三条主线放进同一屏的样子：

```
error[E0442]  Out 参数被重新绑定到已分离的值，写回丢失
  --> deepseek_v4/decode_indexer.py:214:9
   |
214|         y = pl.matmul(t1b, w2, out_dtype=pl.FP32)
   |             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 结果未写入 Out 参数 y
   = 影响：设备端输出为全零，运行时不会报错
   = 修复：改为 y[:] = pl.matmul(...)，或用 pl.assemble 显式写回
   = 相关：pypto#1525（已修）· pypto#2352（同族）

note  本次编译中 MemoryReuse 复用了 3 个缓冲区
   = 查看它的决策依据：pypto explain --pass MemoryReuse
```

这里同时体现了：**回到用户那一行**（主线二）、**说清后果而不只是现象**（主线三）、**自动化主动交代自己做了什么**（主线一）。这不是设计稿，是一个用来对齐讨论的靶子。

## 方法与局限

**怎么做的**：全量解析 hw-native-sys 组织下 7 个活跃仓库的 1 465 个 issue（`*_raw_pages.json` 按要求未读取），先做结构化分类定位高信号区域，再对其中的关键 issue 做正文精读，还原每个角色的真实工作流。报告中每一处引用都可回溯到具体 issue 编号。

**四点必须说明的局限**：

1. **没有包含评论内容**——真实的排查往往发生在评论区，那里可能有比正文更强的证据，尤其是那些讨论最激烈的 issue。
2. **样本以内部团队为主**，外部开发者的上手体验被系统性低估，"新人"那一节的证据基础明显薄于其他角色。
3. **issue 只记录被写下来的痛**——那些让人默默放弃、绕过、或者干脆不用某个功能的体验，从不出现在这份数据里。
4. **角色是从行为模式归纳的，不是团队的实际组织划分**；同一个人可能同时扮演多个角色。

**建议的下一步**：这份报告能告诉你"哪里痛"，但告诉不了你"痛的时候人在想什么"。建议针对角色 01（算子开发者）做 5 场情境访谈，让他们复盘一次真实的"结果全零"排查全过程——issue 记录的是结论，只有访谈能拿到过程，而设计需要的正是过程。
