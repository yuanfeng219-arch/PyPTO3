NVIDIA Dynamo · UX / Product Perspective · Updated 2026-08-29

Dynamo 的核心产品价值，正在从“部署框架”走向“意图驱动的推理系统优化闭环”。

本材料只保留 NVIDIA / Dynamo 产品分析。技术细节仅用于解释产品边界、用户旅程和交互逻辑，不展开底层实现原理。

Executive summary

一页结论

Intent
DGDR 把用户输入从完整部署参数上移到 model / workload / SLA / hardware constraints。
Search
Profiler 负责生成、评估、排序并选择部署方案，最终生成 DGD。
Measure
AIPerf 负责对真实 deployment 发压、sweep、重复实验与结果分析。
Operate
Observability + Planner 把部署前选型延伸到运行时监控与容量调整。
当前最重要的产品判断：Dynamo 已经形成“Intent → Search → Deploy → Measure → Observe → Adjust”的工程闭环，但用户体验仍由 DGDR YAML、Profiler、AIPerf、Grafana、Kubernetes 等多个触点共同完成。

Profiler 与 AIPerf 的重叠不是功能重复，而是同一“Configuration Evaluation”任务在不同阶段、不同自动化程度下的两种入口。

Product positioning

Dynamo 是什么产品？

事实Dynamo 是面向生成式 AI 推理的分布式 serving 平台。它不替代 vLLM、SGLang、TensorRT-LLM 等 inference engine，而是在它们之上组织部署拓扑、请求路由、KV 相关能力、容量与运行时管理。

部署层

把模型、硬件和后端组织成真正可运行的 serving deployment。

优化层

通过 Profiler / AIConfigurator / AIPerf 找到更适合 workload 与 SLA 的配置。

运营层

通过 metrics、traces、Planner 等能力理解并调整运行中的服务。

产品定位：不是“配置一个模型”，而是“让一个模型在指定 workload、SLA 和硬件条件下形成可部署、可验证、可持续调节的推理系统”。
Product object model

更适合 UX 的产品对象模型

Intent Model / Workload / SLA / Hardware DGDR Deployment Request Candidate 可行配置 Evidence Estimated / Measured DGD 可执行部署方案 Deployment 真实运行实例 Benchmark Run AIPerf 实验 Runtime State 服务状态与指标 Planner Decision 运行时容量调整
Intent / DGDR→Candidate Configurations→Evidence→DGD→Deployment→Benchmark / Observe→Adjust

从产品分析角度，DGD 是“执行层 artifact”，而 DGDR 更接近用户意图层；Profiler 与 AIPerf 则是为 Candidate 积累证据的两种机制。

Deploy by intent

DGDR / Auto Deployment：把用户输入从 Configuration 上移到 Intent

事实DGDR 是 Dynamo 的 deploy-by-intent 路径。用户描述 model、workload、可选 latency targets、hardware limits、backend 等要求，Profiler 再生成真正的 DGD。用户不必从一开始手工决定所有 worker、parallelism 和 replica count。

DGDR：需求表达

关注“我要跑什么、面对怎样的流量、希望达到什么目标、资源边界是什么”。

DGD：执行方案

关注“最终 worker topology、parallelism、replicas、resources 和 platform features 应该是什么”。

DGDR→Profiler→Selected Configuration→DGD→Serving
产品价值：这是 Dynamo 最明确的抽象层升级：用户表达“目标与约束”，系统负责推导“实现配置”。
Configuration search

Profiler：当前更像自动化 Configuration Search Engine，而不是可视配置比较器

事实Profiler 是 DGDR Auto Deployment 背后的核心 engine：验证请求、搜索候选配置、评估、pick 最佳配置、生成 DGD。

Rapid vs Thorough：本质是 Evidence Quality 的选择

RapidThorough
候选来源Profiler / AIConfigurator 生成。Profiler 枚举候选 parallelization mappings。
评估方式性能模型 / simulation 估算。把候选部署成真实 Kubernetes workload，并用 AIPerf benchmark。
证据类型EstimatedMeasured
成本约几十秒，无 profiling GPU。通常 2–4 小时，需要真实 GPU capacity。
定位快速 sizing、迭代、CI。生产调优或需要真实数据时。

Profiler 的“选择”当前主要由系统完成

Profiler 会根据 DGDR 中的 workload / SLA 等信息决定 picking mode，并自动选择配置。生成 DGD 后，`autoApply` 再决定是否把最终方案自动部署；它与 Rapid / Thorough 是正交控制。

Generate Candidates→Score / Measure→Rank→Pick #1→Generate DGD→Review or Auto Apply
UX 判断：Profiler 当前已经非常“自动决策化”，但 candidate → ranking → selected plan 之间的解释与人工比较体验相对弱。这是自动化能力领先于 decision UX 的典型状态。
Benchmark & analysis

AIPerf：真实 Deployment 的实验执行与结果分析层

事实AIPerf 会向 OpenAI-compatible endpoint 发送真实负载，测量 live deployment；它不负责像 AIConfigurator 一样预测配置。Dynamo 的 Thorough Profiler 也会把 AIPerf 当作真实测量 engine。

Profile / Load

定义 request shape、request rate / concurrency、重复次数等 benchmark 条件。

Sweep / Multi-run

对多个 workload intensity 或实验条件重复运行，并计算 confidence / variance。

Plot / Dashboard

把单 run 与多 run 结果转成时序、Pareto、trade-off 与 configuration comparison。

AIPerf Web Dashboard 当前能做什么

能力用户价值
Multi-run comparison同时比较多个实验或多个 deployment 结果。
TTFT vs Throughput查看交互时延与吞吐之间的 trade-off。
Throughput/GPU vs Latency / Interactivity观察资源效率与体验之间的 Pareto frontier。
Joint uncertainty用置信区间而不是单一平均值表达实验可信度。
Run filtering控制哪些实验进入比较。
Metric switching在 avg / p50 / p90 / p95 / p99 等统计口径间切换。
Config viewer点击 datapoint 回看对应的完整 run configuration。
Custom plots / export支持专家进一步探索与输出分析结果。
产品定位：AIPerf Dashboard 是“Experiment Result Explorer”，不是 production observability dashboard，也不是 configuration generator。

Experiment model

NVIDIA 当前实际上已经形成“两层实验空间”

Configuration Space

topology、parallelism、replicas、backend / runtime settings 等决定“系统以什么方式提供服务”。Profiler 主要负责这一层的搜索与选型。

Workload Space

input/output shape、request rate、concurrency、arrival behavior 等决定“如何给这个系统施加负载”。AIPerf 主要负责这一层的实验与 sweep。

Configuration A×Workload Sweep→Performance Curve→SLA / Pareto Evidence
Configuration B×Same Workload Sweep→Performance Curve→Compare with A

AIPerf 支持 parameter sweep、multi-run statistics、confidence reporting；因此它已经不只是“测一个点”，而是在形成较完整的实验基础设施。

产品意义：NVIDIA 的工具边界目前是“Profiler 搜 Configuration，AIPerf 测 Workload 与真实表现”；从用户任务看，这两层天然属于同一个 optimization experiment。
Runtime loop

Observability 与 Planner：部署后的运行时闭环

Observability

回答服务状态、请求、worker、latency、errors 等“现在发生了什么”。

Planner

根据运行时负载与目标动态调整 capacity，例如 prefill / decode worker 数量。

Operator

把期望状态落实到 Kubernetes deployment lifecycle。

产品缺口：当前运行时自动化更强的是“做出调整”，相对较弱的是“把触发信号 → 决策原因 → 资源变化 → SLA 影响”组织成统一、可解释的 decision history。

Dynamo 当前最值得关注的产品体验缺口

较弱

1. Search 与 Compare 之间缺少统一决策层

Profiler 能自动 pick，AIPerf 能比较真实结果，但“候选、证据、推荐理由、人工取舍”并没有被统一成一个产品对象。

2. Estimated 与 Measured 证据分散

Rapid prediction、Thorough benchmark、独立 AIPerf、生产 metrics 属于不同触点，尚未自然累积到同一个 configuration history。

3. Profiler 自动化强于解释

系统可以 rank / pick，但用户对“为什么这个配置最好、哪些约束最关键、替代方案代价是什么”的可视解释有限。

4. AIPerf 强分析、弱决策

Dashboard 擅长展示曲线与 Pareto，但仍主要是 data exploration，而不是直接生成 recommendation / next action。

5. Runtime decision history 不完整

Planner 做动态 capacity 调整后，缺少与实验阶段一致的“原因—变化—结果”可追溯体验。

6. 工具间 context switching 高

用户需要在 DGDR、DGD、AIPerf artifact、Dashboard、Grafana、kubectl 之间保持同一个 mental model。

Product trajectory

从当前产品可以看到的几个明确演进方向

从 Configure 到 Intent

DGDR 明确降低了用户直接操作 topology / parallelism / replicas 的必要性。

从 Estimate 到 Evidence

Rapid / Thorough 把“快但估算”和“慢但真实”变成正式的产品选择。

从单点 Benchmark 到 Experiment

AIPerf 的 sweep、multi-run、confidence、dashboard 让 benchmark 开始具备实验管理雏形。

从人工配置到自动决策

Profiler 自动 rank / pick、Planner 动态调整，都在减少人工逐项配置。

从独立工具到编排

Thorough 直接调用 AIPerf，说明 NVIDIA 已经开始把独立工具能力组合为自动化 workflow。

下一阶段可能是统一 Decision Experience

推断如果继续产品化，最自然的下一层不是更多参数，而是把 candidate、evidence、recommendation、validation、runtime outcome 串起来。

Dynamo 的竞争力越来越不只是“能部署”，而是“能把一个复杂的推理系统从意图、搜索、验证一路推到运行时自适应”。

Final product judgment

最终判断

Dynamo 已经具备一个较完整的推理优化系统骨架：DGDR 负责意图表达，Profiler 负责配置搜索，DGD 负责方案落地，AIPerf 负责真实实验，Observability / Planner 负责运行时闭环。

它目前更像一组高度协同的专业工程能力，而不是统一的一站式产品。最明显的体验机会集中在三个连接处：Search → Decision、Estimated → Measured、Experiment → Runtime。

Intent → Configuration Candidate → Evidence Evidence → Recommendation Deploy → Validation Runtime → Decision History
