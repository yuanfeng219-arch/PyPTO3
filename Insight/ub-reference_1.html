灵衢 UnifiedBus (UB) 参考手册

面向超节点（SuperPoD）的统一互联协议。它要解决的问题只有一句话：把"总线的低时延内存语义"从主板内延伸到整个机房，让上万颗 CPU / NPU / 内存 / SSD / DPU 像一台机器里的部件一样对等互联。本手册同时覆盖概念、硬件层级与现场交付旅程，作为工具链设计的共同底稿。

§00阅读指南

这份手册假定读者没有 UB 背景，用来为超节点交付工具链的设计打底 —— 先把领域概念、硬件层级和现场流程搞清楚，后续用它和产品、架构师对齐。不确定"报文"是什么，从 §01 开始读。

三处必须先纠正的认知

① 不存在 UB-Mem / UB-Link / UB-IO 这三个子协议。这是与 CXL.mem / CXL.io、UALink 的混淆。UB 侧真实存在的是协议语义（Load/Store、URMA 的读写/收发/原子、uRPC）与软件组件（UBS Mem / UBS Comm / UBS IO）。两者不是一回事。

② "L1 / L2 总线交换板"不是灵衢规范里的官方术语。它来自 Atlas 900 A3 SuperPoD 的工程实现（节点内 7 颗 L1 交换芯片 + 总线柜内 L2 交换设备）。交付语境沿用没问题，写规范类文档时要注明出处。详见 §05。

③ 没有"灵衢产业联盟"这个法人实体。目前的生态形态是「华为开放规范 + 灵衢社区 unifiedbus.com + openEuler SIG + 第三方 IP 互通验证」，不是 UALink Consortium 那样的独立联盟。

先把词认全，后面读起来快很多。四类分开看：A 协议语义是"数据怎么走"，B 硬件物理是"东西长什么样"，C 软件栈是"哪个组件干哪件事"，D 管理交付是"现场用什么工具"。缩写全称以官方规范附录 A 为准。

§01预备知识：报文、报文头与分层

这一节是给"看到 NTH / BTAH / 封装 这些词就卡住"的读者准备的。全部用快递做类比，读完再回头看 §03 会顺很多。

1.1 什么是报文

报文（packet / message）就是网络上传输的一个数据包裹。两台机器之间不会把一整个文件当成连续水流送过去，而是切成一个个有固定格式的小块，一块一块发 —— 每一块就是一个报文。

一个报文分成两部分：

一块有多大？单位是字节

报文的长度单位是字节（Byte，缩写 B）—— 1 个字节 = 8 位二进制，大致等于一个英文字符。给你几个可以当尺子用的量级：

东西大小说明
一次 CPU 读内存的最小单位64 B叫一个 cache line。本手册反复出现的"读远端 64 字节"就是它
UB 报文的头（四层加起来）58 B见 §03.2 —— 读 64 B 数据要背 58 B 的头
以太网一个报文的标准上限1,500 B叫 MTU。超过就要切开分多个报文发
数据中心常用的"巨帧"9,000 B把上限调大，减少切片次数与头开销
一张 1 MB 的图片≈ 1,000,000 B按 1,500 B 切 → 要发大约 700 个报文
所以"切成小块"是多小：典型是几十到几千字节一块。这也解释了为什么 §03.3 要专门为 64 B 这种"小得可怜"的访问开一条快车道 —— 按 1,500 B 设计的机制，用来搬 64 B 实在太亏。

报文头（Header）＝ 快递面单

贴在包裹外面的那张纸。写着从哪来、送到哪、怎么处理、这是第几件。网络设备只看面单，不拆包裹。

载荷（Payload）＝ 包裹里的东西

真正要送的数据。对中间的交换机来说它完全不可见，也不关心。

1.2 什么是封装

问题来了：一次传输要解决好几件不同的事 —— 这一跳送到哪块网卡、整条路最终送到哪台机器、丢了要不要重发、这次到底是要读还是要写。如果把这些全写在同一张面单上，会又长又乱，而且改任何一件事都要动整张单子。

网络的解法是分层：每一层管一件事，每一层贴自己的一张面单。发送时从里往外层层套盒，这个过程叫封装（encapsulation）；接收时从外往里层层拆盒，叫解封装。

1.3 逐层封装：一次完整的演示

抽象说完了，走一遍具体的。但先把"应用"这个词落到实处 —— 它不是某个 UB 专用软件，就是普通跑在机器上的程序。

具体场景：计算节点 A 上跑着一个大模型训练任务的进程（比如 PyTorch 的一个 worker）。它算到某一步，需要取一段模型参数。但 A 的内存不够，这段参数其实存在节点 B 的内存里 —— 因为 A 之前向 B 借了一块内存（见 §10 资源池化）。

程序里那行代码可能就长这样：

float w = weights[i];   // 就是一次普通的数组读取

关键点：这个应用完全不知道数据在另一台机器上。它以为自己在读本地内存。是操作系统把 B 的那块内存映射进了 A 的地址空间（UMMU 干的活），所以 CPU 一执行这条读指令，硬件就自动把它变成了一次跨机柜的 UB 事务。
"应用发送指令"不是应用主动决定要发网络请求 —— 它只是读了一个地址，而这个地址恰好在别人家。

下面就跟着这一次读，看报文是怎么被一层层套出来的。目标：从 A 读 B 上的 64 字节。

发送侧：从内往外，一层贴一张面单

步谁在做贴了什么面单面单上写着这时报文长这样
起点应用—"我要读 B 的某个地址，64 字节"〔尚未成形〕
①事务层BTAH 16 Bopcode = READ；服务模式；执行序标签；对方哪个 Jetty 收[BTAH][请求参数]
②传输层RTPH 16 B这是第几号报文；用哪条 TP Channel；丢了怎么补[RTPH][BTAH][参数]
③网络层NTH 12 B目的地的 CNA（24 bit 简短网络地址）[NTH][RTPH][BTAH][参数]
④链路层Ethernet 头 14 B下一跳的 MAC；Ethertype = 0xCAFE[ETH][NTH][RTPH][BTAH][参数]
⑤物理层不贴头把这一串字节编码成光信号，推上光纤〔线上的光〕

路上：中间设备只拆到自己需要的那层

L1 交换芯片

拆开 ① Ethernet 头看"这一跳给谁" → 拆开 ② NTH 看 CNA 决定往哪个口转 → 到此为止。里面的 RTPH / BTAH 它看都不看。

L2 交换设备

同上。它不知道你是在读内存还是写内存，也不需要知道 —— 这就是分层带来的解耦。

为什么这很重要

交换机按固定字节偏移取字段（NTH 永远在第 14–25 字节），不用解析整个包。这是线速转发能做到纳秒级的前提。

接收侧：从外往里，一层拆一张

光信号进来
 └─ 物理层：解码成字节流，做 FEC 纠错
     └─ 链路层：撕掉 Ethernet 头，校验 CRC；看 Ethertype=0xCAFE，知道"这是 UB 报文"
         └─ 网络层：撕掉 NTH，确认 CNA 就是本机
             └─ 传输层：撕掉 RTPH，登记序号；缺号就发 SACK 请求重传
                 └─ 事务层：撕掉 BTAH，读出 opcode=READ 和目的 Jetty 编号
                     └─ 按 Jetty 编号投递到对应应用的接收队列
                         └─ 功能层：应用拿到数据（或 CPU 的 load 指令返回）
对称性：发送时从上往下走一遍协议栈，每层加一张面单；接收时从下往上走一遍，每层撕一张。加的顺序和撕的顺序正好相反 —— 就像套盒和拆盒。这就是"封装 / 解封装"这两个词的全部含义。

1.4 为什么头的大小很关键

把 UB 的四层头加起来：Ethernet 14 B + NTH 12 B + RTPH 16 B + BTAH 16 B = 58 字节的面单。

这意味着：如果你只想读远端 64 字节数据，就要背着 58 字节的头上路 —— 开销接近 50%。小包效率是所有高性能互联协议的核心战场，也是为什么 UB 要为 Load/Store 专门做一条"TP Bypass（传输层旁路）"路径：小粒度同步访问直接绕过完整的传输层封装。

1.6 两组容易混的概念

时延 vs 带宽

时延是"一个包从发出到收到要多久"（单位 ns/μs）；带宽是"单位时间能搬多少数据"（单位 GB/s、PB/s）。两者可以彼此独立 —— 一条高带宽链路完全可能时延很差。
类比：时延 = 快递几天到；带宽 = 一次能发多少件。

消息语义 vs 内存语义

消息语义：我打包一段数据"发给你"，你要准备好收（像寄快递）。
内存语义：我直接用一条 CPU 指令"读你那块内存"，你根本不参与（像直接伸手去对方书架上拿书）。
UB 最大的卖点就是把内存语义做到了跨机柜尺度。

§02灵衢是什么：它填的是哪个空

从一个具体问题讲起，再看它为什么必须造一套新协议。

2.1 先看全景：这东西在 AI 基础设施的哪一层

在讲 UB 之前，先把地图摊开 —— 否则后面所有的"规模""带宽""平面"都没有参照系。

两个方向：Scale-Up 和 Scale-Out

Scale-Up · 纵向扩展

把一台机器做得更大更强 —— 更多卡、更大内存、更快互联。
好处：卡与卡之间近、快、能共享内存。
天花板：一台机器物理上塞不下无限多卡。
UB 主攻这个方向，超节点就是 Scale-Up 做到极致的产物。

Scale-Out · 横向扩展

用更多台机器堆起来。
好处：理论上可以无限堆。
代价：机器之间只能走网络，慢一到两个数量级，且没有内存语义。
超节点之间靠 UBoE 或 RoCE 组成 SuperCluster。

为什么这个区分决定了一切：行业过去十年一直在拼 Scale-Out（堆机器），但 AI 训练的通信特征让 Scale-Out 的效率越堆越差。超节点的赌注是：先把 Scale-Up 的单位做大 10 倍以上（从 8 卡的一台服务器，做到 384 / 8192 卡的一台"逻辑机器"），再去 Scale-Out —— 这样绝大部分通信被关在了快的那一侧。

训练和推理是两种不同的活动

训练 Training推理 Inference
在干什么用海量数据反复调整模型参数，把模型"教会"模型已经练好，拿它来回答问题、生成内容
持续多久一次跑几周到几个月，不能中断（断了要从上一个存档点重来）每次几秒到几分钟，但并发量巨大、7×24 不停
通信特征每一步都要把各卡的梯度加起来再分发（AllReduce），占用 30%~70% 的时间主要是搬运 KV Cache（对话的上下文缓存），容量大、要低时延
为什么也需要超节点模型太大，一张卡放不下，必须拆到很多卡上协同大模型推理同样放不下单卡；且 KV Cache 吃内存，正好吃池化内存
对应手册章节§03.5 弱事务序、§06 平面带宽、§11.6 集合通信§10 内存池化（MemCache 支撑 KVCache）

为什么 384 卡不够，要 8192 卡

逻辑链是这样的：模型参数量变大 → 一张卡装不下 → 拆到更多卡 → 卡之间通信量暴涨 → 通信占比越高，有效算力越低。

关键矛盾：卡加得越多，算力是线性涨的，但通信开销是超线性涨的。所以业界用 线性度 衡量：加一倍的卡，实际性能涨了多少倍？理想是 2 倍，现实往往只有 1.5 倍甚至更低。
UB-Mesh 论文给出的口径是 LLM 训练线性度 95%+ —— 意思是加 10 倍卡能拿到 9.5 倍性能。超节点的全部工程努力，都是在守住这个数字。

2.2 先看问题：算力堆上去了，为什么还是慢

训练一个大模型，模型参数一张卡放不下，只能拆到很多张卡上。拆开之后每一步计算都要交换中间结果 —— 最典型的是 AllReduce（把各卡算出的梯度加起来再分发回去）。

关键事实：AllReduce 在分布式训练中占用 30%~70% 的时间。也就是说，一半左右的时间机器不在算，而在等数据搬运。

更麻烦的是这个搬运有一道断崖：

卡在哪走什么大致时延能用什么语义
同一台机器内的 8 张卡NVLink / UB 等总线百纳秒级直接读写对方内存（load/store）
跨机器RoCE / InfiniBand 网络微秒级，慢一到两个数量级只能打包发消息，CPU 要参与
结论：算力可以靠堆卡线性增长，但"卡与卡之间的对话"不能。一旦超出单机边界，通信就掉进另一个世界 —— 这就是为什么大规模训练的实际有效算力远低于标称算力。互联，而不是芯片，成了瓶颈。

2.5 那为什么不直接改现有协议

把 PCIe / CXL 拉长？

做不到。它们的主从树形结构与短距电气规范是骨子里的设计前提：地址空间由 Root Complex 统一枚举、时序容忍度极小。拉到几十米、上万端点，枚举和时序都会崩。

把 RDMA 做快？

天花板明确。RDMA 的 QP 是 per-connection 的，全对全通信下硬件状态量是 O(N²M²)，万卡规模网卡片上内存直接爆掉（详见 §04）。而且它没有 load/store 语义，CPU 无法用一条指令访问远端。

用 NVLink 那套？

私有协议，且规模主要落在单柜（NVL72 = 72 GPU）。对需要自主可控 + 万卡规模的场景，两条都不满足。

所以只能重做

UB 的选择是重新设计一套六层协议栈，从物理层的光可靠性一直做到功能层的语义，同时用 UBoE、RoUB、Socket over UB 三个兼容层把老生态接进来，避免"必须全部推倒重来"。

2.6 两个必须澄清的名词

为什么叫"灵衢"

取"九省通衢"之意，象征大规模算力四通八达。英文正式名 UnifiedBus™，缩写 UB。华为 2019 年开始研究；灵衢 1.0 已用于 Atlas 900 A3 SuperPoD（384 卡），2025 年 3 月起累计部署超 300 套、服务 20 多个客户。已核实

"超节点"到底是什么

不是"一个大机柜"，而是打破主机边界后的一台逻辑机器：几十到上百个物理机柜通过 UB 全互联，域内任一 NPU 可以用内存读写的方式直接访问域内任何一块内存。
对操作系统而言，它需要被当成"一台超大机器"来调度 —— 这正是必须改 Linux 内核（UB OS Component）的原因，也是为什么超节点不是"把机器堆起来"就能得到的。

2.7 UB、昇腾、鲲鹏、超节点：四者什么关系

这四个词经常被混着说，其实分属三个不同层次：

UB 灵衢 ＝ 协议

一套互联协议规范，加上配套的交换芯片、光模块、软件栈。它本身不提供算力 —— 它是"怎么连"，不是"用什么算"。

昇腾 / 鲲鹏 ＝ 芯片

昇腾 Ascend 是 AI 加速芯片（NPU）产品线：910 / 950PR / 950DT / 960 / 970。
鲲鹏 Kunpeng 是通用 CPU 产品线：920 / 950。

超节点 SuperPoD ＝ 系统

用 UB 把上面这些芯片连成一台逻辑机器的系统形态。品牌上：Atlas = 昇腾 AI 系列，TaiShan = 鲲鹏通算系列。

2.8 边界：UB 不解决什么

把边界说清楚，比把能力吹满更重要 —— 现场被问到时不至于答不上来：

  • 不提供硬件级全局缓存一致。跨机 Cache Coherence 由 UBS Mem 的 SHMEM 软件层维护，超节点域内并非硬件一致（见 §03）。
  • 不替代 Scale-Out 集群网络。超节点之间仍走 UBoE 或 RoCE 组成 SuperCluster，UB 主要解决 Scale-Up。
  • 不保证严格全局顺序。UB 刻意选择弱事务序（NO/RO/SO 可配 + Fence），换取零开销 —— 强序需求要应用自己用 Fence 表达。
  • 不消除拓扑感知。7 平面并行、跨柜跳数差异仍然存在，调度与集合通信仍需感知拓扑才能跑满带宽（见 §06）。

3.1 协议层和报文头是对应的吗

是对应的，但不是一一对应。六层里只有中间四层真的往报文上贴头，两头两层不贴：

协议层贴头？对应的报文头大小为什么
功能层✗ 不贴——它是给程序员看的 API 语义（一条 load 指令、一次 urma_read()），不是线上的东西
事务层✓ 贴BTAH（+ 可选 MAETAH / TVETAH / MTETAH）16 B写明"这次要干什么"：opcode、服务模式、执行序、目的 Jetty
传输层✓ 贴RTPH 或 UTPH（二选一）16 B写明序号、窗口、SACK —— 丢了怎么补
网络层✓ 贴NTH（含 24-bit CNA）12 B写明最终送到哪个 UB 实体 —— 中间交换机看这个转发
链路层✓ 贴Ethernet 帧头（Ethertype 0xCAFE）+ 帧尾 FCS14 B写明这一跳送到哪块网卡
物理层✗ 不贴——它把上面这一串字节变成电信号或光信号（SerDes 编码、FEC），不增加语义字段
所以对应关系是：封装顺序（从内往外：BTAH → RTPH → NTH → Ethernet）正好就是协议栈从上往下走一遍，跳过不贴头的功能层与物理层。

3.3 TP Bypass：为什么 Load/Store 不走完整封装

上面这条路径是 UB 规范 §8.4 定义的 URMA Work-Request 路径。但 UB 还有第二条路 —— 规范 §8.3 的 TP Bypass（传输层旁路），专门给同步的 Load/Store 用。章节号来自第三方清洁室实现 OpenURMA

为什么需要第二条路

① 头开销吃不消

58 B 头背 64 B 数据。CPU 的一次 load 通常只取一个 cache line（64 B）甚至更少 —— 走完整封装等于每次都付近 50% 的线上税。

② 队列开销吃不消

完整路径要经过：写 doorbell（MMIO）→ 硬件 DMA 取 WQE → 传输层封装 → 上线 → 远端处理 → DMA 写回 CQE → 软件轮询完成队列。每一步都是几十纳秒的固定成本，加起来比数据本身的传输时间还长。

③ 语义本来就不需要

load/store 是 CPU 一条指令、同步阻塞，由 CPU 的 memory ordering 和 cache 协议保证正确性。它不需要传输层再做一遍序号、重传、完成通知 —— 那套机制是为异步消息设计的。

旁路掉的东西，谁来兜底

代价有两个，都很实际：
  • 故障隔离差。远端节点故障时，同步 load/store 意味着 CPU 卡死在一条指令上，处理起来比异步的 URMA 难得多。这正是白皮书说 URMA "故障隔离更好"的原因，也是为什么数据面首选 URMA 而不是 Load/Store。
  • 不适合长距离多路径。TP Bypass 把可靠性押在链路层上；路径越长、跳数越多，链路层兜底越吃力。

· 需要对端参与 / 通知 → URMA 双边收发

3.5 弱事务序：UB 的设计哲学

先说清楚"序"是什么问题。你连续发出 4 个请求 R1 R2 R3 R4，它们走不同路径、落在不同远端，完成的先后完全可能和发出的先后不一样。传统协议（如 RDMA RC）的做法是硬件强制按序完成 —— 代价是每个操作都要过一遍顺序检查，而且后面的必须等前面的。

UB 的选择是把"要不要保序"交给应用决定，提供三档 + 一个显式屏障：

同一套哲学也用在缓存一致上。AllReduce 在分布式训练中占时 30%~70%，UB 选择在梯度同步点实现最终一致性，而不是全程强制硬件缓存一致。跨机 Cache Coherence 由 UBS Mem 的 SHMEM 软件层维护 —— 这是一个非常关键的架构事实：超节点域内并非硬件全局缓存一致，写对外材料时别说错。

§04Jetty 与 TP Channel：UB 最重要的两个抽象

这一节解释 UB 相对 RDMA 最本质的可扩展性差异。理解了它，就理解了为什么 UB 能撑到万卡而 RDMA 不行。

4.1 先说结论：两者分别是什么

用港口来理解最直观 —— Jetty 这个词本身就是"码头"的意思：

Jetty ＝ 码头泊位

每个应用在网卡上开一个自己的泊位，货物（数据）在这里装卸。泊位有三条传送带：JFS 发送队列、JFR 接收队列、JFC 完成队列，还有一个 doorbell（按铃通知硬件"我这有活了"）。
泊位属于货主（应用），一个应用可以开多个。

TP Channel ＝ 港口之间的航道

连接本机与某台远端主机的一条航道，负责"船怎么开、丢了怎么补"：序号窗口、SACK 位图、拥塞状态。
航道属于"主机对"，不属于任何一个货主 —— 所有泊位的船共用同一条航道。多条航道组成 TPG，走多路径。

为什么共用航道不会乱：因为每个报文头里就写着"送到对方港口的第几号泊位"（目的 Jetty 标识放在事务层头 BTAH 里）。船到岸后按面单直接分派到对应泊位，所以航道不需要为每一对货主单独开一条。

4.3 问题：RDMA 的 QP 为什么撑不住

RDMA 的连接抽象是 QP（Queue Pair），它是 per-connection 的 —— 每一对通信端点都要在网卡硬件里维护一份状态。假设 N 台主机、每台 M 个线程要做全对全通信，硬件状态量就是 O(N²M²)。到万卡规模，网卡片上内存直接爆掉。

Jetty — 端点，per-application

可以理解成"一个应用在网卡上的收发窗口"。每个 Jetty 有自己的发送队列 JFS、接收队列 JFR、完成队列 JFC，以及独立的 doorbell（提交铃）。

TP Channel — 传输状态，per-remote-host

可以理解成"通往某台远端主机的那条公共车道"。约 56 B，含序号窗口、SACK 位图、拥塞状态，每通道 64-slot ring。多个 TP Channel 组成 TPG 实现多路径负载均衡。

§06"平面"是什么

这是超节点里最容易被忽略、但交付时最容易踩坑的概念。一句话：平面 = 一整套并行且互相独立的交换网络。

6.1 概念

每个计算节点有 7 颗 L1 交换芯片。每一颗独立承载一套完整的互联网络，这就是一个"平面"（plane）。平面 3 的 L1 只连到 L2 的平面 3 子平面 —— 平面之间不互通。所以超节点内部不是一张大网，而是7 套物理隔离、并行工作的网络叠在一起。

6.2 澄清：平面之间"不通"，到底是什么不通

这里最容易理解偏。准确的说法是：平面之间没有横向连线，但同一张 NPU 卡同时挂在全部 7 个平面上。

✓ 对的理解

7 颗 L1 芯片各自只和其它节点的同号 L1 打交道（通过 L2 的同号平面）。平面 3 的流量永远不会跑到平面 5 上去，也没有物理连线让它跑过去。

✗ 常见误解一

"资源被切成 7 份互不相干" —— 不是。同一份数据流会被同时拆到 7 个平面并行发送，到对端再汇合。7 个平面服务的是同一批 NPU 卡。

✗ 常见误解二

"坏一个平面就有 1/7 的卡失联" —— 不是。每个平面自己都是一张能到达全部节点的完整网络，所以坏一个平面时，所有卡仍然互通，只是可用带宽降到 6/7。这就是"优雅降级"的机制来源。

一句话：7 个平面是带宽维度的并联，不是连通性维度的分区。并联所以能叠加带宽，也所以能坏一条不断路。

6.3 为什么要这样设计

① 带宽聚合

单颗交换芯片的端口数与带宽有物理上限。把出口拆到 7 个平面并行跑，总带宽 = 7 × 单平面 —— 这是堆出 PB/s 级聚合带宽的基本手段。详见下方 7.3.1。

② 优雅降级（最关键）

一个平面故障，只损失 1/7 带宽，业务继续跑；如果是一张大网，一个核心故障可能全断。§08 拓扑图里"影响域 = 该平面在此节点损失 1/7 带宽"就是这么来的。

③ 路由简单 + 多路径均衡

每个平面内部是规则拓扑，路由计算简单、可预测。跨平面的负载均衡交给传输层的 TPG / 多 TP Channel 做。

④ 可滚动运维

固件升级、重启可以按平面分批，永远保留可用平面。这是 §14 里反复强调"按平面分批"的原因。

6.3.1 带宽聚合具体是怎么回事

起点是一个物理事实：一颗交换芯片的总吞吐是有天花板的。这个天花板由几件事共同决定 —— SerDes 通道数量、芯片封装能引出的引脚数、功耗与散热、以及良率（芯片面积越大良率越差）。你不可能靠"再做一颗更大的芯片"无限往上堆。

所以扩带宽只有两条路：

路线做法问题
纵向：把芯片做大单颗芯片塞更多 SerDes、更高速率受封装、功耗、散热、良率的硬约束，而且每一代提升有限、成本非线性上涨
横向：多颗芯片并联 UB 走的这条一张 NPU 卡的出口不接到 1 颗 L1，而是拆成 7 份接到 7 颗 L1，每颗只承担 1/7 的量需要上层把流量真正均匀分到 7 个平面上，否则白搭（见下）

8.1 什么是"亚健康"

这个词在本手册出现十几次，是工具链 M4 模块存在的全部理由，值得正式定义一次。

定义：链路层状态显示为 Up、单点测试全部通过，但存在持续的误码或重传，导致集群级性能塌陷的状态。

三个识别特征，缺一不可：

  • 状态灯是绿的 —— 端口 Up，不触发任何常规告警
  • 单机测试全过 —— §14 步骤 19 的单节点算力、带宽、健康检查一路绿灯
  • 只有跑集合通信才暴露 —— 症状是"慢"，不是"坏"

为什么它是超节点特有的：木桶效应 × 规模

两个因素叠在一起，才让亚健康从"小毛病"变成"交付验收最难的一关"：

① 集合通信是同步的 —— 木桶效应

一轮 AllReduce 必须等最慢的那条链路完成才能进入下一步（见 §11.5）。5,376 条链路里只要有几条在重传，整轮就被拖住。不是"损失几条链路的带宽"，而是"所有卡一起等"。

② 规模让"至少坏一条"成为常态

做个直觉计算：假设单条链路在任意时刻健康的概率是 99.99%，那么 5,376 条全部健康的概率 ≈ 0.9999^5376 ≈ 58%。
换句话说，任意时刻大约有 4 成的概率至少存在一条不健康的链路。示意计算，非实测数据

所以工具链的结论是：不能等它报警 —— 它不会报警。必须主动、周期性地把 5,376 条链路的误码趋势扫一遍，看的是增长速率而不是状态位。这决定了 M4 模块是一个"持续采集 + 趋势分析"的东西，而不是一个"看告警列表"的东西。

8.2 四类链路问题的定位链条

下面四张表就是上方交互面板里点开各按钮看到的内容 —— 放到正文，方便打印和照着做。顺序即优先级，从上往下查。

A · 链路 Down

  1. 物理层优先：光模块是否在位 / 插到位、光纤极性是否反接、端口与模块是否清洁。
  2. 查 iBMC / 设备侧在位状态（在位检测走 CPLD/I2C，CPLD 版本异常会导致读不到在位）。
  3. 核对光模块型号是否在兼容清单内；链路两端型号是否一致。
  4. 查端口配置是否被固件升级重置（速率 / FEC 模式）。
  5. 用 LLDP 邻居表与规划拓扑做 diff，确认不是接错平面（见 §06.4）。
  6. 最后才怀疑交换板 / 芯片 —— 换件前先做完上述五步。

B · 亚健康（Up 但误码增长）最难的一类

  1. hccn_tool -i <id> -link_stat -g —— 看链路状态是否变化（端口 flapping）。
  2. hccn_tool -i 0 -stat -g —— 看 roce_new_pkt_rty_num 是否持续增长。看增长速率，不看绝对值。
  3. 看光模块 DDM：收发光功率是否贴近规格边界、温度是否偏高。合格窗口以模块规格书为准，不要用网上流传的 dBm 数字
  4. 看端口 CRC / FEC 纠错计数的增长速率。
  5. 交换机侧：buffer 门限、PFC、ECN 在 spine / leaf 之间是否配置一致；DSCP 与 PFC 队列映射是否匹配。
  6. ascend-dmi 眼图测试 / PRBS 码流测试定位信号质量。

C · 光模块进入 LP mode（低功耗关闭发射）

  1. 现象：模块在位但对端收不到光，端口 Down 且告警不指向线缆。
  2. 这是华为知识库里的典型场景：模块进入低功耗模式后关闭 Tx。
  3. 先确认模块温度 / 供电是否异常触发保护。
  4. 核对模块固件与设备侧固件的配套关系。
  5. 复位端口或重新插拔模块验证；仍不恢复则更换模块。

D · L1 交换板纳管不到

  1. 优先怀疑 CPLD 版本与 CSR 描述文件不配套 —— 部件会表现为 LoadStatus = 1（链路不通）、EEPROM 读不到。
  2. 回到 §14 步骤 10 核对 CPLD ↔ CSR 是否成套升级。
  3. 部分端口读不到状态：I2C 通道被占用，或 CPLD 通道选择逻辑随版本变更。
  4. 确认 iBMC 部件树中 L1 板数量 = 规划数（每节点 7 颗）。
给工具链的直接输入：这四条链条就是 M4 规则引擎的初始规则集。注意它们的共同结构 —— 先物理、再配置、再拓扑、最后才换件。工具链要做的不是替代这个顺序，而是把每一步需要的数据自动取好放在一屏里，让工程师不必在五个窗口之间来回切。

9.2 UBS Core 五大服务

UBS Engine · 控制面核心

内存 / DPU 资源池化管理与动态调度；分布式自选主，支持 N-1 节点故障高可用；屏蔽 EID/CNA 等 UB ID 体系，统一对接 UBFM 与 OS，提供集群单一北向 API。

运维相关：支持 Prometheus 生态兼容的监控度量，部署、巡检、日志等运维北向开放。

UBS Mem · 内存服务

两层解耦。语义层：SHMEM（共享内存，CPU 直驱 C2C / NPU 直驱 D2D，软件维护跨机 Cache Coherence）、MemCache（高带宽 + 弱一致，支撑推理 KVCache）、MemStore（低时延 + 强一致，金融多副本）。基础设施层：MemFabric 统一虚拟编址（基于 UB 与 RoCE）+ xDMA。

UBS Comm · 通信服务

HCOM（多协议高性能通信框架，屏蔽 RDMA/TCP/URMA/SHM 差异）、Socket over UB（应用零修改，数据面 bypass TCP/IP）、HCAL（异构通信加速库，D2H、CPU-xPU 直传，加速推理 KV Cache）、RoUB（RDMA over UB，把 UB 接口转成 verbs 语义，RDMA 应用无感迁移）。

UBS IO · IO 服务

全局数据读写缓存 + NPU Direct SSD/SSU（bypass Memory 直通本地 SSD）。模块：APP-Aware 预取/淘汰、多协议（POSIX/HDFS/block）、Cache Daemon（跨节点数据读取）、Metadata Acceleration（网卡/DPU 加速）、HBM Direct（HBM→SSD/SSU/OceanDisk 直通）。场景：Spark/Hive、训练 CKPT、推理 KV Cache、HPC 小文件。

UBS Virt · 虚拟化服务

Virt OVS（EID/UPI/TP 网络属性配置、UVS 虚拟网络 TP 层建链、SIP/DIP/vTP 表项持久化）、Virt Optimizer（NPU 虚拟化加速 + Host/Guest 自动化探测调优）、Virt VM（解析超节点拓扑信息、Timer Sync、心跳、KVM 页表/中断转发、分布式内存管理）。支持热迁移决策、极速快恢与容灾。

10.2 四种池化之间是什么关系

它们不是并列的四件事，而是一个有依赖顺序、以内存为中心的结构。三句话概括：

  1. 底座是「统一全局地址空间 + 对等协同」。这两条不成立，四种池化一种都做不出来 —— 所以 §07 里"对等协同是胜负手"的说法在这里兑现。
  2. 内存池化是核心与前提。另外三种在实现路径上都要经过内存这一层：SSD 的数据要先落到某处缓存，DPU 加速的元数据在内存里，NPU 的"直驱远端"本质就是访问远端的 HBM / 内存。所以 UB 的池化是 memory-centric（以内存为中心） 的。
  3. 控制面只有一个。四类资源都由 UBS Engine 用同一套四原语（调度 / 借用 / 归还 / 故障处理）纳管、走同一套北向 API。"全量池化"里的"全量"指的是这个 —— 不是四套独立的池化系统，而是一个控制面管四类资源。

10.3 池化到底是怎么做到的

先纠正最常见的理解：池化不是把任务切开。任务一点没动，还在原来那台机器上跑，代码也没改。动的只是"这段内存物理上放在谁家"。

被"借"的到底是什么

问题答案
切分 / 分配的是什么？一段内存地址空间（按内存页 / 大页管理，实际调度单位是 GB 级）。不是任务，也不是数据
借的是容量还是内容？只借容量。B 借给 A 的意思是"你可以用我这 100 GB"，不是"我把我的数据给你"
任务会被搬走吗？不会。进程还在 A 上跑，只是它 malloc 出来的一部分内存物理上落在 B 的内存条上
应用要改代码吗？不用。借来的内存出现在 A 的普通虚拟地址空间里，指针照常用（UBMM Lib 兼容 glibc / jemalloc / tcmalloc）

归还与故障

归还

A 用完释放 → A 的 Engine 通知 B → 双方撤销映射 → B 收回这段内存。RMRS 还会把各节点零碎的空闲片段重新聚合再利用。

出借方故障

B 宕机 → A 上那段映射失效 → A 访问时收到错误，但 A 不会跟着崩（池化内存跨节点故障不扩散）→ Engine 重新调度，把借用关系挪到 C。这是 N-1 节点故障高可用的基础。

10.4 跨节点访存的完整路径

把"应用读了一次远端内存"这件事，从上到下走一遍。重点看两件事：① 应用侧完全没有改动；② UBS Engine 只在建立借用关系时参与，不在每次访存的数据路径上。

两个关键性质：① 跨机 Cache Coherence 由软件（UBS Mem SHMEM）维护，不是硬件全局一致；② 池化内存跨节点故障不扩散 —— 这是"敢用别人内存"的前提，也是 UBS Engine 支持 N-1 节点故障高可用的基础。

场景选为什么

对端需要知道"数据到了"URMA 双边收发单边是对端无感的；要通知就得用双边（对端预投递 JFR 接收缓冲）
AllReduce 等集合操作在网 Coll Ops两者都不用 —— 直接卸载到交换芯片算，见 §03
四条判断线，按顺序问自己：
① 数据有多大？ 一个 cache line 量级 → Load/Store；KB 以上 → URMA
② 发完还能不能干别的？ 需要重叠计算 → URMA（同步的 Load/Store 会把 CPU 钉住）
③ 远端挂了能不能优雅处理？ 需要 → URMA（Load/Store 会让 CPU 卡在指令上）
④ 要不要跑满多平面带宽？ 要 → URMA（Load/Store 走单路径）

算法层不随硬件变 —— 这是整张表最重要的一句

集合原语（Broadcast / Scatter / Gather / AllGather / Reduce / ReduceScatter / AllReduce / AllToAll）和算法（ring / tree / 多 channel / 开环拼接）都是逻辑层 —— NCCL 怎么在环上搬数据，昇腾 HCCL 也一样搬。硬件只决定这条环 / 树落到哪些物理链路上（UB 域内还是跨 rail），以及换轨发不发生。

对工具链的直接启示：「原语数据流 / Ring·Tree 展开」两边通用，「物理路径投影」才是随硬件变的部分。也就是说 M5 可视化模块可以拆成两层 —— 上层的算法视图是厂商无关、可复用的资产，下层的物理投影才需要针对昇腾定制。这个拆分直接影响模块边界怎么划。

① 通信节点是"卡"，不是 die

② "平面 ≈ rail" 要加个限定

我在 §06 写过"平面 ≈ rail"。结构上确实同构（同号口归一条轨 / 同号 L1 归一个平面），但作用域不同：
· UB 的 7 个平面在 Scale-Up 域内部
· NCCL 的 rail 在 Scale-Out 的 RDMA 网络上
两者是同一种设计思想用在两个不同尺度上。

③ 换轨（PXN）是个真机制

之前我只把它当成一个名词。它的实际做法是：先在域内网把数据搬到"与目标 rail 对齐的那张卡"上，再从那张卡出网 —— 这样跨节点流量只走一条轨，避免跨 rail 多跳。
这解释了为什么域内带宽必须远大于出网带宽：域内要承担这些额外的搬运。

14.1 五条贯穿全程的硬约束

① 版本配套矩阵（最高优先级）

已核实的硬依赖至少五条：driver ↔ firmware 必须同一软件版本列表；首装 driver→firmware，升级 firmware→driver（顺序相反）；CPLD ↔ CSR 必须成套；Smart Provisioning 依赖 iBMC/BIOS 最低版本；CANN Kernels 依赖 Toolkit/NNAE/NNRT。这些全部可以在离场前静态校验。

② 三层设备模型 + 独立网元

iRM/RM211(机柜) → iBMC(节点) → L1交换板/NPU(部件)，再加 L2 灵衢交换设备（独立网元）。只做服务器一层的工具链在超节点上会立刻失效。详见 §05。

③ 拓扑即数据

384 卡超节点 = 5,376 条光连接 / 7 平面 / 56 块交换板。规划拓扑必须机器可读，且能与 LLDP 实测结果 diff。人工核对不可能做对。详见 §06。

④ 幂等 + 断点续跑 + 按平面分批

批量操作跑一半失败是常态。所有动作必须幂等、可续跑；升级与重启必须按 UB 平面分批，永远保留可用平面。

⑤ 亚健康是超节点特有的验收难点

链路 Up 但误码高 → 单机测试全过、集群带宽塌陷。必须把 hccn_tool -stat -g 的 roce_new_pkt_rty_num、-link_stat -g 的 flapping、ascend-dmi 眼图/PRBS、CCAE"光路类"诊断做成交付卡点，而不是事后运维项。

§15工具链形态草案

这一节是草稿 —— 目的是给下一轮讨论一个可以拍砖的靶子。整体思路：底层尽量包装官方工具而不是重写，上层做统一对象模型、拓扑真值与可视化。

先复用，别重写。下面四个官方能力组合起来已经能覆盖 23 步的大部分执行层：Ascend Deployer（Ansible 架构、离线可用、有 inventory 与报告）、FusionServer Tools uREST / FwUpgrade（Redfish 批量固件与 BIOS）、ascend-dmi（压测/诊断/眼图/PRBS）、CCAE 北向 API（巡检结果与验收证据，支持查询 + 订阅，Token 认证）。工具链的增量价值在编排、真值、可视化与证据链。

18.1 刀片构成：内部口径 vs 公开数据

内部口径数量公开资料能印证什么核对结果
NPU 计算刀片× 8每计算节点确为 8 颗昇腾 NPU（384 ÷ 48 = 8），三个独立第三方来源一致数量对得上。1 刀片 1 NPU 的对应关系未见公开印证
CPU 计算刀片× 8每计算节点为 4 颗鲲鹏 920（192 ÷ 48 = 4）对不上，需要现场确认 —— 见下方说明
灵衢互联刀片× 4每计算节点有 7 颗灵衢（L1）交换芯片，承担 8 NPU + 4 CPU 的节点内交换功能吻合，但 7 颗芯片放 4 块刀片不能整除，承载关系待确认
灵衢 IO 转换刀片× 2华为官方对计算节点的芯片描述里明确列有 CDR 芯片（Clock and Data Recovery，"用于扩展信号传输距离、保障信号传输质量"）功能上最可能对应 CDR + 光模块面板转接。名称未找到印证
CPU 刀片数量的三种可能解释（都需要现场核实）：
  • ① "8" 是槽位数不是 CPU 数 —— 8 个 CPU 刀片槽位，Atlas 900 A3 上只插 4 块。
  • ② 一块刀片承载多颗，或 4 块双路刀片被计成 8 —— 那么 CPU 总数仍是公开的 4 或 8。
  • ③ 这套划分对应的不是 Atlas 900 A3。已知 Atlas 950 SuperPoD 的 CPU:NPU 配比从 1:2 变成 1:4（1024 昇腾 950DT + 256 鲲鹏 950），说明刀片配比在代际之间会变。你手上这套划分即使正确，也要标明它对应哪个型号。

18.3 交换板形态：Union、FM 全连接、SFU 板

你问的查证结论
板中间的 "Union" 是什么公开资料零命中。合理推测是板中央那颗 UB 交换 ASIC 的丝印 / 内部代号（语义上与 UnionBus / UnifiedBus 同源），也可能只是"统一互联结构"的口语说法。不要当成确定的芯片型号使用。至于"不同类型或状态" —— 公开资料完全没有，需要内部确认
"FM 全连接"FM = Full Mesh 基本可以确定。华为自己的论文标题就是《UB-Mesh: a Hierarchically Localized nD-FullMesh Datacenter Network Architecture》，FullMesh 是官方用词。
但要区分是哪一级的 full mesh：公开描述的是设备级 —— "56 个交换板与 48 个计算节点实现 full mesh 互联，共 5,376 条灵衢连接"（48 × 56 × 2 = 5376）。交换板内部（芯片之间 / 端口组之间）的全连接，公开资料未找到。从 LingQu 630 V1 的结构看，板上 2 颗交换芯片各出 200G 合成一个 400G 端口，那属于端口级 bonding，不是芯片间 full mesh
有没有 SFU 板大概率没有。SFU（Switch Fabric Unit 交换网板）/ MPU（主控板）/ LPU（线路板）是华为 CloudEngine / NetEngine 框式设备的命名，这点已核实。但 Atlas 900 A3 的 L2 灵衢总线设备是 盒式设备（最大 1200 W、面板侧进出风、支持正装倒装），不是框式插板机框，所以不太可能沿用那套命名。
