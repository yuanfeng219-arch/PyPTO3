# PyPTO 开发者体验（DX）洞察报告

> 基于 `hw-native-sys/pypto` 仓库 **561 个 Issue** 的 UX 分析
> 数据窗口：2026‑01 ～ 2026‑07 ｜ 样本状态：516 已关闭 / 45 开放
> 视角：以「开发者使用全流程」为主线，梳理痛点、期望与设计机会点

---

## 摘要（Executive Summary）

PyPTO 是一个 **Python DSL → IR Passes → Codegen → NPU 运行时** 的编译器产品，用户是**编写算子 / 编排（orchestration）的编译器与算法工程师**。

对 561 个 issue 的系统性分析指向一个明确结论：

> **这个产品最大的 DX 问题不是「不能用」，而是「错了却不告诉你」。**
> 「编译通过 → 设备上跑出全零 / 错值 → 无任何提示」这一失效模式在全流程反复出现。

产品的断点在**反馈回路（feedback loop）**，而非功能缺失。同一根因反复显现：**编译器内部已拥有正确知识，却在缺信息 / 边界情况时选择「静默默认 + 继续」，把错误推迟到运行时甚至数值结果里。**

**若只做一件事**：为每个 Pass 增加「不变量校验器（verifier）+ 静默行为的编译期诊断」，把「运行出错值」整类问题前移到「编译期报错」。它命中最广、伤害最深，且贯穿编译—运行—调试三个阶段。

## 二、开发者全流程 · 痛点 / 期望 / 机会点

### 阶段 0 — 环境搭建与上手（Onboarding）
**痛点**
- 照 README 跑测试直接 `ModuleNotFoundError: No module named 'pypto.ir'`（#63）——第一步就撞墙。
- 跑真实模型 kernel 必须手动 `export PTO2_RING_HEAP / PTO2_RING_DEP_POOL / …`，否则 `rtMalloc failed 207001` 或 `507018`，且运行时**不给该设多少的任何指引**（#1008）。默认值对真实模型「太小」，设大了又爆 16GB HBM。

**期望**：装完即可跑通第一个 kernel；环境需求由工具**自动推断**，而非在团队里口口相传。

**设计机会点**
- `pypto doctor` / 冒烟测试：装完即验证 import + 一个最小 kernel 端到端。
- 运行时根据 kernel **自动探测 GM/heap 需求**（#1008 明确诉求）；报错时打印**建议值**而非裸错误码。
- 将 README 的命令做成 CI 中被真实执行的「可运行文档」，杜绝 #63 这类过期指引。

### 阶段 1 — 编写 Kernel（前端 DSL / 类型标注）
**痛点**
- pyright 对 DSL 类型频繁**误报**，用户只能 `# type: ignore` 绕过（#119：`Scalar` 不支持 `<`、`float` 不可赋给 `Scalar[Unknown]`）——IDE 变成噪声源。
- API「字节中心」的 foot‑gun：`alloc_window_buffer(nr*SIZE*4)` 中 `4` 是魔法数，shape/dtype 要重复书写且可能不一致（#1968 RFC）。
- 早期大量「语言能力缺失」单（While/Break/Continue、parallel for、dynamic shape：#150 #159 #163 #165‑167）——**表达力边界不清**，用户靠试错发现「哪些能写」。

**期望**：DSL 与 Python 类型系统和谐共处；API 用 shape+dtype 等**领域语义**而非硬件字节；「能写什么 / 不能写什么」有明确清单。

**设计机会点**
- 提供官方 **type stubs / mypy 插件**，消除 pyright 假阳性（直接影响 67 个摩擦点）。
- **语义化分配 API**（`alloc(shape, dtype)`），把字节计算收进框架内部。
- 发布「**语言特性支持矩阵**」，标注每个控制流 / 形状特性的支持状态。

### 阶段 2 — 编译 / IR Passes / 编排（Lowering）
> bug 密度最高的地带。

**痛点**
- Pass **悄悄丢东西**：`ExpandMixedKernel` 丢 matmul（#963）、丢嵌套 loop 累加器初始化（#977）；`MemoryReuse` 复用仍存活的 loop yield 缓冲导致**数据损坏**（#768）；`ConvertToSSA` 跨作用域错连同名变量（#642）。
- **作用域规则不可见且不一致**：incore/auto_incore 块外的语句被**静默丢弃、无警告**（#919）；chunked `pl.parallel` 放在 auto_incore 外**被接受而非被拒绝**（#577）。
- 单一 Pass（`ExpandMixedKernel`）独占 37 单——**某些 Pass 是脆弱热点**。

**期望**：Pass 要么正确变换、要么**明确报错**，绝不静默丢弃；作用域 / 合法性规则应在编译期强制并给出可读诊断。

**设计机会点**
- **Pass 级不变量校验（verifier）**：每个 Pass 后断言「op 数量守恒 / 依赖完整 / 作用域合法」，把 #963/#977/#768 从「运行出错」提前到「编译报错」。
- 把「块外语句被忽略」「非法嵌套」等从静默行为升级为**编译期诊断**（#919/#577 的直接诉求）。
- 对高频脆弱 Pass（ExpandMixedKernel）建**控制流 / 边界的属性测试（property/fuzz）**，取代逐 case 补丁。

### 阶段 3 — 代码生成（Codegen）
**痛点**：codegen 持续「生成语义错误但能编译的代码」——
- `[M,1]` 少写 `pl.DN` → **静默生成错误 stride**（#739）；矩阵右操作数用错 block layout（#762）；chunked 循环里发 `add_output` 而非 `add_inout`（#858）；写进临时张量而非外部输出（#866）；const 表达式 dtype 发错（#934）；序列化丢 `memory_space`（#522/#553）。
- 根因常被明确写为「**层间知识不一致**」：C++ codegen 已知规则，但 Python type resolver 未同步（#739 原文）。

**期望**：一处正确的规则应在所有层自动生效；codegen 不应在缺信息时「猜一个默认值」然后错下去。

**设计机会点**
- 建立布局 / 类型规则的**单一事实源（single source of truth）**，消除 C++/Python 双写漂移（#739、#522、#553、#1300 RFC 的共同诉求）。
- Codegen 前做**完整性校验**：布局 / 内存空间 / 输出方向缺失时报错，而非默认 ND、默认 row‑major。

### 阶段 4 — 运行与验证（Runtime / Correctness）
**痛点**
- **最坏失败模式**：编译干净、设备上跑出全零或 4094/4096 mismatch（#1525）。用户无法判断是自己写错还是编译器错。
- 依赖 / 同步类竞态：向量产出的 GM tensor 作为后续 matmul 右操作数**未被依赖排序**，间歇读到零初始化数据（#1648）；TensorMap 有依赖边但下游仍读到**陈旧路由表**（#1503）；删掉一个 vector op 竟致 fence EVENT_ID 复用**运行时死锁**（#1789）。这些**间歇、非确定**，最难调。

**期望**：正确性问题在编译期被拦；即使到运行时，也能定位「哪个 tensor 在哪个 scope 读到脏数据」。

**设计机会点**
- **依赖 / 一致性校验器**：对「写后读未排序」「缓冲复用与存活期冲突」做静态检查（覆盖 #1648/#768/#1503）。
- **运行时哨兵**：debug 模式下检测未初始化读 / 全零输出，把 #1525 从「人工二分 40 行 repro」变成一条告警。

### 阶段 5 — 调试与定位（Debug）
**痛点**：调试成本极高。issue 正文普遍需要「~40 行 repro + 逐 Pass dump IR（如 `37_after_Simplify`）+ 人工比对 valid_shape」。**缺乏针对静默失败的可观测性工具**，全靠专家读 IR dump。

**期望**：快速回答「我的 op 在哪个 Pass 消失了 / 值在哪一步变错了」。

**设计机会点**
- **Pass 时间线 Diff 工具**：一键对比相邻 Pass 的 IR，高亮「消失的 op / 变化的 shape/layout」（仓库中已有 `compare-codegen` / `diff_pto` 雏形，值得产品化）。
- 编译产物保留 op 的**来源 span**，报错能指回用户源码行，而非仅内部 IR。

### 阶段 6 — 学习与文档
**痛点**：285 个 issue 触及文档 / 示例；文档本身有错（`tsort32` / `tmrgsort` 文档错误 #664；中文翻译错误 #337）。**文档既缺又不可信**。

**期望**：可信、与代码同步、有真实可跑示例。

**设计机会点**：文档中的算子签名 / 示例由源码**自动生成 + CI 校验**，避免手写漂移。

## 三、贯穿全流程的核心洞察

沿流程看，同一失效模式反复出现：

> **编译器内部拥有正确知识，却在缺信息 / 边界情况时选择「静默默认 + 继续」，把错误推迟到运行时甚至数值结果里。**

三条根因线：
1. **反馈回路断裂** —— 静默丢弃 / 静默默认，用户拿不到「哪里错、错在哪一步」的信号。
2. **层间知识不一致** —— 同一规则在 C++ codegen 与 Python 前端各写一份，天然漂移，是一大批 codegen bug 的共同根因。
3. **可观测性缺失** —— 定位问题依赖专家读 IR dump，无工具化的「Pass 前后 diff / 数值哨兵」。

| 优先级 | 方向 | 攻击的痛点 | 代表 issue |

| 🟠 P1 | **依赖/一致性静态校验 + 运行时哨兵** | 运行时竞态与全零输出（247 崩溃） | #1648 #1503 #1789 #1525 |
| 🟡 P2 | **入门速赢**：doctor 脚本、自动 heap 探测、type stubs | 入门（56）+ 前端摩擦（67） | #63 #1008 #119 |

**一句话行动项**：先做「Pass verifier + 静默行为诊断」。它直接攻击命中最广（201）、伤害最深（跑出错值却无提示）、且贯穿阶段 2–5 的那条主痛线——是全局 ROI 最高的一步。
