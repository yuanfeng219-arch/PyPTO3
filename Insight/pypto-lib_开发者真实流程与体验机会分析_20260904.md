# 从“能跑”到“可信迭代”

**pypto-lib 开发者真实流程、任务痛点与产品体验机会分析**

> 面向体验设计团队与业务团队的共创材料  
> 数据快照：2026-09-04｜证据范围：`hw-native-sys/pypto-lib` 全量公开 Issue、Pull Request 与评论

---

## 0. 执行摘要

`pypto-lib` 的核心体验矛盾不是“功能不够”，而是**开发者很难快速确认一次改动是否真的正确、为什么正确、在哪些条件下仍然正确**。仓库在不到 6 个月内产生了 1006 个 PR，其中 831 个已合并，合并中位时间仅 1.53 小时；这说明团队交付能力和自动化吞吐很强。但同一时期，Issue 反复出现静默丢写、概率性越界、固定种子输出漂移、长序列后才出现的错误、模拟器与真机表现不一致、同一性能结论被多轮修正等问题。**速度很快，信任成本也很高。**

开发者实际使用 PyPTO/PyPTO-lib 时，并不是“写一个算子—运行—完成”的直线流程，而是在**契约定义、编译、仿真、真机、精度、性能、服务集成和跨仓定位**之间反复往返。最贵的时间通常不在写代码，而在回答五个问题：当前环境是否可复现？错误从哪一层开始？这个 PASS 是否覆盖真实服务状态？性能比较是否同口径？临时 workaround 能否安全保留？

现有工具能产生大量 IR、生成代码、日志、Golden、泳道图和机器人评审意见，但这些产物彼此分散，且经常只描述“发生了什么”，没有把它们组织成**一次可信迭代的证据链**。设计机会因此不应只落在新增一个页面或再做一个图表，而应围绕三类能力展开：

1. **预防错误**：把 Shape、缓存、分布式一致性和精度敏感边界变成机器可检查的契约。
2. **缩短定位**：从最终输出异常自动回溯到首次偏离的层、Kernel、任务和源码。
3. **沉淀判断**：把环境、运行、Golden、Profile、对照实验、机器人意见和人类结论收进同一个“运行证据包”。

如果只做三件事，优先建议：**可信运行包（Run Capsule）**、**首次偏离定位器（First Divergence Navigator）**、**服务化契约中心（Contract Studio）**。三者分别解决“能不能复现”“从哪里开始错”“各层是否理解同一件事”，也是体验设计和业务团队最适合共同定义的跨层产品能力。

### 1.2 分析方法

本次采用四层分析法：

1. **全量统计**：状态、周期、评论、作者、月份与 PR 任务类型。
2. **标题辅助编码**：对 Issue 按正确性、编译/契约、运行时、服务化、分布式、性能、环境和文档做多标签归类；只用于判断信号方向，不把关键词命中当作严格发生率。
3. **关键事件精读**：优先精读能呈现完整“现象—假设—实验—归因—验收”链路的 Issue/PR。
4. **旅程重建**：把离散问题放回真实任务流，区分预防、发现、定位、恢复和沉淀五种体验成本。

### 1.3 事实、推断与建议的边界

- **观察事实**：直接来自 Issue/PR 字段、正文、评论或统计。
- **研究推断**：由多条证据共同支持，但仍需访谈或现场观察验证。
- **设计机会**：面向产品体验的建议，不代表技术实现已经评估完成。

### 1.4 重要限制

这是一份**公开工程协作语料研究**，不是用户访谈。Issue 作者多为核心贡献者，不能代表所有潜在用户；“没有评论”也不等于没有线下讨论。归档未包含非行级的 approve/request-changes 评审事件、附件实体和完整 Git diff，因此本报告不评价个人绩效，也不把评论量直接等同于工作量。

## 2. 数据告诉我们的五个核心事实

### 事实一：仓库交付速度很快，但正确性风险会延迟暴露

- 1006 个 PR 中，831 个已合并（82.6%），134 个关闭未合并（13.3%），41 个仍开放（4.1%）。
- 已合并 PR 的创建到合并中位数为 **1.53 小时**，P75 为 13.08 小时，P90 为 36.66 小时。
- 119 个 Issue 中，89 个已关闭（74.8%），30 个仍开放（25.2%）；已关闭 Issue 的关闭中位时间为 **5.7 天**，P75 为 16.9 天，P90 为 32.2 天。

这两个周期之间存在明显落差：代码可以快速合入，但问题从被发现到关闭要慢得多。部分风险只在真实服务状态下暴露：

- Prefix cache 热路径概率性丢写，单次运行不一定出现：[Issue #713](https://github.com/hw-native-sys/pypto-lib/issues/713)。
- Persistent worker 固定输入连续通过，只有 A/B/A 变化输入才暴露旧路由残留：[Issue #929](https://github.com/hw-native-sys/pypto-lib/issues/929)。
- 固定种子、相同请求仍产生多种输出，并在第 30 token 跳入无关 JSON：[Issue #1122](https://github.com/hw-native-sys/pypto-lib/issues/1122)。
- 长 Decode 前 80–100 token 正常，之后才逐渐漂移：[Issue #951](https://github.com/hw-native-sys/pypto-lib/issues/951)。

**研究推断**：当前质量门更擅长证明“这个样例现在能过”，不擅长证明“这个状态机在复用、长序列、边界 Shape 和多 Rank 下仍然成立”。

### 事实二：真实工作不是单层 API 使用，而是跨 5 层归因

一个症状可能从 `pypto-lib` 场景出现，最终落在 PyPTO、PTOAS、Simpler 或设备运行时：

- 首次编译超时最后被转移到 PTOAS：[Issue #50](https://github.com/hw-native-sys/pypto-lib/issues/50)。
- 生成代码中的死 TMOV 和多余 barrier 被定位为 PTOAS codegen：[Issue #623](https://github.com/hw-native-sys/pypto-lib/issues/623)。
- Persistent worker 的 MoE 错误最后被定位到 Host Tensor → runtime 参数链路，而不是 MoE Kernel：[Issue #929](https://github.com/hw-native-sys/pypto-lib/issues/929)。
- A5 被诊断成 `S1:running-stalled`，真正的首发故障却是更早发生的 UB 越界：[Issue #858](https://github.com/hw-native-sys/pypto-lib/issues/858)。
- WAR 依赖缺失只能先靠 no-op self-copy 欺骗自动依赖分析：[Issue #481](https://github.com/hw-native-sys/pypto-lib/issues/481)。

**研究推断**：用户不只是缺少更多日志，而是缺少一个能跨层回答“责任边界在哪里”的导航系统。今天最有经验的人承担了人工路由器的角色。

### 事实三：性能优化已有大量测量，但“可比性”本身仍需人工辩论

Issue #622 最初提出 PyPTO 与 CCE paged-attention 存在约 2.3× 差距，评论随后指出两侧统计范围不同；再经过同 Shape、同运行时、同计时口径重测，结论变为两者基本持平；进一步批量扫描又发现 Shape 才是主导因素，且部分大 Shape 下两条自定义 Kernel 路径存在正确性问题。这个案例不是一次普通的数值修正，而是完整暴露了性能研究的体验成本：[Issue #622](https://github.com/hw-native-sys/pypto-lib/issues/622)。

另一个外部基线 Issue 记录了“为了让基线跑起来做了什么”，包括源码构建、缺失镜像、上游 workaround 和不可复现的公开 MTP 数据：[Issue #1054](https://github.com/hw-native-sys/pypto-lib/issues/1054)。

**研究推断**：团队已经有“测量工具”，但还没有统一的“比较产品”。指标名称、统计范围、Shape、运行时、Warmup、Golden 和硬件版本没有被强制绑定，导致结论需要靠资深开发者反复校正。

### 事实四：服务化改造的主要难点是契约漂移，而不是单个 Kernel

从固定 `B × S` 到 packed tokens、从逻辑块到物理 slot、从单请求到 continuous batching，需要同时修改 Attention、MoE、KV Cache、Golden 和 Serving adapter。多个 Issue 专门用长篇文档定义契约：

- Packed prefill metadata：[Issue #382](https://github.com/hw-native-sys/pypto-lib/issues/382)。
- Decode paged KV contract：[Issue #383](https://github.com/hw-native-sys/pypto-lib/issues/383)。
- KV/cache/state 统一语义：[Issue #511](https://github.com/hw-native-sys/pypto-lib/issues/511)、[Issue #512](https://github.com/hw-native-sys/pypto-lib/issues/512)。
- 动态 token Shape 与 `num_tokens` 双重真相：[Issue #766](https://github.com/hw-native-sys/pypto-lib/issues/766)。
- TensorSpec `is_output` 同一个字段表达两种意思，导致 ABI 检查拒绝正确产物：[Issue #1050](https://github.com/hw-native-sys/pypto-lib/issues/1050)。
- DSpark Golden 自身跟随错误的 rank-local cache 语义，因而无法发现副本不一致：[Issue #1094](https://github.com/hw-native-sys/pypto-lib/issues/1094)。

**研究推断**：接口说明目前以 Issue、代码、Golden 和下游接入实现四种形式存在。每次改造都要人工同步多份“真相”，这是服务化体验中最持续、最具产品杠杆的问题。

### 事实五：自动化评审提升了吞吐，也制造了新的信号管理问题

- 1006 个 PR 中，666 个（66.2%）存在行级评审评论。
- PR 中共可见 4578 条对话/行级评论，其中 3789 条（82.8%）来自机器人，789 条来自人类（包含作者自己的回复）。
- 只有 40 个 PR（4.0%）出现作者之外的人类反馈；这些 PR 的首次外部人类反馈中位数为 58.3 小时。
- 245 个 PR 至少有 5 条行级评审评论，86 个至少有 10 条，最高 27 条。

PR #197 展示了较成熟的处理方式：作者逐条说明哪些建议接受、哪些拒绝，并给出 codegen/精度证据；PR #1014 也把机器人意见转换为明确的修正和拒绝理由。相反，大多数 PR 的人类决策并没有形成同样清晰的可见记录。

**研究推断**：下一阶段的评审体验重点不是“让机器人再多发现一些”，而是帮助人快速完成四件事：去重、分级、验证、形成可追溯的最终判断。

## 3. 核心用户与真实工作目标

Issue/PR 显示的用户不是一个统一的“开发者”，而是四类目标不同、相互交接的人。

| 用户角色 | 真实目标 | 成功标准 | 最害怕的失败 |
| --- | --- | --- | --- |
| 模型/算子开发者 | 把 Qwen、DeepSeek 的模块写成能运行的 PyPTO Kernel | 精度正确、接口可组合、关键 Shape 可覆盖 | 编译通过但输出悄悄错；优化改变数值语义 |
| 性能工程师 | 找出关键路径并验证优化收益 | 同口径 A/B、可复现、收益能解释 | 比较范围不一致；Profile 把等待画成计算 |
| Serving/集成工程师 | 把单次 Kernel 变成可复用、多请求、多 Rank 的服务 | Cache/slot/shape 契约一致，状态复用可靠 | 单测通过，热路径、长序列或复用后失效 |
| 编译器/运行时协作者 | 判断问题属于哪一层并提供修复 | 最小复现、跨层证据、责任边界清楚 | 下游症状掩盖首发错误；同一问题在仓库间搬运 |
| Coding Agent（新兴用户） | 按仓库规则自动实现、测试、Benchmark、提 Issue/PR | 指令机器可读、产物可验证、反馈可闭环 | 文档矛盾、过期命令、机器人反馈堆积、无风险边界 |

最后一类用户已不是假设。PR #587 把 tile 调优方法做成 Agent skill；PR #967 为 Benchmark 和问题处理增加 Agent 规则；PR #184、#197 等多处保留了生成式工具参与痕迹。体验设计需要同时面向“人如何理解系统”和“Agent 如何读取契约、返回证据”设计。

## 4. 开发者真实使用流程与逐环节痛点

真实流程是一个反复回环的“可信迭代环”：

> 定义目标与契约 → 固化环境 → 编写 Kernel → 编译/生成 → 仿真/Golden → 真机/分布式 → 精度定位 → 性能归因 → Serving 集成 → PR/CI → 新问题回流

### 4.1 旅程全景

| 环节 | 用户在做什么 | 关键产物 | 主要痛点 | 常见 workaround | 设计机会 |
| --- | --- | --- | --- | --- | --- |
| 1. 定义任务与契约 | 确认模型、Shape、缓存、并行和验收条件 | Tracking Issue、接口草案、Golden 规格 | 契约散落；同一字段多义；固定 Shape 与运行时有效长度并存 | 在 Issue 写长篇设计文档；人工同步上下游 | 可执行契约、字段语义词典、版本 Diff |
| 2. 准备环境 | 对齐 pypto-lib/PyPTO/PTOAS/Simpler/ISA/CANN | 环境变量、Commit SHA、二进制、镜像 | 多仓版本漂移；首次编译冷启动；公开镜像缺失 | 手工维护表格；先跑一次“预热”；从源码构建 | 共享版本清单、环境健康检查、可复现运行包 |
| 3. 编写 Kernel | 组织 `pl.at`、`pl.spmd`、Shape、Tile、依赖和 Buffer | Python DSL、模型配置 | DSL 能表达计算但难表达动态写、依赖和生命周期 | 静态广播替代动态 scatter；no-op self-copy 造依赖 | 明确依赖语法、约束感知编辑、Shape/Buffer 预算提示 |
| 4. 编译与生成 | PyPTO → IR → PTOAS → C++/PTO | IR、生成代码、编译日志 | 错误跨层；单 Opaque/多 Out 等结构边界不可预测 | 手工最小化到 1/2 个子函数；直接读生成代码 | 源码映射、编译置信度、结构边界 Lint |
| 5. 仿真与 Golden | 在 a2a3sim/a5sim 做快速正确性验证 | Tensor dump、Golden、误差报告 | 仿真与真机不完全等价；Golden 可能复制错误语义 | 同时维护多个 Golden；手动构造 tie-aware 比较 | Golden 谱系、语义不变量、模拟器差异提示 |
| 6. 真机与分布式 | 在 A2/A3/A5、多 Rank、EP/TP/CP 上运行 | 任务日志、错误码、设备 Trace | 概率性故障；首发异常被超时掩盖；同一任务随共驻关系变化 | 多轮 sweep、改变任务顺序、手工 grep 早期 errcode | Failure-first 诊断、状态矩阵回归、跨 Rank 因果时间线 |
| 7. 精度定位 | 从最终 Logits 向前找首次差异 | 中间 Tensor、分层比较、复现种子 | 小 ULP 误差被 INT8/top-k 放大；PASS 阈值不能代表语义稳定 | 固定 seed；逐层 dump；替换为 L3/参考实现 | 首次偏离定位、敏感边界分析、确定性检查 |
| 8. 性能调优 | 看泳道、重排任务、改 Tile/融合/依赖 | Swimlane、PMU、Benchmark 表 | 图上等待和计算混在一起；A/B 口径不一致 | 手工对齐 Shape/版本；反复纠正结论 | 可解释泳道、实验对照工作台、测量口径锁定 |
| 9. Serving 集成 | 做 packed batching、paged KV、persistent worker | Slot mapping、block table、服务测试 | 单次样例和真实状态机差距大；Cache 不变量难验证 | 写专门 stress 脚本；热/冷双跑；A/B/A 输入 | Serving 场景矩阵、Cache 可视化、状态不变量断言 |
| 10. PR/CI/知识沉淀 | 提交、机器人评审、修复、记录结论 | PR、CI、规则、文档 | Bot 信号多；人类决策少；过期经验继续传播 | 作者手工逐条答复；另写 Agent rules/技能 | 评审信号中心、结论模板、经验自动晋升 |

### 4.2 环节一：定义任务与契约

开发者经常先写一份接近产品规格的 Issue，而不是直接写代码。#382、#383、#511、#512 都在定义 packed token、slot mapping、block table 和 cache visibility 的共同语义。这说明用户真正需要的不是普通 API 文档，而是**跨 Kernel、Golden、Serving 和 Runtime 共用的模型契约**。

痛点在于契约仍是自然语言：字段何时废弃、谁是 source of truth、一个 Shape 是容量还是本次有效长度，都依赖阅读上下文。#766 明确指出物理固定 `T` 与运行时 `num_tokens` 构成两个真相；#1050 则显示 `is_output` 的双重含义已经让 ABI 检查误拒绝正确产物。

### 4.3 环节二：准备环境与建立基线

#34 直接提出跨 `pypto`/`pypto-lib` 的共享版本清单；#50 记录新 PTOAS 二进制第一次运行必超时，开发者的 workaround 是先做一次无意义预热；#1054 的“what it took to run”甚至比最终性能数字更长。

这里的关键体验问题是：**环境不是任务的前置条件，而是任务本身的一部分。**一次结果只有绑定完整版本、硬件、Shape、运行命令和 Golden 才有意义，但今天这些信息靠作者手动粘贴。

### 4.4 环节三：编写 Kernel 与表达意图

#255 展示了 DSL 表达力的边界：理想的 MoE dispatch 需要数据依赖的写地址，但 `pl.assemble` 只接受编译期偏移，开发者只能在 scalar write 与 broadcast/static-mask 两种不理想方案之间试验。#481 则更直接：自动依赖分析漏掉 WAR 边后，开发者加入无意义 self-copy，只为了迫使系统产生正确依赖。

这类 workaround 的共同问题是：**代码表达的已经不是业务计算，而是对编译器行为的暗示。**后来的维护者无法从代码本身判断它是算法、性能技巧还是不得删除的语义护栏。

### 4.5 环节四：编译与生成

#294 中多个 `pl.Out` 只有第一个写回，编译和运行均正常退出；#302 中调用一个 Opaque 子函数失败、调用两个反而成功。为了定位，作者搭建了两套 decorator 路径、1/2 个子函数矩阵，并读到 `InferFunctionCoreType` 源码。

这个环节的体验问题不是报错文字不够友好，而是**系统没有提前告诉用户哪些结构已经被验证、哪些组合处于未知区**。对产品而言，“编译通过”应该升级为一份置信度声明：验证了什么、用了什么假设、哪些模式历史上高风险。

### 4.6 环节五：仿真、Golden 与正确性判断

#1111 在两个模拟器上因越界读取崩溃，真机反而“通过”，原因是越界落入仍可映射的内存，而垃圾行恰好未被后续读取。#1094 更危险：实现和 Golden 同时采用了错误的 rank-local cache 语义，所以验证全部通过。

这说明 Golden 不是绝对真相，它也有来源、假设和适用边界。设计上需要展示：Golden 来自参考模型、同构实现还是与待测代码共享的 fixture？哪些不变量是独立验证的？

### 4.7 环节六：真机、分布式与异常恢复

#858 的错误分类把真实 UB 越界显示为 `running-stalled`，开发者花大量时间排查依赖，最终通过时间戳确认硬件异常比调度器超时早 38 秒。#502 中同一卡两个 die 的 Rank 进入 barrier 后挂死，定位必须结合 task id、core、ring 和 Rank 状态。

现有错误输出按组件分开打印，用户需要自己重建因果顺序。更好的体验应遵循“首发错误优先”，把后续超时、drain 和连锁故障降级为影响，而不是覆盖根因。

### 4.8 环节七：精度定位与确定性

这是体验成本最高的一环：

- #362 中合法的 FP32 累加顺序差异在 BF16 产生约 1 ULP 漂移，开发者不得不在精度与性能之间换配置。
- #368 中 score 仍在容差内，但 near-tie/top-k 顺序翻转，索引验证概率失败。
- #1081 展示完整放大链：`1e-6` 量级 FP32 尾差 → INT8 边界 → top-k 变化 → sparse attention 输入不同 → 最终大误差。
- #396 中单层宽松 Logits 验证可以通过，但自回归生成第 3 token 即分叉。
- #1122 中固定 seed 仍无法复现固定输出，服务没有任何错误日志。

共同结论是：**逐点误差阈值不足以描述模型语义风险。**验证产品需要理解敏感边界：argmax margin、top-k tie、量化阈值、cache visibility 和多轮状态复用。

### 4.9 环节八：性能调优与归因

#531 说明泳道条长度包含等待和同步，空闲的 vector subblock 看起来像在工作；#623 说明生成代码可包含数百次 dead self-copy 和上千次多余 barrier；#1037 直接报告全核空闲间隙。开发者能看到“慢”，但必须读 PTO/C++、统计 core parity、对照 PMU 才能知道“为什么慢”。

#828 是非常强的需求证据：用户自己制作了 15 类优化语法图鉴和 20 组泳道调优日志，并给出“现象→假设→实验→归因→精度验证”的方法。这不是普通文档贡献，而是在产品之外补了一套优化工作台。

### 4.10 环节九：Serving 集成与状态机验证

静态单次 Kernel 的成功不能覆盖服务状态：prefix cache、persistent worker、continuous batching、变长 token、多 Rank cache 副本、长 Decode 都会引入新状态。#713、#929、#951、#1122 分别说明热缓存、复用输入、长序列和重复请求会产生单次样例不可见的问题。

因此，Serving 验收不应是几个固定输入，而应是一个可视化状态矩阵：冷/热、首次/复用、短/长、固定/变化输入、单/多 Rank、整 Tile/尾块、MTP on/off。

### 4.11 环节十：PR、CI 与知识沉淀

标题规则估算显示，1006 个 PR 大致分为：能力新增 206、缺陷修复 203、性能优化 202、重构 160、测试/CI 78、文档/知识 28、其他 129。新增、修复和性能三类几乎等量，说明产品仍处于**能力扩张、稳定性修补和性能追赶同时发生**的阶段。

PR 作者共 38 人，贡献最高的 1 人占 30.9%，前 5 人占 61.6%。这不等同于组织风险，但说明大量判断集中在少数专家。自动评审可以扩展检查能力，却不能替代“为什么接受风险”的团队知识沉淀。

### 5.1 问题背后的共同结构

这 8 个问题可以归纳为三个断层：

1. **意图断层**：用户想表达“这个 Tensor 是动态有效长度”“这个 Cache 必须跨 Rank 一致”“这里必须有 WAR 依赖”，代码却只能用额外参数、Golden 约定或 no-op 间接表达。
2. **证据断层**：日志、Golden、泳道、PMU、生成代码和版本信息互不关联，用户需要手动拼图。
3. **知识断层**：一次定位形成的安全边界没有自动转成 Lint、契约、测试模板或上下文帮助，下一位开发者仍会重新踩坑。

## 6. 体验设计机会地图

### O1. 可信运行包 Run Capsule

**要解决的问题**：环境、命令、代码、Golden、Profile 和结果分散，难以复现。

一次运行自动生成一个可分享的证据包：

- 五仓 Commit、PTOAS/CANN/驱动、硬件和环境变量摘要；
- 模型/Shape/并行/Cache/MTP 等运行配置；
- 编译产物指纹、Golden 来源和比较规则；
- 结果、首发错误、关键 Tensor Diff、性能统计；
- 与上一个基线的可解释 Diff；
- 一键生成 Issue/PR 的复现块。

**关键设计原则**：不是再生成一份长日志，而是让每个结论都能展开查看原始证据。

### O2. 首次偏离定位器 First Divergence Navigator

**要解决的问题**：最终输出错误后，开发者人工向前逐层 Dump。

从请求输出、Logits 或目标 Tensor 出发，系统自动回答：

1. 哪一个 token/row/rank 首先偏离？
2. 哪一层、哪个 Kernel、哪个 task 首次产生差异？
3. 差异属于普通浮点尾差、量化边界、top-k 翻转、Cache 可见性还是未初始化写？
4. 对应哪一行 Python、哪段 IR/PTO/C++？
5. 与哪些历史 Issue 模式相似？

**关键设计原则**：默认使用模型/算子开发者的语言，IR 和生成代码作为下钻层，而不是入口。

### O3. 服务化契约中心 Contract Studio

**要解决的问题**：Shape、slot、cache、rank 和有效长度语义散落。

把契约从 Issue 文档升级为机器可读对象：

- 字段名、dtype、容量 Shape、运行时有效 Shape；
- source of truth 和废弃字段；
- per-request/per-token/per-rank 作用域；
- cache 写入、可见性、副本一致性和 padding 语义；
- Kernel、Golden、Serving adapter 各自消费的字段；
- 版本兼容矩阵和 Contract Diff；
- 自动生成 runtime assertion、fixture 和文档。

**关键设计原则**：契约变更必须能看到下游影响，而不只是代码搜索结果。

### O4. Failure-first 可观测性

**要解决的问题**：后续 timeout/stall 掩盖真正的首发硬件或任务异常。

- 按时间和因果链排序错误，突出 first fault；
- 将计算、内存、同步、等待、dispatch 和 idle 用不同语义呈现；
- 跨 Rank 对齐 task/barrier/notify/wait；
- 失败时仍保留泳道、依赖图和关键 Tensor；
- 对“分类器判断”和“原始证据”分别显示置信度。

### O5. 状态场景回归矩阵

**要解决的问题**：单次、固定输入验证无法覆盖服务状态机。

内置可组合场景：

- cold ↔ warm cache；
- fixed ↔ changing input；
- first run ↔ persistent worker reuse；
- aligned ↔ tail Shape；
- short ↔ long decode；
- single ↔ multi Rank；
- MTP on/off；
- prefix cache on/off；
- 连续重复与随机 seed sweep。

产品输出不是“跑了 20 次”，而是状态矩阵中哪些不变量在何处被破坏。

### O6. 性能实验工作台

**要解决的问题**：A/B 口径靠人维持，结论容易被范围和 Shape 污染。

- 强制绑定 workload、Shape、版本、Warmup、重复次数和 Golden；
- 自动检查比较范围是否一致；
- 同时展示 wall time、on-core busy、有效工作、等待和正确性；
- 支持同 session 交错 A/B，显示方差和置信区间；
- 保存“原结论—纠正—最终结论”的推理链。

### O7. 约束感知的编写与编译反馈

**要解决的问题**：依赖、Buffer、尾块和精度敏感模式只能靠经验。

优先做成编译期提示：

- 动态有效长度与物理 Shape 双重真相；
- `valid_shape` 缺失和尾块未覆盖；
- 多 Out 写回、Opaque 组合等历史高风险结构；
- `split` + dequant/narrowing cast 的精度风险；
- WAR/WAW 依赖意图无法证明；
- 设备 Buffer 预算与共驻风险。

提示需包含“为什么、影响什么、如何验证”，并允许显式接受或局部覆盖。

### O8. 评审信号中心

**要解决的问题**：Bot 评论很多，但最终判断分散。

- 将相似 Bot 意见聚类去重；
- 区分 correctness/security/performance/nit；
- 自动跟踪 fixed/declined/outdated；
- 对拒绝建议要求附实验或契约依据；
- 合并前生成“风险与证据摘要”；
- 将高价值规则转成 Lint、测试模板或 Agent skill 候选。

## 7. 机会优先级与业务价值

### 7.1 建议优先级

| 优先级 | 机会 | 为什么现在做 | 预期业务价值 |
| --- | --- | --- | --- |
| P0 | 可信运行包 | 数据已经存在，只缺统一组织；是其他诊断能力的数据底座 | 降低复现时间、跨团队沟通成本和基线争议 |
| P0 | 状态场景回归矩阵 | 已有多个线上/热路径问题证明单次验证不足 | 减少高代价正确性问题后移到 Serving 阶段 |
| P0 | Failure-first 可观测性 | #858 等案例显示错误方向会被系统主动带偏 | 缩短 MTTR，减少跨仓错误流转 |
| P1 | 首次偏离定位器 | 当前最昂贵的人工活动，且已有 Tensor/Golden/任务数据基础 | 显著缩短精度调试闭环，提高迭代信心 |
| P1 | 服务化契约中心 | DeepSeek 服务化仍在快速演进，契约漂移高频 | 降低 Lib/Serving/Runtime 联调与回归成本 |
| P1 | 性能实验工作台 | 性能 PR 约占五分之一，且测量口径争议明显 | 提高优化结论可信度，减少无效优化和重复测量 |
| P2 | 约束感知反馈 | 需要编译器/运行时配合，但能从根源减少 workaround | 将专家经验产品化，降低学习门槛 |
| P2 | 评审信号中心 | 自动评审已规模化，信息架构价值开始显现 | 提高 Review 决策效率和风险可追溯性 |

### 7.2 建议 North Star

不要只用编译成功率、CI 通过率或 PR 吞吐衡量体验。建议定义：

> **可信迭代时间（Time to Trusted Iteration）**：从开发者完成一次代码改动，到他能够用可复现证据确认“正确性、性能和适用边界均满足目标”的时间。

可拆为：

- Time to Reproduce：从问题出现到他人可稳定复现；
- Time to First Divergence：从最终异常到定位首次偏离；
- Time to Attribution：从症状到确定责任层；
- Time to Comparable Benchmark：从运行到形成同口径 A/B；
- Evidence Completeness：环境、Golden、状态矩阵、Profile、风险说明的完整率；
- Escaped State Bugs：只在复用、长序列、热缓存、多 Rank 或尾块状态下发现的问题数。

## 8. 共创工作坊材料

### 8.1 建议形式

建议开展一次 120 分钟共创，参与者包括：算子/模型开发、PyPTO/编译器、Runtime/DFX、Serving、测试、业务产品和体验设计。

### 8.2 三张事实卡

**事实卡 A｜正确性信任**  
相同请求、固定 seed，16 次运行产生 3–5 种输出，部分在 token 30 跳成无关 JSON；服务无报错。  
证据：[Issue #1122](https://github.com/hw-native-sys/pypto-lib/issues/1122)

**事实卡 B｜错误归因**  
系统显示 `running-stalled`，真正的首发故障是 38 秒前的 UB 越界；开发者最初被引导排查依赖。  
证据：[Issue #858](https://github.com/hw-native-sys/pypto-lib/issues/858)

**事实卡 C｜性能可信度**  
同一对比从“慢 2.3×”经口径修正变为“基本持平”，随后发现 Shape 才是主因且大 Shape 有正确性风险。  
证据：[Issue #622](https://github.com/hw-native-sys/pypto-lib/issues/622)

### 8.3 议程

| 时间 | 活动 | 产出 |
| ---: | --- | --- |
| 0–15 min | 阅读三张事实卡，个人标注“最不可接受的损失” | 共同问题语言 |
| 15–35 min | 按真实旅程贴痛点：预防/发现/定位/恢复/沉淀 | 旅程热力图 |
| 35–55 min | 选一条痛点，补全证据链中缺失的信息 | 缺失证据清单 |
| 55–80 min | 以 “How might we” 生成跨层方案 | 机会草案 |
| 80–100 min | 用用户损失×覆盖面×实现依赖×证据置信度排序 | P0/P1/P2 |
| 100–115 min | 为前 3 个机会定义最小验证实验 | MVP 假设与指标 |
| 115–120 min | 明确 owner、依赖和下一次评审时间 | 行动清单 |

### 8.4 共创问题

1. 哪些错误必须在编译期阻止，哪些可以警告，哪些只能运行时诊断？
2. 一次“可信运行”最少需要绑定哪些证据？
3. 当 Golden 与实现共享同一假设时，系统如何提醒用户？
4. 从最终 Logits 错误下钻，用户第一屏最想知道哪三件事？
5. 性能对比在什么条件下才允许显示“更快 X%”？
6. 哪些 Cache/Shape/Rank 不变量应该由契约自动生成测试？
7. Bot 提出的建议，如何快速变成“已修复、已拒绝、需人判断、已过期”四类？
8. 哪些 workaround 值得升级成正式 API，哪些应该由 Lint 禁止？

### 8.5 优先级评分模板

每个机会按 1–5 分评分：

- 用户损失：不解决会造成多少时间、错误或上线风险？
- 覆盖面：影响多少角色和任务环节？
- 频次信号：Issue/PR 中是否反复出现？
- 证据置信度：是否有可复现、多案例或跨版本证据？
- 产品杠杆：一次设计能否同时服务人、Agent 和多个仓库？
- 实现依赖：需要多少编译器/Runtime/Serving 改造？此项反向计分。

## 9. 建议的概念验证

### MVP A：可信运行包

选择 #1122 的重复请求场景，自动收集 16 次运行的版本、配置、设备、输出 token、首个分叉 token、MTP 接受率和关键告警。成功标准：另一位开发者无需询问作者即可复现实验并确认分叉位置。

### MVP B：首次偏离定位

选择 #1081 的 FP32→INT8→top-k 放大链，做一条可交互证据链。成功标准：用户能在 5 分钟内从最终 `x_out` 失败定位到 `qr_fp32` 的首次差异，并理解“合法尾差为什么变成语义错误”。

### MVP C：Failure-first 泳道

选择 #858，把首发 AICore exception、后续 scheduler timeout、running/waiting task 和 core 信息放到统一时间线。成功标准：首次阅读者不会把问题误判成依赖死锁。

### MVP D：服务化契约 Diff

选择 #766/#1050，把固定 T + `num_tokens` 与动态 token axis 两版契约并排。成功标准：系统能自动指出调用方、Golden、ABI 和测试中受影响的字段，并生成至少一个尾块用例。

## 11. 最终判断

`pypto-lib` 已经证明团队能够高速构建模型能力、修复问题并推进性能，但产品体验仍停留在“专家可以把问题查清楚”的阶段。下一阶段的设计目标应当是：

> **让普通开发者和 Coding Agent 都能以更少的隐性知识，完成一次可复现、可解释、可比较、可回归的可信迭代。**

体验设计团队最有价值的介入点，不是替技术团队美化日志，而是帮助团队共同定义：什么叫可信、一次判断需要哪些证据、不同层如何共享同一份契约、失败时用户应该先看到什么、一次经验如何自动进入下一次开发流程。
