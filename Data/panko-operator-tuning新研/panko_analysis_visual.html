每类文件承担什么职责

nodes/
当前搜索过程中保留下来的 candidate kernel；不是所有 trial 都会保存。
report/*.py
历史 best-so-far kernel；只追加，不覆盖。
report/*.json
对应 report 的 provenance：来源、日期、精确 latency、原始/翻译 hash。
optimization.md
人类可读的 PANKO 优化日志：症状、假设、动作、结果与下一步。
searchstate.json
真正的机器状态：search tree / eval cache / config / progress / BO memory 等。
仓库不包含完整 environment version、input data、test harness 和 NPU runtime 环境，因此它能保存 optimization provenance，但还不能单独完成完整 reproducibility。
01

Current best

从当前 incumbent kernel 开始。

02

Observe

latency、util、bubble、AIC/AIV、stall。

03

Diagnose

识别 vector-bound、occupancy、memory 等症状。

04

Choose action

从 F / I / S optimization action 中选方向。

05

Prune

UB、L1、alignment、shape、重复候选先过滤。

06

Evaluate

compile → correctness → 真机 performance。

07

Learn

keep / revert，并用新 profile 调整下一轮搜索。

关键不是线性 pipeline，而是循环：结构变化会改变约束；约束变化会重新打开或关闭搜索轴，因此 Search Space 本身会动态变化。

ActionF-17 reduce materialization
Result255.26 → 208.98 µs
Next更新 bottleneck，继续 evolve

代表性变化：避免大型 concat intermediate，把 Q/K 的计算结构拆开，并把部分 scale 移出循环。

核心体验原则

不要只展示 trial

用户关心系统学到了什么，不是跑了多少次。

把约束讲清楚

“UB 320KB > 192KB”比“candidate rejected”有价值。

解释 why

把 Observation → Action 的因果链暴露出来。

保存现场

补齐 environment / input / harness，才能从 provenance 走向 reproducibility。
