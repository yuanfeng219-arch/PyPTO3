1.2编程模型：三层分发 + 五级 JIT

操作分发分三层：pl.*（统一层，按输入类型自动分发）、pl.tensor.*（DDR 级）、pl.tile.*（片上）。语言指南里明确写着"推荐尽量使用 pl.*"——这句话分量很重，它意味着官方推荐的写法是不写内存层次。

@pl.jit 家族提供五个入口，一个程序可以横跨 host、chip、core 三级：

装饰器对应 IR用途
@pl.jitFunctionType.Orchestration芯片级入口，分发 InCore 工作
@pl.jit.hostlevel=HOST, role=Orchestrator分布式（L3+）入口，分配窗口缓冲、按 rank 分发
@pl.jit.incoreFunctionType.InCore独立 InCore 子函数
@pl.jit.inlineFunctionType.Inline调用点由 InlineFunctions pass 展开
@pl.jit.opaqueFunctionType.Opaque包裹编排循环与 pl.at 作用域

子函数依赖从入口函数体自动发现，因此一个完整的分布式程序可以不依赖任何 @pl.program 类写出来。examples/models/qwen3_jit/ 就是这个形态：kernels/ 下按 scope 拆分的 inline/incore 工具，加一个 @pl.jit 入口组合，跨文件用普通 Python import。

作用域体系有六种一等 ScopeStmt（InCore / Cluster / Hierarchy / Spmd / SplitAiv / Runtime），每种只携带对该类型合法的字段——非法组合在构造时即不可表达。

1.4编译器工程：IRProperty 契约与每 pass 前后验证

这是我认为最被低估、也最难被复制的资产。每个 pass 都声明三组属性：

VerificationInstrument 在每个 pass 执行前检查 required、执行后检查 produced 加上全部结构性属性（TypeChecked、UseAfterDef、InOutUseValid、PipelineLoopValid、ManualDepsOnSubmitOnly 等）。配合 IR 本身的设计——不可变、shared_ptr<const T>、Var 以指针而非名字为标识、每个节点带 Span 源位置、反射字段系统区分 Ignore/Def/Usual——编译器中间任何一步破坏不变量，都会立刻在带源位置的诊断里炸出来。

Submit 被做成与 Call 并列的一等 IR kind：异步任务启动对同步调用，有独立的 deps_ / core_num_ / sync_start_ 字段，贯穿全流水线不下沉，并由 ManualDepsOnSubmitOnly verifier 保证依赖 attr 永不落到普通 Call 上。

整个 IR 层是一致的："用类型系统而非约定来防错"。

1.5分布式是一等公民

12 个 pld.* 算子 + 4 个 append-only ABI 枚举，全部作用于窗口绑定的 DistributedTensorType——由 pld.alloc_window_buffer 分配的对称、按 rank 划分的通信窗口的切片。verifier 用严格 kind-trait 拒绝普通 TensorType 进入跨 rank 槽位：非窗口绑定的 tensor 永远不会被误传入跨 rank 槽位，这是类型系统保证的，不是文档约定。

覆盖 remote_load/remote_store（TLOAD/TSTORE）、get/put（TGET/TPUT）、allreduce/broadcast/reduce_scatter/allgather/all_to_all/barrier，以及 notify/wait 控制面。运行时侧有 DistributedWorker、alloc_stacked_tensor（权重按卡切分常驻）和 prepare()（跨 dispatch 复用 setup）。

1.6DFX 与可观测性

五个完全正交的运行时开关（L2 swimlane、args dump、PMU、dep gen、scope stats），1:1 映射到 simpler 的 CallConfig，产物路径契约固定。文档甚至解释了为什么 onboard 平台开 swimlane 要跑两趟：抓图趟必须在独立子进程里跑，因为 runtime 无法可靠回收 DFX collector 申请的 SVM host-register 映射，同进程第二趟会撞上 halHostRegister 返回 8 的注册上限。

加上编译期分阶段耗时 profiling、dump_passes=True 的每 pass IR 快照，以及 pypto-skills 里独立发布的 generate-ir-trace / incore-profiling / setup-and-run 插件（Claude Code 与 Codex 双支持）。

1.7成熟度实况——文档自己给的数字

ptoas-op-status.md 是我见过最诚实的状态表，判定原则写得很硬：一个 op 是否"完成"以是否有 ST 测试为准；"前端已写 + 无 ST" 一律判为未完成。

Part 03 / 03

八个维度的深度对比

3.1抽象起点：这是根本分歧，不是程度差异

TileLang 的起点是"一个 kernel 的内部"：先 T.Kernel(bx, by, threads=128) 声明网格，再手工声明 shared / fragment buffer、手工 T.copy 搬运、手工 T.Pipelined(K, num_stages=3)。编译器做的是 layout inference、向量化、同步插入——它优化你写好的 schedule，但 schedule 是你给的。

PyPTO 的起点是"一段张量计算"：pl.matmul / pl.exp / pl.row_max，用 with pl.at(level=CORE_GROUP) 圈出在哪一级执行，其余交给 pass 管线。它自己产生 schedule。

决策PyPTOTileLang
网格 / 线程数不暴露；pl.spmd(N) 是任务级用户写 T.Kernel(..., threads=)
片上 buffer 声明InitMemRef 自动用户 T.alloc_shared/fragment
数据搬运自动（可用 pl.load/move 手工接管）用户 T.copy
buffer 复用MemoryReuse 自动装箱Ascend 侧自动（TL_ASCEND_MEMORY_PLANNING）
Cube / Vector 分核ExpandMixedKernel 自动 + pl.split 提示Developer 自动 / Expert 手工 T.Scope
流水深度用户 stage=F + 编译器 skew用户 num_stages=

结论：在"kernel 内部"这一层，两者的自动化能力其实是同一量级的——TileLang-Ascend 的 Developer 模式 + auto sync + memory planning，对应 PyPTO 的 InferTileMemorySpace + ExpandMixedKernel + MemoryReuse。PyPTO 的抽象高一格，这既是优势也是风险：抽象越高，编译器猜错时用户越无处下手。

3.2控制权：TileLang 有明确的逃生舱，PyPTO 的更窄

TileLang 的 Expert 模式是同一套语法内的降级——把 T.Scope("C") 写出来即可，其他代码不动。这是一条连续谱。

PyPTO 的分层是 pl.* → pl.tile.*：从 Tensor 掉到 Tile 要重写数据流（显式 pl.load(..., target_memory=pl.Mem.Mat) → pl.move(..., Mem.Left) → pl.matmul → pl.store）。手工模式确实存在，但这是换一套写法，不是加一个标注。

这是 PyPTO 开发者体验上最实际的一个弱点：性能不达标时，从自动降到手动的迁移成本是重写，而非微调。

3.3并行模型：SPMD 对 MPMD——PyPTO 的真正护城河

TileLang 是纯 SPMD：一个 kernel、一个网格、所有 block 跑同一段代码。跨 kernel 的编排交给外部框架（PyTorch / ACLGraph）。

PyPTO 是 MPMD：Orchestration 函数编译到 AICPU 上运行，用 pl.submit / pl.spmd_submit 提交任务，任务间有一等的 deps_ 依赖边；AutoDeriveTaskDependencies 还能自动推导依赖，并把 Input→NoDep、InOut→OutputExisting 改写掉以省去运行时的 overlap 查询。

这意味着 PyPTO 能表达 TileLang 结构上表达不了的东西：

  • 一个程序里同时描述 Q/K/V projection、attention、MLP 三个 scope，让它们在 AICPU 的任务图里按真实依赖并发（qwen3_jit 就是这个形态）
  • 计算–通信深度融合：pld.tensor.put + pld.system.notify 与本地计算重叠
  • 跨核软流水：SkewCrossCorePipeline 让 cube 领先 vector D 个迭代

TileLang-Ascend 的官方描述里完全没有多卡、没有模型级编排。这不是它做得差，是它不在这个赛道上。

3.4分布式：不对称竞争

PyPTO 有 @pl.jit.host、12 个 pld.* 算子、window buffer 类型系统、DistributedWorker、alloc_stacked_tensor，且分布式 comm op 的 ST 覆盖相对完整——test_l3_allreduce 含 ring / host / parallel / intrinsic 四种实现，broadcast / allgather / reduce_scatter / get / put / notify_wait 均有覆盖。

TileLang 两侧都没有。这一维度上没有竞争，只有空白。

3.5调优路径：TileLang 明确领先

PyPTOTileLang
Autotuner不存在eager-mode；pipelined / grouped compilation，multi-GPU benchmarking
手工 schedule 空间中——stage、split、tile 常量大——threads、num_stages、layout annotate、swizzle
编译器自动决策大中
性能不达标时的路径读 IR dump → 理解 pass 决策 → 改 tile 常量或降到 tile 级重写调参 → autotune 扫 → 降到 Expert 模式

这是 PyPTO 最该补的一块。没有 autotuner，意味着"编译器自动决策"这个赌注的收益完全依赖固定启发式的质量；一旦启发式在某个 shape 上失手，用户拿不到"多试几组"的廉价出路，只能进 IR dump。PyPTO 的 IR trace 与 DFX 工具链做得很好，但那是诊断工具，不是搜索工具——它降低理解成本，不降低试错成本。

结论

它们不是同一类产品

TileLang 是一个 kernel 编译器，赌的是"覆盖足够多硬件 + autotune 帮你找到好 schedule"。PyPTO 是一条从模型到多卡执行的整栈，赌的是"编译器自己产生 schedule + 用 IR 契约保证这个过程可信 + 把编排和通信也编译进来"。

把它们放在同一张雷达图上比"谁的 tile DSL 更好"，会得出错误结论。

PyPTO 明确领先

  • MPMD 任务编排
  • 分布式 / 通信原语
  • 编译器 IR 工程与验证体系
  • 抽象层级（Tensor 起手）
  • DFX 与可观测性

势均力敌

  • kernel 内自动化
  • Cube / Vector 分核
  • 软流水

TileLang 明确领先

  • Autotuner（PyPTO 为零）
  • 算子覆盖与真机验证率
  • 多后端可移植性
  • 社区与生产用户
  • 安装与上手门槛
  • 手工调优的逃生舱设计

三条判断

不要在"tile DSL 好不好用"上跟 TileLang 正面比。 那个战场上 PyPTO 的抽象更高但逃生舱更窄，且缺 autotuner，赢面不大。真正无法被复制的是 MPMD + 分布式 + IRProperty 验证体系——这三样 TileLang 在架构上根本没有位置放。
Autotuner 是当前最高优先级的能力缺口。 它是"编译器自动决策"这个赌注的必要保险。没有它，自动化的每一次失手都要用户付出读 IR 的代价；有了它，自动化的失手可以用机器时间兑换。
45% 的真机 ST 覆盖率与卷积整族缺失，是任何性能叙事的前置条件。 在这个数字上去之前，"整栈协同"的故事很难在开发者那里兑现成信任——TileLang-Ascend 的样例列表里有 conv、sort、CE loss、TopK，那是一份可以直接拿来对照的清单。
