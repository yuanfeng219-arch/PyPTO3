# 算子开发 Agent 能力规划与 Coding Agent 原型

> 文档版本：v0.1  
> 更新时间：2026-08-12  
> 适用范围：PyPTO / PTO 算子开发、调试、正确性验证与性能调优  
> 原型入口：[Toolkit Studio](../Design/Toolkit%20Studio/index.html)、[算子 Coding Agent 独立原型](../Design/operator-coding-agent/index.html)

---

## 1. 规划目标

算子开发的难点并不只是“如何生成一段代码”，而是开发者需要持续回答一组跨层问题：

- 当前硬件、数据类型和算子能力是否支持目标实现？
- DSL 源码表达了什么 shape、layout、scope、依赖和精度意图？
- 源码经过编译 Pass 后发生了什么变化？
- 错值、编译失败、设备异常或性能回退最早从哪里出现？
- 一个调优方案为什么更快，是否破坏了正确性或资源约束？
- 当前结论是源码事实、静态推断，还是来自真实设备运行？

因此，Agent 不应只作为对话助手存在，也不应被设计成固定步骤的流程向导。更合适的产品形态是：**Agent 嵌入开发现场，理解当前文件、选区、编译产物和运行证据，在不同任务场景中提供针对性的分析与操作能力。**

### 1.1 规划逻辑

Agent 能力按以下逻辑组织：

`典型任务场景 → 开发者需要做出的判断 → Agent 应提供的内容 → 可执行动作 → 验证证据`

每个 Agent 都应具备三个共同特征：

1. **上下文感知**：理解当前源码、相邻实现、目标硬件、编译配置和测试基线。
2. **证据可追溯**：结论能够回到源码行、IR 节点、规则、日志、Tensor 或性能数据。
3. **人机协作**：默认提供解释和建议；修改源码、运行测试、应用调优参数等动作由开发者确认或明确授权。

## 2. 算子开发 Agent 全景

建议围绕算子生命周期规划六类核心 Agent。它们不是六套彼此割裂的产品，而是共享同一份开发上下文和证据链，在不同任务阶段承担不同主责。

| Agent | 主要阶段 | 核心问题 | 典型输出 |
|---|---|---|---|
| 算子 Coding Agent | 编码与改造 | “应该怎样写，当前代码表达了什么？” | 能力检索、代码契约、实现建议、源码解释、测试草案 |
| 编译与 Guard Agent | 编译与 Lowering | “为什么编不过，变换是否仍然合法？” | 错误归因、Pass 变化、不变量校验、修复建议 |
| 调试 Agent | 运行与故障定位 | “错误最早从哪里开始？” | 症状归类、跨层链路、首个异常点、最小复现 |
| 正确性与精度 Agent | 数值验证 | “结果是否可信，精度损失在哪里发生？” | 多 Oracle 对比、Tensor Diff、误差归因、容差建议 |
| 性能调优 Agent | Profiling 与优化 | “为什么慢，改什么最有效？” | 瓶颈排序、数据流分析、候选方案、对比实验 |
| 集成与服务 Agent | 模型集成和服务验证 | “算子放回模型或服务后是否仍然成立？” | 算子覆盖、端到端影响、SLO 下钻、发布门禁 |

### 2.1 共享底座

各 Agent 应共享以下底层能力，避免不同阶段重复建立上下文或给出相互矛盾的结论：

- 项目与环境画像：代码版本、依赖版本、目标昇腾硬件、编译选项和运行配置；
- 算子知识索引：PyPTO DSL、PTO IR、PTOAS、ISA 约束、样例、测试和已知问题；
- 统一对象关联：`source span → DSL op → IR op/pass → PTOAS/ISA → runtime task → tensor/metric`；
- Shape、dtype、layout、scope、依赖、内存和资源语义解析；
- 可复现的构建、测试、运行和 benchmark 入口；
- 结论可信度标记与证据引用。

## 3. 典型任务场景与 Agent 能力

### 3.1 算子 Coding Agent

#### 场景 A：新增一个算子或补齐一层能力

例如 PTOAS 已支持某个操作，但 PyPTO 前端、类型推导、Lowering、CodeGen 或测试尚未完整接入。

Agent 应提供：

- 查询算子在各层的支持状态和硬件约束；
- 找到最相近的现有算子，提取 API、注册、推导、Lowering 和测试模式；
- 生成需要修改的文件集合与影响范围；
- 给出符合仓库风格的最小代码提案；
- 说明为什么采用当前分层方式，以及没有修改哪些层；
- 生成覆盖 dtype、shape、边界值和错误路径的测试草案。

#### 场景 B：阅读和理解已有算子源码

Agent 应从当前文件中提取：

- 算子名称、数学语义和模型上下文；
- 输入、权重、输出的 shape 与 dtype 契约；
- 核心计算阶段和中间 Tensor；
- scope、并行方式、依赖链和执行资源；
- Chunk、Tile、pipeline stage 和循环次数；
- cast 位置、累加精度和最终输出精度；
- 可能的尾块、对齐、广播和越界风险；
- 相关测试及当前证据缺口。

#### 场景 C：修改已有算子

Agent 应提供：

- 当前修改影响到的函数、调用点和相邻实现；
- 修改前后的契约差异；
- 需要同步更新的变体、测试和文档；
- 对 shape、dtype、layout、内存占用和后端能力的影响；
- 可直接执行的局部检查，以及接受修改前的风险摘要。

#### 场景 D：解释源码如何映射到昇腾硬件

Agent 应建立源码与硬件对象之间的可视关联：

- 数据从 DDR/GM 搬入片上缓存和 UB 的路径；
- Vector、Cube、Scalar 等执行单元承担的计算；
- 中间值在片上内存中的逻辑驻留；
- dtype 在载入、计算、累加和写回阶段的变化；
- 每个执行阶段对应的源码行；
- 哪些是源码语义映射，哪些必须等待 Pass 后 IR 或真实指令才能确认。

### 3.2 编译与 Guard Agent

#### 典型场景

- DSL 语法正确但编译失败；
- 某个 Pass 后 op、依赖或属性消失；
- layout、地址、索引宽度或 ISA 容量不合法；
- 自动依赖和手工依赖发生冲突；
- 编译成功，但存在静默错值或死锁风险。

Agent 应提供：

- 将原始错误映射到源码位置和具体约束；
- 展示 Pass 前后 IR 的结构化差异；
- 校验 op 合法性、作用域、依赖、liveness、layout、地址和资源容量；
- 解释自动 Lowering 的原因、代价与覆写方式；
- 给出最小修复建议，并预测修复影响；
- 在每个关键 Pass 后形成可审查的 Guard 结果。

### 3.3 调试 Agent

#### 典型场景

- 输出全零、NaN、Inf 或局部错误；
- 设备报错、hang、超时或任务长期等待；
- 同一份代码在不同环境中表现不一致；
- 只有模型级输出异常，无法确认是哪个 kernel 引起。

Agent 应提供：

- 从症状出发自动选择低干扰的取证方式；
- 串联源码、IR、指令、Task、Event、Fence 和 Tensor；
- 优先定位首个消失的 op、首个非法复用、首个 Tensor 分歧或最早的长期等待；
- 区分环境、编译、运行时、同步和数值问题；
- 生成最小复现、关键日志摘要和可共享证据包；
- 给出下一步验证动作，而不是只堆叠原始日志。

### 3.4 正确性与精度 Agent

#### 典型场景

- 新算子需要建立数值基线；
- BF16/FP16/FP32 混合精度导致偏差；
- 算子融合或调优后需要确认精度没有退化；
- 需要定位首个出现误差的中间 Tensor。

Agent 应提供：

- CPU/Torch reference、库实现和 PyPTO device 多 Oracle 对比；
- 最大绝对误差、相对误差、ULP、异常值和误差分布；
- 按模型层、kernel、执行阶段和 Tensor 定位首个分歧；
- 标出 cast、累加和归约的精度路径；
- 根据算子数学特征建议容差，但不自动放宽断言；
- 区分结构验证、间接证据和当前实现的直接数值证据。

### 3.5 性能调优 Agent

#### 典型场景

- 算子正确但延迟或吞吐不达标；
- 不确定 Chunk、Tile、stage 或并行参数如何选择；
- 出现冗余搬运、GM round trip、同步等待或流水空洞；
- 新版本相对可信基线发生性能回退。

Agent 应提供：

- 将总耗时拆解到计算、搬运、同步、调度和缓存；
- 将 PMU、trace 和 runtime 指标映射回源码和硬件路径；
- 识别主要瓶颈并按预期收益排序；
- 给出有边界的参数搜索空间和候选实现；
- 对每个候选同时执行正确性、资源和性能门禁；
- 展示相对基线的因果 Diff，而不是只给出一组更快的数字；
- 将优选结果保存为可复用的 tuning recipe。

### 3.6 集成与服务 Agent

#### 典型场景

- 将算子放回完整模型；
- 检查 fallback、算子覆盖和端到端精度；
- 分析 kernel 变化对 TTFT、TPOT、吞吐和显存的影响；
- 验证不同 batch、序列长度和并发配置。

Agent 应提供：

- 从模型节点追踪到具体算子实现和 fallback；
- 建立 token/decode step、模型节点、kernel 与运行指标的关联；
- 对比单算子收益与模型/服务级实际收益；
- 给出容量边界、推荐配置和服务就绪门禁；
- 保存模型、算子、编译产物和运行配置的版本关系。

## 4. Coding Agent 的产品定位

### 4.1 一句话定义

> 算子 Coding Agent 是嵌入代码工作台的上下文型开发搭档，帮助开发者理解算子、发现能力、生成或修改实现，并在编码当下预览数据、精度、分块、硬件执行和验证风险。

### 4.2 不做什么

- 不把算子开发包装成固定步骤的向导；
- 不只提供聊天回答而缺少源码定位和结构化证据；
- 不把静态推断伪装成真实设备运行结果；
- 不在没有验证的情况下直接宣称实现正确或性能更优；
- 不替代开发者做关键的接口、精度和性能取舍。

### 4.3 核心能力结构

| 能力域 | Coding Agent 提供的内容 |
|---|---|
| 上下文建立 | 当前文件、选区、调用点、相邻算子、测试、目标硬件、配置 |
| 知识检索 | DSL/API 语义、硬件能力、支持矩阵、限制、样例和已知问题 |
| 代码理解 | 数学语义、输入输出契约、中间值、控制结构和变体差异 |
| 代码生成与修改 | 最小实现提案、跨文件修改、风格对齐、影响说明 |
| 编码期预览 | shape、dtype、layout、scope、依赖、分块、数据流和硬件映射 |
| 风险提示 | 不支持能力、危险默认、尾块、精度、资源和同步风险 |
| 验证准备 | 单测、Golden、边界用例、编译检查和 benchmark 草案 |
| 证据表达 | 源码行、规则、关联文件、推断依据和可信边界 |

## 5. Coding Agent 原型的信息结构

当前原型采用“文件树 + 源码编辑区 + 右侧 Agent 分析面板”的工作台结构。Agent 内容与当前文件及源码行联动，不额外引入流程向导。

### 5.1 左侧：工程上下文

- 当前文件和相关文件；
- 修改状态；
- Agent 已读取的参考实现、能力文档和测试；
- 当前目标硬件和任务上下文。

### 5.2 中间：源码与协作

- 完整源码或修改 Diff；
- Agent 提案及修改理由；
- 源码行与右侧分析对象双向联动；
- 开发者可追问、要求调整或应用局部修改。

### 5.3 右侧：结构化分析

右侧面板不是通用属性表，而是 Coding Agent 对当前算子的“可视化理解”。针对 RMSNorm 原型，分为四个页签。

#### 概览

- 算子数学语义；
- 模型中的上游和下游；
- 输入、权重、输出的 shape 与 dtype；
- 执行 scope；
- 同文件多实现或多变体对比；
- Agent 的关键结论与联动修改提醒。

#### 数据与精度

- 输入、计算、累加和输出的 dtype 变化；
- 中间 Tensor 的逻辑 shape；
- 完整输入、单 Chunk、Gamma 和输出的逻辑字节数；
- 两遍或多遍扫描产生的数据读取量；
- 昇腾硬件上的数据流转路径；
- 源码阶段与 DDR、ND-DMA、UB、Vector 的联动；
- 静态估算与真实后端分配之间的边界说明。

#### 分块流水

- Hidden 维度如何切分为 Chunk；
- Chunk 数量、每遍迭代次数和总处理次数；
- pipeline stage；
- 两遍计算的职责分工；
- 尾块、对齐和整除性检查。

#### 验证

- 当前已存在的编译、结构和数值证据；
- 直接证据、间接证据和缺失证据；
- 需要补充的 Torch Golden、逐 Pass 数值验证和性能对比；
- 一键生成当前 Kernel 测试草案的动作入口。

### 5.4 可信度标记

右侧所有内容应明确标记来源类型：

| 类型 | 含义 | 示例 |
|---|---|---|
| 源码事实 | 可直接从当前文件读取 | shape、dtype、stage、cast 位置 |
| 跨文件解析 | 来自调用点、配置、测试或相邻实现 | 模型上下游、输出契约、已有测试 |
| 静态估算 | 基于 shape、dtype 和语义推导 | 逻辑字节数、扫描量、工作集 |
| 运行实测 | 来自编译产物或设备运行 | 实际地址、指令、PMU、耗时、误差 |

只有“运行实测”可以用于确认真实指令时序、片上地址、实际占用和性能结论。

## 6. RMSNorm 示例：Coding Agent 可以提取什么

示例源码：[rmsnorm.py](../repo/pto/examples/models/qwen3_jit/kernels/rmsnorm.py)

文件中包含两个具有相同数学语义、但数据类型和调度参数不同的实现。

| 属性 | `input_rmsnorm` | `post_rmsnorm` |
|---|---|---|
| 模型位置 | Attention 前 | Attention 后、MLP 前 |
| 输入 | `hidden_states`，BF16 | `resid`，FP32 |
| Gamma | FP32 | FP32 |
| 输出 | BF16 | BF16 |
| Chunk | 512 elements | 128 elements |
| Chunks / pass | 16 | 64 |
| Pipeline stage | 4 | 2 |
| 输入 Cast | BF16 → FP32 | 无 |
| 输出 Cast | FP32 → BF16 | FP32 → BF16 |
| 计算结构 | 两遍 RMSNorm | 两遍 RMSNorm |

### 6.1 两遍计算结构

第一遍：

1. 按 Hidden 维度读取当前 Chunk；
2. 必要时将输入提升为 FP32；
3. 计算平方；
4. 执行 `row_sum`；
5. 将结果累加到 FP32 部分和；
6. 计算 `variance` 和 `inv_rms`。

第二遍：

1. 再次读取当前输入 Chunk；
2. 读取对应的 Gamma；
3. 用 `inv_rms` 完成归一化；
4. 与 Gamma 相乘；
5. 转为 BF16；
6. assemble 到最终输出。

### 6.2 Chunk 的含义

Chunk 是一次送入当前计算流水处理的一段数据，而不是完整 Tensor。

对于 Hidden Size 8192：

- `input_rmsnorm`：`8192 ÷ 512 = 16` 个 Chunk；
- `post_rmsnorm`：`8192 ÷ 128 = 64` 个 Chunk。

Chunk 会影响：

- 单次片上工作集大小；
- 循环次数；
- pipeline 的并行机会；
- 搬运与计算的重叠；
- UB 使用和临时值生命周期；
- 尾块与对齐处理。

Chunk 更大不一定更快。它会减少循环和调度次数，但也可能增加片上内存压力、降低流水灵活性。Chunk 更小则相反。因此，Chunk 是需要结合硬件资源和实测结果调优的调度参数。

### 6.3 昇腾硬件数据流

原型将源码语义映射为以下逻辑路径：

`DDR/GM → ND-DMA Cache → UB ⇄ Vector → UB → DDR/GM`

四个可交互阶段如下：

| 阶段 | 硬件路径 | 数据与精度 | 关联源码语义 |
|---|---|---|---|
| 01 载入 | DDR → ND-DMA → UB | Input 为 BF16→FP32；Post 保持 FP32 | 读取输入 Chunk 和 Gamma |
| 02 归约 | UB ⇄ Vector | FP32 平方与累加 | `mul`、`row_sum`、`add` |
| 03 归一化 | UB ⇄ Vector | FP32 `sqrt`、`recip`、expand multiply | `inv_rms`、归一化、乘 Gamma |
| 04 写回 | Vector → UB → DDR | FP32→BF16 | `cast`、`assemble` |

交互要求：

- 点击执行阶段时高亮对应硬件节点、数据路径和源码行；
- 点击源码行时切换到对应函数和执行阶段；
- Input/Post 切换后同步更新数据类型、Chunk、流水和硬件路径说明；
- 硬件图支持最佳视图、缩小、放大、比例显示和拖拽平移；
- 默认加载时根据面板尺寸计算最佳视图。

### 6.4 当前可得结论

- 两个函数共享相同的两遍 RMSNorm 数学结构；
- 两者不能因为数学语义相同就直接统一 Chunk 和 stage；
- `input_rmsnorm` 两遍均存在 BF16→FP32 输入转换；
- `post_rmsnorm` 的残差输入已经是 FP32，只在输出前转换为 BF16；
- 两遍计算意味着输入会被逻辑读取两次；
- Hidden 8192 能被 512 和 128 整除，当前没有尾块；
- 修改归约、精度或 assemble 逻辑时，需要同步检查两个函数。

### 6.5 当前不能仅靠源码确认的内容

- 实际 MTE 搬运指令与调度时序；
- UB 的真实地址、对齐和复用；
- 临时 Buffer 的实际占用；
- Vector 指令序列和流水重叠；
- 真实 GM 流量、带宽利用率和执行周期；
- 两个 Chunk/stage 配置的实际性能优劣。

这些内容需要结合 Pass 后 IR、内存分配结果、PTOAS/ISA 和设备 Profiling 数据，由 Guard Agent 或性能调优 Agent 继续补全。

## 7. Agent 输出的通用结构

为了让 Agent 的回答可以直接进入 IDE、Studio、CLI 和 CI，建议统一为以下结构：

1. **结论**：一句话说明当前发现或建议；
2. **影响**：影响哪些输入、输出、函数、调用点或硬件资源；
3. **证据**：源码行、规则、IR、日志、Tensor 或指标；
4. **可信度**：事实、解析、估算或实测；
5. **风险**：未验证项、边界条件和潜在回归；
6. **动作**：查看、修改、生成测试、运行验证或建立实验；
7. **验收条件**：怎样证明当前任务真正完成。

示例：

> **结论**：`post_rmsnorm` 不需要输入 Cast。  
> **证据**：`resid` 来自 FP32 residual stream，源码直接参与平方和归一化。  
> **影响**：若复用 `input_rmsnorm` 的 BF16→FP32 路径，会产生冗余转换。  
> **可信度**：源码事实 + 跨文件解析。  
> **下一步**：通过 Pass 后 IR 确认没有被重新插入冗余 Cast，并使用设备 Profiling 验证。

---

## 8. Agent 之间的协作边界

Agent 的切换应由任务和证据状态驱动，而不是要求用户理解产品内部角色。

- Coding Agent 负责把意图表达清楚，并建立可编译、可测试的实现；
- Guard Agent 负责证明编译变换和硬件约束成立；
- 调试 Agent 负责从异常现象找到首个异常证据；
- 正确性 Agent 负责证明数值结果达到目标；
- 性能 Agent 只在正确性和资源门禁成立后进行性能优化；
- 集成与服务 Agent 负责验证单算子结论能否在模型和服务中兑现。

同一任务可以由多个 Agent 协作，但面向开发者应保持一个统一上下文、一个结论入口和一条连续证据链。

## 9. 后续演进建议

### 阶段 1：静态 Coding Agent

- 完成源码、调用点、测试和文档索引；
- 提取算子契约、精度流、分块和静态风险；
- 建立源码与硬件对象的语义映射；
- 支持生成局部实现和测试草案。

### 阶段 2：编译证据接入

- 接入逐 Pass IR；
- 将静态硬件映射替换或补充为真实 Lowering 结果；
- 展示实际 Buffer、地址、依赖和指令；
- 支持源码—IR—硬件节点双向定位。

### 阶段 3：运行与验证闭环

- 接入多 Oracle、Tensor checkpoint 和设备日志；
- 自动定位首个数值分歧；
- 形成从编码建议到正确性验收的闭环。

### 阶段 4：性能实验闭环

- 接入 PMU、trace 和 benchmark；
- 对 Chunk、Tile、stage、layout 和 fusion 建立可控搜索空间；
- 对候选方案执行正确性、资源和性能联合验收；
- 沉淀可复用的调优配方和回归基线。

## 10. 原型验收标准

Coding Agent 原型达到以下条件时，可以认为完成了第一阶段验证：

1. 打开算子源码后，Agent 能自动建立当前文件上下文；
2. 右侧能够展示算子契约、精度、分块、验证和硬件数据流；
3. 多函数或多变体可以快速切换并对比；
4. 源码行与结构化分析、硬件路径可以双向联动；
5. 静态事实、跨文件解析、估算和实测有清晰区分；
6. Agent 建议能够落到查看源码、修改代码、生成测试或运行验证等具体动作；
7. Agent 不依赖流程向导，开发者可以自由浏览源码和分析结果；
8. 所有“正确”“更快”“真实占用”等强结论都有直接证据支持。
