# Hardware-Native 真实问题：筛选判据与重新梳理

> 日期：2026-11-04

> 用途：从既有案例集中剔除"框架演进期 bug"，重新梳理真正由 Hardware-Native 设计不足导致的用户问题

## 一、为什么必须重筛

前一轮的四个案例中，**有两个的根因是框架缺陷，不是 Hardware-Native 设计问题**：

- **#626**（Right buffer 校验算法）：`AllocatedMemoryAddrVerifier` 用 `high_water = max(addr + size)` 不考虑生命周期，误拒合法 kernel。这是一个算错了的校验器。
- **#2287**（跨核 FIFO 过量预留）：`GetCommonSlotSizeBytes` 取双向最大值、PyPTO 从不发出 `local_slot_num`，导致 8 倍过量预留。这是 codegen 的两处实现错误。

这两条支撑了前一轮的两条核心洞察（"信息不缺缺归因"、"同报错不同责任"）。**剔除它们之后，那两条洞察失去了主要依据，必须重新推导，而不是删掉表格里两行。**

更根本的问题是：拿框架 bug 论证"Hardware-Native 是体验设计方向"，在评审中会被正确地驳回——因为这些问题的答案是"修 bug"，不是"改设计"。用它们立论，等于把 UX 的工作建立在工程缺陷之上；bug 修完，论点就消失了。

## 二、筛选判据

### 2.1 主判据：反事实检验

> **假设框架完全按它自己的设计意图工作，没有任何实现错误——这个用户问题还在吗？**
>
> - **不在** → 演进期缺陷。剔除。
> - **还在** → Hardware-Native 问题。保留。

这条判据把"实现没达到设计"和"设计本身的取舍"分开。后者才是设计团队的工作对象。

### 2.2 三条辅助判据

**一、修复方式。** 修复是"改代码让它符合既定意图"，还是"改接口、改抽象层级、改契约表达"？前者是工程任务，后者是设计任务。

**二、Issue 标签。** 社区自己的分类是强信号。`[Bug]` / `[Pass Bug]` 是提报人认定的实现缺陷；`[Discussion]` / `[New Op]` / `[Feature]`（指能力与接口类）是设计议题。

**三、提报人在问什么。** "这是不是坏了"是缺陷报告；"为什么这样设计""能不能提供这样的接口"是设计讨论。#630 的提报人问的是"PTO 3.0 取消 tile shape 设置的设计初衷是什么"——这不是 bug 报告。

### 2.3 一条重要的例外

一个 Issue 可以**同时**包含 bug 和设计问题，必须拆开看。

#2287 的主体是 bug，但其中一句是真正的 Hardware-Native 问题：

> `local_slot_num` 已存在于 IR op（`system_ops.py:412-426` 同时接受 `slot_num` 和 `local_slot_num`），但 DSL 旋钮 `pl.cross_core_slot(*, slot_num: int)` 只暴露了 `slot_num`，用户也没法自己设。

即便预留算法完全正确，这个控制缺口依然存在。因此：**bug 叙事剔除，这一句作为设计面证据保留**（见第五节）。

## 三、剔除结果

### 3.1 原四案例逐条裁定

| 案例 | 根因 | 反事实检验 | 裁定 |
|---|---|---|---|
| **#630 / #628** 抽象退化 | PTO 3.0 不提供 tile shape 接口 | 框架完美工作，问题照在——这就是设计 | **保留** |
| **#1935** hard syncall 满占用 | FFTS 要求该核型全部物理核到达 | 硬件语义，框架如实实现；契约不在 API 表面 | **保留（需重构叙事）** |
| **#2287** FIFO 过量预留 | codegen 取双向最大、不发 `local_slot_num` | 修复后问题消失 | **剔除**（保留控制缺口一句） |
| **#626** 容量校验算错 | 校验器高水位算法不考虑生命周期 | 修复后问题消失 | **剔除** |

**#1935 需要重构叙事。** 前一轮把它讲成"缺少编译期检查"——那是一个可以补的缺陷。真正的 Hardware-Native 问题在另一面：`pl.system.syncall(core_type="aiv_only")` 这个签名**没有任何地方表达"要求满占用"**。两种模式有完全不同的硬件前提，却共用一个接口形态，差异写在测试文件的 docstring 里。补一个检查能堵住这个洞；把契约放进 API 表面才是设计解法。

### 3.2 归档样本的量化

对 `github_issues/pto/pypto_issues.json`（632 条）按标题标签统计：

| 标签 | 条数 | 占比 |
|---|---:|---:|
| `[Bug]` / `[Pass Bug]` | **288** | **45.6%** |
| `[Discussion]` / `[New Op]` / `[RFC]` / `[Proposal]` / `[Design]` | 47 | 7.4% |

**pypto 仓近一半的 Issue 是提报人自己标注的实现缺陷。** 这是一个处于快速演进期的框架的正常形态，但它意味着：任何基于全量 Issue 的关键词分类，都会把大量框架 bug 计入"Hardware-Native 问题"。

另一个发现：扫描 `[Feature]` 类目后，pypto 的 Feature 大多是框架内部工程（IR 管线、类型检查、重构、SSA 验证器），不是用户的硬件使用问题；pypto-lib 的 Feature 基本是模型 bring-up 跟踪任务；pto-isa 的是指令新增。**真正的 Hardware-Native 设计议题高度集中在 pypto 仓的 `[Discussion]` 与 `[New Op]`，总量很小。**

### 3.3 对旧 1463 条口径的影响

既有研究（`Insight/Hardware-Native失效类型_基于1463条Issue_20261019.md`）用标题与正文关键词归类，得出 31.0% 等比例。研究报告已声明不复用该比例作为已验证的缺陷率。本轮进一步给出不能复用的具体理由：

**关键词分类无法区分"框架没实现对"和"设计不该这么设计"。** 一条写着 `Right buffer usage exceeds platform limit` 的 Issue，既可能是 #630（设计），也可能是 #626（bug）——两者报错文本几乎相同。按关键词，它们会被归入同一类。

因此，**Hardware-Native 问题的规模目前无法从归档样本估计。** 可靠的做法是定性检索设计级标签（47 条量级），再逐条做反事实检验。这个数量不足以支撑发生率主张，但足以支撑类型归纳。

## 四、重新梳理：四类 Hardware-Native 失效

剔除 bug 之后重新检索，得到四个案例。它们各自对应一种**不同的失效机制**，且全部通过反事实检验。

### 类型一｜抽象层级错配：框架该管的，推给了用户

**案例：pypto #628 + #630**（`[Discussion]`，2026-03-19，提报人同一人，#630 仍 open）

**设计事实。** PTO 2.0 提供 tile shape 声明接口，框架自动生成切分与循环。PTO 3.0 取消了这个接口。#628 的原文把两种风格并排：

```python
# PTO 2.0 风格（理想）
tile_matmul(lhs, rhs, tile_shape=[128, 512, 128])
tile_rmsnorm(x, gamma, tile_shape=[16, 7168])   # h=7168 自动切分

# PTO 3.0 风格（当前）
for m0 in range(0, M, M_CHUNK):
    for k0 in range(0, K, K_CHUNK):
        lhs_tile = pl.slice(lhs, [M_CHUNK, K_CHUNK], [m0, k0])
        # ... 手动处理每个 chunk

for h0 in range(0, H, H_CHUNK):
    x_chunk = pl.slice(x, [BATCH, H_CHUNK], [b, h0])
    # ... 还需要处理跨 chunk 的 reduce 操作
```

**用户代价**（#628 原文列举）：

1. MatMul 切分：开发者不得不自己考虑如何切分 m、n、k
2. RMSNorm 内层循环：`[b, s, h]` 且 h 很大时需手写内层循环，并处理跨 chunk reduce
3. **UB 溢出处理：为了避免 tile 溢出 UB，开发者有时需要自己调整代码结构，增加 loop 层级**

第 3 条是最关键的一句——**片上容量约束直接变成了用户代码的结构。** 模型配置一变（#630 中 `kv_lora_rank` 从 128 到 512），代码结构就得跟着改。

**为什么不是 bug。** #628 的提报人自己列出了 PTO 3.0 的设计优势："更灵活的控制粒度、更好的可预测性、便于优化特定场景"，然后问"取消 tile shape 设置的设计初衷是什么？是否考虑过上述易用性问题？"这是一次设计权衡的讨论，没有人实现错了任何东西。

**提报人想要的解法**——注意它是**减少**暴露：

```python
@pl.tile_policy(shape=[128, 512, 128])
def my_matmul(lhs, rhs):
    # 框架根据 policy 自动生成循环结构
```

并提出三个方向：提供高层声明式抽象 / 静态分析自动推导最优切分 / 支持混合模式让开发者按场景选择。

**对工具的要求。** 这类问题的设计对象不是"把容量显示得更好"，而是"这个决定应该由谁作出"。工具能做的是：当模型配置变化传导到片上容量约束时，让这条链路可见，并且**把能自动的部分还给框架**。

### 类型二｜表达能力缺失：用户只能写出硬件不友好的代码

**案例：pypto #536 `[New Op] Batch Matmul`**

**设计事实。** PyPTO 不支持 BatchMatmul。DeepSeek V3 MLA 的 sparse attention 阶段需要对每个 head 做 latent→value 投影，权重是三维的：

```
w_latent_to_v: [NUM_HEADS, KV_LORA_RANK, V_HEAD_DIM] = [128, 512, 128]
```

理想写法是一次批量矩阵乘：`ctx_latent[1, 512] @ w_latent_to_v[128, 512, 128] → [128, 128]`。

**用户实际被迫写的**（原文）：

```python
for h in pl.parallel(0, NUM_HEADS_CFG, 1, chunk=8):
    # 期望：从 w_latent_to_v[h] 提取 [512, 128] 的权重矩阵
    wv_tile = pl.slice(w_latent_to_v, [512, 64], [h, 0, v0])  # shape 2D, offset 3D
    v_part = pl.matmul(pl.cast(ctx_latent, target_type=pl.BF16), wv_tile, out_dtype=pl.FP32)
```

逐 head 循环，并从三维 tensor 里 slice 出二维权重。`shape` 参数是 2 维、`offset` 参数是 3 维——**语义本身不清晰**，同样的写法还出现在该文件第 299、407 行。

**用户代价。** 这不是"看不懂硬件"，而是**写出的代码在硬件上本身就更差**：一次可以批量下发的矩阵乘被拆成 128 次循环迭代。同时用户被迫依赖一个维度不自洽的 API 语义，正确性风险转移到了用户身上。

**为什么不是 bug。** 没有 BatchMatmul 是能力边界，不是实现错误。`pl.slice` 的维度语义不清是接口设计问题，提报人给出了三个方案（改 shape 为 3D / 引入降维 slice 语义 / 支持 BatchMatmul 从根本消除变通）——都是设计选择。

**对工具的要求。** 当用户的计算意图在当前抽象里无法直接表达时，工具至少应让这件事**可见**：这段代码是变通写法、它相对理想表达多付了什么执行成本、有没有已登记的能力缺口。目前用户只能自己发现、自己绕、自己承担后果。

### 类型三｜硬件契约不在 API 表面

**案例：pypto #1935**（已关闭。本轮重构叙事：剔除"缺编译期检查"这一面，保留契约表达这一面）

**设计事实。** `syncall` 有两种模式，硬件前提完全不同：

| 模式 | 机制 | 硬件前提 |
|---|---|---|
| `hard` | FFTS 硬屏障 | **要求该 `core_type` 的全部物理核都到达** |
| `soft` | 共享 GM workspace 轮询 | 支持部分占用，需 `gm_workspace`、`used_cores` |

用户写下的是：

```python
pl.system.syncall(core_type="aiv_only")      # 默认 hard
with pl.spmd(24):                             # 910B 有 48 个物理 AIV
```

`pl.spmd(24)` 与"要求 48 个核全到"之间的冲突，**在接口形态上完全不可见**。两种模式共用一个函数名和近似的参数表，而其中一种带着一条隐含的全局前提。

**用户代价。** AICore 507018 超时、设备被强制 reset、后续任务报 `code 13` 直到恢复。共享开发设备，影响不止一个人。

这条契约当时已经写在 `tests/st/runtime/cross_core/test_syncall.py` 的 docstring 里——**知识存在，但不在用户写代码时会看到的地方。**

**为什么保留、以及和 bug 的界线。** "编译器应该加一个静态检查"是一个可修的缺陷，修完这个具体错误就不会再发生——那一面按判据应当剔除。但"一个接口承载两套硬件前提、前提不在签名里"是设计问题：即便加了检查，用户依然要在**写代码时**决定用哪个模式，而决定所需的信息仍然不在手边。检查把失败从运行期移到编译期，契约表达才让用户一开始就选对。

**对工具的要求。** 硬件契约应当进入类型、签名或编辑期反馈，而不是文档与测试文件。这是 API 设计与编辑器集成问题，不是诊断文案问题。

### 类型四｜映射断裂：去硬件化的命名切断了对照路径

**案例：pypto #268 `[Feature] Rename MemorySpace enum values to hardware-agnostic names`**

这是本轮新发现的案例，也是最能说明"Hardware-Native 是设计张力而非对错"的一条。

**设计事实。** 框架**主动**把 `MemorySpace` 的枚举值从昇腾硬件名改成了去硬件化的逻辑名：

| 旧名 | 新名 | 含义 |
|---|---|---|
| `L1` | `Mat` | Matrix / L1 buffer |
| `UB` | `Vec` | Unified Buffer / 向量操作数暂存 |
| `L0A` | `Left` | 左矩阵操作数 |
| `L0B` | `Right` | 右矩阵操作数 |
| `L0C` | `Acc` | 累加器 |

**原文给出的理由**，三条都成立：

1. **更可移植**——抽象可以映射到昇腾以外的硬件目标
2. **更可读**——名字反映逻辑角色，而不是硬件内部标签
3. **更可维护**——在 pass 和文档里推理时不必了解昇腾内部

原文明确把现状称为"将低层微架构细节泄漏进 IR 抽象层"（*leak low-level microarchitecture details into the IR abstraction layer*），并且**考虑过保留硬件名作为别名、但主动否决了**，理由是增加维护负担和混淆。

**用户代价。** 一个开发者拿到这条报错：

```
Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)
```

他要弄清"65,536 是什么"，需要知道 `Right` = L0B = Ascend910B 上 64 KiB 的矩阵右操作数缓冲。**但这条映射不在任何用户可见的地方：** 报错说 `Right`，昇腾官方文档说 `L0B`，框架刚好把两者之间的那条线索删掉了。

**为什么这是 Hardware-Native 问题的典型形态。** 没有人做错任何事。去硬件化命名是正确的架构决策，可移植性和可读性都是真实收益。但它有一个没有被定价的代价：**用户失去了把工具的词汇对回硬件事实的路径。** 当抽象泄漏被消除时，查证路径也被一起消除了。

这正好说明 Hardware-Native 不是"暴露多少硬件"的刻度问题。#268（隐藏硬件名）和 #630（隐藏切分决定）方向相反，都有正当理由，却都产生了用户代价。**真正的问题是：抽象在哪里收口，以及收口之后用什么补偿查证能力。**

**一个值得注意的时序。** #268 的重命名创建于 2026-02-26，#628 与 #630 撞上 `Right buffer usage ... exceeds platform limit` 是在三周后的 2026-03-19。也就是说，**开发者遇到那条报错时，能把 `Right` 对回昇腾文档的那个线索刚被移除不久。** 这不构成因果证明（两者由不同的人提报，重命名也不是报错的原因），但它说明抽象决策与用户查证成本之间的距离可以很短。

**对工具的要求。** 去硬件化的抽象需要配一层**可按需展开的映射**：`Right` 能一跳查到"L0B / Ascend910B / 64 KiB / 来自后端参数表 `GetL0bCapacityBytes()`"。抽象让日常工作更干净，映射让排查时能落回硬件。两者不冲突，但必须被设计——它不会自动存在。

## 五、不依赖 Issue 的固有设计面

比 Issue 更可靠的一类证据：这些是框架当前设计的**稳定属性**，不是某个版本的缺陷，因此不会被"修好了"而失效。

| 设计面 | 事实 | 用户需要知道却不易知道的 |
|---|---|---|
| **强制两跳** | `tile.load` 不能直接把数据放进 `Left`/`Right`/`Acc`，必须 `DDR → Vec/Mat → Left/Right/Acc` | 中间那一跳由编译器自动插入 `tile.move`，占用不出现在用户代码里 |
| **零拷贝视图的例外** | `tile.slice`/`reshape`/`transpose_view` 通常只改元数据，但硬件指令消费不了该视图时，`CanonicalizeTileSlice` 会转成 `tile.extract`，**产生真实搬运** | 源码里看起来免费的一行，编译后可能不是 |
| **非阻断的性能提示** | 最内维字节数低于阈值（910B 512 B / 950 128 B）时产生 `PH001` 提示 | 提示不阻断编译，很容易被忽略 |
| **目标相关的跨核开销** | 910B 的 AIC/AIV `tpush/tpop` 经 GM 中转，需 `__gm_pipe_buffer`；950 直连不需要 | 同一份代码在两代硬件上的片上预算不同 |
| **专家控制缺口** | `local_slot_num` 在 IR op 中存在，DSL `pl.cross_core_slot` 只暴露 `slot_num` | 用户无法表达非对称载荷下的正确配置（#2287 的非 bug 残留） |

这五条都通过反事实检验：框架完美按设计工作时，它们依然成立。**建议在后续材料中优先使用这类证据**——它们不依赖某个 Issue 的开闭状态，也不会被"已修复"反驳。

## 六、新的洞察主线

替代前一轮的三条（那三条中两条建立在 bug 上）。

### 洞察一：Hardware-Native 做得不好，主要表现为抽象层级定错，不是硬件信息没展示好

四个案例的解法分别是：恢复一个声明式接口（#630）、增加一个算子（#536）、把契约放进签名（#1935）、补一层名称映射（#268）。**没有一个的答案是"加一个硬件可视化面板"。**

这重新定位了整个方向：它是接口与抽象的设计问题，而接口设计正是 UX 与框架共同的工作面。

### 洞察二：用户的真实代价不是"看不懂硬件"，而是"被迫用硬件不友好的方式写代码"

- #536：一次批量矩阵乘被拆成 128 次循环
- #628：为避免 tile 溢出 UB，开发者调整代码结构、增加 loop 层级
- #630：模型配置一变，代码结构跟着改

**片上容量约束变成了用户代码的结构。** 这比"信息理解困难"严重得多——它直接降低了产出代码的质量和可维护性。

### 洞察三：隐藏硬件与可查证性是一对需要被设计的矛盾

#268 隐藏硬件名、#630 隐藏切分决定，方向相反、理由都正当、都产生了用户代价。所以不存在"该暴露多少硬件"的最优刻度。真正要设计的是两件事：**抽象在哪里收口，以及收口之后用什么补偿查证能力。**

### 洞察四：框架演进会反复调整同一个层级的收口位置

PTO 2.0 有 tile shape、3.0 取消；`L0A/UB` 改成 `Left/Vec`。每次调整都有正当理由，但累积起来，用户需要反复重新学习"哪些事现在归我管"。

**这给工具提出一个少见但重要的要求：抽象边界的变化本身需要被表达。** 用户需要知道"这件事在当前版本由谁负责"，而这个答案是会变的。

### A.2 判据应用上的两处判断

**#1935 的归类是本文最可争议的一处。** 它带 `[Bug]` 标签，提报人要求的是编译期检查。本文认为其中包含一个独立于检查的设计问题（契约不在签名），因此保留并重构叙事。**若评审认为应按标签一并剔除，则真正的非 bug 案例只剩三个**，类型三需要另找证据。

**#268 带 `[Feature]` 标签但被归为设计案例。** 理由是它是一次已执行的架构决策，不是能力请求；其用户代价（映射断裂）是决策的后果，不是实现缺陷。

### A.3 不能支持的结论

- **不能推断规模。** 设计级标签共 47 条，本文只做了定性检索与类型归纳，未穷举。Hardware-Native 问题的发生率目前无法从归档样本估计（第 3.3 节给出理由）。
- **不能推断当前状态。** 仅 #630 仍 open。#268 已关闭即意味着重命名**已执行**——映射断裂是当前状态，不是历史问题。
- **不能把本文的设计要求当作已验证收益。** 四类失效与四条洞察均为分析结论，需要按研究报告第七节的计划验证。
- **剔除 bug 不等于否认其存在。** pypto 仓 45.6% 的 Issue 是实现缺陷，这是真实的用户成本，只是它的责任方与解法不在体验设计。
