## 1. 产品结论

推理产品的核心矛盾，已经从“有没有一个推理引擎”转变为：**如何让模型在昇腾 NPU 上从适配、部署、上线验证，到运行、优化、诊断和迭代，形成一条可观测、可比较、可回归的工程闭环。**

访谈中反复出现的四个断点决定了产品形态：

1. **方案到适配**：缺少可靠的昇腾算子 / shape / CANN 版本能力查询和收益预估。
2. **验证到上线**：精度、性能、故障用例分散，缺少统一准入基线。
3. **监控到诊断**：线上 P99 指标与 profile、代码、算子之间无法自然关联。
4. **变更到回归**：跨版本、跨配置、跨卡的差异难以自动解释，全靠专家经验。

因此，PyPTO Studio 不做“又一个推理引擎”，也不做“又一块静态监控大盘”，而是做一个 **以统一任务 / 实验为中心，串联准入测试、运行监控、性能 profile、精度对齐、版本变更和故障闭环的推理工程诊断工作台**。它的差异化价值集中在业界工具在昇腾场景下尚未系统化解决的四件事：**规范化、对齐、Diff、异常归因**。

### 1.1 一句话定位

> **PyPTO Studio 是面向昇腾 NPU 大模型推理的“比较优先、证据贯通、专家在环”的诊断与准入工作台。**
> 它不替代 MindIE / vLLM-Ascend / SGLang 等昇腾推理引擎，也不替代 msprof / MindStudio Insight / Perfetto 等采集工具，而是把它们产生的指标、trace、日志、精度和版本数据，统一成可比较、可归因、可回归的工程证据。

### 1.2 核心价值主张

| 用户问题 | PyPTO Studio 的承诺 |
|---|---|
| “这次 CANN / 引擎 / 权重变更，性能和精度到底改善还是回退了？” | 一屏给出相对基线的多维 Diff：TTFT / TPOT / 吞吐 / 显存 / 精度 / 热点算子 / 回退项 |
| “多卡里到底哪张卡拖慢了整体？” | 自动多 rank 对齐，识别慢卡、负载不均、HCCL 通信等待和首个偏离 rank |
| “线上 evaluation 掉分，问题从哪一层开始？” | 以同一 token / 样本为锚点定位首个偏差点，区分正常浮点误差与异常放大 |
| “Python 报了个 tuning 错误，到底是谁的问题？” | 聚合 Python / 框架 / CANN / 算子 / plog / HCCL 日志成一条因果链，直接给出参数 / shape / 版本根因 |
| “这个调用当前 CANN 版本到底支不支持？” | 运行前昇腾兼容性预检，明确不支持项及可选替代方案 |
| “RL 训推一致性卡在 92%，差异在哪？” | 训练侧与推理侧双链路对齐，定界到模型模块、框架接口或昇腾算子 |
| “能不能不让这次回退发上线？” | 精度 / 性能 / 稳定性 / 故障注入统一为可配置准入门禁，保留可复现证据 |

### 1.3 在 PyPTO 产品家族中的位置

PyPTO Studio 与 [PyPTO 3.0 Toolkit](PyPTO3.0_Toolkit_产品功能规划.md) 同属 PyPTO 家族，互补而不重叠：

- **PyPTO 3.0 Toolkit** 面向昇腾模型 — 算子开发者，解决“如何安全表达意图、可信编译、把 kernel 和模型正确高性能地做出来并构建服务”，是**开发与构建侧**的一体化控制面。
- **PyPTO Studio** 面向推理交付与运营链路，跨推理引擎、跨 CANN / 算子 / 权重版本、跨卡，解决“如何观测、比较、诊断、归因和准入”，是**运行与诊断侧**的工程工作台。

集成点：PyPTO 的 Inference Bundle、算子实现版本、编译产物指纹、serving profile 可以直接作为 PyPTO Studio 的“实验对象”与“版本锚点”；PyPTO Studio 在诊断中定界到昇腾算子层时，可将标准证据包回流给 PyPTO 的 Compile Guardian / Correctness Lab。两者共享 Run ID 与 artifact schema，避免“开发侧和运营侧结论不一致”。二者的 CLI 统一在 `pypto` 下：Toolkit 用 `pypto doctor / explain / diff …` 面向开发，Studio 用 `pypto studio …` 面向运营诊断。

### 1.4 产品边界

- **做**：跨引擎 / CANN / 算子 / 权重版本 / 卡的推理实验管理与 Diff、多 rank 对齐、精度回归定位、服务指标到代码 / 算子的下钻、错误与日志归因、昇腾算子能力知识库、准入流水线、RL 训推一致性诊断、证据化 AI 诊断。
- **不做**：不重复实现推理引擎的调度 / batching / KV 管理；不做生产集群的租户计费、自动扩缩容和 7×24 告警值守；不替代已有采集工具（msprof / msprof-analyze / MindStudio Insight / Perfetto），而是消费和增强它们的产物。

## 2. 业界能力参考与差距

产品设计必须建立在“用户已经有什么”之上——访谈明确指出**性能数据不缺，缺的是自动对比与归因**。下表梳理昇腾场景下主流工具能力与其留下的空白；GPU 侧工具仅作成熟实践参考。

### 2.1 推理引擎与服务框架（昇腾侧）

| 类别 | 代表产品 | 已提供的能力 | 留给 PyPTO Studio 的空白 |
|---|---|---|---|
| 昇腾推理引擎 | MindIE（MindIE LLM / Service）、vLLM-Ascend、SGLang（Ascend backend） | PagedAttention / 连续批处理 / chunked prefill / prefix cache、Prometheus 指标端点、`bench serve` 类压测 | 单引擎自测，不做跨引擎 / 跨 CANN / 跨卡的统一 Diff 和异常归因 |
| 分离式服务 | PD 分离部署、KV cache 分层 / 迁移 | PD 分离、KV-aware 路由 | 缺少把 PD 分离下的等待、KV 迁移、路由决策映射回请求级根因的诊断视图 |
| GPU 侧参考 | vLLM、SGLang、TensorRT-LLM、NVIDIA Dynamo | 成熟的连续批处理、投机解码、KV-aware 路由与自动化压测实践 | 作为工程实践与指标口径的参考基线，不作为部署目标 |

### 2.2 性能采集与 trace 分析

| 代表产品 | 已提供的能力 | 留给 PyPTO Studio 的空白 |
|---|---|---|
| Ascend msprof / msprof-analyze | NPU 采集、算子级 profile、部分对比脚本 | 与 Python 报错、plog、CANN / HCCL 日志的因果串联不足；跨版本 Diff 不成体系 |
| MindStudio Insight | NPU trace / timeline 可视化 | 单次采集为主，跨实验对比、多卡自动对齐依赖人工 |
| Perfetto / Chrome trace | 通用 trace 可视化 | 一次只能打开一个 profile；GB 级 trace 打不开需手工切分；靠 hover 人工比对 |
| PyTorch Profiler + Holistic Trace Analysis（GPU 参考） | 多 rank trace、idle time、通信分析方法论 | 面向训练与 GPU，缺少昇腾推理请求级（prefill/decode、KV、batch）语义 |

### 2.3 应用级可观测与评测

| 代表产品 | 已提供的能力 | 留给 PyPTO Studio 的空白 |
|---|---|---|
| Langfuse、Arize Phoenix、Helicone、Datadog LLM Observability | 请求 / span 级 tracing、token、成本、质量评估；OpenTelemetry GenAI 语义规范 | 停在应用层，不穿透到 kernel / HCCL / 算子 / 昇腾硬件 |
| lm-evaluation-harness、OpenCompass、HELM | 标准化精度 / 能力评测 | 只给最终分数，不做“首个偏差点”定位，不与版本变更、张量、算子实现关联 |
| MLPerf Inference | 标准化性能基准 | 面向横向对标，不面向单团队的持续回归与准入门禁 |

### 2.4 RL 训推链路

| 代表产品 | 已提供的能力 | 留给 PyPTO Studio 的空白 |
|---|---|---|
| verl (HybridFlow)、OpenRLHF、NeMo-Aligner、TRL | 训推分离 / 混合、以 vLLM(-Ascend)/SGLang 做 rollout、权重同步、训推 mismatch 的重要性采样修正 | 最多定界到训练 / 推理框架边界，缺少向昇腾算子和精度体系穿透的一致性诊断；缺少一致性 / KL / reward / logprob 与推理性能的联合看板 |

**结论**：业界在“采集”和“单点展示”上已经很成熟，PyPTO Studio 的护城河必须落在昇腾场景下的 **跨维度对齐、Diff、首个偏差 / 首个异常定位、多源日志因果归因（含 plog / CANN / HCCL）、以及把系统级证据与业务指标打通** 上。

## 4. 产品设计原则

沿用访谈的六条设计原则，并落到本产品的具体约束：

1. **证据优先**：任何 AI 或自动诊断结论，必须能跳回原始 trace、日志、指标、代码或版本变更；杜绝不可核验的“一次性报告”。
2. **比较优先**：所有性能和精度结果默认支持基线比较，而不是孤立展示绝对值；单实验视图是 Diff 视图的降级形态。
3. **场景可配置**：在线低时延、离线高吞吐、RL 边训边推、PD 分离等场景的指标权重和门槛均可调整；拒绝固定综合健康分。
4. **分层但不割裂**：允许从服务层逐级下钻到算子 / HCCL / 昇腾硬件，同时支持把标准证据包移交给框架、算子或硬件团队。
5. **专家在环**：自动分析用于“缩小范围 + 给出验证实验”，最终判断保留人工复核与交互追问；结论区分事实、推断、建议。
6. **对 Agent 友好**：昇腾算子能力、错误码、接口、实验数据结构化、可检索、可被 IDE / CI / Agent 直接调用。

## 5. 总体架构

### 5.1 一个底座、一个中心对象、七个能力中心

**底座：Inference Evidence Graph（推理证据图）**

为每次实验 / 任务生成统一 Run ID，维护以下对象的稳定关联，这是区别于“工具集合”的核心数据能力：

```text
业务请求 / 样本 → 请求阶段(admission / queue / prefill / decode / streaming)
   → 模型模块(attention / MoE / norm / lm_head)
   → 算子 / 通信(Ascend kernel / HCCL collective)
   → rank / 卡 / 昇腾硬件
   → KV / 显存 / tensor
   → 版本锚点(模型 / 引擎 / CANN / driver / 算子包 / 量化 / 硬件 / 随机性配置)
   → 指标 / oracle 结果 / 日志事件(plog / CANN / HCCL)
```

错值定位、性能归因、实验对比、精度回归、故障复现和 AI 辅助都建立在这张图上。

**中心对象：统一“推理实验”（Inference Experiment）**

一次准入测试、一段线上采样、一次性能 profile、一次精度评测、一次 RL rollout，都是同一种“实验”对象，携带完整版本锚点和证据链。**任意两个实验可比较**，任意一个异常都可下钻。这直接回应访谈结论——“以统一任务 / 实验为中心”。

**七个能力中心**

1. Experiment & Diff Hub：实验管理与跨维度 Diff（P0 核心）；
2. Multi-Rank Aligner：多卡 / 多 rank 自动对齐；
3. Accuracy Lab：精度回归与首个偏差定位；
4. Service Observatory：服务监控 → 诊断 → 决策闭环；
5. Trace Navigator：大 trace 智能切片与证据导航；
6. Diagnosis & Knowledge：错误 / 日志归因 + 昇腾算子能力知识库；
7. Admission Pipeline：准入流水线与门禁；
   （RL 训推一致性作为贯穿 3 / 4 / 6 的横切场景，见 §6.8。）

### 5.2 统一实验 Manifest

每次实验生成版本化 Manifest，至少包含：

- 版本锚点：模型 / 权重 / tokenizer、推理引擎（MindIE / vLLM-Ascend / …）commit、CANN / driver / runtime、算子包、量化参数、昇腾硬件型号、并行策略（TP/DP/EP/PP/CP、PD 分离）、随机性 / 确定性配置；
- 负载定义：请求到达分布、prompt / 输出长度、并发、数据集、采样参数；
- 服务指标：TTFT、TPOT、TPS、RPM/TPM、SLA 成功率、错误码、排队时间、prefill/decode 耗时、batch 利用率、KV Cache 命中 / 占用；
- 系统证据：trace 切片索引、rank 对齐结果、热点算子 / HCCL 通信、显存水位；
- 精度证据：oracle、逐层 / 逐 token 摘要、首个偏差点、阈值配置；
- 日志证据：Python / 框架 / CANN / 算子 / plog / HCCL / 系统日志的归并因果链；
- 门禁结果：精度 / 性能 / 稳定性 / 故障注入各门禁的通过与回退项；
- 采集元数据：采集等级、估算开销、脱敏状态、复现命令。

## 6. 功能规划

优先级遵循访谈的 P0 → P1 → P2：**先解决“比较与定界”，再形成端到端诊断闭环，最后覆盖高价值 RL 场景。**

### 6.1 Experiment & Diff Hub：推理实验 / 版本 Diff（P0 核心）

**目标**：把用户当前“分别抓 trace、肉眼叠图、手工 hover 记录”的比较过程，变成一屏自动 Diff。（回应洞察 3）

核心功能：

- **多维实验 Diff**：对比模型版本、推理引擎版本、CANN / 算子包、量化方案（FP8 vs BF16）、并行策略与硬件配置；统一输出 TTFT / TPOT / 吞吐 / 显存 / 精度 / 热点算子 / 回退项的变化。
- **双实验 / 多实验一屏对比**：耗时、调用次数、空泡、HCCL 通信重叠、显存、吞吐和时延变化并排展示，支持相对差和百分比，标注置信区间与测量噪声。
- **可比性保护**：锁定模型 / 数据 / 采样 / warmup / 硬件条件，条件不一致时显式告警，避免“苹果比橘子”的误判。
- **自动变更报告**：相对基线哪些指标改善、哪些回退、是否达到上线门槛、建议复测项——直接产出可评审的结论，而非一堆数字。
- **热点算子 Diff**：对齐两个实验的算子表，标注新增 / 消失 / 变慢的昇腾算子及占比变化。

建议命令：

```bash
pypto studio diff <baseline-run> <candidate-run>
pypto studio diff <baseline-run> <candidate-run> --focus accuracy,ttft,kernel
```

### 6.2 Multi-Rank Aligner：多卡 / 多 rank 自动对齐

**目标**：替代“把多卡数据叠在一起肉眼比对”。（回应洞察 3）

核心功能：

- 自动对齐多 rank profile，识别慢卡、负载不均、异常等待和**首个偏离 rank**；
- 通信视图：HCCL AllReduce / AllGather / P2P 等 collective 的配对、等待和 overlap 分析；空泡（bubble）与首个阻塞点定位；
- 支持 TP / DP / EP / PP / CP 与 PD 分离场景的依赖与空泡视图；
- 输出“哪张卡、哪个 step、哪个 collective 造成了整体等待”的结论，而不是要求用户自己在多张 timeline 间来回切换。

### 6.3 Accuracy Lab：精度回归与首个偏差定位

**目标**：把“线上 evaluation 掉分 / 输出不对”变成可定位的首次数值分歧。访谈明确——**精度问题比性能问题更容易阻塞发版**。（回应洞察 2）

核心功能：

- **以同一输入 token / 样本为锚点**，对比基线与候选版本的输出、logit / logprob、层级张量和算子结果；基线 oracle 可以是 CPU/GPU golden torch、库实现或上一可信版本；
- **首个偏差点定位**：不只展示最终误差，而是找到误差第一次异常放大的层 / 算子 / step；自动区分正常浮点误差与异常放大（按 dtype / op 配置 atol/rtol/ULP、NaN/Inf、分布漂移）；
- **变更关联**：把精度回归与最近的模型 / 算子 / 引擎 / CANN / 量化 / 硬件版本变更自动关联；
- **量化专项**：针对量化算子、并行策略、KV Cache 管理变化导致的掉分，即使单点算子正确性测试通过，也能在端到端评测层捕获；
- **非确定性处理**：对采样场景用分布和统计一致性指标，避免把随机性误判为错误。

### 6.4 Service Observatory：服务监控 → 诊断 → 决策闭环

**目标**：监控大盘只有与诊断和决策联动才有价值。（回应洞察 1、洞察 7）

核心功能：

- **推理专属指标内置**：TTFT、TPOT、吞吐、成功率、排队时间、prefill/decode 耗时、batch 利用率、KV Cache 命中 / 占用，并覆盖引擎指标、NPU / 网络健康和负载相关错误码；
- **服务 → 代码 / 算子下钻路径**：从 P99 TTFT/TPOT 或错误码，定位到请求阶段 → 模型模块 → rank → 原始事件；
- **场景化健康模型**：在线低时延、离线高吞吐、RL 边训边推、PD 分离分别配置指标权重；健康度可查看组成、可调整权重，拒绝固定综合分误导；
- **告警自动关联**：每条告警自动关联对应请求、rank、profile 片段、版本变更和历史相似故障；
- **异常处置卡片**：每个异常给出“影响范围、最可能根因、需要补采的数据、建议实验和责任域”，减少跨团队扯皮。

### 6.5 Trace Navigator：大 trace 智能切片与证据导航

**目标**：面向 GB 级 trace（十分钟在线 trace 可达数 GB，超 1GB 可能打不开），避免整包加载。（回应洞察 3）

核心功能：

- 按请求 / 时间 / 模块 / 异常窗口对大 trace 做**无损切片与摘要**；
- 保留跳回原始事件的证据链接，支持用户用 timeline 做确定性事实核验（访谈强调用户不盲信 AI 结论）；
- 摘要视图与原始事件视图双向导航，任何结论可回溯到具体 trace span；兼容 msprof / MindStudio Insight / Perfetto 导出格式。

### 6.6 Diagnosis & Knowledge：错误 / 日志归因 + 昇腾算子能力知识库

**目标**：NPU 用户最耗时的不是写模型，而是确认“当前 CANN 版本能不能支持这个调用、为什么不支持、该改什么”。（回应洞察 4）

**错误与日志归因**

- 聚合 Python、框架、CANN、算子、HCCL、plog 与系统日志，自动归并成一条**因果链**；
- 直接指出疑似责任域、参数 / shape / 版本限制和下一步动作，而不是让用户从 plog 里大海捞针；
- 典型场景：Python 层只报 tuning 问题，有效信息藏在 plog——产品自动把二者串联，指出根因参数或 shape。

**算子能力与兼容性知识库**

- 建立可机器读取的昇腾算子能力库：支持 CANN 版本、硬件型号、dtype、shape、布局、量化方式和已知限制查询（例如 FA 因 KV/Q 头数变化的支持边界）；
- **运行前兼容性预检**：明确指出不支持项及可选替代方案（改参数 / 换算子 / 换 CANN 包 / 提需求）；
- 支持自然语言和结构化查询，可被 Agent、IDE、CI 直接调用；
- 为快速实验提供 Triton Ascend / PyPTO 等路径提示，为生产交付提供向 Ascend C 高性能实现的迁移与收益评估。

### 6.7 Admission Pipeline：准入流水线与门禁

**目标**：成熟团队已在自建准入体系，但能力分散在流水线、脚本、监控和文档中。把“基线、环境、配置、用例、结果、门禁”标准化。（回应洞察 6）

核心功能：

- **版本矩阵管理**：统一管理模型 / 框架 / CANN / 算子 / 硬件的版本组合与准入结果；绑定不同 CANN 与推理框架版本的多条 CI 流水线；
- **四类门禁模板**：精度、性能、稳定性、故障注入；允许按模型和服务 SLA 自定义阈值；
- **自动准入报告**：相对基线的改善 / 回退项、是否达到上线门槛、建议复测项，并留存可复现实验上下文；
- **线上问题回流 CI**：把线上异常样本和流量特征沉淀为回归用例，形成“线上问题 → 离线复现 → CI 防护”闭环；
- 兼容已有实践（如基于 vLLM benchmark serve 改造的统一性能测试、服务化故障注入 / 流量仿真工具），作为门禁的执行后端接入，而非重造。

### 6.8 RL Consistency：训推一致性与 RL 全链路诊断（P2）

**目标**：RL 把推理从独立服务变成训练主链路（训练 70%–90% 时间在推理侧），训推一致性成为新的推理基础能力。（回应洞察 5）

核心功能：

- **训推精度穿透对齐**：同 token、同层、同接口逐步定位首个偏差点，至少定界到模型模块、框架接口或昇腾算子；
- **权重同步与推理等待分析**：展示训练 → 权重发布 → 推理加载 → prefill/decode → 结果回传的关键路径与等待；
- **多指标联合诊断**：一致性、KL、reward、logprob 与推理性能联动展示，识别“单指标看起来正常”的假收敛（生产一致性目标可达 0.99，实际可能长期卡在 ~92%）；
- **变更追踪**：对训练 / 推理框架 commit、算子清单、量化与确定性配置做变更追踪，异常时自动关联最近变化；
- **推理作业状态诊断**：覆盖 hang、回调失败、外部依赖 / 沙箱不可用、实例创建 / 释放等状态。

### 6.9 Diagnosis Copilot：证据化 AI 诊断

**目标**：用户不盲信 AI 结论，仍会用 timeline 做事实核验，并要求建议关联到代码和运行证据。（回应洞察 3 的交互要求）

核心功能：

- AI 诊断采用 **“结论 — 证据 — 置信度 — 建议实验”** 结构；
- 每条建议引用具体指标、trace span、日志事件或版本 Diff，不允许仅凭日志文本生成无依据结论；
- 支持继续追问与反证：用户可要求“换个假设”“给出验证这个假设的实验”“展示支撑证据”；
- 结论明确区分事实、推断、建议三层，推断可一键触发验证实验。

## 7. 关键交互设计

### 7.1 统一“实验详情页”

每个实验是一个可共享、可比较的对象，默认只显示：

- **状态**：精度 / 性能 / 稳定性 / 故障注入四个门禁；
- **首要结论**：最可能阻塞用户的 1—3 个问题；
- **影响**：精度回退风险、SLA 违约风险或预计性能损失；
- **下一步**：可执行命令、建议实验或责任域移交；
- **证据**：可下钻的服务指标 / trace / tensor / 日志 / 版本变更链。

### 7.2 统一“Diff 视图”

- 左侧固定：两个实验的版本锚点（模型 / 引擎 / CANN / 量化 / 硬件 / 并行）；
- 中央按需切换：指标 Diff、热点算子 Diff、多 rank 对齐、精度逐层 Diff、trace 切片；
- 顶部：改善 / 回退汇总与门禁结论；
- 任一回退指标可下钻到请求阶段、模型模块、rank 和原始事件。

### 7.3 三层信息密度

| 层级 | 面向场景 | 展示内容 |
|---|---|---|
| L1 结论层 | 模型工程师、测试、首次使用者 | 发生了什么、影响什么、下一步做什么 |
| L2 工程层 | Infra / 性能 / RL 工程师 | 请求阶段、batch / KV、多 rank 对齐、指标归因 |
| L3 专家层 | 算子 / 底层专家 | 原始 trace、Ascend kernel / HCCL collective、plog、算子约束、tensor 事实 |

### 7.4 诊断信息标准

每条诊断包含：

```text
[严重度] [稳定规则 / 错误码 ID] 一句话结论
影响：可能导致的精度回退、SLA 违约或性能代价
证据：违反的约束 / trace 事实 / 日志因果链 / 版本 Diff
建议：最小修改、下一步命令或建议实验
责任域：疑似模型 / 框架 / 算子 / 硬件 / 环境
下钻：相关 trace、tensor、日志、版本变更
```

## 8. 核心指标体系

### 8.1 北极星指标

> **从发现推理性能 / 精度异常，到完成责任域定界的中位时间（MTTI, Mean Time To Isolate）。**

这是访谈中最能代表产品价值的度量——用户真正的痛点是“定界慢、扯皮多”。

### 8.2 用户价值指标

| 指标 | 目标方向 |
|---|---|
| 首次完成模型推理适配的时间（Time to First Successful Inference） | 下降 |
| 从异常到责任域定界的时间（MTTI） | 下降 |
| 从定界到修复并通过回归的时间（MTTR） | 下降 |
| 人工 profile 对比 / 日志整理 / 逐层 dump 工时下降比例 | 上升 |
| 版本发版因精度 / 性能问题阻塞的次数与时长 | 下降 |

### 8.3 产品效果指标

| 指标 | 12 个月建议目标 |
|---|---:|
| 异常自动定界到正确责任域的 Top-1 / Top-3 命中率 | Top-3 ≥ 80% |
| 多 rank 异常与首个偏离点检出率 | ≥ 85% |
| 精度回归首个偏差点自动定位率 | ≥ 70% |
| 自动建议被采纳并验证有效的比例 | ≥ 50% |
| 准入门禁拦截真实回退的比例 | ≥ 80% |
| 门禁误报率 | < 10% |
| 从线上异常自动生成可复现回归用例的成功率 | ≥ 60% |

### 8.4 护栏指标

- 低干扰采集性能开销 < 3%；完整取证需在启动前明确预计开销；
- 服务性能结论必须同时报告负载分布、P50/P90/P99、错误率和 goodput，不以单一平均吞吐替代；
- 准入报告只对已实测的硬件 / 模型 / 序列长度 / 并发边界作出承诺，外推值显式标记；
- prompt、响应、权重、KV 内容默认不进入 trace 与共享报告，仅保存脱敏摘要（shape / dtype / hash / statistics）；
- 高危 error 级诊断规则假阳性率 < 1%，低置信度降级为 warning 并附最小复现。

## 9. 分阶段路线图

优先级依据“降低发版阻塞风险 × 贯穿角色数量 × 对后续能力的基础性”。

### Phase 0：比较与定界底座（0—3 个月）——对应访谈 P0

- 统一 Run ID、实验 Manifest、版本锚点与 correlation ID；
- Experiment & Diff Hub v1：双实验多维 Diff、可比性保护、自动变更报告；
- Multi-Rank Aligner v1：慢卡 / 首个偏离 rank / HCCL 通信等待识别；
- 错误与日志归因 v1：Python + 框架 + CANN + 算子 + plog 因果链；
- Admission Pipeline v1：精度 / 性能门禁 + 可复现上下文。

**退出标准**：一次真实版本变更（如 CANN 或引擎升级），能自动产出“改善 / 回退 + 责任域初判 + 可复现证据”的 Diff 报告。

### Phase 1：端到端诊断闭环（3—9 个月）——对应访谈 P1

- Service Observatory：服务指标 → 请求阶段 → 模型模块 → rank → 原始事件下钻；场景化健康模型；
- 昇腾算子能力与兼容性知识库 + 运行前预检，开放结构化 / 自然语言查询与 Agent / CI 调用；
- Trace Navigator：GB 级 trace 智能切片与证据导航；
- Accuracy Lab：同 token 锚点、首个偏差点定位、量化专项；
- 线上问题回流 CI；
- Diagnosis Copilot v1：结论 — 证据 — 置信度 — 建议实验。

**退出标准**：典型“线上 P99 异常 / 精度掉分”案例可自动定位到首个异常阶段 / 偏差点，并生成可复现证据包。

### Phase 2：RL 训推与规模化智能诊断（9—18 个月）——对应访谈 P2

- RL Consistency：训推精度穿透对齐、权重同步与等待分析、多指标联合诊断、作业 / 沙箱状态诊断；
- Multi-Rank Aligner v2：大规模集群、慢卡 / 吊卡 / HCCL 通信中断自动定位；
- 组织级知识治理：算子能力库、错误码库、历史故障库、recipe 版本化；
- Diagnosis Copilot v2：基于证据图的“提出假设 — 运行验证 — 提交建议”Agent；
- 与 PyPTO 3.0 的证据包互通（定界到昇腾算子层时回流 Compile Guardian / Correctness Lab）。

**退出标准**：RL 版本迭代能在同一工作台完成训推一致性诊断、性能归因和准入回归，一致性异常可定界到模块 / 接口 / 算子。

## 10. MVP 定义

MVP 必须形成“比较—定界”闭环，不能只交付分散命令。

### 10.1 MVP 用户故事

> 一名 MaaS Infra 工程师升级了 CANN 与推理引擎版本，线上 P99 TTFT 上涨。他把新旧两次实验拖进 Diff Hub，一屏看到 TTFT 回退主要来自 decode 阶段的某个 attention kernel 变慢和一张慢卡的 HCCL 通信等待；Multi-Rank Aligner 指出首个偏离 rank；错误归因排除了环境问题；他把这次 Diff 作为准入门禁的回退证据，拦截了发版，并一键生成脱敏复现包移交算子团队。

> 一名测试工程师在版本准入中发现精度评测掉分。Accuracy Lab 以同一批样本为锚点，定位到某个量化算子在特定 shape 下的首个偏差点，并关联到最近的算子包变更；他将该样本沉淀为 CI 回归用例。

### 10.2 MVP 功能包

- 实验 Manifest + Run ID + 版本锚点；
- Experiment & Diff Hub：双实验多维 Diff（TTFT/TPOT/吞吐/显存/热点算子）、可比性保护、变更报告；
- Multi-Rank Aligner：慢卡 / 首个偏离 rank / HCCL 通信等待；
- Accuracy Lab 最小闭环：同 token 锚点、首个偏差点定位；
- 错误与日志归因 v1（Python + CANN + 算子 + plog）；
- Admission Pipeline 最小门禁（精度 + 性能）+ 可复现包；
- 现有采集工具（msprof / MindStudio Insight / Perfetto / vLLM-Ascend bench）的产物导入适配器。

### 10.3 不纳入首版 MVP

- 完整 RL 训推链路诊断；
- 大规模集群吊卡 / HCCL 通信中断自愈；
- 自主改代码的 AI Agent；
- 生产运维、扩缩容、计费和告警值守。

## 11. 主要风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 只做 UI，不统一数据 | 页面好看但仍无法跨层定位 | 优先交付 Manifest、Run ID、证据图 schema，再扩展界面 |
| 又变成一块静态大盘 | 指标堆砌但不联动诊断 | 每个指标异常必须挂“根因假设 + 证据 + 建议动作” |
| 比较不可比 | warmup / 采样 / 硬件不同导致误判 | 版本化负载，锁定模型 / 数据 / 采样 / 硬件，条件不一致强制告警 |
| 精度非确定性误报 | sampling 差异被当作回退 | 确定性 profile、固定种子、分布一致性指标 |
| AI 结论不可信 | 用户不采纳 | 结论绑定证据、置信度和验证实验；区分事实 / 推断 / 建议 |
| 采集开销改变问题本身 | full trace 引发 backpressure | 两档采集、预算预估、启动前告知开销 |
| 推理数据泄露 | prompt / 响应 / KV 进入 trace | 默认只采 hash / shape / statistics，分级授权、可审计导出 |
| 与既有工具重复造轮子 | 用户已有 msprof / MindStudio / vLLM-Ascend bench | 定位为“消费与增强”，做导入适配器和 Diff / 归因层，不重做采集 |
| 依赖昇腾底层数据不开放 | plog / CANN / HCCL 事件 schema 不稳定 | 与 CANN / 引擎团队约定诊断事件契约，schema 版本化并留降级路径 |
| 范围膨胀为生产运维平台 | 核心诊断闭环延期 | 严守边界：诊断、比较、归因、准入；生产编排交外部平台 |

## 13. 最终产品判断

PyPTO Studio 的先进性，不在于“再做一个推理引擎”或“再加一块大盘”，而在于它系统性地补齐了昇腾场景下业界工具留下的空白：

- **知道两次实验之间到底变好还是变坏**，并能自动归因，而不是让用户肉眼叠图；
- **知道多卡里哪张卡、哪个 step、哪个 HCCL collective 拖慢了整体**，而不是把多张 timeline 扔给用户；
- **知道精度回退从哪一层、哪个算子、哪次变更开始**，而不是只报一个最终分数；
- **知道一条 Python 报错背后的真实根因链（含 plog / CANN）**，而不是让用户去 plog 里大海捞针；
- **知道一次上线是否安全**，并留下可复现、可回归的证据，而不是靠专家拍板；
- **知道 RL 训推一致性差异出在哪**，而不是止步于框架边界。

因此，建设顺序应是：**比较与定界底座 → 服务到算子的诊断闭环 → 精度回归与知识沉淀 → RL 训推一致性 → 规模化智能诊断。** 只有先把“比较、对齐、Diff、归因”这四件业界尚未在昇腾侧系统化的事做扎实，才能把分散在各团队的采集工具和准入脚本，真正升级成 PyPTO 家族的下一代推理工程工作台。
