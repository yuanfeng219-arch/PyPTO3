# 昇腾大模型推理融合规则目录

> 文档定位：面向模型整网的算子融合推荐器，帮助开发者从模型计算图中发现高价值融合候选，并给出融合收益、实现形态、前置条件、风险和验证建议。
>
> 文档性质：规则底稿，不等同于 PyPTO 编译器 Pass 规范。本文关注“模型层面是否值得尝试融合”，具体能否编译、能否达到性能目标，仍需结合目标芯片、CANN/PyPTO 版本、shape、dtype、layout、并行策略和实测结果确认。
>
> 适用日期：2026-08-28

## 1. 推荐器的目标与边界

### 1.1 目标

给定模型整网图、节点属性和推理场景，推荐器应回答：

1. 哪些连续节点或子图值得组成一个融合算子。
2. 推荐的是局部数据流融合、跨算子阶段融合、复合模型算子，还是调度/通信协同方案。
3. 融合能节省哪些 GM 读写、kernel launch、同步或中间张量。
4. 需要满足哪些 shape、dtype、layout、内存、并行和精度条件。
5. 为什么不能融合，或者为什么当前不建议融合。
6. 应通过哪些 correctness、performance 和稳定性实验验证。

### 1.2 不应直接做出的判断

推荐器不应仅凭算子名字判断“节点越多越好”。以下问题不能由图模式单独决定：

- 片上容量是否足够；
- 融合后 Cube/Vector 利用率是否下降；
- AIC/AIV 之间搬运和同步是否抵消收益；
- 动态 shape、batch、prefill/decode 场景下是否仍然成立；
- FP16/BF16/FP32/INT8 等不同精度下是否满足误差要求；
- 融合后的 kernel 是否真的优于已有 CANN/PyPTO/library kernel。

## 2. 规则的统一模型

每条规则由三类子规则组成：

| 类型 | 作用 | 示例 |
|---|---|---|
| Pattern Rule | 从整网图中找候选模式 | MatMul → BiasAdd → GELU |
| Legality Rule | 判断候选是否具备实现条件 | bias 可广播、无多消费者、归约轴合法 |
| Ranking Rule | 对多个合法候选排序 | GM 流量收益、launch 减少、实现复杂度 |

建议每条规则至少包含以下字段：

~~~json
{
  "rule_id": "matmul_bias_activation",
  "category": "matmul_epilogue",
  "pattern": ["matmul", "bias_add", "activation"],
  "priority": "P0",
  "recommendation": "strong",
  "scenario": ["prefill", "decode"],
  "hard_constraints": [],
  "soft_constraints": [],
  "benefits": [],
  "risks": [],
  "fusion_shape": "local_dataflow | composite_model_op | stage_fusion | multi_branch | schedule_synergy",
  "validation": [],
  "implementation": {
    "mode": "custom_fused_op | composite_op | orchestrated_subgraph | overlap_schedule",
    "pypto_status": "not_checked | draft | ir_verified | runtime_verified",
    "required_capabilities": [],
    "resource_constraints": {}
  },
  "fallback_chain": [],
  "evidence": {
    "status": "validated | experience | hypothesis",
    "source_refs": [],
    "tested_capability": []
  }
}
~~~

### 2.1 模型层面的融合单元

推荐器的基本对象是“模型融合单元”，而不是某个 kernel 或某段 DSL。一个融合单元由以下内容组成：

```text
模型子图 + 语义边界 + 数据复用关系 + 场景 + 融合收益 + 风险 + 可落地实现路径
```

建议把融合候选分为四类：

| 模型层类型 | 识别重点 | 典型例子 |
|---|---|---|
| 数据流局部融合 | 前后算子存在短路径，且中间结果只被局部消费 | residual add → RMSNorm、MatMul → bias → activation |
| 分支汇合融合 | 多个分支共享输入，或在同一算子处汇合 | gate/up projection → SwiGLU、Q/K/V projection |
| 阶段链融合 | 一个模型阶段内部存在稳定的计算链和统一的 tile/sequence 处理方式 | QKᵀ → mask → softmax → PV、RoPE → cache write |
| 调度/通信协同 | 算子本身不宜合成一个计算单元，但可按模型阶段重排、分块或重叠 | AllGather → projection、MoE dispatch → expert compute |

融合边界应优先按模型语义确定：Transformer block、Attention、FFN、MoE layer、KV cache update 等是推荐器的一级上下文；算子数量、是否同一 kernel 只作为实现属性，不作为“融合价值”的定义。

### 2.2 PyPTO 在模型级推荐中的角色

PyPTO 信息用于回答“该模型融合候选能否形成可交付的算子/算子组合”，而不是把推荐器变成核内融合器。推荐器只需保留以下实现标签：

| 字段 | 含义 |
|---|---|
| `implementation_mode=custom_fused_op` | 候选可实现为一个面向模型子图的自定义融合算子 |
| `implementation_mode=composite_op` | 候选由多个 PyPTO/CANN 算子组成，但对模型层提供统一算子接口 |
| `implementation_mode=orchestrated_subgraph` | 保留多个阶段，通过统一编排、buffer 和依赖交付 |
| `implementation_mode=overlap_schedule` | 保留通信/计算边界，以分块、流水或调度重叠获得收益 |
| `pypto_status` | `not_checked`、`draft`、`ir_verified`、`runtime_verified` |

PyPTO 只做二级可行性校验：操作支持、shape/layout/dtype、内存和依赖是否有实现路径。它不能否定模型层候选本身；校验失败时应返回“候选保留、实现路径降级”以及最小回退方案。

## 3. 推荐等级与融合形态

### 3.1 推荐等级

| 等级 | 含义 | 产品表现 |
|---|---|---|
| 强推荐 | 收益明确、实现路径成熟、阻断条件少 | 默认进入候选列表前列 |
| 条件推荐 | 收益较好，但依赖 shape、layout、dtype 或场景 | 展示条件和缺失信息 |
| 谨慎推荐 | 理论收益存在，但可能损失并行度、精度或稳定性 | 需要人工确认和小规模实验 |
| 不推荐 | 收益低、风险高或存在硬阻断 | 解释原因，不生成实现建议 |
| 信息不足 | 关键 shape、场景或硬件信息缺失 | 引导补充输入 |

### 3.2 融合形态

| 形态 | 说明 | 典型场景 |
|---|---|---|
| Local dataflow | 相邻算子形成稳定的数据流短链 | add → mul → relu、matmul → bias → activation |
| Composite model op | 多个基础算子对外封装为一个模型语义算子 | RMSNorm、SwiGLU、QKV projection |
| Stage fusion | 一个模型阶段内的多个子步骤共享数据访问或中间状态 | Attention 主链、RoPE → cache write |
| Multi-branch fusion | 共享输入、汇合输出或多输出关系共同评估 | Q/K/V projection、gate/up → multiply |
| Schedule/communication synergy | 不强行合并算子，按阶段做分块、流水或重叠 | AllGather → projection、MoE dispatch → expert |
| Subgraph orchestration | 保留多个执行步骤，以统一依赖、buffer 和回退路径交付 | 多阶段 FFN、Paged Attention |

## 4. 全局候选生成规则

### 4.1 图拓扑规则

优先从以下结构生成候选：

- 单输入链：A → B → C；
- 多输入汇合：A/B → C；
- 一个大算子后接一到三个轻量算子；
- 同一输入被多个相同投影或逐元素分支读取；
- 同一循环或同一 token/block 内重复执行的局部子图；
- 通信前后具有明确 producer/consumer 关系的子图。

### 4.2 基础可融合条件

候选默认需要满足：

- 中间张量至少有一个明确消费者；
- 中间张量不是模型对外输出；
- producer 和 consumer 的数据依赖顺序可保持；
- shape 相同，或广播/reshape 关系可静态解释；
- dtype 转换次数可控；
- 中间结果可以表示为 tile、局部 buffer 或流式状态；
- 融合边界没有随机、状态写入、通信或外部副作用；
- 候选不会把多个互相独立的并行分支强行串行化。

### 4.3 默认阻断条件

满足以下任一条件时，默认不推荐直接融合：

- 中间结果被两个以上不相邻分支消费；
- 融合需要把大型 activation 长时间保存在片上；
- 融合跨越通信域、rank 边界或 KV cache 所有权边界；
- 动态维度决定了归约长度、tile shape 或内存大小，且无法给出稳定上界；
- 融合会改变归约顺序、随机数顺序或量化顺序；
- 候选包含多个重量级 MatMul，且没有明确的 blocking/streaming 方案；
- 目标算子已有成熟高性能库实现，融合收益只来自一次很小的搬运；
- 融合后需要大量额外同步或跨 Cube/Vector 数据交换。

### 4.4 中间张量、消费者与模型边界

模型层推荐必须以“消费者关系和语义边界”而不是节点距离判断是否值得融合：

- 单消费者且中间结果只在同一模型阶段使用：优先作为局部融合候选；
- 多消费者：评估一次共享物化与多次重复计算的代价，不默认强行合并；
- 中间结果被 residual、skip、loss/观测分支或 cache 更新复用：保留模型语义边界，除非收益有明确证据；
- 循环状态、KV cache、MoE route table 等状态数据：按模型阶段生命周期和复用范围评估，不按单次算子邻接判断；
- 对外输出、跨层复用或跨 rank 使用的 Tensor：默认视为融合边界。

推荐器应返回 `materialization_decision`：`eliminate`、`keep_for_reuse`、`keep_for_boundary` 或 `unknown`，并同时返回 `consumer_summary`。

### 4.5 模型语义归一化规则

在模式匹配前，先将不同框架的算子图归一化为模型语义角色，避免因为命名不同漏掉同一类融合：

| 归一化角色 | 可能的原始算子 | 需要保留的属性 |
|---|---|---|
| `projection` | Linear、MatMul、GEMM、QuantizedLinear | 输入/输出维度、权重布局、bias、量化参数 |
| `normalization` | RMSNorm、LayerNorm、FusedNorm | 归约轴、epsilon、affine、累计精度 |
| `activation` | ReLU、GELU、SiLU、SwiGLU | 公式/近似版本、分支关系、输出范围 |
| `attention_core` | QKᵀ、scale、mask、softmax、PV | causal、GQA/MQA、cache、序列范围 |
| `routing` | softmax、top-k、dispatch、combine | expert 数、top-k、token 重排、通信域 |
| `state_update` | RoPE、KV cache write/read、残差更新 | 地址、所有权、更新时序、跨请求复用 |

归一化后再匹配 `projection → activation`、`residual → normalization` 等语义模式。规则必须记录原始节点与归一化角色的映射，便于解释和回溯。

### 4.6 候选冲突与整网选择规则

同一模型区域可能命中多个嵌套候选，推荐器不能把它们的收益简单相加：

1. 先生成最小候选，如 `MatMul + Bias`、`Bias + Activation`；
2. 再生成组合候选，如 `MatMul + Bias + Activation`、`Residual + RMSNorm`；
3. 对重叠候选形成互斥方案集，计算每个方案在整网中的净收益；
4. 结合实现复用、回退成本和验证成本选择主推荐，同时保留次优方案；
5. 对不同 Transformer layer、prefill/decode 或 shape 分别允许不同方案，不强制全网使用同一融合边界。

候选至少需要返回 `region_id`、`parent_candidate_id`、`overlap_group` 和 `selected_variant`，使用户能看懂“为什么推荐这个边界而不是更大的边界”。

## 5. 收益估算规则

### 5.1 主要收益项

~~~text
收益 = 消除的 GM 写回/读取
     + 减少的 kernel launch
     + 减少的中间 buffer 分配
     + 减少的同步和依赖管理
     + 输入/权重的复用收益
     + 通信与计算重叠收益
~~~

### 5.2 主要成本项

~~~text
成本 = 新增的 tile move
     + 片上内存压力
     + AIC/AIV 同步
     + 并行度损失
     + 归约与精度风险
     + 编译和调试复杂度
     + 动态 shape 特化数量
~~~

### 5.3 推荐排序建议

~~~text
FusionScore =
  4 × GM traffic saved
  + 3 × launch saved
  + 2 × reuse/overlap benefit
  - 3 × extra synchronization
  - 3 × on-chip pressure
  - 2 × parallelism loss
  - 2 × numerical risk
  - 1 × implementation complexity
~~~

该公式只适合作为 MVP 启发式。正式版本应使用 profile 数据校准权重，并按 prefill、decode、batch size、sequence length 分别建模。

### 5.4 评分前的硬门禁与单位

Score 只对通过图语义 Legality 的候选计算。PyPTO/CANN 可行性作为实现置信度和落地路径参与排序，不应在模型候选阶段提前过滤掉有价值的子图。所有收益项统一为单次执行量：GM traffic 用 bytes，launch/sync 用次数，片上压力用峰值 bytes，性能收益用 profile 的 latency 或 throughput 变化；不能把 FLOPs 直接与 bytes 相加。

建议先计算可解释的中间量：

~~~text
gm_saved_bytes = producer_output_bytes × eliminated_materializations
launch_saved = original_kernel_count - candidate_kernel_count
live_working_set = sum(live_tile_bytes + accumulator_bytes + temp_bytes)
sync_added = cube_vector_handoff + cross_tile_reduction + explicit_fence
~~~

当缺少 profile 或 capability 信息时，分数应标记为 `provisional`，不能输出看似精确的百分制结论。

### 5.5 整网收益聚合

模型层排序不能只比较一次算子的局部收益，还要考虑该子图在整网中的出现次数和服务场景：

~~~text
net_benefit(candidate) =
  per_invocation_benefit
  × invocation_count(model, scenario)
  × execution_weight(batch, sequence, token_position)
  - integration_cost
  - validation_cost
~~~

其中 `invocation_count` 要区分层数、MoE expert 命中次数和 Attention 调用次数；`execution_weight` 要分别覆盖 prefill 的 token 数、decode 的实际 batch 和请求并发。推荐器应同时展示局部收益与整网贡献，避免一次收益很小但高频出现的候选被遗漏，也避免一次收益很大但只在极少数路径出现的候选排名过高。

## 6. 规则目录总览

| 类别 | 代表规则 | 优先级 | 默认判断 |
|---|---|---:|---|
| 逐元素链 | add → activation、cast → scale → add | P0 | 强推荐 |
| MatMul 尾融合 | matmul → bias → activation | P0 | 强推荐/条件推荐 |
| Norm | residual_add → RMSNorm、RMSNorm 内部归约链 | P0 | 条件推荐 |
| Attention | QKᵀ → scale → mask → softmax → PV | P0 | 高收益、高复杂度 |
| QKV/RoPE | QKV projection → split → RoPE/cache | P1 | 条件推荐 |
| FFN/MLP | up/gate → activation → multiply → down | P0 | 分段推荐 |
| 量化 | dequant → matmul → requant | P1 | 条件推荐 |
| MoE | router → topk → dispatch → expert → combine | P1 | 局部推荐 |
| 通信 | collective → compute 或 compute → collective | P1 | 谨慎推荐 |
| KV Cache | RoPE → cache write → attention read | P1 | 场景化推荐 |

## 7. P0：逐元素与轻量后处理

### FUS-ELE-001：逐元素链融合

**模式**：

~~~text
Add/Sub/Mul/Div → Cast/Scale → Relu/GELU/SiLU/Clamp
~~~

**推荐条件**：

- 所有节点作用于相同 logical shape；
- 只包含逐元素或可局部广播操作；
- 中间结果没有额外消费者；
- 不需要跨 token/head 的归约；
- dtype 转换不超过推荐上限；
- 最终结果可以一次 store。

**强推荐模式**：

~~~text
add → relu
add → scale
mul → add
bias_add → activation
~~~

**降级条件**：

- 广播维度很大且导致重复加载；
- div、复杂 exp 或近似函数明显增加 Vector 计算时间；
- 中间结果需要被其他分支复用。

### FUS-ELE-002：Cast 与后处理融合

**模式**：

~~~text
Cast → Scale/Add/Activation
~~~

**必须检查**：

- cast 是计算需要还是存储需要；
- 是否可以只在寄存器/片上完成 cast；
- 激活函数是否要求 FP32 中间精度；
- 是否改变舍入点；
- 最终输出误差是否达到模型阈值。

凡涉及量化、softmax、归一化和 top-k 的 cast，都应进入精度回归。

## 8. P0：MatMul 尾融合

### FUS-MM-001：MatMul + BiasAdd

**模式**：

~~~text
MatMul(X, W) → BiasAdd(·, bias)
~~~

**推荐等级**：强推荐。

**收益来源**：

- MatMul 输出无需先写回 GM；
- Bias 可以直接作用于输出 tile；
- 少一次中间 Tensor 的生命周期管理；
- 减少一次 kernel launch。

**必要条件**：

- bias 可广播到 MatMul 输出；
- MatMul 输出 tile 能被 BiasAdd 消费；
- bias 的读取方式不会造成严重重复访存；
- 输出 dtype 和 accumulation dtype 明确。

**模型层说明**：`MatMul + BiasAdd` 的推荐价值来自线性层尾部的稳定数据流、bias 中间结果的消除机会和 activation 前的统一边界；是否最终由一个 PyPTO 自定义算子实现，属于后续落地选择。若当前只能用多个算子编排，也应保留该模型候选，但将收益标注为“待实现验证”，不能直接承诺 GM 往返或端到端时延收益。

### FUS-MM-002：MatMul + BiasAdd + Activation

**模式**：

~~~text
MatMul → BiasAdd → ReLU/GELU/SiLU
~~~

**推荐等级**：

| 激活 | 默认判断 |
|---|---|
| ReLU | 强推荐 |
| SiLU | 条件推荐 |
| GELU | 条件推荐，需关注近似公式与精度 |
| Sigmoid/Tanh | 谨慎推荐，需确认 Vector 代价 |

**实现路径**：通常是面向线性层尾部的自定义融合算子或复合模型算子；若受实现能力限制，也可退化为 MatMul、BiasAdd、Activation 的多算子编排。

**阻断条件**：

- 激活前后需要保存完整大矩阵；
- 激活函数实现不具备目标后端支持；
- MatMul 输出被多个分支消费；
- AIC/AIV 交接和同步成本高于 GM 往返收益。

### FUS-MM-003：MatMul + Cast/Quantize

**模式**：

~~~text
MatMul(FP16/BF16 accumulate) → Cast/Quantize(FP16/BF16/INT8)
~~~

重点检查 scale/zero-point 粒度、是否需要动态统计范围、MatMul accumulation 是否必须保留 FP32，以及融合是否改变量化边界。

推荐等级：条件推荐。若量化参数已经是局部可读且无需额外归约，可提升等级。

## 9. P0：Norm 与残差

### FUS-NORM-001：ResidualAdd + RMSNorm

**模式**：

~~~text
residual + hidden → RMSNorm
~~~

**推荐等级**：强推荐或条件推荐，取决于归约维度和 token/block 分片。

**收益来源**：

- residual 和 hidden 可以一次加载并完成相加；
- RMSNorm 的平方、归约、rsqrt、缩放在局部完成；
- 避免 residual add 的中间结果落 GM。

**必要条件**：

- RMSNorm 归约维度与 tile 分块一致；
- 归约结果可以在本地得到或有明确的跨 tile reduction 方案；
- epsilon、权重和 accumulation dtype 明确；
- residual 结果不会被其他分支独立复用。

### FUS-NORM-002：RMSNorm 内部链融合

**模式**：

~~~text
x → square → reduce_mean/sum → add epsilon → rsqrt → multiply weight
~~~

整体作为一个 Norm 模板评估，不建议逐个节点独立推荐。

**高风险情况**：

- hidden size 跨多个 tile，需要跨 tile 归约；
- 动态 hidden size；
- 低精度直接归约造成累计误差；
- 后续紧接量化或 top-k，对误差敏感。

### FUS-NORM-003：LayerNorm 融合

模式为 mean → variance → normalize → affine。默认等级为谨慎推荐，应优先检查已有库算子性能，再决定是否开发自定义融合算子。

## 10. P0：Attention

### FUS-ATTN-001：完整 Attention 主链

**模式**：

~~~text
QKᵀ → scale → mask → softmax → PV
~~~

**推荐等级**：高收益、高复杂度。

**推荐原因**：

- 避免 attention score、masked score、probability 等大中间矩阵落 GM；
- softmax 可以采用 online/block 方式；
- Q/K/V tile 可以在局部循环中复用；
- 适合组织为 streaming attention。

**必须识别的语义属性**：

- prefill 或 decode；
- causal 或 non-causal；
- head 数、KV head 数和 GQA/MQA 关系；
- sequence length、KV cache length；
- mask 类型；
- 是否使用 paged/block KV cache；
- QK 和 PV 的矩阵布局。

**不应直接整体融合的情况**：

- score 矩阵必须被多个后续分支使用；
- mask 或 top-k 引入复杂动态稀疏控制；
- sequence 维度过大且没有 block/online 方案；
- 目标场景是 decode，但规则只适用于 prefill，或反之。

### FUS-ATTN-002：QKᵀ + Scale + Mask

适合作为 Attention 的第一阶段候选，尤其在 softmax/PV 已由成熟实现负责时。

检查 scale 是否为标量或可局部广播、mask 是否可以按 block 生成、QK 输出是否能直接进入 softmax，以及是否需要 FP32 计算或特殊布局转换。

### FUS-ATTN-003：Softmax + PV

**模式**：

~~~text
softmax(score) → MatMul(probability, V)
~~~

适合采用 online softmax，避免完整 probability 矩阵物化。

**关键风险**：

- softmax 的 max/sum 状态需要跨 block 合并；
- PV 的 V tile 读取与 softmax block 顺序耦合；
- 归约顺序变化会带来数值差异；
- decode 场景下 KV cache 访问可能比计算更占主导。

## 11. P1：QKV、RoPE 与 KV Cache

### FUS-QKV-001：Q/K/V Projection 共享输入

**模式**：

~~~text
x → Q projection
x → K projection
x → V projection
~~~

**推荐方向**：

- 如果权重已经拼接为一个大矩阵，优先推荐合并 projection；
- 如果 Q/K/V 权重独立，评估 multi-output 或 grouped projection；
- 如果 Q/K/V 后续处理不同，不应强行合并整个后处理链。

**必须检查**：

- 权重布局是否支持合并读取；
- Q/K/V 输出 shape 是否兼容；
- GQA/MQA 下 Q head 与 KV head 是否不同；
- Q/K/V 是否具有不同的量化参数；
- 输出是否需要分别写入不同 cache 或 buffer。

### FUS-QKV-002：Projection + RoPE

**模式**：

~~~text
Q/K projection → reshape/split → RoPE
~~~

推荐等级：条件推荐。RoPE 只作用于 Q/K 而不作用于 V 时，应考虑多输出算子或复合算子与不同消费路径，避免为了共享输入而增加大量分支逻辑。

### FUS-KV-001：RoPE + KV Cache Write

**模式**：

~~~text
K/V → RoPE(K) → KV cache update
~~~

推荐等级：条件推荐。需要检查 cache 写入地址连续性、paged cache 的 block table、K/V 转置或量化，以及 cache 写入的跨 rank/stream 依赖。

## 12. P0：FFN、MLP 与 SwiGLU

### FUS-FFN-001：单分支 FFN 尾链

**模式**：

~~~text
up_proj → activation → down_proj
~~~

优先尝试 up_proj + activation，再评估是否把 down projection 纳入 streaming 方案。

直接整体融合的风险：

- up projection 输出通常较大；
- down projection 需要完整或分块消费上游激活；
- 融合可能降低两个 MatMul 的并行度；
- 权重读取和片上 buffer 竞争加剧。

### FUS-FFN-002：SwiGLU 局部融合

**模式**：

~~~text
gate_proj(x) → SiLU → multiply(up_proj(x))
~~~

推荐等级：强推荐或条件推荐。这是 FFN 中优先级最高的融合候选之一，因为两个 projection 结果需要在逐元素乘法处汇合。

必要条件包括 gate/up 输出 shape 一致、两路输出按相同 tile/block 对齐、SiLU 只作用于 gate 分支、dtype 和 accumulation 规则明确，以及 multiply 结果没有额外分支消费者。

### FUS-FFN-003：SwiGLU + Down Projection

默认谨慎推荐。只有当存在明确的分块矩阵乘和流式消费方案时，才提升为条件推荐。

## 13. P1：量化与反量化

### FUS-QUANT-001：Dequant + MatMul

**模式**：

~~~text
weight/int activation → dequant → MatMul
~~~

推荐等级：条件推荐。检查 scale/zero-point 粒度、scale 变化维度、dequant 是否可在 MatMul tile 装载路径中完成、dequant 后是否必须落 Mat/L1，以及权重布局和稀疏格式是否支持融合。

### FUS-QUANT-002：MatMul + Requant

**模式**：

~~~text
MatMul → bias/scale → clamp → cast/quantize
~~~

推荐等级：条件推荐。若 requant 需要动态统计范围，默认降级。

### FUS-QUANT-003：Dequant + MatMul + Activation

这是高收益但高风险的复合候选。应拆解为三个实验版本：只融合 dequant + MatMul、只融合 MatMul + Activation、尝试三者整体融合。不能直接用整体融合失败来否定其中的局部融合价值。

## 14. P1：MoE

### FUS-MOE-001：Router 局部链

**模式**：

~~~text
router logits → softmax/normalization → top-k → route weight normalize
~~~

推荐等级：条件推荐。适合融合局部逐元素与 top-k 前处理，不建议默认把大规模 top-k、token reorder 和通信全部封装为一个算子。

### FUS-MOE-002：Router + Dispatch 元数据生成

**模式**：

~~~text
router/top-k → expert indices/weights → dispatch metadata
~~~

收益主要来自减少小型中间张量和元数据往返。必须检查 expert 数量和 top-k 是否静态、token reorder 是否产生不规则写入、dispatch 是否跨 rank，以及 route table 是否被多个阶段复用。

### FUS-MOE-003：Expert GEMM + Combine

**模式**：

~~~text
dispatch → grouped expert GEMM → weighted combine
~~~

默认推荐“局部融合”和“编排融合”，谨慎推荐跨 rank 整体融合。

优先顺序：

1. expert GEMM + activation；
2. combine 内部的权重乘加；
3. dispatch metadata 生成与消费；
4. 跨 rank AllToAll + expert compute 的重叠。

## 15. P1：通信与计算

### FUS-COMM-001：Collective + Compute

**模式**：

~~~text
AllGather → MatMul/Vector compute
MatMul/Vector compute → ReduceScatter
~~~

推荐等级：谨慎推荐。推荐器应优先判断“是否可以重叠”，而不是直接判断“是否可以合成一个 kernel”。

检查通信数据是否可以分块到达、分块消费，计算是否存在独立 tile，collective 完成依赖是否阻塞整个计算，是否增加通信 buffer 生命周期，以及多 rank 的 shape、拓扑和同步是否一致。

### FUS-COMM-002：通信边界阻断规则

以下情况默认不推荐跨通信边界进行逻辑融合：

- 需要等待完整 collective 结果后才能计算；
- 不同 rank 的数据依赖不对称；
- 通信 buffer 同时被多个任务写入；
- 需要手工声明复杂依赖但缺少可验证的拓扑信息；
- 融合会隐藏通信失败、超时或死锁定位信息。

## 16. P1：KV Cache 与 Decode 专项

### FUS-DECODE-001：Decode 单 token 局部链

适合候选：

~~~text
RMSNorm → QKV projection
Q/K projection → RoPE → cache write
QK score → scale/mask → online softmax
~~~

Decode 推荐需要特别关注 actual batch、batch 动态变化、KV cache length、block table、页式地址、小矩阵 MatMul 的 launch/sync 成本，以及融合是否牺牲多请求并发。

### FUS-DECODE-002：Prefill/Decode 分场景规则

同一算子链必须分别计算 prefill 和 decode 的推荐分数。不能把 prefill 的高吞吐结论直接迁移到 decode：

| 场景 | 更看重 |
|---|---|
| Prefill | 大矩阵吞吐、GM 带宽、长序列 block 流水 |
| Decode | launch/sync、KV cache 访问、实际 batch、短 token latency |

### 17.1 图语义

- 是否保持原始数据依赖；
- 是否改变可观察输出；
- 是否存在多消费者、分支、循环状态或副作用；

- 广播维度；
- reduce 维度；
- transpose/reshape/slice；
- head、sequence、hidden、expert 维度；
- producer/consumer 的 tile 对齐方式。

### 17.3 Dtype 与精度

- 输入、累加和输出 dtype；
- cast、quantize、dequantize 边界；
- reduction accumulation dtype；
- 近似激活函数；
- 融合前后舍入点和误差预算。

### 17.4 硬件和执行侧

- Cube/Vector affinity；
- 片上 buffer 估算；
- GM 往返字节数；
- tile move 数量；
- AIC/AIV pipe 与同步；
- 多核、SPMD、流水和并行度；
- 通信域、rank 和 stream 依赖。

### 17.5 工程可交付性

- 是否存在可复用的 PyPTO/CANN 模板；
- 是否需要新增后端算子支持；
- 是否需要多 shape 特化；
- 是否能建立 golden 和误差阈值；
- 是否可以单独 benchmark 和回退。

## 18.1 从模型子图到融合推荐方案的生成契约

推荐器为每个候选生成一个“最小推荐包”，而不是只生成一句建议：

| 产物 | 最低内容 |
|---|---|
| 子图摘要 | 节点、输入输出、shape/dtype/layout、场景和消费者 |
| 融合边界 | 模型阶段边界、输入输出、保留/消除的中间张量和跨层依赖 |
| 语义说明 | 该子图在 Attention、FFN、MoE、KV cache 等模型结构中的作用 |
| 实现路径 | 自定义融合算子、复合算子、子图编排或通信/计算协同 |
| 能力依赖 | 所需算子、shape/layout/dtype、CANN/PyPTO 版本和硬件信息 |
| 收益估算 | 中间张量物化、GM 流量、launch、通信、并行度和端到端指标 |
| 验证任务 | 子图正确性、算子 benchmark、模型层 benchmark、整网 benchmark |
| 回退链 | 更小子图 → 复合算子/多算子编排 → 库实现/原始图 |

进入算子开发前必须明确这是“模型层推荐”“可编译草图”还是“已验证实现”。模型层推荐不因为 PyPTO 尚未支持某个实现路径而消失，只需降低实现置信度并提供回退方案。

## 19. 失败原因分类

推荐器不要只输出“不可融合”，应使用稳定的原因码：

| 原因码 | 含义 |
|---|---|
| MULTI_CONSUMER | 中间结果有多个消费者 |
| SHAPE_MISMATCH | shape 或广播关系不满足 |
| DYNAMIC_SHAPE_UNBOUNDED | 动态 shape 缺少稳定上界 |
| REDUCTION_CONFLICT | 归约维度与分块/并行冲突 |
| LAYOUT_CONFLICT | layout 转换成本或约束不可接受 |
| MEMORY_PRESSURE | 片上 buffer 估算超限或压力过高 |
| CUBE_VECTOR_BOUNDARY | Cube/Vector 交接成本过高或缺少实现路径 |
| COMMUNICATION_BOUNDARY | 跨通信域，依赖或同步不适合融合 |
| NUMERICAL_RISK | 归约顺序、舍入或近似函数风险 |
| PARALLELISM_LOSS | 融合后并行度明显下降 |
| LIBRARY_BASELINE_STRONG | 现有库实现可能更优 |
| MISSING_BACKEND_SUPPORT | 目标后端缺少必要算子或模板 |
| INSUFFICIENT_PROFILE | 缺少实测数据，无法排序 |

## 20. 验证闭环

每个“强推荐”候选至少经过四道门：

1. **图级语义验证**：融合前后输出、shape、依赖和 side effect 一致。
2. **算子级精度验证**：覆盖随机输入、边界值、长序列、极值和不同 dtype。
3. **实现级性能验证**：比较原始子图、局部融合、组合融合和编排方案。
4. **整网级收益验证**：按层数、场景和 workload 观察 TTFT、TPOT、吞吐、峰值内存和服务稳定性。

建议保留以下 baseline：

~~~text
Baseline A：原始模型图
Baseline B：已有 CANN/库算子
Candidate A：局部融合
Candidate B：更大范围融合
Candidate C：融合 + tile/layout/并行调优
~~~

## 21. MVP 实施优先级

### P0：第一版必须支持

- add/mul/sub → activation；
- matmul → bias；
- matmul → bias → relu/gelu/silu；
- residual_add → RMSNorm；
- gate_proj → SiLU → multiply(up_proj)；
- 候选收益估算、阻断原因和 fallback 建议；
- prefill/decode 场景区分；
- 融合前后正确性与 benchmark 任务生成。
- 模型语义归一化、重叠候选消解和局部收益到整网收益的聚合；
- PyPTO/CANN 实现路径、能力状态和回退链作为推荐解释字段，而不是主推荐对象；
- 规则命中 → 能力检查 → 资源估算 → 回退链的可解释决策链。

### P1：第二阶段支持

- QK/softmax/PV Attention 模板；
- QKV projection、RoPE、KV cache；
- dequant/matmul/requant；
- MoE router、dispatch、combine 局部融合；
- 通信与计算重叠建议；
- 基于历史 benchmark 的评分校准。

### 暂不纳入首版

- 任意动态控制流的自动融合；
- 跨 rank 的全自动融合改写；
- 只凭理论 FLOPs 自动承诺性能收益；
- 自动替换已有高性能库 kernel；
- 未经过精度门禁的激进低精度融合。

## 22. 规则维护要求

每条规则需要记录：

- 规则来源：模型结构、算子实现、硬件约束、profile 或 issue；
- 适用芯片、软件版本和日期；
- 已验证的 shape/dtype/layout 范围；
- 成功案例和失败案例；
- 典型收益区间及测试 workload；
- 精度阈值和回退策略；
- 规则置信度：已验证、经验规则、待验证假设。
- PyPTO 实现状态：`not_implemented`、`draft`、`ir_verified`、`runtime_verified`；
- 规则版本、能力表版本、代码模板版本和验证证据包 ID；
- 失败发生在哪一层：图语义、DSL/API、IR、codegen、runtime 或整网收益。

涉及外部硬件或软件能力的内容，不应写成永久结论；应通过版本化能力表维护：

~~~text
backend capability = (chip, CANN version, PyPTO version, dtype, layout, scenario)
~~~

## 23. 现阶段的核心判断

整网融合推荐器最有价值的能力不是生成一张“可融合/不可融合”清单，而是把每个候选解释成：

~~~text
模型子图
  → 推荐融合边界
  → 融合形态
  → 节省的 GM/launch/sync
  → 需要满足的 shape/layout/dtype 条件
  → 可能的硬件代价
  → 可回退实现
  → 正确性与性能验证计划
~~~

第一版建议优先做“高频、局部、可解释”的模板化推荐，再逐步扩展到 Attention、MoE 和通信计算协同。

特别需要避免两个概念混淆：

1. PyPTO/CANN 的实现方式（自定义融合算子、复合算子或多算子编排）是模型候选的落地路径，不应反过来定义模型层的融合边界；
2. 具备 online softmax、循环累加器或多阶段 pipeline 的子图，仍可作为 Attention/KV cache 等模型阶段候选，重点评估状态复用、序列场景和整网收益。
