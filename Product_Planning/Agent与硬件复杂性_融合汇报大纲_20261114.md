## 主轴

> **用户要的不是看见 Agent 做了什么，而是看见 Agent 依据什么。而在算子开发里，依据就是硬件事实与框架契约。**

这条主轴承担一件事：让「Agent 协作」与「硬件复杂性」不再是两个并列维度，而是一条因果链上的前后两段——Agent 把瓶颈从「写不出来」推到「判断不了」，而判断所需的依据，恰好是昇腾场景里最不可见的那一类。

**页序逻辑：** 诉求 → 依据 → 决策内容 → 工具载体 → 方向。
（原稿的串联问题在于把「工具载体」插在了「诉求」和「依据」之间，导致讲工具时「过程里有什么」尚未定义，讲硬件时又像在回头补一个新问题。）

## P1｜趋势：降低的是「写出来」的门槛

**页面要传达：算子生成能力正在被官方化、开源化，「有没有 Agent」不再是差异点；但降低的只是「写出来」的门槛。**

**内容要点**

- 【外·一手】华为在 HUAWEI CONNECT 2026（2026-09-19，上海）把「从人工算子编程到 Agent 编程与调优」列为智能体时代五个转变之一，并开源 CANNBot（算子生成）、Model Agent（模型适配）、MindStudio Agent（精度调优）、Solution Agent（行业部署）四类端到端 Agent 工具。
- 【外·一手】PTO ISA 对外开放，现含 8 类、120+ 条虚拟指令，支持 Auto 与 Manual 两种优化模式，并把「跨代兼容、算子源码可移植」作为公开承诺。
- 【外·一手】Ascend 社区开放万卡级算力、推出「100 NPU-Hour 计划」，未来三年投入 50 亿元人民币生态建设——**算力门槛也在同步下降**。

**落脚句（务必说出来）**

> 降低的是「写出来」的门槛。**没有降低的是「判断对不对、够不够快」的门槛**——而后者才是算子交付的瓶颈。

这半句在此处预埋，用于消解 P1 与后续硬件页在读者眼里的表面矛盾（「门槛都降低了，怎么又说硬件很复杂」）。

**建议画面：** 两条曲线。一条明显下行（生成门槛），一条基本走平（判断门槛），两线在右侧张开一个缺口——这个缺口就是全篇要讲的东西。

**过门到 P2：** 门槛降低的直接后果，是执行链条里多了一个会自己调用工具的参与者。

## P2｜分工：从「人用工具」到「人与 Agent 协作调用工具」

**页面要传达：Toolkit 的调用者变了。人的位置从逐步串联者，转为委托者与验收者。**

**内容要点**

- 旧链路：开发者 → Toolkit（逐个命令、逐次实验、状态存在人脑里）。
- 新链路：开发者 ↔ Agent → Toolkit（Agent 读工程、生成候选、调用编译与测试，并据反馈继续修改）。
- 【内】三方职责的简版划分（详表见[人、Agent 与 Toolkit 协作模式](./人-Agent-Toolkit协作模式_算子开发流程.md)，此处只保留一行一方，不展开四阶段矩阵）：

| | 承担什么 |
|---|---|
| 人 | 定义目标与边界、处理关键歧义、做取舍、验收与担责 |
| Agent | 建立上下文、生成候选、调用工具、组织实验、汇总证据 |
| Toolkit | 产生可信结果：编译、正确性、测量、诊断与产物留存 |

**本页的真正伏笔（一句话，为 P6 埋）**

> **Toolkit 的第一读者，从此不只是人。** 工具的输出要同时被人采信和被 Agent 使用——这件事在 P6 会决定工具形态怎么变。

**建议画面：** 两条链路上下对照，用高亮圈出「Toolkit 的调用方」这一处变化，而不是把重点放在 Agent 的能力清单上。

**过门到 P3：** 分工变化带来的不是单纯的效率提升，而是一次成本结构的反转。

## P3｜两种不透明：生成变便宜，判断没有 ★核心转折页

**页面要传达：用户面对的是两处不透明——结果判断不了，过程看不见也插不进手。两者收到同一个缺口上。**

**内容要点（建议按这个版式落页）**

**结果端｜用户要理解 Agent 写出来的代码，判断它是否合理**

- 但算子的对错与快慢都不写在代码里：对错取决于 shape / dtype / 归约顺序 / 依赖边，快慢取决于片上预算、共驻、搬运路径与同步形态。
- 【事实】最极端的一例：[pypto-lib#858](https://github.com/hw-native-sys/pypto-lib/issues/858) 中，故障 build 与通过 build 的编译器片上分配**逐字节相同**（跨 Vec / Acc / Left / Right / Mat 逐函数比对），故障只随纯时序翻转，原文结论是「**IR 里没有任何东西能区分这两种情况**」。
- 【推断】一般软件里读 Diff 能判断对不对；**算子开发里读 Diff 判断不了对不对，更判断不了快不快。**

**过程端｜生成过程黑盒，用户希望看见，并且希望能介入**

- 但用户要看的不是 Agent 说了什么，而是**它依据什么**：用了哪条硬件事实（它以为 L0B 是多大？它知道 hard syncall 要求满核吗？）、改完 tile 之后片上预算变成什么样、上一个候选为什么被放弃（编译不过／精度不过／还是它自己判断慢）、在哪台设备上测了哪些 shape。
- 要介入的也不是措辞：**暂停、取消、接管是控制权；改掉它的硬件假设与实验口径才是干预权。** 只有控制权，用户能做的只是「让它停下来然后自己从头干」——那是协作失败，不是协作设计。

**两端收到同一句（本页落脚，也是全篇主轴）**

> **用户要的不是看见 Agent 做了什么，而是看见 Agent 依据什么。**
> ——而在算子开发里，依据就是硬件事实与框架契约。

**外部印证**

- 【外·一手】Stack Overflow 2026 开发者调查：编码助手与 Agent 以 66% 成为第一大 AI 用例、73% 每日使用，但只有 **48%** 表示「在能轻易验证答案时才信任 AI」，仅 16% 把信任扩展到非重要决策；官方结论是 human-in-the-loop 仍是主导工作模式。
- 【推断】这组数字说明「可验证性」而非「能力强弱」决定采信，与本页两端诉求同向。

**建议画面：** 左右两栏（结果端 / 过程端），各列 2–3 行用户原话式问题，两栏下方收束到同一个词——**依据**。这个收束动作是本页的全部设计意图，不要让两栏平行到底。

**过门到 P4：** 既然两端都落在「依据」上，那就必须回答：算子开发的依据到底是什么，它现在在哪里。

## P4｜依据是什么：决定成败的事实不在代码里

**页面要传达：算子开发的依据是硬件事实与框架契约；它们当前有三种典型的不可见形态，而 Agent 在每一种上都有特定的失效方式。**

**内容要点｜三类不可见 × Agent 的失效方式**

| 不可见的类型 | 那个事实在哪里 | Agent 介入后变成什么 |
|---|---|---|
| **① 事实不在任何产物里**<br>【事实】[pypto-lib#858](https://github.com/hw-native-sys/pypto-lib/issues/858)（2026-07-30，**仍 open**）：同一份 kernel 18 次运行失败 16 次；UB 是核级共享资源，两个 vector task 各自远在预算内（98 816 B、98 304 B，a5 vector buffer 262 144 B），相加仍在限内；术语手册把 logical block → physical core 定义为「N:M（按时间）」，**谁与谁共驻同一物理核由运行时决定** | 运行时决定；**连 IR 都不区分**。把 `runtime_cfg["log_level"]` 提到 `v0` 这一个语义 no-op 动作就能让未修改的 kernel 通过 | 【推断】候选按通过率筛选 → **2/18 的偶然通过被读成「已修复」**；偶发性失效在批量生成下必然被误判，而人在跑挂 16 次后会知道「这事不对」 |
| **② 契约不在 API 表面**<br>【事实】[pypto#1935](https://github.com/hw-native-sys/pypto/issues/1935)（2026-07-02，closed）：`pl.spmd(24)` + 默认 hard `syncall` → 507018 挂死，**只把 24 改成 48**（910B 有 48 个物理 AIV 核）即 PASS。hard 走 FFTS 硬屏障，要求该核型**全部物理核**到达；而术语手册明确把「`spmd(48)` 就是同时启动 48 个核」列为常见误解 | 当时已写在 `tests/st/runtime/cross_core/test_syncall.py` 的 docstring 里 | 【推断】Agent 只继承**可检索到的**事实。按概念文档「N 是逻辑分片数」学得越对，这个 N 填得越错；且【事实】代价外溢——设备进入 draining／reset，该设备后续运行一律返回 `code 13` 直到重置 |
| **③ 查证路径被抽象收口切断**<br>【事实】[pypto#268](https://github.com/hw-native-sys/pypto/issues/268)（2026-02-26，closed）主动把 `MemorySpace` 去硬件化：`L1→Mat`、`UB→Vec`、`L0A→Left`、`L0B→Right`、`L0C→Acc`，并**主动否决了保留硬件名作为别名**。于是报错说 `Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)`，而官方文档说 L0B | 曾在枚举名里，**已被主动移除**；`65536` 来自后端 `GetL0bCapacityBytes()` | 【推断】Agent 拿到这条报错后**没有锚点**把 `Right` 对回「L0B / 910B / 64 KiB」——它要么瞎试，要么编一个归因。**修复回路空转** |

**一条可以单独成页的证据（若需要一张最锋利的图，用这个）**

- 【事实】#858 的量化对照：未修改 **2/18** 通过；把 `rope_cs` 上提（语义上完全是个 no-op，只改变它与谁重叠）后 **19/19** 通过。最后 8 组是候选与对照在**同一个 job 里交替运行**的，排除了会话与设备漂移。
- 【事实】提报人还记录了 6 条真机实测过的死路，并特别标注 `PTO2_RING_HEAP` 那一条：512 MiB 与 1 GiB 都通过，随后 1 GiB 又 **5/5 失败**——那两次通过是约 11% 基础通过率下的巧合。他的原话是「记录下来，因为这里的错误故事很诱人」。
- 【推断】**在 11% 通过率下做二分查找，每一个中间结论都可能是噪声。** 一个人类专家会察觉并先去建立「多少次通过才算通过」的统计判断；一个按「编译通过＋测试通过」推进的 Agent 不会——**它会把噪声当作信号，并据此继续迭代，整条推理链都建在上面。** 这是本大纲中 Agent 侧风险最具体的一处。

**一条行为证据（把 4.3 提到这里当证据用）**

> 【推断】开发者与 Agent 每现场写一个临时脚本，都是在标记标准工具链里的一个事实缺口。而这些脚本在算子场景下基本在干同一类事：翻 IR、数 buffer 占用、比对两次片上分配、把报错里的数字对回硬件参数——**正是上表第 ③ 类所在的位置。**

这让「依据不可得」不停留在推断，而是有可观察、可统计的行为痕迹。临时工具的分布，就是工具链缺口的分布。

**本页的两句收口**

1. 【推断】三类不可见有一个共同结构：**决定成败的那个事实，存在于编译器或运行时，而不存在于用户写的代码里，也不存在于用户能看到的任何产物里。**
2. 【推断】而 Agent 能读到的，恰好只有产物。

**抗质疑：为什么这不是「等模型变强就好了」**

- 【事实】#1935 的契约**当时已经存在**，只是不在用户写代码时会看到的地方；#268 的映射是被**主动删除**的。两条都说明问题出在**事实的放置位置**，不在模型的推理能力。
- 【外·一手】AgenticCANN 在 Ascend 910B 六个算子上的数据同向：知识注入把 elementwise 可行率从 57% 提到 86%——**提升来自知识的可得性，不是模型换代**；同时 fusion 可行率仅 56%，说明越难的算子越依赖可得的依据。

**建议画面：** 三行横向推进，每行三格：「用户看到的现象 → 那个事实在哪里 → Agent 介入后变成什么」。第三格统一用红色，形成一条视觉上的失效带。

**过门到 P5：** 既然依据是硬件事实与框架契约，那「要给用户可视化什么」就不再是一个开放问题——它等于：用户在做哪些决定，每个决定依赖哪条事实。

## P5｜要可视化的「决策」是什么：四类硬件决定

**页面要传达：「决策可视化」不是做面板，是把四类具体开发决定所依赖的事实、可改的项和验证方式显式化。**

**内容要点｜四类决定（取自仓内 O1–O4，不新造分类）**

| | 决定 | 用户要知道什么 | 可改什么 | 怎么确认 |
|---|---|---|---|---|
| **O1** | 面向 AIC／AIV 协同的**计算分工** | 哪段计算交给谁；切分是否保持归约与结果语义 | 计算区域、切分轴、分支有效 Tile | 编译映射 + 数值 + 目标耗时，而非核数或利用率 |
| **O2** | 面向片上存储的 **Tile 形态与资源** | 哪个空间受限、占用归属何处、改哪一层才对 | 分块、布局、物理形态、分配与生命周期 | 模型维度→分块→物理形态→分配→资源限制的整条关系 |
| **O3** | 面向 Cube／Vector 交接的**数据路径与融合** | 融合省掉了什么、又增加了什么 | 融合边界、中间 Tensor、搬运与转换 | 实际生成路径 + 占用 + 等待；相邻 ≠ 写回被消除 |
| **O4** | 面向多流水协同的**并行与同步** | 并行是否成立、等待来自哪里、哪块缓冲可复用 | stage、slot、事件、屏障参与者、buffer 生命周期 | 并发配置与空间需求同时核对；stage ≠ 物理槽数 |

**干预权落在哪里（回答 P3 的第二问）**

> 【推断】用户要干预的不是 Agent 的措辞或步骤，而是**它的硬件假设与实验口径**：上表「可改什么」四列 + 测哪些 shape、容差多少、哪台设备、与谁对照。这些才是干预的抓手。

**反面校准（本页必须说，否则会被一句话打掉）**

> 【推断】P4 的三类不可见，要的都不是更多硬件数字，而是**概念边界两侧的对照关系**。三者的解法分别是：让共驻成为一等对象、把契约放进签名与编辑期反馈、补一层可按需展开的映射（`Right` → L0B / 910B / 64 KiB / `GetL0bCapacityBytes()`）。
> **没有一条是「把硬件信息显示得更好」。**「加一个硬件可视化面板」答不了这三条。

**证据强度的诚实交代**

> 【事实】仓内结论：O1、O2、O4 已有具体技术产物或开发记录支撑；**O3 具有明确架构依据，真实融合决策任务的用户证据仍需补充。** 四类机会的证据不等强，也不要求一一对应独立页面。

**建议画面：** 四行表格即可，不要画成四个页面原型。重点让读者看到每一行的「用户要知道什么」都指向一条具体硬件事实，而不是一个泛泛的「可观测性」。

**过门到 P6：** 决策内容定下来之后，才能回答工具形态该怎么变——因为工具是这些依据的载体。

## P6｜载体：传统工具的形态变化

**页面要传达：工具不会被 Agent 替代，但它的读者变了——从「专家的探索工具」变成「人与 Agent 共用的证据源」。**

### 6.1 性能分析工具：仍在被使用，原因不是「AI 还不够强」

- **【建议改掉原表述】** 不要写成「复杂算子 AI 自动调优能力还不足，所以传统工具仍在用」——这把原因归给模型能力，评审必然追问「那等模型变强这页是否失效」，整条建设论证会被挂起。
- 【推断】**不会被替代的真实原因：调优的判据必须来自真机实测。** Agent 可以提出假设、组织实验、解释结果，但「在这台设备上到底快了多少」只能由测量给出。所以 AI 分析能力是**接在工具上的一层**，不是工具的替代品——这也解释了业界普遍给传统工具集成 AI 的动作：判据层与解释层本来就该分开。
- 【推断】真正的风险在这一层：**AI 分析若不能把结论连回硬件事实与测量条件，它只是把一个不可追溯的结论包装得更流畅、更可信。** 这是体验设计要防的事，不是要促成的事。
- 【事实】[pypto-lib#531](https://github.com/hw-native-sys/pypto-lib/issues/531)（2026-06-15）：看似两个 Vector 子块不均衡，实际有子块仅在等待握手；提报人需检查生成 PTO、按子块统计并构造最小实验才能区分有效计算与等待，并明确要求区分等待与计算。
- 【事实】[pypto-lib#828](https://github.com/hw-native-sys/pypto-lib/issues/828)（2026-07-24）：固定版本调优资料索引，含失败尝试与后续归因修正，提供同 session A/B 的口径方法。

### 6.2 过程可观测：要观测的是「硬件事实如何裁决了这次实现」

- 【推断】「可观测」若不限定内容就是万金油。要观测的不是更多日志，而是：这条约束是平台上限、是当前抽象的能力边界，还是一个可能算错的校验结果；泳道上这段占用是在算、在等，还是在同步。
- **判据只有一条：一条诊断能不能回到用户写的那一行。** 【内】回不到源码的诊断对人价值有限，对 Agent 价值更低——**Agent 无法用一个指向 IR 行的提示去改用户的代码。**
- 【事实】[pypto#1305](https://github.com/hw-native-sys/pypto/issues/1305)（2026-05-07）：报告 PH001 对不同存储空间的提示、计算依据与参数定位存在问题，提报人需逆向判断提示对应的内存空间、shape/dtype 与 chunk 常量，并核对不一致的字节数；无法把 IR 相对行号映射回 DSL。
- 【事实】[pypto#953](https://github.com/hw-native-sys/pypto/issues/953)（2026-04-10）：自动命名难表达区域意图，增删区域后名称变化影响对照。**当前校正**：`pl.at` 已有 `name_hint`，因此待建能力不应再表述为「缺少命名参数」，而是**名称与来源在编译、运行、profiling 之间的贯通**。

### 6.3 使用方式：直接调用小工具，与让 Agent 生成临时工具

- 【推断】这既是新用法，也是三件事：
  1. **一个诊断信号**——临时工具的分布就是标准工具缺口的分布，可统计、可排优先级；
  2. **一个设计输入**——反复被现场重造的那几个脚本，应被收编为一等能力；
  3. **一座桥**——它让「工具建设」这一页自己长出硬件话题（已在 P4 作为证据用过一次，此处回指）。
- 【推断】对应的产品问题：Agent 现场造的工具，其**结果口径与留存**如何进入证据链。一个临时脚本给出的数字，与 Toolkit 给出的数字，在验收面上不应等价呈现。

**建议画面：** 三栏，每栏统一三行结构「现在的现象 → 变化的实质 → 判据」。判据那一行要具体到可检查（例：诊断能否回到源码的那一行）。

**过门到 P7：** 三类载体的共同要求，可以收成三条可评审的设计主线。

## P7｜设计方向、验证方式与边界

**页面要传达：先建立可信的最小闭环，用真实任务验证，再扩展；并明确当前证据能证到哪里。**

**三条主线（取自仓内，映射到本汇报的页）**

| 主线 | 对应本汇报 | 最小可评审交付 | 成功判据 |
|---|---|---|---|
| **决策前可预判** | P4 ① ② + P5 | 自动化责任说明、约束预算、scope 改动影响预览 | 用户能说明改什么、为什么改、预期付出什么代价 |
| **失败后可追溯** | P4 ③ + P6.2 | 从诊断／trace 到源码与依赖的可检查证据链 | 用户能定位首发问题，并选择能验证判断的下一步动作 |
| **优化后可复用** | P6.1 + P6.3 | 绑定代码、环境、精度、性能与适用范围的实验记录 | 后续开发者能复现实验，并识别哪些条件变化需重验 |

**承载对象**

> 【建议】三条主线共用一套对象：**任务契约 → 候选 → 证据（IR / trace / 测量条件）→ 决策**，外加预算与接管。这是设计提议，不预设统一平台已存在；若不共用，会产出两套不互通的界面。

**建议的首轮验证任务（不预设改善百分比）**

- 【内】三个研究任务：**#1305 的诊断行动性、#531 的状态区分、#630 的 shape 变更决策**。选择依据是证据具体程度与任务可观察性，**不是发生率或商业价值排序**。
- 衡量指标：正确预测率、首次有效修改时间、无效实验次数、回归漏检数、证据可追溯性。
- 分组：新人、熟悉 PyPTO 的算子开发者、性能专家分别观察，避免把新人学习问题与专家控制需求混成同一种痛点。
- 【建议】可能触发死锁的历史案例（如 #1935）只做静态判断，不在共享设备上重演。

**边界与证据缺口（建议明写，不等评审问出来）**

1. **Agent 侧后果目前是【推断】。** P4 引用的三个案例全部是**人类开发者**的记录；仓库中尚无 Agent 在硬件事实不可见处失败的直接证据。本页主张依赖的是**机制**（Agent 只能读到产物、按通过率筛候选、不会卡住求助），不依赖发生率。
2. **补证动作（成本低、收益高）：** 拿 #268／#630 的真实报错让一个 Coding Agent 去修，记录它的归因与修改动作；再把 `Right → L0B / 64 KiB` 的映射注入上下文重跑一次对照。两次运行的差异即「映射缺失的代价」的直接证据，同时验证 P5 的「可展开映射」这一设计对象。
3. **GPU 研究不能直推昇腾。** KernelBench-Verified（修正基线后几何平均 1.43×→0.88×、28% 抬高峰值显存）与 KernelBenchX（46.6% 的「正确」kernel 慢于 eager、72% 的 Fusion 任务五种方法全失败、量化类 0/30）均基于 GPU 场景，只能用于说明「自称成功不可直接采信」这一命题，不能作为 PyPTO／昇腾的效果数据。
4. **历史问题不等于现状。** #1935 已关闭；`pl.at` 已有 `name_hint`；AutoTileMatmulL0 已覆盖特定静态二维 MatMul 的 L0 切分；官方文档已提供逻辑空间与昇腾物理空间的对应。应保留历史教训，但不把它们描述为今天完全未改进的状态。
5. **待核对：** [pypto#630](https://github.com/hw-native-sys/pypto/issues/630) 的开闭状态在仓内两份材料中不一致（[三张典型案例卡](./Hardware-Native_三张典型案例卡_20261104.md)记为 open，[全流程体验问题地图](./Hardware-Native_开发全流程体验问题地图_20261104.md)记为 Closed as not planned）。**汇报前请核实一次**；本大纲在引用时未依赖其状态。
6. **#1935 带 `[Bug]` 标签**是已知的判据争议点。若评审认为应按标签剔除，P4 第 ② 行需另找证据（见[真实问题筛选](./Hardware-Native_真实问题筛选与典型案例_20261104.md)附录 A.2）。

**建议画面：** 左侧三条主线，右侧对应的验证任务与指标；底部一条「当前证据到哪里 / 下一步补什么」的横条。

## 备用页｜预期质疑与应答

| 质疑 | 应答 |
|---|---|
| 「Agent 开源了、门槛降低了，怎么又说硬件复杂是重点问题？」 | P1 落脚句已回答：降低的是「写出来」的门槛，没有降低的是「判断对不对、够不够快」的门槛 |
| 「这些透明化能力，通用 Agent 产品以后不会做吗？」 | 【推断】通用方案做的是「过程可见」（思考链、工具调用、Diff），算子开发者需要的是「依据可见」。一般软件里两者差别不大（依据多在代码文本里），算子开发里差别是决定性的——依据是领域资产 |
| 「等模型变强不就解决了？」 | P4 抗质疑段：#1935 的契约当时已存在但不在用户视线内；#268 的映射是被主动删除的。问题在事实的放置位置。AgenticCANN 的 57%→86% 来自知识可得性而非模型换代 |
| 「P4 这三条都是 bug，修了就没了」 | 每条在[三张典型案例卡](./Hardware-Native_三张典型案例卡_20261104.md)都有反事实检验，明确标出哪一面剔除、哪一面保留；HNC-03 全部通过检验 |
| 「这些问题占比多少？」 | **不能回答。** 归档样本不支持频率推断，见 P7 边界第 1、4 条 |
| 「可视化具体做成什么样？」 | 本汇报到设计对象为止。P5 的反面校准已明确：要的是概念边界两侧的对照关系，不是硬件数字面板；具体形态需在首轮任务验证后出原型 |
