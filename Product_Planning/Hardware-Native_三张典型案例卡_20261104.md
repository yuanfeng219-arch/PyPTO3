## 一、这三张卡是怎么选出来的

### 1.1 入选判据

在[真实问题筛选](./Hardware-Native_真实问题筛选与典型案例_20261104.md)第二节的反事实检验之上，增加一条**双轴判据**：

> **只讲昇腾硬件事实解释不了这个问题，只讲 PyPTO 框架概念也解释不了。两者缺一不可。**

这条判据排除了两类常见但不适合立论的案例：纯硬件知识问题（查文档即可）、纯 API 易用性问题（与昇腾无关）。留下的是**硬件事实与框架概念在某个边界上错位**的那一类——这才是 Hardware-Native 作为体验设计方向的工作对象。

### 1.2 证据标注

沿用 Hardware-Native 系列的标注口径：

| 标注 | 含义 |
|---|---|
| 【事实】 | 可核对到 Issue 号与原文，或仓内源码/文档 |
| 【推断】 | 基于事实的判断，需进一步验证 |

本文所有【事实】均摘自 `github_issues/` 归档的 `body` 字段，未经改写。

### 1.3 索引

## 二、HNC-01｜共驻：决定成败的变量不在用户代码里

- **来源**：[pypto-lib#858](https://github.com/hw-native-sys/pypto-lib/issues/858)，2026-07-30 创建，**仍 open**
- **场景**：`models/deepseek/v4-pro/prefill_sparse_attn.py`，Ascend950（a5），单卡真机
- **角色与目标**：模型开发者把 DeepSeek V4-Pro 的 sparse attention prefill 跑通并稳定

### 2.1 现场

【事实】同一份 kernel 在 merged-main revision 上**18 次运行失败 16 次**。开发者第一眼看到的是调度器的分类结论：

```
sched_error_code=100 SCHEDULER_TIMEOUT
sub_class=S1:running-stalled (detail=1) completed=3/312 running=2 ready=0
  waiting=307 orch_done=1 stuck_task_id=4294967299 stuck_core=2
```

【事实】这些计数器是**后果**。真正的首发故障只能靠时间戳看出来：

```
20:06:30.583  kernel launch 前最后一行 setup
20:06:30.639  EZ9999 AICore exception      ← launch 后 56 ms
20:07:08.716  SCHEDULER_TIMEOUT            ← 38 秒后的计时器到期
```

【事实】每一次失败的运行都带第二个错误码，而**通过的运行一个都没有**：

```
errcode:(341) errorStr: The address for VEC to access UB is out of bounds.
subErrType: 0x4.
```

【事实】提报人还排除了一个假象：约 30 个核在几乎相同 PC 上打出的 `aicore error exception ... error code = 0` 是 drain 快照，不是 30 个独立故障——**只有 PC 落在不同区间（`0x1200000db458`）的那一个核真的在干活**。

### 2.2 两轴如何交叉

**硬件事实。**【事实】UB 是核级共享资源。两个 vector task 各自远在预算之内：

| task | Vec 占用 | a5 vector buffer |
|---|---:|---:|
| `merge_norm` | 98 816 B | 262 144 B（256 KB） |
| `rope_cs` | 98 304 B | 262 144 B |
| `gather_kv`（kernel 内最大，**从不出错**） | 132 096 B | 262 144 B |

容量数字来自 pto-isa `buffer_limits.hpp` 的 `PTO_UBUF_SIZE_BYTES`（`PTO_NPU_ARCH_A5`）。即便两者相加（197 120 B）仍在 256 KB 以内。

**框架概念。**【事实】[术语手册](./PTO3_源码_调度_硬件执行概念术语手册.md)第 5 节把 `logical block → physical core/core group` 的关系定义为「**N:M（按时间）**」，并明确「block 不永久占某个核；同一核会在不同时间执行多个 block」。

【推断】于是：**谁和谁共驻同一个物理核，是运行时决定的，用户代码里没有任何一个符号表达这件事。** `task` 本身也不是用户写出来的对象——它是编译与运行时的产物。

### 2.3 为什么两者缺一不可

只讲硬件：两个 task 都在预算内，按容量规则**不该出错**。
只讲概念：N:M 映射本身是正常的调度设计，**不会导致越界**。
只有把两者放在一起才成立：**UB 的预算是按单 task 校验的，而占用是按共驻累积发生的。**

### 2.4 最锋利的一句

【事实】原文：

> 编译器的片上分配在故障 build 与通过 build 之间**逐字节相同**（跨 `Vec` / `Acc` / `Left` / `Right` / `Mat`，逐函数比对），故障只随纯时序翻转，**所以 IR 里没有任何东西能区分这两种情况**。

【事实】GM 布局同样相同，`MemoryReuse` 与 `AllocateMemoryAddr` 之后的 IR 只差 SSA 重命名；每个 workspace tensor 保有自己的 `mem_ddr_*` ref，不存在别名差异。【事实】把 `runtime_cfg["log_level"]` 提到 `v0` 这一个动作，就能让未修改的 kernel 通过。

### 2.5 用户代价

| 对照 | PASS / 运行次数 |
|---|---|
| 未修改 | **2 / 18** |
| `rope_cs` 上提（#857 的 workaround） | **19 / 19** |

【事实】修法是把 `rope_cs` 这个块上提到 kernel 顶部，使它与 `gather_kv` 重叠而不是与 `merge_norm` 重叠——**语义上完全是个 no-op**。最后 8 组是候选与对照在同一个 job 里交替运行的，排除了会话与设备漂移。

【事实】提报人记录了 6 条全部在真机上实测过的死路，并特别标注 `PTO2_RING_HEAP` 那一条：512 MiB 与 1 GiB 都通过，随后 1 GiB 又 **5/5 失败**——那两次通过是约 11% 基础通过率下的巧合。他的原话是「记录下来，因为这里的错误故事很诱人」。

【推断】**在 11% 通过率下做二分查找，每一个中间结论都可能是噪声。** 这是本案最被低估的成本：开发者不仅要排查，还要先建立「多少次通过才算通过」的统计判断。

【事实】提报人连归属都无法确定，并在开头说明了理由：

> 提交在这里而不是 pto-isa，因为我还不能把它归到某个具体层，**我不想让任何人去追错的仓库。**

### 2.6 反事实检验

| 面 | 裁定 |
|---|---|
| 越界故障本身 | 大概率是某一层的实现缺陷，修复后消失 → **剔除** |
| 用户无法预知共驻关系 | task → core 的 N:M 映射是设计属性，框架完美工作时依然成立 → **保留** |
| 诊断用调度层词汇描述设备层故障 | 分层设计问题，不是文案问题 → **保留** |

【事实】第二条有提报人自己的证词：

> 如果 `S1:running-stalled` 能提一句 stall 期间记录到的任何 AICore exception，或者提示行能说「先 grep `errcode:(`」，会帮上很大的忙。**按现在的写法，它笔直地指向依赖分析。**

### 2.7 设计含义

【推断】三条，按优先级：

1. **共驻必须成为一等可见对象。** 泳道需要能表达「同一时刻哪些 task 在同一个核上」，而不只是时间轴上的条块。今天这个维度在任何产物里都不存在。
2. **首发故障必须压过后续超时与 drain 噪声。** 本案的证据层级是：设备层 errcode(341) → 调度层 SCHEDULER_TIMEOUT → drain 快照。现有输出把第三层展示得最充分、第一层最隐蔽。
3. **预算校验的口径需要和占用的发生方式对齐。** 单 task in-budget 不等于运行时安全，而用户只能看到前者。

## 三、HNC-02｜逻辑并行度 ≠ 物理核数

- **来源**：[pypto#1935](https://github.com/hw-native-sys/pypto/issues/1935)，2026-07-02，closed
- **场景**：Ascend 910B，`a2a3` target，ptoas 0.48
- **角色与目标**：算子开发者在 SPMD kernel 中插一个跨核屏障

### 3.1 现场

【事实】用户写下的是这两行：

```python
pl.system.syncall(core_type="aiv_only")   # 默认 hard 形式
with pl.spmd(24):                          # 910B 有 48 个物理 AIV 核
```

【事实】结果：

```
[ERROR] sync_run_streams: aclrtSynchronizeStreamWithTimeout (AICPU) failed: 507018
[ERROR] recover_device_or_mark_unusable: AICore error 507018:
        bounded device drain failed (force reset will follow in finalize)
RuntimeError: run_prepared failed with code 507018
```

【事实】对照干净得像一份规格：`pl.spmd(24)` → 507018；**只把 24 改成 48** → PASS。原文结论是「占用率是唯一变量」。

### 3.2 两轴如何交叉

**硬件事实。**【事实】hard 形式走 FFTS 硬屏障（`SYNC_AIV_ONLY_ALL` / mix），等待**每一个**该核型的物理核到达；未启动的核永远到不了，FFTS wait 永不完成。

**框架概念。**【事实】`pl.spmd(N)` 的 N 是**逻辑 block 数**。[术语手册](./PTO3_源码_调度_硬件执行概念术语手册.md)第 10 节把这一点直接列为常见误解：

| 容易说错 | 应改为 |
|---|---|
| 「`spmd(48)` 就是同时启动 48 个核。」 | 「`spmd(48)` 产生 48 个 logical block；实际是否同波执行取决于可用资源和调度。」 |

### 3.3 为什么两者缺一不可

【推断】这里有一个很别扭的局面，也是本案最值得在汇报里讲的一点：

> **框架正确地教会用户「N 是逻辑分片数，不要理解成物理核数」，而 hard syncall 恰恰要求用户按物理核数来填这个 N。**

一个按概念文档学得越认真的用户，越不会想到去数物理核。只讲硬件解释不了为什么用户会填 24；只讲概念解释不了为什么填 24 会挂死。

### 3.4 契约在哪里

【事实】两种模式的硬件前提完全不同：

| 模式 | 机制 | 硬件前提 |
|---|---|---|
| `hard`（默认） | FFTS 硬屏障 | **要求该 `core_type` 的全部物理核都到达** |
| `soft` | 共享 GM workspace 轮询 | 支持部分占用，需 `gm_workspace`、`used_cores` |

【事实】两者共用一个函数名和近似的参数表。而这条契约当时**已经**写在 `tests/st/runtime/cross_core/test_syncall.py` 的 docstring 里——原文确认「其 docstring 已经记录了 hard SYNCALL 需要满 AIV 占用」。

【推断】**知识存在，但不在用户写代码时会看到的地方。**

### 3.5 用户代价

【事实】挂死不只影响这一次运行：

> 设备之后处于 draining/reset 状态，**该设备上后续的运行都返回 `code 13` 直到重置**。

【推断】在共享开发设备上，一次失误的影响范围超过提报人本人。这是本案与 HNC-01、HNC-03 不同的一点：**代价会外溢到他人。**

### 3.6 反事实检验

| 面 | 裁定 |
|---|---|
| 「编译器应该加静态占用检查」 | 可修缺陷，修完这个具体错误不再发生 → **剔除** |
| 「一个接口承载两套硬件前提、前提不在签名里」 | 即便加了检查，用户仍要在写代码时决定用哪个模式，而决定所需信息不在手边 → **保留** |

【事实】这与[真实问题筛选](./Hardware-Native_真实问题筛选与典型案例_20261104.md)第 3.1 节对 #1935 的裁定一致（保留，重构叙事）。该文附录 A.2 也指出这是判据应用上最可争议的一处——**若评审认为应按 `[Bug]` 标签一并剔除，本卡需另找证据。**

### 3.7 设计含义

【推断】

1. **硬件契约应进入类型、签名或编辑期反馈**，而不是文档与测试文件。这是 API 设计与编辑器集成问题。
2. **前提不同的两种机制不应共用一个函数形态。** 原文建议的报错文案本身就是一份好的契约表达：
   > `hard pl.system.syncall(core_type="aiv_only") requires the spmd launch to fill all 48 AIV cores, but pl.spmd(24) launches 24 blocks. Use mode="soft" (GM-polling) for partial occupancy.`
3. **检查与契约是两件事。** 检查把失败从运行期移到编译期；契约表达让用户一开始就选对。前者是兜底，后者是设计。

## 四、HNC-03｜抽象收口把查证路径一起删掉了

- **来源**：[pypto#268](https://github.com/hw-native-sys/pypto/issues/268)（`[Feature]`，2026-02-26，closed）+ [pypto#628](https://github.com/hw-native-sys/pypto/issues/628) / [#630](https://github.com/hw-native-sys/pypto/issues/630)（`[Discussion]`，2026-03-19，#630 **open**）
- **角色与目标**：算子开发者在 910B 上写 MLA / MatMul 类算子

### 4.1 现场

【事实】开发者拿到这条报错：

```
Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)
```

要弄清 `65536` 是什么，他需要知道 `Right` = L0B = Ascend910B 上 64 KiB 的矩阵右操作数缓冲，数字来自后端参数 `GetL0bCapacityBytes()`。

【事实】**但这条映射不在任何用户可见的地方**：报错说 `Right`，昇腾官方文档说 `L0B`。

### 4.2 两轴如何交叉

**框架概念（第一层）。**【事实】#268 **主动**把 `MemorySpace` 枚举从昇腾硬件名改为去硬件化的逻辑名：

| 旧名 | 新名 | 含义 |
|---|---|---|
| `L1` | `Mat` | Matrix / L1 buffer |
| `UB` | `Vec` | Unified Buffer / 向量操作数暂存 |
| `L0A` | `Left` | 左矩阵操作数 |
| `L0B` | `Right` | 右矩阵操作数 |
| `L0C` | `Acc` | 累加器 |

【事实】原文给出的三条理由都成立——更可移植、更可读、更可维护；并把现状称为「将低层微架构细节泄漏进 IR 抽象层」（*leak low-level microarchitecture details into the IR abstraction layer*）。【事实】原文**考虑过保留硬件名作为别名，但主动否决了**，理由是增加维护负担和混淆。

**框架概念（第二层）。**【事实】#628 指出 PTO 2.0 提供 tile shape 声明接口、3.0 取消了。其列举的第三条用户代价是最关键的一句：

> **为了避免 tile 溢出 UB，开发者有时需要自己调整代码结构，增加 loop 层级。**

【事实】#630 给出触发条件：`kv_lora_rank` 从 128 改到 512。**模型配置一变，代码结构就得跟着改。**

**硬件事实。** L0B = 64 KiB、UB 容量上限——这些是裁决编译能否通过的硬约束。

### 4.3 为什么两者缺一不可

【推断】只讲硬件：容量不够就缩 tile，是个普通的工程动作。只讲概念：命名更干净、控制更细，都是收益。

两者交叉后才出现真正的代价：**硬件约束仍然在裁决，但用户失去了把工具的词汇对回硬件事实的路径。** 当抽象泄漏被消除时，查证路径也被一起消除了。

### 4.4 一条附加证据：报错文本本身无法区分责任

【事实】[真实问题筛选](./Hardware-Native_真实问题筛选与典型案例_20261104.md)第 3.3 节指出：一条写着 `Right buffer usage exceeds platform limit` 的 Issue，既可能是 #630（设计），也可能是 #626（校验器算错）——**两者报错文本几乎相同**。

【推断】这意味着**用户拿到这条报错时，无法判断自己该缩 tile、该改代码结构，还是该提 bug**。注意：#626 本身按反事实检验已被剔除，此处只用它说明报错文本的信息量不足，**不重建两者的对照关系**（该对照已按第 7.2 节要求废弃）。

### 4.5 用户代价与一个值得注意的时序

【事实】#628 的提报人想要的解法是**减少**暴露，而不是增加：

```python
@pl.tile_policy(shape=[128, 512, 128])
def my_matmul(lhs, rhs):
    # 框架根据 policy 自动生成循环结构
```

【事实】时序：#268 的重命名创建于 **2026-02-26**，#628 与 #630 撞上 `Right buffer usage ... exceeds platform limit` 是在**三周后的 2026-03-19**。

【推断】两者由不同的人提报，重命名也不是报错的原因，**这不构成因果证明**。但它说明抽象决策与用户查证成本之间的距离可以很短。

### 4.6 反事实检验

全部通过。#268 是一次**已执行**的架构决策（closed 意味着重命名已生效，映射断裂是当前状态而非历史问题），不是能力请求；#630 的提报人问的是「PTO 3.0 取消 tile shape 设置的设计初衷是什么？是否考虑过上述易用性问题？」——这是设计讨论，不是缺陷报告。

### 4.7 设计含义

【推断】

1. **去硬件化的抽象需要配一层可按需展开的映射**：`Right` 能一跳查到「L0B / Ascend910B / 64 KiB / 来自 `GetL0bCapacityBytes()`」。抽象让日常工作更干净，映射让排查时能落回硬件。两者不冲突，但必须被设计——**它不会自动存在。**
2. **报错需要携带责任指向**：这条约束是平台上限、是当前抽象的能力边界，还是一个可能算错的校验结果。
3. **不存在「该暴露多少硬件」的最优刻度。** #268 隐藏硬件名、#630 隐藏切分决定，方向相反、理由都正当、都产生了用户代价。要设计的是两件事：**抽象在哪里收口，以及收口之后用什么补偿查证能力。**

## 五、三张卡的共同结构

【推断】把三条并排看，共同点不是「硬件太难」，而是：

> **决定成败的那个事实，存在于编译器或运行时，而不存在于用户写的代码里，也不存在于用户能看到的任何产物里。**

| 卡 | 那个事实 | 它在哪里 |
|---|---|---|
| HNC-01 | 两个 task 共驻同一物理核 | 运行时决定；**连 IR 都不区分** |
| HNC-02 | hard barrier 要求满占用 | 测试文件的 docstring |
| HNC-03 | `Right` = L0B = 64 KiB | 曾在枚举名里，已被主动移除 |

【推断】而这三个事实的「不可见」，都恰好发生在一个**框架概念的边界**上：task → core 的映射边界、逻辑 block 与物理核的语义边界、MemorySpace 的命名边界。

**这解释了为什么「加一个硬件可视化面板」答不了这三条**——它们要的不是更多硬件数字，而是概念边界两侧的对照关系。三条的解法分别是：让共驻成为一等对象、把契约放进签名、补一层可展开映射。**没有一条是「把硬件信息显示得更好」。** 这与[真实问题筛选](./Hardware-Native_真实问题筛选与典型案例_20261104.md)第六节洞察一同向。
