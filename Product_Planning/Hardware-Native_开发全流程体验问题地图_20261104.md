# Hardware-Native 开发全流程体验问题地图

> 日期：2026-11-04  
> 面向：昇腾模型／算子开发工具 UX、产品与框架团队  
> 范围：从学习与方案判断，到算子实现、运行验证、性能调优、模型集成与回归。沿用八阶段口径；环境与版本准备贯穿各阶段。  
> 核心问题：硬件约束与 PyPTO 抽象如何影响开发者的决策、验证和返工？

## 1. 阅读方式与证据口径

**这张地图区分“问题有真实报告”“技术机制有依据”“当前用户仍受影响”三个不同结论。**

| 标记 | 含义 | 可以支持什么 | 不能支持什么 |
| --- | --- | --- | --- |
| **实：已核实案例／反馈** | 已阅读原始 Issue 正文，核实其中的场景、报告现象或需求 | 某个版本、场景确实有此反馈；有原文记录的排查或变通动作 | 本轮独立复现、所有开发者都会遇到、当前版本仍未修复 |
| **机：已核实机制** | 当前官方文档明确描述的行为或约束 | 此类决策确实存在；解释案例可能涉及的技术背景 | 单凭机制证明用户困惑、量化时间损失、确定个案根因 |
| **假：待验证假设** | 从机制和案例推导的体验问题、影响范围或设计收益 | 形成用户研究问题和原型验证任务 | 写成已经证实的用户结论或性能收益 |

“已验证问题”在本图中限定为**有可追溯原始反馈的问题**，不等于完成了真机复现。表中所有 UX 设计机会均为建议，收益待验证。没有测得的时间、发生率、普遍性和情绪不作量化。

根因分为 **硬件约束、框架抽象、诊断／工具表达、实现缺陷**。一个案例可以涉及多类；历史 bug 只证明当时的失败，不能自动证明其为硬件固有问题。片上容量、执行单元和指令支持均须绑定具体目标设备，不能把一个型号的数值泛化到所有昇腾。

## 2. 开发全流程体验问题地图

**学习与方案判断 → 算法拆解与切分 → 编码与内存组织 → 融合与任务划分 → 编译与错误处理 → 运行与正确性验证 → 性能调优 → 集成、迁移与回归**

这是一条存在回路的流程：编译失败常返回切分和内存组织；精度失败常返回执行边界与依赖；性能结果会推动再次融合或拆分；集成问题可能反过来修改算子接口。

| 阶段／核心体验问题 | 具体开发场景 | 硬件或框架根因 | 开发者付出的代价 | 真实案例证据与验证边界 | UX 设计机会（建议） |
| --- | --- | --- | --- | --- | --- |
| **① 学习与方案判断：概念与责任边界难建立** | 从 PyTorch 或已有算子迁移；选择 Tensor／Tile 表达；判断计算该放在 InCore、编排函数还是其他 scope；对照新旧教程。 | **机·框架抽象：**数学计算、执行位置、运行顺序分别建模；InCore 执行区域与 runtime scope 不是同一种边界。**实·历史接口设计：**曾有多套表达 placement 的命名。[D1][D2] | **实：**#879 指出需要记忆不同命名并查阅分散文档。**假 H1：**用户会把源码顺序当成设备执行顺序，或把 InCore 当成固定单个物理核，因此反复试错、求助。 | **pypto #879，2026-04-07：**统一 `incore/auto_incore/at` 的提案明确指出命名和文档负担；本轮读取本地原始归档，在线获取超时。[E1] 当前文档已统一解释 placement；不能把历史三套入口描述为今日完全未改进的状态。**验证程度：有历史设计反馈；当前误解类型与频率待测。** | 在用户所写代码旁解释“计算什么／在哪里执行／依赖谁”；按框架版本提供术语迁移对照；展示当前由编译器、运行时和用户分别负责的事项。以代码理解任务验证，避免只测术语背诵。 |
| **② 算法拆解与切分：模型参数变更传导为实现重构** | 增大 attention 的维度、RMSNorm 的归约长度或 batch；原实现出现容量错误，需要决定 M/N/K 等维度如何切分。 | **机·硬件约束：**各片上空间有容量与布局限制。**框架抽象：**自动切分有支持范围；手动 L0 操作数不会被无条件重新切分。[D3] | **实：**#630 报告调整配置后需要增加循环；#628 描述手写切分及跨块归约。**假 H2：**当前用户仍难预判自动化边界，导致多轮“改 chunk—编译—失败”。 | **pypto #630／#628，2026-03-19：**`kv_lora_rank` 从 128 增到 512，报告 Right buffer 所需 98,304 B 超过该案例 65,536 B 限制。[E2] #630 当前为 Closed as not planned；这不是已修复证明。当前已有 AutoTileMatmulL0，不能宣称“现在全部 MatMul 都靠手切”。**验证程度：历史返工有反馈；当前残留范围待测。** | 输入 shape/dtype/目标设备后标出自动切分适用性；区分逻辑 shape 与物理 footprint；指出哪个参数触发哪项约束；给出候选切分及其内存／任务数影响，保留用户覆盖入口。 |
| **③ 编码与内存组织：逻辑数据难对应物理资源和搬运** | 把 MatMul 接到向量计算；选择 Vec、Mat、Left、Right、Acc；处理非整块输入、padding 和有效区域；尝试扩大 tile。 | **机·硬件约束：**多个存储空间不是同一缓存的嵌套；合法搬运路径不同；分配 shape 与有效 shape 不同。[D4] **诊断表达：**资源名、数据路径和用户可调常量之间需要对应。 | **实：**#1305 提报人需逆向判断提示对应的内存空间、shape/dtype 与 chunk 常量，并核对不一致的字节数。**假 H3：**在编辑期缺乏可追溯预算，会导致先凭逻辑 shape 估算、失败后再查编译产物。 | **pypto #1305，2026-05-07：**报告 PH001 对不同存储空间的提示、计算依据和参数定位存在问题。[E3] 这证明当时的提示可解释性问题，不证明所有报告数值都源于硬件本身。当前官方已列出 `Right=L0B`、`Vec=UB` 等映射，不能声称没有映射文档。**验证程度：历史诊断反馈＋当前内存机制；编辑期认知成本待测。** | 联动“源码值 → 物理空间 → 数据通路 → 分配与生命周期”；标注估算、编译确定和实测数据；显示容量计算所用的 shape/dtype/布局及预留项；使每项资源占用可回到对应代码。 |
| **④ 融合与任务划分：一个边界牵动多项成本** | 合并两个 InCore 区域；将 chunk 循环移到核内；把 MatMul 与向量后处理融合；改变跨核切分方式。 | **机·硬件与调度：**减少任务可节省下发成本，数据留片上可减少搬运，但粒度增大可能减少并行，融合可能增加片上压力。[D5] **历史框架抽象：**显式 load/store 与 scope 边界耦合。 | **实：**#188 描述调整边界时需移动 load/store 并重新检查一致性；#828 记录任务粗化、切细及融合／反融合实验。**假 H4：**用户无法在改动前判断多项成本变化，只能反复编译和测量。 | **pypto #188，2026-02-13：**提出自动插入数据搬运以降低改 scope 成本。[E4] **pypto-lib #828，2026-07-24：**提供固定版本调优资料索引，包含失败尝试与后续归因修正。[E5] 当前 Tensor 层可自动插入搬运，不能泛化为每次改 scope 都必须手改 load/store。**验证程度：历史耦合反馈＋真实实验记录；当前试验成本待测。** | 预览修改前后的任务图、并行工作量、中间搬运与内存峰值；把“合并／拆分”的收益和代价一起展示；同时保存代码、编译结果、精度和性能对照；不承诺融合一定更快。 |
| **⑤ 编译与错误处理：诊断难转成具体修改动作** | 收到 `<string>:行号`、生成的 InCore 名称、容量错误或重复性能提示；需要找回原始 slice、scope 和可调参数。 | **机·编译机制：**源码经过 outlining、展开和 AIC/AIV 拆分形成多个产物。**实·诊断／工具表达：**来源映射、名称稳定性与提示去重不足会阻断追溯；其中可包含实现缺陷。 | **实：**#1305 报告无法把 IR 相对行号映射回 DSL；#953 提出自动命名难表达区域意图、增删区域后名称变化影响对照。**假 H5：**多数定位时间消耗在重建映射，而非决定修复方法。 | **pypto #1305** 提供具体提示与追溯困难；**#953，2026-04-10** 提出可命名区域的需求。[E3][E6] 当前 `pl.at` 已有 `name_hint`；不再以“缺少命名参数”定义待建能力。**验证程度：历史反馈明确；当前跨产物映射覆盖和耗时待测。** | 每条诊断提供原始代码、生成对象、触发约束、计算依据与候选改法；重复实例聚合但可展开；保留稳定区域身份；源码位置不可用时明确显示证据缺失，避免伪精确定位。 |
| **⑥ 运行与正确性验证：难区分数值变化、执行错误和同步问题** | 开启 split 后输出漂移；手动接管依赖；减少 SPMD 参与数量后超时；需要判断该改算法、依赖还是验收标准。 | **机：**数值顺序与 dtype 会影响结果；MANUAL scope 关闭自动依赖跟踪，遗漏边可能产生竞争。[D2][D6] **历史硬件契约／实现缺陷：**特定 hard syncall 要求全核参与，当时缺少静态检查。 | **实：**#362 记录拆 scope、换 split、缩 chunk 的排查和变通；#1935 记录超时及后续设备恢复影响。**假 H6：**开发者因无法分类异常而放弃可行优化，或用放宽容差掩盖真实错误。 | **pypto-lib #362，2026-05-23：**报告约 1 ULP BF16 漂移，但“归约顺序导致”在原文仍是假设，性能代价也未测。[E7] **pypto #1935，2026-07-02：**记录部分占用下硬屏障超时；当前已关闭。[E8] **验证程度：报告现象与排查动作有据；#362 个案根因未确认，不能写成合法漂移定论。** | 关联首个差异 tensor／首发异常、输入和版本；分别展示数值容差、依赖证据和同步前提；切换 MANUAL 时预览失去的自动保障；将可静态判定的同步错误前移；不自动放宽精度标准。 |
| **⑦ 性能调优：看到耗时，却难判断可行动的瓶颈** | 泳道上两个 Vector 子块时长不一致，或核心存在空白；决定是调 tile、split、依赖还是任务粒度。 | **机·执行机制：**占用时段可能包含计算、等待和同步。**实·工具表达：**把不同状态绘成相同条形会误导解释；仅凭空白无法判定调度供给不足。 | **实：**#531 提报人检查生成 PTO、按子块统计并构造最小实验，才区分有效计算和握手等待。**假 H7：**状态不清会让开发者选择错误优化方向，显著增加无效实验。 | **pypto-lib #531，2026-06-15：**记录看似双 Vector 不均衡，实际有子块仅等待的案例，并明确要求区分等待与计算。[E9] #828 补充同 session A/B 与归因修正方法。[E5] **验证程度：特定版本误读与排查过程有报告；当前工具覆盖范围、普遍发生率待测。** | 区分计算、等待、同步、已就绪未下发；显示每项判断的数据来源；采集不足时标“未知”，不由条形长度猜测 busy；从等待事件连到生产者、依赖边和源码；锁定 A/B 测量口径。 |
| **⑧ 集成、迁移与回归：局部成功难转成明确适用范围** | 将固定 shape 算子接入 packed prefill；使用非整 tile token 数；迁移目标设备或升级工具链；判断优化可复用范围。 | **机·框架与接口抽象：**物理容量、逻辑有效长度和请求边界是不同信息。**实·历史接口设计：**固定 T 与 num_tokens 并行存在，调用者维护一致性。硬件对齐需求不能直接等同于公共接口必须固定形状。 | **实：**#766 描述为适配子算子而循环、padding、重复 guard 与手动维护两份长度；#34 提出跨仓重复维护版本。**假 H8：**shape/设备迁移时缺少适用性记录会导致优化被误复用；具体回归时间待测。 | **pypto-lib #766，2026-07-13：**动态 packed-prefill 接口需求有详细现状与验收场景。[E10] **#34，2026-03-23：**共享环境版本清单需求；它是通用工程辅助证据，不单独论证硬件特有性。[E11] **验证程度：历史接口与维护负担有反馈；跨硬件迁移代价缺直接案例验证。** | 为实现保存 shape/dtype/硬件/版本与验证覆盖；区分容量、有效长度和请求元数据；自动生成整块／尾块、变长／多请求回归矩阵；在变更时指出需重验的假设。 |

## 3. 当前能力校正：避免把历史问题写成现状

1. **Tiling：**当前 AutoTileMatmulL0 已覆盖特定静态二维 MatMul 的 L0 切分。保留“自动化边界能否被用户理解”的问题，删除“所有 MatMul 都必须手切”的概括。[D3]
2. **内存术语：**当前官方文档已经提供逻辑空间与昇腾物理空间的对应。要验证的是用户能否在任务中找到并使用映射，而不是假定映射不存在。[D4]
3. **命名与定位：**当前 `pl.at` 有 `name_hint`。应评估名称和来源在编译、运行、profiling 中的贯通，而不是重复提一个已经存在的参数。[D1]
4. **依赖：**当前文档明确说明 MANUAL scope 接管依赖的责任；文档存在不等于用户能够正确运用，也不等于仍然缺少文档。[D2]
5. **同步：**#1935 已关闭，当前执行位置文档也要求 hard syncall 的 launch 数量按设备能力确定。保留其历史教训，不把相同运行失败当成已确认的现存 bug。[D1][E8]
6. **数值：**#362 只支持“报告了漂移且实施了排查／变通”；其归因与收益应继续标为未知。[E7]

## 4. 待验证假设与观察任务

将新人、熟悉 PyPTO 的算子开发者、性能专家分组观察，避免把新人学习问题和专家控制需求混成同一种痛点。以下任务以目标版本和固定设备为前提；可能触发死锁的历史案例仅做静态判断，不要求在共享设备上重演。

| 假设 | 验证任务 | 记录什么 | 什么结果会削弱或否定假设 |
| --- | --- | --- | --- |
| H1：不同 scope 的责任容易混淆 | 给出执行区域、runtime scope 和依赖代码，请参与者预测执行位置与先后关系，再修改一处边界 | 首次预测正确率、查文档次数、误解类型、角色差异 | 多数目标用户能正确预测，且错误主要来自其他语法问题 |
| H2：自动切分边界难预判 | 给一组自动切分可处理和手动 L0 配置案例，扩大 shape 后先预测再编译 | 是否识别覆盖范围、有效改动前的实验轮次、返工代码范围 | 用户能稳定识别边界；主要失败来自未支持能力而非理解 |
| H3：逻辑值到物理预算的映射负担高 | 解释同一 tensor 在两种布局／融合方式下的占用，以及一个尾块的有效区域 | 预测与编译结果差异、查找路径、是否区分估算与确定值 | 现有工具已经足以快速、准确完成任务 |
| H4：scope 修改的耦合后果难判断 | 在等价计算上选择核内循环、拆分或融合；先写预测，再做同口径实验 | 任务数、并行度、搬运和内存变化的预测准确率；实验次数 | 用户能正确解释主要取舍；实际成本主要来自编译耗时 |
| H5：诊断追溯比修复决策更耗时 | 从匿名化真实错误／提示定位到可修改的参数 | 从诊断到源码、到假设、到有效修改各阶段时间；跨文件跳转次数 | 追溯已很快，主要时间用于算法重构；不支持原先优先级 |
| H6：异常分类不清阻碍优化 | 对已标定的数值差异、缺依赖和同步前提错误进行分类；给出下一步验证 | 分类正确率、错误放宽阈值次数、首次差异定位路径 | 用户能借助现有诊断稳定分类，问题集中在别的环节 |
| H7：泳道状态歧义导致错误调优 | 用带真值注释的 trace 比较现有视图与状态分解视图 | 瓶颈判断正确率、证据质量、所选实验能否验证判断 | 新视图没有改善决策，或现有工具已能提供相同证据 |
| H8：适用范围缺失导致优化误复用 | 把实现迁移到非整块输入／新版本；有设备条件时再加入跨硬件任务 | 漏验条件、接口不一致、重建环境动作、首次回归定位时间 | 现有 CI／元数据已覆盖；跨硬件风险并非主要来源 |

衡量设计收益时，优先比较：**正确预测率、首次有效修改时间、无效实验次数、回归漏检数、证据可追溯性**。本图不预设改善百分比。

## 5. 可形成设计课题的三条主线

| 主线 | 覆盖阶段 | 最小可评审交付 | 成功判据 |

| **决策前可预判** | ①②③④ | 自动化责任说明、约束预算、scope 改动影响预览 | 用户能说明改什么、为什么改、预期付出什么代价 |
