## 摘要

昇腾上写一个算子，计算怎么写只决定了一半。另一半是：这段数据放哪块片上空间、切多大、谁来算、什么时候交接。这半边的规则来自硬件，写在编译器的校验里、后端的容量表里、ISA 的契约里——**但它进入开发者视野的方式，通常是一条编译失败或一次设备超时。**

本文从仓库的真实开发记录出发，得到三个结论：

**第一，硬件事实已经在报错里了，缺的不是信息量，是归因。** PyPTO #2287 的报错明确告诉开发者"UB 用了 213,760 字节、上限 188,416、前 131,072 字节是跨核管道预留"，还给了两条修复建议。两条建议都是错的——真正的问题是编译器把 C2V 方向的缓冲按双向最大值算了，16 KB 的载荷占了 128 KB 的坑。开发者按提示缩小 Tile，是在为编译器的 bug 付出性能代价。

**第二，最贵的一类问题，是本可以静态检查却留到设备上暴露的。** PyPTO #1935 中，hard 模式的 `syncall` 要求 SPMD 启动填满该核型的全部物理核。开发者在 48 个 AIV 的 910B 上启动了 24 个 block，结果是 AICore 507018 超时、设备被强制 reset、后续任务一并失败。编译器同时掌握 `pl.spmd(24)` 和"该 SoC 有 48 个 AIV"这两个数字，这个错误完全可以在编译期拒绝。这条知识当时已经写在仓库的测试文件 docstring 里。

**第三，这个方向的难点不是"给用户看更多硬件"，而是定清楚哪些硬件复杂性不该让用户看见。** PyPTO #630 记录了 PTO 2.0 到 3.0 的一次抽象退化：2.0 里开发者只需 `set_cube_tile_shape([M, K, N])`，框架自动生成循环；3.0 取消了这个接口，模型维度一变，开发者就得手写多层分块循环。提报人直接要求恢复一个声明式的 tile 策略接口。这是典型的 Hardware-Native 问题，而它的答案是**减少**暴露，不是增加。

在此之上，本文给出一套单一分类（第四部分：按"谁来决定"的四个责任层 × 四类决策对象）、七条从案例反推的设计要求（第五部分），以及一个可以证伪这个方向的验证计划（第七部分）。

本文还包含一个反面教材：既有研究材料据 CSA 编译产物断言"第二个 AIV 没有分摊有效计算"。本轮核对发现这个读法站不住（见 3.5 节）。这恰好说明——**不借助正确的工具去读硬件事实，连研究者自己都会读错。**

# 第一部分：昇腾硬件到底长什么样

这一部分是给 UX 同事的背景。读完应当能看懂后面案例里的每一个数字。所有内容来自仓库对 `repo/pto` 源码、头文件与开发者文档的整理。

## 1.1 八个内存空间，和一条不能绕的路

PyPTO 把昇腾的存储抽象成 `MemorySpace`。这不是一个层级缓存结构，而是**一组用途固定的专用空间**——这是和 GPU 最大的心智差异。

| PyPTO 空间 | 硬件 | 用途 | Ascend910B 容量 |
|---|---|---|---:|
| `DDR` | 片外 GM | 输入输出 Tensor | — |
| `Vec` | UB 统一缓冲 | Vector 计算、普通 Tile load | 188,416 B 有效 |
| `Mat` | L1 / CBUF | Cube 操作数暂存、矩阵中间结果 | 512 KiB |
| `Left` | L0A | Matmul **左**操作数 | 64 KiB |
| `Right` | L0B | Matmul **右**操作数 | 64 KiB |
| `Acc` | L0C | Matmul 累加器 | 128 KiB |
| `Bias` | Bias 缓冲 | Matmul bias | — |
| `ScalarLocal` | 标量寄存器 / C 栈 | `ArrayType` | — |

两条基本规则：`TensorType` 恒定表示 DDR 数据；`TileType.memory_space` 是片上位置的唯一来源。

**关键约束：`tile.load` 不能直接把数据放进 `Left`、`Right` 或 `Acc`。** 必须走：

```
DDR → Vec / Mat → Left / Right / Acc
```

所以一次 matmul 的操作数至少经过两跳。编译器会在 `InferTileMemorySpace` 阶段读取算子注册表的输入约束，发现生产者只给到 `Vec` 而 matmul 需要 `Left`/`Right` 时，**自动插入** `tile.move`。这个自动插入就是后面案例里"开发者看不懂占用从哪来"的源头之一。

记住这三个数：**Left 64 KiB、Right 64 KiB、Acc 128 KiB。** 第三部分的两个案例都卡在 Right 的 65,536 字节上。

`Vec` 的 188,416 B 来自 #2287 报错原文中编译器报告的 platform limit。若物理 UB 为 192 KiB（196,608 B），差额恰为 8,192 B，与另一份记录中"约 184 KB 可用、8 KB 保留"的推测吻合（此处 192 KiB 为推断，本轮未独立核实）。**这解释了一个重要现象：面板上"没超过名义容量"的绿条，完全可能已经越过了实际可用预算。**

## 1.2 Tile 不是 Tensor

Tensor 是逻辑数据，Tile 是它在片上的物理分块表达。两者之间隔着一组参数，每一个都可能独立导致编译失败或结果错误：

| 参数 | 作用 |
|---|---|
| `blayout` | block layout，`row_major` / `col_major` |
| `slayout` | scatter / box layout，如 `none_box` |
| `fractal` | 分形尺寸（NZ 布局） |
| `stride` | 各维元素步长 |
| `valid_shape` | **有效数据区域，可以小于 shape** |
| `start_offset` | 视图在底层 buffer 中的起始偏移 |
| `pad` | 越过有效区时的填充模式 |

`valid_shape` 值得单独讲，因为它是正确性问题而不只是性能问题：

```python
tile = pl.tile.load(x, offsets=[0, 0], shapes=[128, 128], valid_shapes=[100, 128])
```

物理缓冲按 `[128, 128]` 规划，但只有 `[100, 128]` 是真数据。剩下的 28 行是什么，取决于 `pad`。这个机制服务于非整除尾块、动态 shape 和分块边界。**读编译产物时，分不清 `shape` 和 `valid_shape` 就会得出完全错误的结论**——3.5 节有一个真实的例子。

还有一类容易误判的操作：`tile.slice`、`tile.reshape`、`tile.transpose_view`、`tile.set_validshape` 通常只改视图元数据，不搬数据。但如果硬件指令消费不了这个视图，`CanonicalizeTileSlice` 会把它转成 `tile.extract`，**产生一次真实搬运**。源码里看起来免费的一行，编译后可能不是。

## 1.3 两种核，和它们之间的管道

昇腾把矩阵计算和向量计算分给两种核：AIC（Cube）和 AIV（Vector）。Ascend910B 上有 **48 个物理 AIV 核**。

两种核之间通过 `tpush` / `tpop` 交接数据。在 910B 上这条通路要经过 GM 中转，因此需要一块额外的 `__gm_pipe_buffer`。编译器的 `InjectGMPipeBuffer` pass 会给 AIC/AIV 函数加上 workspace 参数、沿调用图向上传播、在编排层注入占位 Tensor，最后由 codegen 按管道数量、方向和槽位算出实际占用。Ascend950 的直连跨核通道不需要这块 GM workspace。

这就是为什么跨核交接的开销**不写在用户代码里**，却会吃掉用户的片上预算。#2287 整个案例就发生在这里。

一个真实的跨核管道初始化，来自 CSA 编译产物：

```python
qk_pv_c2v_slot_buffer = pl.system.reserve_buffer(
    name='qk_pv_c2v_slot_buffer', size=32768, base=0)
pl.system.aiv_initialize_pipe(
    qk_pv_c2v_slot_buffer, qk_pv_v2c_slot_buffer_import,
    dir_mask=3, slot_size=16384, slot_num=2)
```

`dir_mask=3` 表示双向；`slot_size=16384`、`slot_num=2` 相乘得到 32,768 字节的预留。这 32 KB 从 UB 的 188,416 里直接扣掉，用户代码里没有任何一行提到它。

## 1.4 同步：hard 与 soft 的契约差异

`pl.system.syncall` 有两种模式，它们的**适用条件完全不同**：

| 模式 | 机制 | 关键约束 |
|---|---|---|
| `hard` | FFTS 硬屏障 | **要求该 `core_type` 的全部物理核都到达** |
| `soft` | 共享 GM workspace 轮询 | 支持部分占用，需 `gm_workspace`、`used_cores` |

soft 模式的 GM workspace 需要约 `used_cores × 8 × sizeof(INT32)`；按核型不同还要额外的 Vec scratch 或 Mat scratch，且 Mat scratch 必须用 `flat_layout=True`，否则计数槽位会错位。

**hard 模式的"满占用"要求，是一条没有写在接口签名里、却会导致设备 reset 的契约。** 这是案例 3（3.3 节）的全部内容。

## 1.5 编译器已经替你做了什么

这一节是理解整个方向的关键。PyPTO 的内存配置**不是在某个 API 里一次确定的**，而是沿编译流水线逐步落实：

```
Tensor / Tile 语义
  → target_memory、shape、layout、valid_shape
  → InferTileMemorySpace      推导 Tile 所在空间
  → AutoTileMatmulL0          按 L0 容量自动选 m/n/k
  → ResolveBackendOpLayouts   修复后端要求的布局
  → ExpandMixedKernel         划分 AIC/AIV 与跨核边界
  → LowerPipelineLoops        生成多 stage / ping-pong 缓冲
  → InitMemRef                创建片上缓冲描述
  → MemoryReuse               按生命周期与别名规则复用
  → AllocateMemoryAddr        分配实际片上地址
  → codegen / PTOAS           生成硬件 Tile 指令
```

`AutoTileMatmulL0` 会依据后端参数自动选择分块，约束近似为：

```
m × k × bytes_a ≤ L0A    k × n × bytes_b ≤ L0B    m × n × bytes_c ≤ L0C
```

`MemoryReuse` 的复用判定包含生命周期不重叠、空间相同、容量足够、不违反 no-alias 约束、不破坏 pipeline stage 并发关系。仓库文档列出了一批**不能原地复用**的算子及原因，例如 `tile.row_sum`（输出时仍要读完整输入行）、`tile.transpose`（边读边写会破坏未读数据）、升精度的 `tile.cast`（更宽的写入会覆盖未读输入）。

**这份清单说明了一件重要的事：绝大部分硬件复杂性，框架已经承担了。** 体验问题不在"用户需要学会这些"，而在剩下那一小部分——框架处理不了、处理错了，或者处理了但用户需要知道结果的时候。

本文讨论的就是那一小部分。

## 1.6 还有一类硬件事实：访存粒度

最内维太窄会严重浪费带宽：

| 参数 | Ascend910B | Ascend950 |
|---|---:|---:|
| GM 访问粒度 | 512 B | 128 B |
| L2 cache line | 512 B | 512 B |
| 推荐最内维 | 512 B | 128 B |

`innermost_dim_bytes = shape[-1] × sizeof(dtype)`。低于阈值时诊断 Pass 产生 `PH001` 性能提示。注意这是**提示**不是错误——它不阻断编译，所以很容易被忽略。

# 第二部分：什么是 Hardware-Native

有了第一部分的背景，定义可以下得很具体。

## 2.1 工作定义

> **Hardware-Native 指：软件系统在抽象、映射、调度和执行时尊重目标硬件的能力、约束与成本；并且当某条硬件约束必须由开发者参与处理时，系统让这个决定可理解、可操作、可验证。**

两句话缺一不可。只有前半句是"硬件亲和优化"，是编译器的事；只有后半句是"把复杂度甩给用户"。

## 2.2 三条判据

对任何一项硬件事实，问三个问题。这三个问题构成了本文第四部分分类的骨架：

**一、谁来决定？** 系统能可靠决定的，系统决定，不要进界面。`AutoTileMatmulL0` 自动选 m/n/k 就是正确的设计。只有当系统不能确定、或用户必须权衡时，这件事才进入体验范围。

**二、什么时候呈现？** 在用户做选择的那一刻，不是在用户查手册的时候，更不是在设备超时之后。#1935 的约束在编译期完全可判定，却在运行时以设备 reset 的形式呈现——这是时机错误，不是信息缺失。

**三、凭什么相信？** 一条诊断必须能回答"这个结论来自目标规格、静态推算、编译产物还是设备实测"。#2287 的报错**听起来**极其确定，但它的归因是错的。确定的语气配错误的归因，比没有建议更糟。

## 2.3 不属于这个方向的

明确排除，避免概念膨胀：

- 与目标设备和执行语义无关的通用编辑器、项目管理、登录体验
- 加一张芯片架构图、一排硬件术语、一个资源仪表盘，但不支持理解、操作或验证
- 把所有软件 bug 归因于"缺少硬件意识"
- 把本应由框架保证的正确性，转交给用户记忆和手工检查
- 以"某块资源是否用满"代替"任务是否更快、结果是否正确"

最后一条尤其重要。第三部分的最后一个案例就是栽在这里。

# 第三部分：四个真实案例，和一个反面教材

每个案例的结构相同：发生了什么 → 开发者实际看到的 → 真实根因 → 这为什么是体验问题。

所有报错原文、代码和数字均摘自仓库 `github_issues/` 归档的 Issue 正文，未经改写。

## 3.1 案例一：抽象退化——框架拿走了一个接口，复杂度落回开发者身上

**来源：** PyPTO #630《[Discussion] PTO 3.0 Tiling Design Impacts Operator Development Usability》，2026-03-19 创建，状态 open。

**场景。** 开发 DeepSeek V3.2 decode 算子时，把 `kv_lora_rank` 从 128 改成 512。只改了这一个模型维度。

**开发者看到的：**

```
Exception: Verification failed after 'AllocateMemoryAddr' for properties {AllocatedMemoryAddr}:

[1] ERROR - AllocatedMemoryAddr
  Message: Function 'deepseek_v3_2_decode_front_layer_incore_6_incore_0_aic':
           Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)
  Location: .../deepseek_v3_2/deepseek_v3_2_decode_front.py:390:20
```

98,304 字节要塞进 65,536 字节的 L0B。报错给了函数名、文件名、行号和两个数字——信息不算少。

**真实根因，不是"Tile 太大"。** 提报人把它归结为 PTO 2.0 与 3.0 的设计差异：

| 能力 | PTO 2.0 | PTO 3.0 |
|---|---|---|
| Tile shape 设置 | 开发者可设 | **不提供接口** |
| MatMul 分块 | 框架自动处理 m/k/n | **开发者手动分块** |
| RMSNorm（大 h） | 框架自动处理 h 维循环 | **开发者手写内层 h 循环** |

在 2.0 里，这是一行声明：

```python
set_cube_tile_shape([M_TILE, K_TILE, N_TILE])
```

在 3.0 里，同一件事变成：

```python
for m0 in range(0, M, M_CHUNK):
    for k0 in range(0, K, K_CHUNK):
        for n0 in range(0, N, N_CHUNK):
            lhs_tile = pl.slice(lhs, [M_CHUNK, K_CHUNK], [m0, k0])
            rhs_tile = pl.slice(rhs, [K_CHUNK, N_CHUNK], [k0, n0])
            # ... 逐块手工处理
```

RMSNorm 更麻烦——手写 h 维循环还要自己处理跨 chunk 的 reduce。

提报人列出四条后果：配置参数一变就要改代码结构；手工管理循环层次和分块逻辑；开发者需要更深地理解硬件 buffer 限制；代码结构与具体参数高度耦合。并直接提出了想要的接口：

```python
@pl.tile_policy(matmul_tile=[128, 512, 128], rmsnorm_tile=[16, 1024])
def my_operator(...):
    # 框架按策略自动生成循环结构
```

**为什么这是体验问题。** 这个案例的价值在于它**反驳了一个直觉**。面对"Right buffer 超限"，产品的第一反应往往是"给用户一个更好的容量可视化，帮他找到该切哪一维"。但提报人要的不是可视化，是**把这个决定还给框架**。

Hardware-Native 在这里的正确答案是减少暴露。衡量标准不是用户理解了多少硬件，而是用户**不需要**理解多少硬件仍能把事做对。工具的职责是：当模型维度变化触发资源约束时，说清楚是哪个配置参数通过哪条路径撞上了哪个物理上限——然后，如果框架有能力自动分块，就自动分块。

**这个案例对工具的要求：** 把"模型配置参数 → 分块方式 → 物理 Tile → 空间分配 → 容量上限"这条链路显式化，并且在链路的每一环都问一次"这一步能不能自动"。

## 3.2 案例二：报错很具体，两个建议都是错的

**来源：** PyPTO #2287《Cross-core FIFO on-chip reserve is over-sized on both depth and slot size》，2026-08-05 创建，关闭为 not planned。环境 Ascend 910B / A2A3，commit `7d743e8d`。

**场景。** DeepSeek v4-flash 稀疏 decode attention 的 `qk_pv` 混合 kernel 编译失败。

**开发者看到的：**

```
ValueError: Vec buffer usage (213760 bytes) exceeds platform limit (188416 bytes).
The first 131072 bytes of that space are reserved by system.reserve_buffer, so tiles are
allocated above them - this is the cross-core pipe ring. Lower its depth with
optimizations=[pl.cross_core_slot(slot_num=N)] on the enclosing pl.at(...), or shrink the
tile that crosses the cube/vector boundary
```

**先肯定这条报错。** 它说出了用量、上限、超出部分的归属（跨核管道预留）、预留的大小，还给了两条具体的修复路径。按任何一份诊断设计规范来衡量，这都是一条好报错。

**然后看真相。** 报告指出这块预留在两个维度上同时算错了：

*过量一：深度。* PTOAS 契约规定，消费者侧本地 FIFO 的预留应为 `slot_size × effective_local_slot_num`，其中 `local_slot_num` 是一个独立的、更小的参数。**PyPTO 从不发出 `local_slot_num`**，于是每条本地 FIFO 管道都按完整的 GM 环深度预留（单向 8 / 双向 4）。这个参数在 IR op 里已经存在（`system_ops.py:412-426` 同时接受 `slot_num` 和 `local_slot_num`），但 DSL 旋钮 `pl.cross_core_slot(*, slot_num: int)` 只暴露了 `slot_num`，用户也没法自己设。

*过量二：槽大小。* `GetCommonSlotSizeBytes` 取 `max(c2v.slot_size, v2c.slot_size)`，然后**两个方向的缓冲都按这个最大值预留**。但 ISA 实际是按各方向自己的消费者 Tile 大小索引本地落地区的。

这个 kernel 的载荷严重不对称：

| 方向 | 消费者 Tile | 字节 |
|---|---|---:|
| V2C（AIV → AIC） | staged KV tile | 131,072 |
| C2V（AIC → AIV） | `qk_raw` `[32, 128]` FP32 | **16,384** |

于是：**16 KB 的载荷，在最紧张的 UB 里占了 131,072 字节的坑——8 倍过量分配。**

正确的尺寸应该是 `local_slot_num × 16,384 = 32,768`（深度 2），加上 82,688 字节的 Tile，总共 115,456 / 188,416，**轻松装下**。

**两条建议分别错在哪。** 建议一是"降低环深度"——报告明确说，即便用 `pl.cross_core_slot(slot_num=1)` 强制最小深度，预留仍是 131,072（因为每个方向的缓冲都按共同最大值定尺寸），kernel 依然超 25,344 字节。建议二是"缩小跨 cube/vector 边界的 Tile"——这会让开发者为编译器的 bug 付出真实的性能代价，而且缩的是那个本来只要 16 KB 的方向。

**为什么这是体验问题。** 这个案例把"信息充分"和"归因正确"彻底分开了。报错给出了全部正确的数字，指向了正确的占用来源（跨核管道预留），但**没有说明这个预留本身是错的**。开发者没有任何线索去怀疑编译器——所有证据都指向"我的 Tile 太大"。

一个有价值的观察：报错里说的"前 131,072 字节被 reserve_buffer 预留"，恰恰就是错误的那个数。**工具把 bug 的产物当作既定事实报告给了用户。**

**这个案例对工具的要求：** 资源占用必须区分来源——计算 Tile、临时工作区、通信缓冲、系统预留，并对每一项标明"这是谁决定的"。用户数据超限和系统生成策略异常，是两条完全不同的处理路径，不能共用一条建议。当某项占用由编译器自动生成时，诊断应当保留"这个数字本身可能需要排查"的余地。

## 3.3 案例三：知识写在测试文件里，学费是一次设备重置

**来源：** PyPTO #1935《hard-form pl.system.syncall deadlocks (AICore 507018) at partial core occupancy — no compile-time check》，2026-07-02 创建，已关闭。环境 pypto `d598b41b`、pto-isa `e722679`、ptoas `0.48`、Ascend 910B。

**场景。** 一个 SPMD elementwise add，在 load 和 add 之间放一个 hard 模式的 `syncall`。

```python
TR = TC = 128
N = 24  # < 48 物理 AIV -> 部分占用（N = 48 为通过的对照）

@pl.program
class PartialSyncAll:
    @pl.function(type=pl.FunctionType.InCore)
    def add(self, a, b, out):
        i = pl.tile.get_block_idx(); o = i * TR
        ta = pl.load(a, [o, 0], [TR, TC]); tb = pl.load(b, [o, 0], [TR, TC])
        pl.system.syncall(core_type="aiv_only")          # HARD barrier
        out = pl.store(pl.add(ta, tb), [o, 0], out); return out

    @pl.function(type=pl.FunctionType.Orchestration)
    def orchestrator(self, a, b, out):
        with pl.spmd(N):                                  # N=24 < 48 -> 部分占用
            out = self.add(a, b, out)
        return out
```

**开发者看到的：**

```
[ERROR] sync_run_streams: aclrtSynchronizeStreamWithTimeout (AICPU) failed: 507018
[ERROR] recover_device_or_mark_unusable: AICore error 507018:
        bounded device drain failed (force reset will follow in finalize)
RuntimeError: run_prepared failed with code 507018
```

设备随后不可用，后续任务报 `code 13` 直到恢复。

**真实根因。** hard 屏障（FFTS）等待该核型的**每一个物理核**到达。910B 有 48 个 AIV，启动了 24 个 block，另外 24 个核永远不会到达屏障，FFTS 等待永不完成。

`pl.spmd(24)` → 507018；只把 24 改成 48 → PASS。**占用度是唯一变量。**

**三件让这个案例特别刺眼的事：**

第一，**编译期完全可判定。** 编译器同时掌握启动的 block 数（`pl.spmd(N)`，写在源码里）和目标 SoC 每种核型的物理核数（在后端参数表里）。这是一次静态比较。

第二，**这条知识当时已经存在于仓库里。** 报告指出，`tests/st/runtime/cross_core/test_syncall.py` 的 docstring 已经写明 hard SYNCALL 需要 AIV 满占用。知识在，但它在一个开发者不会在写代码时打开的文件里。

第三，**替代方案也已经存在。** soft 模式在部分占用下工作正常：`pl.system.syncall(mode="soft", core_type="aiv_only", gm_workspace=ws, used_cores=N)`。开发者需要的不是新能力，只是在选 hard 的那一刻知道它有这个前提。

报告给出了期望的报错，值得整段引用，因为它几乎就是一条理想诊断的样板：

> `hard pl.system.syncall(core_type="aiv_only") requires the spmd launch to fill all 48 AIV cores, but pl.spmd(24) launches 24 blocks. Use mode="soft" (GM-polling) for partial occupancy.`

它包含：违反了什么约束、具体数字对比（48 vs 24）、可执行的替代方案。

**为什么这是体验问题。** 代价不对称到了荒谬的程度：**一次静态整数比较，对应一次设备强制重置加上共享设备的连带失败。** 而且这是在共享开发设备上，影响不止一个人。

这类问题的处理顺序必须说清楚：**首先是编译器加检查，不是工具加提示。** UX 在这里的职责是参与设计这条诊断怎么写（约束、数字、替代方案、代码位置），以及在诊断之外，让 hard/soft 的契约差异在用户**选择**的时刻可见——而不是补一篇文档让用户去记。

**这个案例对工具的要求：** 凡是编译期可判定的约束，都应该在编译期拒绝；凡是必须留到运行期的，要在失败时说清楚本可以提前知道什么。同时，诊断要把"参与者范围"这类跨越源码与目标规格的关系显式化。

## 3.4 案例四：编译器自己的容量校验算错了

**来源：** PyPTO #626《[Bug] AllocateMemoryAddr pass 对 matmul Right buffer 校验算法存在 bug》，2026-03-19 创建，已关闭。

**场景。** 同样是 DeepSeek V3.2 decode，同样卡在 Right buffer。

**开发者看到的：**

```
[1] ERROR - AllocatedMemoryAddr
  Message: Function 'deepseek_v3_2_decode_back_layer_incore_3_aic':
           Right buffer usage (131072 bytes) exceeds platform limit (65536 bytes)
  Location: .../deepseek_v3_2/deepseek_v3_2_decode_back.py:79:12
```

**真实根因。** `AllocatedMemoryAddrVerifier` 用了一个过于简单的高水位算法：遍历所有 TileType 变量，按 MemorySpace 分组，对每个空间计算 `high_water = max(addr + size)`。

问题在于它**不考虑生命周期**。提报人给出了日志证据：

```
wg_0_tile_Right: lifetime [13, 16], size=65536
wu_0_tile_Right: lifetime [15, 18], size=65536
```

两个 64 KiB 的变量被简单累加成 131,072，而实际上它们在地址分配考虑生命周期的情况下可以共享同一块 Right buffer。校验算法本身比 `MemoryReuse` 的判定更保守，于是**拒绝了一个合法的 kernel**。

相关代码位置：校验逻辑 `allocate_memory_addr_pass.cpp:353-361`，验证器 `289-332`；Right 的 64KB 限制定义在 `src/backend/common/soc.cpp:126`；matmul 的 `.set_input_memory(1, MemorySpace::Right)` 在 `matmul.cpp:266`。

**为什么这是体验问题。** 把 #626 和 #630 放在一起看，会发现一件事：**它们的报错长得几乎一模一样。**

```
#630:  Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)
#626:  Right buffer usage (131072 bytes) exceeds platform limit (65536 bytes)
```

同样的空间、同样的上限、同样的措辞、同样的 pass。但一个是真的放不下（需要改分块策略，或者更好——恢复框架的自动分块），另一个是校验器算错了（需要修编译器，用户什么都不用改）。

**开发者没有任何办法从报错里区分这两种情况。** 面对 #626，一个尽责的开发者会去缩小 Tile——他会成功，因为缩小后确实能通过校验，代价是白白损失性能，而真正的 bug 留在原地。

这是"相同表面症状，不同责任层"最干净的一个例证。而且它说明：**归因错误不只浪费时间，它会制造错误的修复，并且掩盖真正的缺陷。**

**这个案例对工具的要求：** 当诊断来自一个推算（高水位估计）而非确定事实（实际分配冲突）时，必须标明。用户有权知道"编译器认为放不下"和"编译器确认放不下"的区别。

## 3.5 反面教材：我们自己也读错了编译产物

这一节讨论既有研究材料中的一个错误，因为它本身就是最好的论据。

**既有主张。** 仓库中 2026-10-31 的两份 Hardware-Native 材料均断言：CSA 的 `qk_pv_aiv` 采用双 AIV 派发，但"第二条分支的相关 softmax Tile 有效形状为零（`valid_shape=[0,0]`）"，据此识别出"有效计算未分摊到第二个 AIV"，并把它作为计算分工机会点（O1）的主要证据和首个试点任务。

**本轮核对。** 直接读取被引用的编译产物 `36_after_AllocateMemoryAddr.py`：

*第一，`dual_aiv_dispatch` 属实。* `qk_pv_aiv` 函数确实带有 `pl.func_attr({"dual_aiv_dispatch": True})`，并在 `subblock_idx == 0` / `else` 上分成两支。

*第二，两支的工作量分配看不出差异。* 两个分支的迭代次数由同一个表达式决定：

```python
# subblock_idx == 0 分支
qk_lane_iters = (qk_items - qk_core + 23) // 24
# else 分支
qk_lane_iters_1 = (qk_items - qk_core_1 + 23) // 24
```

两支随后的结构也对应——读 `qk_order`、同样的下标分解、同样的 `tpop_from_aic(split=0)` 交接。从这份产物看不出哪一支不干活。

*第三，`valid_shape=[0, 0]` 不是"有效形状为零"的证据。* 这个标注在该文件中出现 **68 次**，遍布不同函数和不同分支，包括明显在做实际计算的 Tile。它是 `TileView` 的默认/哨兵标注，不能按字面读成"有效数据为空"。把它当作"某个核空转"的证据，是一次误读。

**结论。** "第二个 AIV 没有分摊有效计算"这个判断，**在当前证据下不成立**。它可能仍然为真，但需要别的证据（分支实际执行次数、profiling、或对 `set_validshape` 调用链的完整追踪），而不是这份产物里的 `valid_shape` 字段。

同时，这份产物确实交叉验证了案例二的一个数字：`qk_raw` 的 Tile 类型是 `pl.Tile[[32, 128], pl.FP32, ...]`，`32 × 128 × 4 = 16,384` 字节，与 #2287 报告的 C2V 载荷完全一致。

**为什么这一节属于这份材料。** 读错这个字段的，不是赶工期的开发者，而是在专门研究这个主题、有充足时间、直接打开了编译产物的研究者。

**如果连我们都会读错，那么"把硬件事实摆出来让开发者自己判断"就不是一个可行的设计策略。** 原始产物是必要的证据底座，但它不能充当界面。Hardware-Native 工具的价值恰恰在这里：把 `valid_shape=[0,0]` 这种需要上下文才能解读的字段，翻译成"这个 Tile 的有效数据范围是 X，依据是 Y"——或者在无法确定时，明确说"这个字段在此处不可解读"。

这也修正了一个机会点的证据状态：**计算分工（见第四部分）目前缺少确凿的昇腾案例证据。**

# 第四部分：分类与对象

既有材料并行使用了九个事实域、六种承载形态、四类硬件机制和 O1–O4 四套分类，彼此重叠。本部分只用一套。

分类的依据来自 2.2 节的第一条判据——**谁来决定**。这是对设计最有用的切分，因为它直接决定某件事该不该进界面。

## 4.1 四个责任层

| 层 | 含义 | 判断标准 | 本文案例 |
|---|---|---|---|
| **L1 系统保证** | 系统必须正确处理，不应进入用户视野 | 规则确定、信息完整、无需权衡 | #1935 的满占用检查；#626 的生命周期感知校验；#2287 的分方向预留 |
| **L2 必须可见** | 系统处理了，但用户需要知道结果 | 影响用户的下一个决定 | 自动插入的 `tile.move`；跨核管道的 UB 预留；`AutoTileMatmulL0` 选中的 m/n/k |
| **L3 必须可控** | 用户需要表达系统无法推断的意图 | 存在真实权衡，或系统信息不足 | #630 要的 `tile_policy`；#2287 要的 `local_slot_num`；hard/soft 模式选择 |
| **L4 必须可验证** | 用户需要确认结果符合预期 | 涉及正确性或性能主张 | 改动后的实际分配、数值结果、目标链路耗时 |

**这个分层的实用价值，是它给出了一条评审时可直接使用的判据：**

> 任何一个 Hardware-Native 设计提案，先问它属于哪一层。如果答案是 L1，那它是技术任务，不是设计任务——做一个更好的界面去解释一个本该被自动修复的问题，是在错误的层上投入。

本文四个案例中，**三个的首要责任都在 L1。** 这不削弱这个方向，反而界定了它：UX 在 L1 问题上的正当工作，是参与设计那条诊断（说什么、在哪说、给什么出路），以及在修复落地前组织用户的判断——而不是用提示框替代修复。

## 4.2 四类决策对象

在责任层之上，昇腾上真正需要开发者参与的决定可以归为四类。每一类对应一组具体的开发对象：

**一、计算分工——谁来算。**
对象：计算区域、AIC/AIV 映射、切分轴、归约关系、各分支有效 Tile、核间交接。
典型决定：这段计算交给哪种核，怎么切分才保持语义。
*证据状态：昇腾侧案例证据不足（见 3.5）。*

**二、形态与容量——数据怎么放。**
对象：Tensor 逻辑维度、分块、`blayout`/`slayout`/`fractal`、`valid_shape`、目标空间、buffer 生命周期与复用。
典型决定：保持计算语义的前提下，怎样满足 L0A/L0B/L0C/UB 的容量要求。
*证据状态：充分。#630、#626、#2287 均落在这里。*

**三、数据交接——数据怎么走。**
对象：中间 Tensor、生产者/消费者、`tile.move`/`extract`、跨核管道、融合边界。
典型决定：中间结果经过哪些空间，融合省掉了什么又增加了什么。
*证据状态：跨核交接有强证据（#2287）；Cube↔Vector 融合决策缺少真实任务案例。*

**四、执行时序——什么时候交接。**
对象：stage、slot、事件、屏障、参与者范围、buffer 存活与复用。
典型决定：哪些操作能重叠，用哪种同步，何时能复用缓冲。
*证据状态：充分。#1935 落在这里。*

**责任层 × 决策对象构成一张表，每个格子是一个可讨论的设计问题。** 例如"形态与容量 × L2"是"用户需要看见哪些自动分块结果"；"执行时序 × L1"是"哪些同步约束必须编译期拒绝"。这比九个事实域更可操作，因为每个格子都直接对应一个设计动作。

## 4.3 工具里需要建立的对象

要支撑上面的判断，工具内部至少需要这几个一等对象。这是数据模型层面的要求，不是界面：

| 对象 | 最少内容 | 为什么必要 |
|---|---|---|
| **Target** | 设备型号、各空间容量、工具链版本、能力来源 | 65,536 和 188,416 是版本相关的事实，不能硬编码在前端 |
| **Workload** | 模型、shape、dtype、batch、序列、并行配置 | #630 的全部问题由一个配置参数变化触发 |
| **Callable** | 源码位置、作用域、生成变体、模型归属 | 把源码、编译产物和执行连起来 |
| **Tile** | 逻辑形状、物理布局、`valid_shape`、驻留位置、生命周期 | 3.5 节证明：缺少上下文的 Tile 字段会被读错 |
| **编译决策** | 选中策略、未采用的策略及原因、自动插入的操作 | 自动 `tile.move` 和管道预留必须可追溯 |
| **Finding** | 对象、触发条件、**证据等级**、责任层、候选动作 | #626 与 #630 的报错文本相同、责任层不同 |
| **Experiment** | 基线、单一改动、编译结果、运行结果、比较条件 | 防止"预览了一个方案"变成"已完成优化" |

`Finding` 上的**责任层**字段是本文新增的要求。它直接来自 #626 与 #630 的对比：两条报错文本相同，但一条应该导向"改你的分块"，另一条应该导向"这可能是编译器缺陷，这是复现材料"。没有这个字段，界面无法区分。

# 第五部分：框架与工具应该怎么设计

## 5.1 一条总原则

> **一条诊断的价值，等于它的归因正确率乘以它的可操作性——而不是两者之和。**

#2287 的可操作性接近满分，归因错误，于是乘积为负：它主动把开发者引向了错误的修复。这条原则意味着，**在归因不确定时，降低建议的确定性比提高建议的具体性更重要。**

## 5.2 从四个案例反推的七条设计要求

**要求一：编译期可判定的约束，必须在编译期拒绝。**
来自 #1935。判据很简单——如果编译器手上的信息足以做这个判断，就不要让它走到设备上。这条首先是编译器的工作项，UX 参与诊断文案的设计。

**要求二：诊断必须标注责任层。**
来自 #626 vs #630。同一条报错文本背后可能是"你需要改代码"或"这是系统缺陷"。界面至少要能表达三种状态：确认是用户配置问题、确认是系统问题、尚不能区分。第三种状态是诚实的，也是有用的——它告诉用户该去提 Issue 而不是继续试参数。

**要求三：资源占用必须按来源拆分，并标明每项由谁决定。**
来自 #2287。至少区分：计算 Tile、临时工作区、通信缓冲、系统预留。并且对自动生成的部分，保留"这个数字本身可能有问题"的表达余地。一个具体设计：占用明细的每一行都带一个来源标记（用户代码 / 编译器自动 / 系统固定），用户代码行可点击跳转，编译器自动行可展开生成依据。

**要求四：推算与事实必须分开。**
来自 #626。"高水位估计 131,072"和"实际同时占用 131,072"是两回事。凡是来自成本模型、静态推算或保守估计的数字，不能和实测数字用同一种视觉权重呈现。

**要求五：把硬件事实翻译成可解读的陈述，不要直接暴露字段。**
来自 3.5 节。`valid_shape=[0, 0]` 不该出现在界面上。该出现的是"有效数据范围：未约束（继承 shape）"或"此处该字段不可解读"。原始字段作为证据保留一跳可达，但不作为默认呈现。

**要求六：先问能不能自动，再问怎么呈现。**
来自 #630。每增加一个硬件相关的界面元素，先回答"这件事为什么不能由框架决定"。如果答案是"框架以前能，现在不能了"，那这是一个退化，应该优先修复而不是补界面。

**要求七：契约差异要在选择的时刻可见。**
来自 #1935。hard 与 soft 的占用度前提，应该在用户写下 `mode=` 的时候出现，而不是在文档里、测试 docstring 里或运行日志里。这是一个编辑器集成问题，不是文档问题。

## 5.3 证据等级

每条结论都应该绑定一个等级。这不是免责，而是让用户知道该采取什么行动：

| 等级 | 可以说 | 用户该做什么 |
|---|---|---|
| 目标规格 | 对该目标和版本，上限是 65,536 字节 | 当作约束接受 |
| 静态推算 | 按当前估计模型，预计占用 131,072 | 核对估计是否合理 |
| 编译确认 | 这次产物中实际分配为 X | 可以据此改代码 |
| 设备观测 | 该运行条件下实测为 Y | 可以据此判断收益 |
| 对照验证 | 相同条件下，改动前后变化为 Z | 可以据此采纳方案 |
| 假设 | 有迹象指向某方向，尚需验证 | 去补证据，不要直接改 |

等级必须逐项绑定。一个候选方案里的某项分配尚未编译确认，不能因为基线来自真实产物就继承"已确认"标签。

## 5.4 Agent 的位置

Agent 适合做的：整理跨文件证据、解释术语、生成候选改动、起草验证计划、在授权后组织实验。

Agent 不能改变的：阈值来自 Target、执行结果来自设备、责任层判断需要可追溯依据。

关键约束是**自然语言不能稀释证据等级**。一段流畅的解释和一条标注"推算"的诊断，传递的确定性感受完全不同。Agent 的输出必须继承底层 Finding 的证据等级，而不是把它抹平成同样自信的叙述。#2287 已经演示了一条措辞确定、归因错误的诊断能造成什么后果；Agent 会让这类输出更容易产生。

# 第六部分：业界实践

> 本部分沿用既有研究在 2026-10-31 检索的官方文档结论，**本轮未重新检索或验证**。这是机制参考，不代表这些产品的体验已被证明更优。

**Ascend C（昇腾官方）：用编程模型承载复杂性。** TPipe/TQue 把资源管理和任务间同步组织成编程接口。启示是：Hardware-Native 做对了的样子，可能是用户看到的硬件细节**更少**。UX 可以参与概念命名、使用顺序和失败反馈的设计。

**NVIDIA Nsight Compute：先建立比较，再解释指标。** 提供跨报告 baseline 比较、源码关联视图和 Roofline。启示是界面应先回答"和什么比、在什么条件下比、变化落在哪"，再给指标。资源利用率脱离工作量和理论上界，不能单独得出好坏结论——这正是 3.5 节踩的坑。迁移边界：GPU 的指标和 roofline 上界不能直接搬成昇腾公式。

**Triton Gluon：给高级用户边界清楚的控制层。** 作为更低层的 GPU 编程模型，直接暴露布局、共享内存和 warp specialization，用易用性换控制力。启示直接对应 #630：常规任务保留简单默认，需要控制时提供**有类型、有语义、有限制说明**的专家层，而不是把内部参数表生成一个表单。注意 #2287 的教训——`local_slot_num` 在 IR 里存在但 DSL 没暴露，这是专家层的缺口。

**AWS Neuron Explorer：按任务在系统、模型、源码、设备间切换。** 文档按"训练步慢""设备利用""通信""kernel"等场景指引不同采集路径，并提供层级、源码、设备和内存视图的关联。启示是模型用户和算子用户可以共享同一套底层证据，但从不同问题进入。对象关联比多加一个硬件页面更有价值。

**AMD ROCm Compute Profiler：用硬件模型解释性能，并说明覆盖边界。** 基于计数器提供 Speed-of-Light、内存分析、roofline 和 baseline 比较，文档同时说明哪些能力依赖具体型号。后半句同样重要——工具说清自己的覆盖边界，是可信度的一部分。

**昇腾 msprof：已有的采集能力。** 提供通信 timeline、汇总数据和计算通信 Overlap Analysis。启示是新工具应优先接入已有采集产物并关联到模型对象和源码，而不是再造一个显示相同数据的看板。

**对本团队最直接的四条：** 可靠的默认抽象优先于更多的暴露；专家控制要有边界和语义；跨层对象关联比新增视图有价值；让"有改善""无收益""证据不足"都能被准确表达。

# 第七部分：怎么验证这个方向值不值得投

## 7.1 可以证伪的假设

每条假设都配了否定条件。如果否定条件成立，应当缩小或放弃该假设。

| 假设 | 验证任务 | 观察指标 | 什么情况下应当放弃 |
|---|---|---|---|
| **H1** 标注责任层能减少错误修复 | 给出 #626 与 #630 两条文本相同的报错，让开发者判断该改什么 | 责任判断正确率、错误修复次数 | 开发者本来就能区分，或标注反而增加犹豫 |
| **H2** 拆分占用来源能让用户找对修改对象 | #2287 场景：UB 超限，判断该缩 Tile 还是报 Issue | 首次有效动作时间、是否误缩 Tile | 现有报错已足够，拆分不改变选择 |
| **H3** 约束前移能减少无效设备实验 | #1935 场景：离线判断 hard/soft 是否匹配启动配置 | 上板前发现率、设备重置次数 | 编译器加检查后问题消失，界面无额外价值 |
| **H4** 自动化比可视化更有价值 | #630 场景：对比"更好的容量可视化"与"恢复 tile_policy 接口" | 任务完成时间、代码改动量、用户偏好 | 用户确实想要手工控制，自动化不被接受 |
| **H5** 翻译硬件字段能减少误读 | 3.5 场景：从编译产物判断双 AIV 分工 | 误读率、结论正确性 | 原始字段配文档已经够用 |

**H4 是这组假设里最该先做的。** 它直接检验本文的一个反直觉结论——如果结果显示用户更想要可视化而不是自动化，那第五部分的要求六需要重写。

## 7.2 首轮研究设计

**样本。** 6–8 名覆盖模型、算子及框架协作经历的开发者，用于发现机制而非统计显著性。效果评估阶段再按基线差异设计样本量。

**方法。** 优先回溯最近真实发生的任务，收集经许可的脱敏代码、报错、版本和结果。把"做了什么、看到什么、据什么判断、最后怎么验证"还原成时间线。不要问用户喜不喜欢某个功能。

**对照设计。** 三个版本：现状、加结构化诊断与责任层标注、再加局部硬件可视化。用难度相近的任务和顺序平衡，分别识别"更好的信息组织"和"额外可视化"各自的贡献。这个设计能回答 H4。

**安全约束。** #1935 这类问题用离线材料或已知测试用例，**不为研究故意使共享设备挂死**。

## 7.3 访谈要追问的

- 最近一次因 shape、dtype、并行配置或目标变化而失败的任务是什么？
- 最早在哪一层发现问题？事后看，哪些信息当时其实已经存在？
- 你做过哪些无效尝试？是缺信息、看不懂，还是根本没有可用的控制？
- 哪一个证据让你从"怀疑"变成"决定修改"？
- 你遇到过报错给的建议是错的吗？当时怎么发现的？
- 哪些底层细节你愿意完全交给框架？什么情况下必须保留控制？
- 如果只给一条归因正确的诊断、不加任何硬件图，够不够？

倒数第二问直接对应 #630，最后一问是整个方向的压力测试。

## 7.4 不要用的指标

面板点击数、用户看过多少硬件名词、资源填满比例、用户会不会说"Hardware-Native"——这些都不代表任务价值。

应当观察：任务完成率与正确率、首次有效决策时间、**错误归因次数**、无效编译与上板次数、跨团队往返、结论可复现性，以及用户的信心是否与证据相称。

**"错误归因次数"是本文最推荐的核心指标。** 四个案例里有三个的核心损失都是归因错误造成的，而它恰好是现有工具完全没有度量的东西。

## 7.5 建议的推进顺序

| 顺序 | 内容 | 依据 | 进入下一步的条件 |
|---|---|---|---|
| 0 | Target / Finding / 证据等级的数据模型 | 所有案例的共同前提 | 一条诊断能携带责任层和证据等级 |
| 1 | 容量与占用来源拆分 | #630、#626、#2287，证据最充分 | 用户能区分三种责任层 |
| 2 | 约束前移与编译期检查 | #1935，收益明确且可度量 | 该类错误不再到达设备 |
| 3 | 执行时序与缓冲复用的解释 | 与 1、2 共享对象 | 用户能理解等待和复用条件 |
| 4 | 计算分工 | **证据不足（3.5），需先补案例** | 找到一个有确凿证据的昇腾分工决策任务 |

**顺序 4 的位置是本轮的一处实质修订。** 既有材料把计算分工列为首个试点，依据是对 CSA 编译产物的一个读法；该读法在本轮核对中不成立。在补到新证据之前，它不应占用试点资源。

# 附录 C：术语表

| 术语 | 含义 |
|---|---|
| AIC / AIV | Cube（矩阵）核 / Vector（向量）核。Ascend910B 有 48 个物理 AIV |
| `Left` / `Right` / `Acc` | PyPTO 中的 L0A / L0B / L0C，分别是 matmul 的左操作数、右操作数、累加器 |
| `Vec` / `Mat` | PyPTO 中的 UB（统一缓冲）/ L1（CBUF） |
| Tensor / Tile | 逻辑数据 / 它在片上的物理分块表达。两者的 shape 可以不同 |
| `valid_shape` | Tile 中实际有效的数据范围，可小于 `shape`。涉及正确性而不只是性能 |
| `blayout` / `slayout` / `fractal` | block 布局 / scatter 布局 / 分形尺寸。决定数据在片上的组织方式 |
| `tpush` / `tpop` | AIC 与 AIV 之间的数据交接原语。910B 上经 GM 中转 |
| C2V / V2C | Cube→Vector / Vector→Cube 方向的跨核传输 |
| hard / soft syncall | FFTS 硬屏障（要求满占用）/ GM 轮询同步（支持部分占用） |
| FFTS | 昇腾的硬件任务同步机制。hard 屏障基于它实现 |
| SPMD | 单程序多数据。`pl.spmd(N)` 启动 N 个 block |
| 507018 | AICore 超时错误码。本文案例三中由 hard 屏障死锁触发 |
| 高水位 | 某空间上 `max(addr + size)` 的统计口径。不等于实际同时占用（见案例四） |
| 责任层 | 本文定义的 L1–L4，表示某个硬件事实应由谁处理 |
| Callable / ExecSpan | 一段计算的领域身份 / 一次执行的资源与时间记录。沿用仓库既有规划用语 |
