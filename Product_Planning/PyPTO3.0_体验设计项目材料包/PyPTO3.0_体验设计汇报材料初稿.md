# PyPTO3.0 体验设计汇报材料初稿

> 版本：v0.1｜整理日期：2026-09-10  
> 用途：作为体验设计汇报的内容底稿，后续再根据汇报对象、时间和案例证据拆分为 PPT 页面。  
> 说明：本文是“简单但完整”的第一版，重点覆盖各个方向的广度，不展开具体页面布局、交互细节和最终指标。

## 一、项目总述：从“能跑”到“可信交付”

PyPTO3.0 面向的是 NPU 模型与算子开发者。它连接模型语义、算子代码、编译器、硬件指令、Runtime、正确性验证、性能优化和推理服务，是一条非常长、非常复杂的工程链路。

过去，用户往往可以通过不同工具完成其中某个环节，但很难在同一条链路上回答几个关键问题：

- 我表达的计算意图是否被正确理解？
- 代码经过编译和 Lowering 后变成了什么？
- 为什么在昇腾硬件上这样执行？
- 结果错了、变慢了或挂住以后，最早的问题发生在哪里？
- 当前结论是事实、推断还是猜测？
- 这个结果能否被别人复现、比较、回归和交付？

PyPTO3.0 的体验设计，试图把这些分散的问题组织成一个连续工作流：

> **让开发者能够用 AI 表达和实现意图，用昇腾硬件知识做出更好决策，并在全过程中获得可观测、可解释、可验证的反馈。**

它的最终目标不是增加更多工具入口，而是把“能运行的技术产物”升级为“可信、可解释、可复现、可回归、可交付的工程产物”。

## 二、为什么这个项目值得被关注

### 1. 它处在昇腾硬件价值转化的关键位置

芯片本身不会自动产生业务价值。模型能否迁移、算子能否高效执行、服务能否稳定运行，取决于硬件能力能否被开发者理解、调用、优化和验证。

PyPTO 所处的位置，正好连接了上层模型和下层硬件：一方面要理解模型的计算语义，另一方面要理解 NPU 的内存、计算单元、数据搬运、同步和通信机制。它是昇腾硬件能力向真实模型性能和服务体验转化的重要入口。

因此，PyPTO3.0 不只是一个开发效率工具，也可以被看作昇腾亲和能力的产品化入口。

### 2. AI 正在改变算子开发的基本方式

算子开发正在从“开发者手工写完所有代码”转向“开发者定义目标、约束和验收标准，AI 协助完成实现、分析和验证”。

AI 可以帮助开发者理解已有算子、检索相似实现、生成代码骨架、补充测试、解释编译结果、分析性能瓶颈、提出修复假设和生成复现包。但算子开发并不是普通代码生成问题，它还涉及 Shape、dtype、Layout、Tile、内存、依赖、同步、AIC/AIV 和硬件约束等多重语义。

所以，AI 带来的变化并不是简单地“让代码写得更快”，而是改变了开发者与复杂系统的协作方式：开发者需要更关注目标定义、方案判断、风险确认和结果验收，AI 需要能够理解工程上下文并用证据支撑自己的建议。

### 3. 系统复杂度让可观测和可解释成为基础能力

在模型、编译和硬件层级不断增加的情况下，仅仅提供更多日志和更多指标并不能解决问题。用户真正需要的是一条能被理解的因果链：

`用户意图 → 源码 → 编译变换 → 生成产物 → Runtime 任务 → 硬件执行 → 正确性/性能结果`

如果这条链路不可见，用户只能依赖专家经验进行人工拼图；如果这条链路不可解释，用户即使看到结论，也无法判断结论是否可信。

因此，可观测性不应只发生在运行时，也应覆盖目标定义、环境准备、编码、编译、验证、调优、服务接入和交付全过程。

## 三、用户正在经历的真实问题

### 1. 用户面对的不是单一开发任务

一个算子从想法到交付，通常要经历：

`定义契约 → 准备环境 → 编写 Kernel → 编译生成 → 仿真/Golden → 真机运行 → 正确性定位 → 性能调优 → Serving 集成 → CI 与知识沉淀`

过程中还会发生多次回环：环境不对需要回到准备阶段，编译错误需要回到源码，精度漂移需要回到中间 Tensor，性能回退需要回到 Tile、同步和内存策略，服务问题又可能回到 Cache、Shape 或多 Rank 契约。

### 2. 四类体验断层

#### 意图断层

用户想表达动态 Shape、数据依赖、内存生命周期或精度意图，但代码中往往只能通过隐式规则、额外参数甚至 workaround 来表达。这样会导致代码表达的不是业务计算，而是对编译器行为的暗示。

#### 证据断层

源码、IR、PTOAS、ISA、Runtime trace、Tensor diff、性能数据和版本信息分散在不同工具和目录中。用户看到的是很多局部结果，却无法快速判断这些结果之间的关系。

#### 协作断层

一个问题可能跨越模型、PyPTO、PTOAS、编译器、Runtime 和硬件多个责任域。用户需要自己判断应该把问题交给谁，专家则承担了人工路由和证据整理的工作。

#### 自动化断层

自动化工具和机器人可以发现大量问题，但信号可能重复、缺少分级，也缺少明确的人类决策记录。用户需要判断哪些建议可信、哪些建议需要验证、哪些建议不应执行。

### 3. 问题的本质

这些问题不能简单归结为“工具不好用”或“用户不熟悉业务”。更本质的问题是：

> **用户缺少一套把意图、硬件、编译、运行和验证连接起来的开发机制，只能依赖个人经验完成跨层判断。**

## 四、体验设计命题

### 1. 从工具集合转向开发控制面

PyPTO3.0 不以“再增加一套工具”为目标，而是把现有能力组织成一个统一的开发与优化控制面。用户可以从任务出发进入系统，不需要先理解每个仓库、工具和日志文件的边界。

### 2. 从代码编辑转向意图表达

用户不应只是在编辑器里填写 API，而应能够表达：我要实现什么计算、处理什么 Shape、使用什么精度、如何切分 Tile、如何映射到硬件、有哪些资源约束，以及最终需要通过哪些验证。

系统再基于这些意图，辅助生成实现、检查约束、解释变换并提出验证方案。

### 3. 从结果展示转向过程解释

系统不仅要告诉用户“通过”或“失败”，还要说明：

- 哪个阶段通过或失败；
- 发生了什么变化；
- 影响了哪些对象；
- 判断基于哪些证据；
- 当前结论有多大可信度；
- 还缺少哪些验证；
- 用户下一步可以做什么。

### 4. 从一次性输出转向可信资产沉淀

一次运行、一次诊断或一次调优不应该随着窗口关闭而结束，而应该沉淀为可复用资产：可信基线、复现包、回归用例、性能 Recipe、问题单、规则或服务准入报告。

## 五、三条核心设计主线

### 5.1 AI 原生的算子开发体验

#### 1. AI 介入的不是一个点，而是一条链

AI 可以贯穿算子生命周期：

- **理解**：解释算子数学语义、Shape、dtype、Layout、内存和执行阶段；
- **检索**：查找相似算子、硬件能力、历史问题、已有测试和调优经验；
- **生成**：生成实现骨架、测试样例、配置、文档和最小 Patch；
- **检查**：检查契约、依赖、资源、编译、正确性和性能风险；
- **推理**：根据源码、IR、日志、Trace 和基线提出责任域或性能假设；
- **执行**：在授权后运行编译、测试、Profile 和对比实验；
- **沉淀**：把验证通过的结论转成规则、Recipe、回归用例和知识资产。

#### 2. AI 让开发者角色发生变化

开发者不会消失，但工作重心会变化：

- 从逐行编写，转向定义意图和约束；
- 从人工翻查资料，转向审阅 AI 整理后的上下文；
- 从凭经验猜问题，转向比较候选假设和验证计划；
- 从亲自执行所有命令，转向授权并监督自动化动作；
- 从记录最终结果，转向验收证据并沉淀可复用资产。

#### 3. 算子开发 Agent 与普通 Coding Agent 的区别

普通 Coding Agent 主要关注代码语法、调用关系和测试结果；算子开发 Agent 还必须理解硬件和编译语义：

- 这个 Shape 是否满足 Tile 和对齐约束？
- 这个 Layout 是否适合当前 Vector 或 Cube 路径？
- 这个 Tensor 位于哪一级内存？是否造成容量压力？
- 这个依赖是业务语义还是为了规避编译器问题？
- 这个优化是否改变精度、同步、通信或 Cache 语义？
- 当前建议来自源码事实、规则推断，还是设备运行证据？

#### 4. AI 体验的关键原则

AI 不应被设计成一个悬浮的聊天窗口，而应嵌入源码、编译结果、运行详情和实验 Diff 中。每一次回答都应尽可能具备：

`结论 → 证据 → 影响 → 可信度 → 候选假设 → 最小验证动作`

在修改代码、重编译、真机实验和发布等关键动作前，应保留人类确认、授权和回退能力。

### 5.2 昇腾亲和的开发体验

#### 1. 昇腾亲和不只是“支持 NPU”

支持 NPU 只是最低层次的兼容。更高层次的昇腾亲和，是让用户能够理解并利用昇腾的计算、内存、数据搬运、同步、通信和编译能力。

#### 2. 四层亲和体验

##### 表达亲和

通过更接近计算意图的方式表达 Shape、dtype、Layout、Tile、并行、内存和依赖，减少字节计算、隐式默认和手工同步带来的风险。

##### 编译亲和

解释源码如何经过 Pass、IR、PTOAS 和 ISA 约束，哪些算子结构被保留、拆分、融合或重排，哪些变化会影响正确性、资源或性能。

##### 执行亲和

让用户看到 GM、L2、UB、L0、AIC/AIV、Pipeline、Barrier、Task、通信和多 Rank 之间的关系，理解最终代码在设备上怎样运行。

##### 优化亲和

性能建议要结合具体昇腾硬件、Shape、内存余量、Core 类型、通信拓扑和真实 Profile 数据，而不是提供脱离场景的通用规则。

#### 3. 硬件信息应该如何进入体验

硬件细节不应该被全部隐藏，也不应该一次性倾倒给用户。更合适的方式是渐进披露：

- 编码时提示当前约束；
- 编译前预览可能的风险；
- 编译后解释 Pass 和 IR 变化；
- 运行中展示数据流、同步和资源使用；
- 调优时提供面向硬件证据的归因；
- 需要时再深入专家级指令和原始 Trace。

#### 4. 亲和体验最终要帮助用户做决定

“昇腾亲和”不是让页面上出现更多硬件名词，而是帮助用户回答：

- 该算子适合哪种执行路径？
- 当前瓶颈是计算、搬运、同步、内存还是通信？
- 这个优化为什么对当前硬件有效？
- 需要牺牲什么，是否会影响正确性或稳定性？
- 这个结论是否可以在另一个 Shape、设备或服务负载下复现？

### 5.3 开发过程可观测、可解释

#### 1. 观察对象从 Runtime 扩展到全过程

需要被观察的不是单一的设备运行状态，而是整个开发过程：

`目标与契约 → 环境与基线 → 源码意图 → 编译变换 → 生成产物 → Runtime 执行 → 正确性/性能结果 → 回归与准入`

#### 2. 可观测回答“发生了什么”

可观测体验需要让用户看到：

- 当前任务进行到哪一步；
- 哪些对象已经生成、验证或失败；
- 哪些阶段发生了异常；
- 哪些指标相对基线发生了变化；
- 当前证据是否完整；
- 还缺少哪些数据或真实设备验证。

#### 3. 可解释回答“为什么这样判断”

可解释体验需要让系统说明：

- 结论引用了什么源码、规则、IR、日志、Tensor 或指标；
- 为什么判断某个阶段或责任域最可疑；
- 事实、推断和建议分别是什么；
- 结论的可信度和适用范围如何；
- 用户如何通过最小实验验证或推翻结论。

#### 4. 统一的诊断表达

建议所有诊断、Agent 建议和性能结论采用统一结构：

`严重度 / 一句话结论 / 影响 / 证据 / 可信度 / 建议动作 / 责任域 / 验证边界 / 可继续下钻内容`

这能避免不同工具用不同方式描述相似问题，也能让诊断结果直接进入问题单、回归和协作流程。

## 六、三条主线如何合成为一个工作台

### 1. 统一工作对象

PyPTO3.0 建议围绕五类对象组织产品：

| 对象 | 作用 |
|---|---|
| Intent / Contract | 表达目标、计算语义和约束 |
| Operator Object | 表达 Tensor、Tile、ComputeOp、依赖、内存和任务 |
| Run / Experiment | 表达一次编译、运行、验证或性能实验 |
| Evidence Graph | 连接源码、编译、运行、验证和指标证据 |
| Trusted Artifact | 沉淀基线、复现包、回归用例、Recipe 和准入报告 |

### 2. 统一端到端闭环

```text
表达意图
  → AI 生成或修改实现
  → 编译过程解释
  → 昇腾硬件执行观测
  → 正确性与性能验证
  → 人类确认与风险决策
  → 形成可信工程资产
```

AI 扩大理解、生成和搜索能力；昇腾亲和保证建议与实际硬件执行一致；可观测和可解释保证每一步都能被理解、验证和交接。

### 3. 统一产品形态

- **CLI**：适合自动化、CI、远程环境和专家操作；
- **IDE Extension**：适合编码时的意图反馈、源码联动和 Agent 协作；
- **Toolkit Studio**：适合跨层证据、时间线、正确性、性能、服务和实验对比；
- **共享底座**：Manifest、Run ID、对象 Schema、诊断协议、规则、权限和脱敏机制。

## 七、典型场景中的设计价值

### 1. 从模型子图到首个可信 Kernel

用户导入模型子图后，系统不仅生成代码骨架，还应展示算子覆盖、Shape/Layout、硬件能力、实现风险和验证计划。开发者可以在编码阶段理解数据流和硬件映射，在编译阶段查看关键变换，在运行阶段通过多 Oracle 和中间 Tensor 对比定位首个分歧，最终获得可复现的可信基线。

这里的核心变化，是把“写完代码再验证”变成“编码时理解、编译时发现、运行后证明”。

### 2. 从编译失败到首个可验证原因

系统聚合源码、配置、环境、最近成功基线、相关测试和编译日志，以 Pass 时间线呈现问题发生的位置，再将源码事实、IR Diff、约束违反和最终失败串成因果链。

Agent 不直接给出无法追溯的答案，而是提出多个候选假设，标记置信度，生成最小验证计划，并明确当前无法确认的证据。

### 3. 从“感觉变慢”到性能可归因

用户把新旧实验放入同一比较空间，系统锁定 Shape、版本、硬件、输入、Warmup 和指标口径，从服务指标逐层下钻到请求阶段、模块、rank、算子和 kernel。

性能结果进一步拆解为计算、搬运、同步、内存、通信和调度原因；每个优化候选都同时经过正确性和资源门禁，避免“变快了但结果不可信”。

### 4. 从模型接入到可交付服务

系统在模型导入阶段识别算子覆盖、fallback、精度和硬件限制，通过 Inference Runner 串起 prompt、token 和 text，再将 logits、decode step、KV Cache、Runtime 任务和服务指标关联起来。

只有当模型正确性、服务稳定性、容量、性能和兼容性都在声明边界内通过后，才形成服务就绪报告和可复现部署清单。

## 八、价值表达

### 1. 对用户的价值

- 更早知道环境、能力和约束是否成立；
- 更快找到错值、hang、编译失败和性能回退的首个异常；
- 更容易理解源码如何映射到昇腾硬件；
- 更放心使用 AI，因为建议有证据、边界和验证动作；
- 更少依赖个人经验完成跨层排查；
- 更容易把一次实验沉淀为可复现、可回归和可交付的资产。

### 2. 对业务的价值

- 降低算子开发、模型接入和问题定位的时间成本；
- 减少性能优化中的无效实验和错误归因；
- 降低跨团队交接和问题复现成本；
- 提高昇腾硬件能力在真实模型和服务场景中的转化效率；
- 将专家经验沉淀为团队可复用的规则、Recipe、基线和回归资产；
- 为模型和服务发布提供更明确的风险边界和准入依据。

### 3. 对体验设计组织的价值

体验设计的工作不再只是页面布局和交互细节，而是进入复杂技术产品的底层机制设计：

- 定义产品的核心对象；
- 组织跨层信息关系；
- 建立复杂系统的渐进披露方式；
- 设计 AI 的可信协作和人类控制边界；
- 建立硬件亲和的体验语言；
- 将可观测、可解释和可回归变成产品默认行为。

这使体验设计能够沉淀为一套面向复杂计算系统的通用方法，而不仅是一组孤立页面。

## 九、落地与验证

### 1. 建议的落地顺序

第一阶段先建立统一 Run、Manifest、对象 Schema、source span 和 Evidence Graph，解决“结果无法识别、无法关联、无法复现”的基础问题。

第二阶段建立环境、编译、Runtime、正确性和性能的最小可观测闭环，先让用户能够看到状态、原因、证据和缺口。

第三阶段在证据底座上引入 AI Agent，提供上下文理解、候选假设、代码提案和最小验证计划。

第四阶段逐步增强昇腾亲和能力，把 AIC/AIV、内存、Tile、同步、通信和硬件约束转化为开发过程中的可理解反馈。

第五阶段扩展到模型推理、Serving、组织级 Recipe 和跨版本迁移。

### 2. 需要验证的不是页面是否漂亮

后续应重点验证：

- 不同角色能否理解当前状态和下一步动作；
- 用户能否更快完成责任域定界；
- AI 建议是否能够被证据和实验验证；
- 用户是否清楚自动化动作的授权点和回退方式；
- 用户是否能据此做出更符合昇腾执行特征的实现选择；
- 一次问题是否能沉淀为后续可复用资产。

### 3. 建议建立的指标类别

现阶段先确定指标框架，不急于承诺具体数值：

- **可信度**：高危静默错误提前发现率、证据完整度；
- **效率**：从首次运行到可信产物的时间、异常定位时间、实验次数；
- **AI 协作**：提案采纳率、验证通过率、人工回退率；
- **昇腾亲和**：硬件约束被利用的程度、性能归因率、资源问题拦截率；
- **可观测性**：过程状态覆盖率、跨层关联完整度、未验证项可见性；
- **交付性**：复现包、回归用例、Recipe 和服务准入报告的生成与复用情况。

## 十、当前材料还需要补充的内容

为了让后续汇报更有说服力，还需要补齐几类案例材料：

1. 一个算子从人工开发转向 AI 协同开发的前后对比；
2. 一个真实算子中 Shape、Tile、内存、AIC/AIV、同步和性能之间关系的案例；
3. 一个 Run 从意图、环境、Pass、Runtime 到正确性/性能结论的全过程案例；
4. 一个编译失败或性能回退案例，明确区分事实、推断、证据缺口和验证动作；
5. 一个真实业务试点，用于建立定位时间、实验次数、模型接入时长或复现完整度的前测基线；
6. 一套体验设计资产清单，包括对象模型、信息分层、诊断卡片、证据状态、Agent 状态和硬件语义反馈模式。

## 十一、结语

PyPTO3.0 的体验升级，本质上不是把复杂系统“做得更简单”，而是让复杂度能够被看见、被解释、被验证和被管理。

在 AI 时代，算子开发会越来越依赖人和智能体的协作；在昇腾生态中，硬件能力需要通过更亲和的开发体验转化为用户价值；在跨层工程系统中，过程可观测和结论可解释则是建立信任的前提。

因此，PyPTO3.0 希望构建的不是一个单纯的代码工具，而是一种新的开发体验：

> **AI 帮助开发者扩大能力，昇腾硬件帮助开发者获得性能，证据链帮助开发者建立信任，统一工作台帮助团队把结果交付出去。**
