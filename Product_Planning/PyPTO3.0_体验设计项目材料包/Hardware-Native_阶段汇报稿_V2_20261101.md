## 一、这部分在整个汇报里的位置

承接用户任务与开发流程洞察，回答一个问题：**为什么昇腾 Hardware-Native 是本次 UX 项目必须关注的体验方向，以及从中识别出了哪些工具机会。**

叙事链：

> 昇腾硬件长什么样 → 框架已经承担了什么 → 剩下那部分出了什么问题 → 问题的共同结构 → 机会点 → 怎么验证

本稿用 HN-01 至 HN-09 作为专题局部编号，不改变整份项目汇报的页码。

**本轮叙事的变化。** 旧稿把四类硬件机制（分工、形态、路径、时序）作为主线，机会点是 O1–O4。本稿改为以**三个核心洞察加一个自证案例**为主线，机会点收敛成一套分类（四责任层 × 四决策对象）。原因是：按硬件机制分类是技术视角，它无法回答"这件事该不该进界面"；而按"谁来决定"分类可以，并且直接给出评审判据。

## 二、九页文案

### HN-01｜昇腾开发的关键挑战：计算怎么写，只决定了一半

模型与算子开发从计算意图出发。但在昇腾上，**计算表达本身并没有决定它怎么执行。**

另一半是四个必须落实的决定：

- 这段数据放哪块片上空间
- 切多大
- 谁来算
- 什么时候交接

这些规则来自硬件。它们写在编译器的校验里、后端的容量表里、ISA 的契约里。

**但它们进入开发者视野的方式，通常是一条编译失败，或者一次设备超时。**

**本项目对 Hardware-Native 的工作定义**

> 软件系统在抽象、映射、调度和执行时尊重目标硬件的能力、约束与成本；并且当某条硬件约束必须由开发者参与处理时，系统让这个决定可理解、可操作、可验证。

两句话缺一不可。只有前半句是"硬件亲和优化"，那是编译器的工作；只有后半句是把复杂度甩给用户。

**核心洞察**

> 我们关注的体验问题是：当硬件约束影响开发选择时，工具能否帮用户理解影响并作出决定。

*讲者备注：定义是本项目的工作定义，不是行业统一标准。如被问"这是不是编译器团队的事"，回到 HN-08 的责任层判据——四个案例里三个的首要责任确实在技术侧，这一点我们在 HN-08 明确承认并给出了 UX 的正当职责。*

### HN-02｜先把硬件讲清楚：三个数字，一条不能绕的路

昇腾的片上存储不是层级缓存，而是**一组用途固定的专用空间**。这是与 GPU 最大的心智差异。

| PyPTO 空间 | 硬件 | 用途 | Ascend910B |
|---|---|---|---:|
| `Left` | L0A | Matmul **左**操作数 | 64 KiB |
| `Right` | L0B | Matmul **右**操作数 | 64 KiB |
| `Acc` | L0C | Matmul 累加器 | 128 KiB |
| `Vec` | UB | Vector 计算、Tile load | 188,416 B 有效 |
| `Mat` | L1 | Cube 操作数暂存 | 512 KiB |

**一条不能绕的路：**

```
DDR → Vec / Mat → Left / Right / Acc
```

`tile.load` 到不了 L0。一次 matmul 的操作数至少经过两跳，中间那一跳由编译器**自动插入** `tile.move`。

**还有两个数字要记住：**

- Ascend910B 有 **48 个物理 AIV 核**
- AIC 与 AIV 之间交接数据要经 GM 中转，预留的缓冲从 UB 的 188,416 里直接扣掉——**用户代码里没有任何一行提到它**

这一页不是硬件科普。**后面三个案例的报错，全部由这几个数字构成。**

**核心洞察**

> 这些不是背景知识，而是开发者每天会撞到的边界。工具要么帮他理解这些边界，要么让他在边界上反复试错。

*讲者备注：容量数字绑定 Ascend910B 及报告时的工具链版本。Ascend950 的 L0C 是 256 KiB、访存粒度从 512 B 变为 128 B——所以这些数字必须从目标档案查询，不能写死在前端。*

### HN-03｜但大部分硬件复杂性，框架已经承担了

这一页用来排除一个错误方向。

PyPTO 的内存配置不是在某个 API 里一次确定的，而是沿编译流水线逐步落实：

```
Tensor / Tile 语义
  → InferTileMemorySpace      推导 Tile 所在空间
  → AutoTileMatmulL0          按 L0 容量自动选 m/n/k
  → ResolveBackendOpLayouts   修复后端要求的布局
  → ExpandMixedKernel         划分 AIC/AIV 与跨核边界
  → LowerPipelineLoops        生成多 stage / ping-pong 缓冲
  → MemoryReuse               按生命周期与别名规则复用
  → AllocateMemoryAddr        分配实际片上地址
  → codegen / PTOAS
```

框架已经在做的事包括：按 L0 容量自动选分块、自动插入跨空间搬运、自动划分 AIC/AIV 边界、按生命周期复用缓冲、以及维护一份"哪些算子不能原地复用"的清单。

**所以体验问题不是"用户需要学会这些"。**

真正的体验问题只在剩下那一小部分：**框架处理不了、处理错了，或者处理了但用户必须知道结果的时候。**

**核心洞察**

> Hardware-Native 做对了的样子，可能是用户看到的硬件细节**更少**。衡量标准不是用户理解了多少硬件，而是用户不需要理解多少硬件仍能把事做对。

*讲者备注：这一页直接排除"做一个硬件工作台/芯片展板"的方案。如有人提议增加硬件可视化，用 HN-08 要求六回应——先问这件事为什么不能由框架决定。昇腾官方的 Ascend C 用 TPipe/TQue 承载复杂性，也是同一个取向。*

### HN-04｜洞察一：信息不缺，缺的是归因

**真实报错，PyPTO #2287：**

```
ValueError: Vec buffer usage (213760 bytes) exceeds platform limit (188416 bytes).
The first 131072 bytes of that space are reserved by system.reserve_buffer, so tiles are
allocated above them - this is the cross-core pipe ring. Lower its depth with
optimizations=[pl.cross_core_slot(slot_num=N)] on the enclosing pl.at(...), or shrink the
tile that crosses the cube/vector boundary
```

**先肯定它。** 用量、上限、超出部分的归属、预留大小、两条修复建议——按任何诊断设计规范衡量，这都是一条好报错。

**然后看真相。两条建议都是错的。**

这个 kernel 的跨核载荷严重不对称：

| 方向 | 消费者 Tile | 字节 |
|---|---|---:|
| V2C（AIV → AIC） | staged KV tile | 131,072 |
| C2V（AIC → AIV） | `qk_raw` `[32, 128]` FP32 | **16,384** |

编译器把两个方向的缓冲都按**双向最大值**预留。于是 **16 KB 的载荷，在最紧张的 UB 里占了 131,072 字节的坑——8 倍过量。**

正确尺寸应为 32,768 字节，总占用 115,456 / 188,416，**轻松装下**。

- 建议一"降低环深度"：报告实测，强制最小深度后预留仍是 131,072，依然超 25,344 字节。
- 建议二"缩小跨边界的 Tile"：让开发者为编译器的缺陷付出真实性能代价。

**最刺眼的一点：** 报错里说的"前 131,072 字节被预留"，恰恰就是那个算错的数。**工具把缺陷的产物当作既定事实报告给了用户。**

**核心洞察**

> 一条诊断的价值，等于归因正确率**乘以**可操作性——不是两者之和。#2287 的可操作性接近满分，归因错误，于是乘积为负：它主动把开发者引向了错误的修复。

*讲者备注：commit 7d743e8d，Ascend 910B / A2A3，Issue 已关闭为 not planned——关闭不自证修复。这条洞察的产品含义是：归因不确定时，降低建议的确定性比提高建议的具体性更重要。*

### HN-05｜洞察二：同样的报错，完全不同的责任

把两个 Issue 的报错并排放：

```
#630:  Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)
#626:  Right buffer usage (131072 bytes) exceeds platform limit (65536 bytes)
```

同样的空间、同样的上限、同样的措辞、同样的 pass。

**但责任层完全不同：**

**#630** 是真的放不下。`kv_lora_rank` 从 128 改到 512，只改了一个模型维度。而它的根因是一次**抽象退化**——PTO 2.0 里开发者只需一行：

```python
set_cube_tile_shape([M_TILE, K_TILE, N_TILE])   # 框架自动生成循环
```

PTO 3.0 取消了这个接口，同一件事变成手写三层循环加逐块处理；RMSNorm 还要自己处理跨 chunk 的 reduce。提报人直接要求恢复一个声明式接口：`@pl.tile_policy(matmul_tile=[128, 512, 128], ...)`。

**#626** 根本不需要用户改任何东西。编译器的容量校验用了一个不考虑生命周期的高水位算法 `high_water = max(addr + size)`，把两个生命周期可以错开的 64 KiB 变量直接累加成 131,072，**拒绝了一个合法的 kernel**。

**开发者没有任何办法从报错里区分这两种情况。**

面对 #626，一个尽责的开发者会去缩小 Tile。他会成功——因为缩小后确实能通过校验。代价是白白损失性能，而真正的缺陷留在原地。

**核心洞察**

> 归因错误不只浪费时间。它会制造错误的修复，并且掩盖真正的缺陷。因此每条诊断必须携带**责任层**：确认是用户配置问题、确认是系统问题、或尚不能区分。第三种状态是诚实的，也是有用的——它告诉用户该去提 Issue，而不是继续试参数。

*讲者备注：#630 仍 open，#626 已关闭。#630 这个案例会反驳一个常见直觉——面对容量报错，产品的第一反应是"做更好的容量可视化"，但提报人要的是把决定还给框架。这正好支撑 HN-03。*

### HN-06｜洞察三：本可以静态检查的，代价是一次设备重置

**真实代码，PyPTO #1935：**

```python
N = 24  # < 48 物理 AIV -> 部分占用（N = 48 为通过的对照）

pl.system.syncall(core_type="aiv_only")   # HARD barrier
...
with pl.spmd(N):                           # N=24 -> 部分占用
```

**结果：**

```
[ERROR] AICore error 507018: bounded device drain failed (force reset will follow)
RuntimeError: run_prepared failed with code 507018
```

设备随后不可用，后续任务报 `code 13` 直到恢复。**这是共享开发设备，影响不止一个人。**

**根因。** hard 屏障（FFTS）等待该核型的**每一个物理核**到达。910B 有 48 个 AIV，启动了 24 个 block，另外 24 个核永远不会到达，等待永不完成。

`pl.spmd(24)` → 507018；只把 24 改成 48 → PASS。**占用度是唯一变量。**

**三件让这个案例特别刺眼的事：**

1. **编译期完全可判定。** 编译器同时掌握 `pl.spmd(N)`（写在源码里）和该 SoC 每种核型的物理核数（在后端参数表里）。这是一次静态整数比较。
2. **这条知识当时已经在仓库里。** 它写在 `tests/st/runtime/cross_core/test_syncall.py` 的 docstring 里——一个开发者写代码时不会打开的文件。
3. **替代方案也已经存在。** soft 模式在部分占用下工作正常。开发者需要的不是新能力，只是在选 hard 的那一刻知道它有这个前提。

提报人自己写出了理想的诊断，几乎就是样板：

> `hard pl.system.syncall(core_type="aiv_only") requires the spmd launch to fill all 48 AIV cores, but pl.spmd(24) launches 24 blocks. Use mode="soft" (GM-polling) for partial occupancy.`

违反了什么约束、具体数字对比、可执行的替代方案——三件齐全。

**核心洞察**

> 代价不对称到了荒谬的程度：一次静态整数比较，对应一次设备强制重置。这是**时机错误，不是信息缺失**。凡是编译期可判定的约束，都应该在编译期拒绝。

*讲者备注：这一页首先是编译器的工作项，不是界面需求——务必主动说明，否则会被正确地质疑。UX 在这里的正当职责有两条：参与设计这条诊断怎么写，以及让 hard/soft 的契约差异在用户写下 `mode=` 的时刻可见（编辑器集成），而不是补一篇文档让用户去记。*

### HN-07｜洞察四：连我们自己，也读错了编译产物

这一页讲我们自己的一个错误。它是本专题最强的论据。

**旧稿的主张。** 20261031 版材料据 CSA 编译产物断言：`qk_pv_aiv` 双 AIV 派发，但第二条分支的 softmax Tile `valid_shape=[0,0]`，据此识别出"有效计算未分摊到第二个 AIV"，并把**计算分工列为首个试点任务**。

**本轮直接核对那份产物，结论是这个读法站不住：**

- `dual_aiv_dispatch` 属性确实存在（第 2952 行）——这部分属实。
- 但两个 subblock 分支的迭代次数由**同一个表达式**决定：`(qk_items - qk_core + 23) // 24`（第 2964、3025 行）。从产物看不出哪一支不干活。
- `valid_shape=[0, 0]` 在该文件出现 **68 次**，遍布不同函数、不同分支，包括明显在做实际计算的 Tile。**它是 `TileView` 的默认哨兵标注，不能按字面读成"有效数据为空"。**

**"第二个 AIV 没有分摊有效计算"这个判断，在当前证据下不成立。**

它可能仍然为真，但需要别的证据——分支实际执行次数、profiling、或对 `set_validshape` 调用链的完整追踪。

**为什么把这件事放进汇报。**

读错这个字段的，不是赶工期的开发者。是在专门研究这个主题、有充足时间、直接打开了编译产物的研究者。

**核心洞察**

> 如果连我们都会读错，那么"把硬件事实摆出来让开发者自己判断"就不是一个可行的设计策略。原始产物是必要的证据底座，但它不能充当界面。工具的价值恰恰在这里：把需要上下文才能解读的字段，翻译成"这个 Tile 的有效范围是 X，依据是 Y"——或者在无法确定时，明确说"此处该字段不可解读"。

*讲者备注：这一页也修正了一个机会点的证据状态——计算分工目前缺少确凿的昇腾案例证据，因此在 HN-09 的推进顺序里从"首个试点"降到第 4 位。主动讲这个修订会增加整份材料的可信度，不要回避。同一份产物确实交叉验证了 HN-04 的数字：`qk_raw` 为 `[32, 128] FP32`，32×128×4 = 16,384 字节，与 #2287 报告一致。*

### HN-08｜机会点：按"谁来决定"分层，而不是按硬件机制分类

四个案例指向同一个结构问题：**一条硬件事实该不该进界面，取决于谁来决定它。**

**四个责任层**

| 层 | 含义 | 本专题案例 |
|---|---|---|
| **L1 系统保证** | 系统必须正确处理，不应进入用户视野 | #1935 的满占用检查、#626 的生命周期校验、#2287 的分方向预留 |
| **L2 必须可见** | 系统处理了，但用户需要知道结果 | 自动插入的 `tile.move`、跨核管道的 UB 预留、自动选中的 m/n/k |
| **L3 必须可控** | 用户需要表达系统无法推断的意图 | #630 要的 `tile_policy`、#2287 要的 `local_slot_num`、hard/soft 选择 |
| **L4 必须可验证** | 用户需要确认结果符合预期 | 改动后的实际分配、数值结果、目标链路耗时 |

**这个分层给出一条评审可直接使用的判据：**

> 任何 Hardware-Native 设计提案，先问它属于哪一层。如果答案是 L1，它是技术任务，不是设计任务。

**我们主动说明：四个案例里，三个的首要责任在 L1。**

这不削弱这个方向，而是**界定**了它。UX 在 L1 问题上的正当工作是：参与设计那条诊断（说什么、在哪说、给什么出路），以及在修复落地前组织用户的判断——不是用提示框替代修复。

**四类决策对象，与各自的证据状态**

| 决策对象 | 核心问题 | 证据状态 |
|---|---|---|
| **形态与容量** | 数据怎么放 | **充分**（#630、#626、#2287） |
| **执行时序** | 什么时候交接 | **充分**（#1935） |
| **数据交接** | 数据怎么走 | 跨核有强证据；Cube↔Vector 融合缺真实任务 |
| **计算分工** | 谁来算 | **不足**（见 HN-07） |

**从案例反推的设计要求**（完整七条见研究报告第五部分，此处为最强三条）

1. **诊断必须标注责任层。** 来自 #626 vs #630。
2. **资源占用必须按来源拆分，并标明每项由谁决定。** 至少区分计算 Tile、临时工作区、通信缓冲、系统预留；对自动生成的部分，保留"这个数字本身可能有问题"的余地。来自 #2287。
3. **先问能不能自动，再问怎么呈现。** 如果答案是"框架以前能、现在不能了"，那是退化，应优先修复而不是补界面。来自 #630。

**核心洞察**

> 机会点不是四个硬件领域，而是一张"责任层 × 决策对象"的表。每个格子对应一个具体设计动作——例如"执行时序 × L1"就是"哪些同步约束必须编译期拒绝"。

*讲者备注：这套分类替代了旧稿的九域、六承载形态、四类硬件机制和 O1–O4 四套并行分类。按硬件机制分类是技术视角，它无法回答"该不该进界面"；按"谁来决定"可以。*

### HN-09｜怎么证明这个方向值得投

**可证伪的假设**（每条都配了放弃条件）

| 假设 | 验证任务 | 什么情况下应当放弃 |
|---|---|---|
| **H1** 标注责任层能减少错误修复 | 给出 #626 与 #630 两条文本相同的报错，让开发者判断该改什么 | 开发者本来就能区分 |
| **H2** 拆分占用来源能让用户找对对象 | #2287 场景：判断该缩 Tile 还是报 Issue | 现有报错已足够 |
| **H3** 约束前移能减少无效设备实验 | #1935 场景：离线判断 hard/soft 是否匹配 | 编译器加检查后问题消失，界面无额外价值 |
| **H4** **自动化比可视化更有价值** | #630 场景：对比"更好的容量可视化"与"恢复 tile_policy" | 用户确实想要手工控制 |
| **H5** 翻译硬件字段能减少误读 | HN-07 场景：从编译产物判断双 AIV 分工 | 原始字段配文档已够用 |

**H4 最该先做。** 它直接检验本专题的反直觉结论。如果结果显示用户更想要可视化而不是自动化，HN-03 和设计要求三都需要重写。

**对照设计。** 三个版本：现状 / 加结构化诊断与责任层标注 / 再加局部硬件可视化。用难度相近的任务和顺序平衡，分别识别"更好的信息组织"和"额外可视化"各自的贡献。

**推荐的核心指标：错误归因次数。**

四个案例里有三个的核心损失都由归因错误造成，而它恰好是现有工具完全没有度量的东西。

不要用的指标：面板点击数、用户看过多少硬件名词、资源填满比例、用户会不会说"Hardware-Native"。

**推进顺序**

| 顺序 | 内容 | 依据 |
|---|---|---|
| 0 | Target / Finding / 证据等级的数据模型 | 所有案例的共同前提 |
| 1 | 容量与占用来源拆分 | 证据最充分 |
| 2 | 约束前移与编译期检查 | 收益明确且可度量 |
| 3 | 执行时序与缓冲复用的解释 | 与 1、2 共享对象 |
| 4 | 计算分工 | **证据不足，需先补案例** |

**衔接后续方案**

> 接下来，我们以容量与占用归属作为第一个试点任务，把"模型配置 → 分块 → 物理 Tile → 空间分配 → 容量上限"这条链路显式化，并在每一环问一次"这件事能不能自动"。通过任务对照验证哪些硬件事实需要显性呈现、哪些应由系统承担。

*讲者备注：推进顺序来自证据成熟度与可验证性，不是发生率或 ROI 排名——四个案例来自定向检索，不构成抽样。安全约束：#1935 这类问题用离线材料或已知测试用例验证，不为研究故意使共享设备挂死。*

## 六、汇报收束段落

> 昇腾上的模型与算子实现，需要同时处理专用存储、核间分工、跨核交接和异步同步。这些机制直接影响分块、放置、融合和流水选择。但真实开发记录显示，问题通常不是硬件信息缺失——报错里的数字往往是齐全的。问题是归因：同样一条"Right buffer 超限"，可能要改分块，也可能是编译器校验算错；一条措辞确定的建议，可能把开发者引向错误的修复；一次本可静态完成的整数比较，代价是设备强制重置。我们自己在读编译产物时也犯了同类错误。因此本阶段将 Hardware-Native 收敛为一个结构问题——**一条硬件事实该不该进界面，取决于谁来决定它**——并按四个责任层组织机会点。能由系统可靠处理的复杂性应当继续自动承担，且优先于任何界面改进；需要用户参与的决定，则提供明确的对象、责任归属与证据等级。
