## 二、8 页阶段汇报核心文案

### HN-01｜昇腾开发中的关键挑战，是把计算意图转化为适合硬件的执行方式

模型与算子开发从计算意图出发，但计算表达本身，并没有完整决定它在昇腾上如何执行。

以 Attention 为例，QK、softmax、PV 构成连续的算法过程。落到设备上，还需要确定：

- **计算分工**：哪些计算交给 AIC，哪些交给 AIV，数据如何切分。
- **数据形态**：Tensor 如何形成 Tile，以什么布局进入对应存储空间。
- **数据路径**：中间结果经过哪些存储、搬运和转换，如何交给下一阶段。
- **执行时序**：哪些搬运与计算能够重叠，何时可以交接和复用缓冲。

这些决定共同影响实现的正确性、资源占用和性能。框架与编译器承担其中大量工作，开发者仍然需要在配置、优化和问题定位时理解或核验关键选择。

**本项目对 Hardware-Native 的理解**

> 软件系统尊重目标硬件的能力、约束与执行成本，并让需要开发者参与的硬件相关决定，具有可理解、可操作、可验证的依据。

因此，我们关注的体验问题是：**当硬件机制影响开发选择时，工具能否帮助用户理解影响并作出决定。**

**依据与证据边界**

研究底稿第 2、3 节；[Ascend C 同步控制简介][S17]。上述定义是本项目工作定义，不是行业统一标准；示例中的实际映射取决于目标、实现与编译结果。

### HN-02｜昇腾的四类硬件机制，具体改变了开发者需要处理的对象与选择

昇腾的硬件特征，需要通过具体开发对象进入工具设计。

| 硬件机制 | 对开发实现的影响 | 开发者需要处理的对象与选择 |
| --- | --- | --- |
| **AIC／AIV 分工** | 矩阵计算与向量计算需要分别映射，并组织交接 | 计算区域、切分轴、有效 Tile；决定谁处理哪些数据 |
| **专用存储与布局要求** | 不同计算使用不同存储空间，容量和布局分别受限 | Tensor、Tile、分块、布局、buffer；决定数据怎样放入并参与计算 |
| **目标相关的数据通路** | 中间结果的可用搬运路径受到架构与软件支持约束 | 生产者、消费者、中间 Tensor、融合边界；决定数据怎样传递 |
| **异步执行与同步机制** | 搬运和计算可以并行，但必须满足数据依赖与复用条件 | stage、slot、事件、屏障、buffer 生命周期；决定何时执行、交接和复用 |

以 2201 架构为例，AIC 与 AIV 分离，核配比为 1∶2；L0A、L0B、L0C、UB 等存储具有不同用途。这意味着“增加并行”和“降低内存占用”都需要落实到具体对象。[Ascend C：2201 架构][S18]

硬件代际也会改变实现条件。例如，3510 相比 2201 增加了 L0C→UB、UB→L1 通路。因此，工具中的可选策略必须关联目标架构及软件支持范围。[Ascend C：数据通路][S19]

**核心洞察**

> 昇腾 Hardware-Native 的设计内容，存在于“硬件机制怎样改变开发对象和可选操作”的具体关系中。

**依据与证据边界**

研究底稿第 3.4、5 节。2201 示例不外推为全部昇腾设备的固定核数或容量；3510 的硬件路径不代表当前 PyPTO 后端已支持或实际采用。不同空间的空闲容量不能直接合并理解为可互换预算。

### HN-03｜已有开发记录表明：看见硬件信息，仍不足以完成关键判断

源码、错误信息和编译产物已经包含部分硬件事实，但开发者仍需进一步解释这些事实与当前选择之间的关系。

| 案例 | 已经出现的事实 | 仍需完成的开发判断 |
| --- | --- | --- |
| **CSA 的 AIV 分工** | 双 AIV 派发，但第二条分支的相关 softmax Tile 有效形状为零 | 是否需要切分有效计算？怎样切分才符合算法语义？是否影响整体耗时？ |
| **模型维度变化引发 Right 超限** | `kv_lora_rank` 增大后，Right 使用量超过目标限制 | 保留模型要求时，应改变哪个维度的分块？会增加什么执行成本？ |
| **跨核 FIFO 预留占用过大** | 开发记录报告消费者本地缓冲的预留策略导致 UB 容量失败 | 占用来自计算 Tile 还是通信缓冲？应该修改用户配置还是系统生成策略？ |
| **部分核参与硬同步导致超时** | 历史案例中，启动核数与硬同步要求的参与范围不匹配 | 当前同步方式是否适合实际参与者？哪些条件应在编译前检查？ |

这些案例揭示了三个具体困难：

- **同一个代码选择会影响多个硬件对象。** 调整分块可能同时改变存储、搬运和循环结构。
- **表面现象与实际原因之间存在距离。** 容量超限不一定来自计算 Tile；派发多个核也不等于有效计算已分摊。
- **合法实现与有效优化需要分别判断。** 编译通过、结果正确、局部改善，分别回答不同问题。

**核心洞察**

> 开发者需要跨越计算表达、物理资源和实际执行，才能理解一次选择的完整后果。这种关联工作构成了具体的体验设计机会。

**依据与证据边界**

研究底稿第 6.1、6.2、6.4、6.7 节；[CSA 编译产物][L08]、[PyPTO #630][S04]、[PyPTO #2287][S07]、[PyPTO #1935][S05]。案例属于特定版本的开发记录，未在本项目独立复现。#1935 已关闭；#630、#2287 的关闭状态也不能自行证明问题已修复。第三列及跨案例归纳为 UX 分析，不是发生率统计。

### HN-04｜Hardware-Native 的体验价值，是支持开发者完成必要的硬件相关决定

从前述案例可以看到，工具需要连接三个层次：

**用户想实现什么 → 系统实际怎样映射 → 这一映射产生什么结果。**

只有这三层建立联系，用户才能回答：

- 这个限制为什么与我的代码有关？
- 当前实现有哪些可调整的选择？
- 一项修改会同时影响哪些计算、存储和交接？
- 哪些结果能够证明修改有效？

这需要框架、编译器与 UX 共同参与。

| 技术系统承担的能力 | 体验设计需要完成的连接 |
| --- | --- |
| 目标能力查询、合法性检查 | 将限制关联到当前参数、代码位置和可选策略 |
| 分工、布局、分配与搬运生成 | 解释用户表达与最终实现之间的关系 |
| trace、资源信息和数值验证 | 将执行证据关联到具体对象与优化目标 |
| 编译与实验执行 | 组织候选比较，帮助用户决定是否采用 |

**显性化的边界**

能够由系统可靠处理的复杂性，应由系统自动承担；当用户需要权衡、系统无法确定，或执行结果偏离预期时，再呈现相关硬件事实与控制入口。

**阶段判断**

> Hardware-Native 是值得投入的体验方向，因为硬件相关选择已经进入真实开发任务，而这些选择的依据与后果仍需要更有效地组织。具体界面形态及收益，需要通过任务验证。

**依据与证据边界**

研究底稿第 1、4.4、7 节。这是基于技术机制与案例形成的职责和机会判断；不以界面提示替代编译器修复，也不宣称已测得效率收益或已证明最高优先级。

### HN-05｜围绕四类开发决定，形成四个昇腾 Hardware-Native 设计机会

四个机会围绕具体开发对象展开，分别支持计算分工、数据放置、数据传递和执行衔接。

| 机会点 | 核心开发对象 | 工具需要支持的决定 | 预期体验价值 |
| --- | --- | --- | --- |
| **O1：面向 AIC／AIV 协同的计算分工设计** | 计算区域、切分轴、有效 Tile、核间交接 | 哪段计算交给谁？怎样分担有效数据？ | 理解分工后果，选择并验证合理的切分 |
| **O2：面向片上存储的 Tile 形态与资源设计** | 分块、布局、存储空间、buffer、生命周期 | 怎样保持计算语义，并满足对应空间的资源要求？ | 找准资源压力来源，比较可行实现 |
| **O3：面向 Cube／Vector 交接的数据路径与融合设计** | 中间 Tensor、生产者／消费者、搬运与转换、融合边界 | 中间结果怎样传递？哪种融合真正减少执行成本？ | 根据实际路径选择融合边界与实现 |
| **O4：面向多流水协同的并行与同步设计** | stage、slot、依赖、事件、屏障、缓冲复用 | 哪些操作能够重叠？何时能够交接与复用？ | 配置正确且有效的并行，理解等待原因 |

四个机会需要在同一任务中关联。例如，改变 AIV 切分后，还要核对 Tile 占用、交接方式和同步关系。

模型与算子场景可以采用不同入口：

- **模型开发者**从模块、输入配置和实现方案进入，判断适用条件与整体收益。
- **算子开发者**进入计算区域、Tile 和交接对象，控制具体策略。
- 两者通过同一份编译与运行证据建立联系。

**设计原则**

> 用约束提示、映射解释、影响分析和实验比较，支持这四类具体决定。它们是贯穿机会点的方法，而非独立的领域机会。

**依据与证据边界**

研究底稿第 6.8、7.7 节。四个机会是基于当前研究收敛的方向，不是全部模型开发问题的穷尽分类，也不是四个必须建设的独立页面。O3 的架构依据明确，真实融合决策任务的用户证据仍需补充。

### HN-06｜以 CSA 为例：从识别空闲 AIV，推进到计算分工决策

CSA 中的 QK、softmax、PV，为探索 AIC／AIV 协同提供了具体对象。

**当前证据**

编译产物显示，`qk_pv_aiv` 采用双 AIV 派发，但第二条分支的相关 softmax Tile 为 `valid_shape=[0,0]`，并保留管道交接操作。

这支持我们识别出“有效计算未分摊到第二个 AIV”的映射现象，但尚不能证明它构成性能瓶颈。

**用户真正需要决定的是：是否尝试切分，以及怎样确认切分有价值。**

建议围绕这一决定组织探索：

1. **理解当前分工。** 将 QK、softmax、PV 与 AIC／AIV 对应起来，呈现各分支的有效数据范围及交接关系。
2. **建立候选策略。** 将按行切分作为候选，核对其与归约维度、结果组合和消费者要求的关系。
3. **核对实现变化。** 重新编译，确认有效 Tile、分配和交接是否按预期改变。当前“32/0 变为 16/16”只能作为待验证预期。
4. **判断任务收益。** 结合数值结果与运行证据，确认是否减少相关等待，以及 `qk_pv` 和上层任务是否改善。

这个案例以 **O1 计算分工**为主，同时关联 **O3 数据交接**与 **O4 执行时序**；候选占用变化还需按 O2 核对。

**探索目标**

> 用户能够依据计算语义和执行证据，作出“尝试切分”或“保持当前实现”的合理决定，并知道需要验证什么。

**依据与证据边界**

研究底稿第 6.7、8.4 节；[CSA 页面逻辑][L07]、[CSA pass 36 编译产物][L08]，重点核对双 AIV 派发、subblock 分支及相关 Tile。未重新编译或上板；页面推算不是候选实测。原型表达、设备效果和用户任务效果分别验证。

### HN-07｜以容量问题为例：从超限提示，推进到 Tile 与缓冲策略选择

模型维度变化，会把上层配置要求传导到具体片上空间。

在 PyPTO #630 的开发记录中，`kv_lora_rank` 从 128 增加到 512 后，Right buffer 使用量达到 98,304 字节，超过当时目标的 65,536 字节限制。[PyPTO #630][S04]

用户需要保留模型要求，同时调整实现。因此，工具应建立：

**模型维度 → 分块方式 → 物理 Tile → 存储分配 → 资源限制**

围绕这条关系，工具需要帮助用户判断：

- 哪个 Tile、哪个分块维度造成当前压力？
- 占用如何受到数据类型、布局和补齐影响？
- 缩小分块后，会增加哪些循环、搬运或累加？
- 多个对象的存活与复用，怎样影响实际分配？

还需要区分资源占用的来源。#2287 报告的跨核 FIFO 问题表明，通信缓冲的预留策略也可能造成 UB 容量失败；不能默认要求用户缩小计算 Tile。[PyPTO #2287][S07]

因此，资源解释应区分：

**计算 Tile、临时工作区、通信缓冲，以及目标与软件配置相关的预留。**

这个案例以 **O2 Tile 形态与资源**为主，同时关联 **O4 缓冲深度与生命周期**。

**探索目标**

> 用户能够判断资源压力来自哪里，选择正确的修改对象，并在保持计算语义的前提下比较候选实现。

**依据与证据边界**

研究底稿第 6.1、6.4 节。数值来自原记录指定版本，不作为通用规格。FIFO 生成策略问题首先属于技术修复责任，工具负责解释归属和支持必要判断；布局、补齐和生命周期为应核查维度，不意味着它们都是 #630 已确认的根因。

### HN-08｜阶段结论：以具体开发决定为单位，验证四个 Hardware-Native 机会

本阶段分析建立了从硬件机制到体验机会的对应关系：

- AIC／AIV 分工，引出计算区域与有效数据的分配问题。
- 专用存储与布局要求，引出 Tile 形态与资源取舍问题。
- 目标相关的数据通路，引出中间结果交接与融合选择问题。
- 异步流水与同步机制，引出并行、依赖和缓冲复用问题。

**由此，我们将昇腾 Hardware-Native 收敛为四类具体的工具设计机会，并按证据成熟度推进验证。**

| 优先探索 | 当前依据 | 下一步需要验证 |
| --- | --- | --- |
| **AIC／AIV 计算分工** | CSA 编译产物与明确的切分候选 | 用户能否理解有效分工，选择正确的实验与判断标准 |
| **Tile 资源与缓冲策略** | 容量、分块及 FIFO 开发记录 | 用户能否识别占用来源，避免修改错误对象 |
| **并行与同步关系** | 同步参与范围及缓冲机制案例 | 哪些检查应自动完成，哪些关系需要解释与控制 |
| **数据路径与融合选择** | 明确的架构通路差异 | 补充真实融合任务，验证路径信息是否改变方案选择 |

设计效果与技术效果应分别验证：

- **设计效果**：用户是否理解正确、定位准确、选择合理，是否减少无效试错。
- **技术效果**：实现是否正确，资源是否符合预期，局部与整体性能是否改善。

**衔接后续方案**

> 接下来，我们以 CSA 的 AIC／AIV 分工和 Tile 资源问题为切入点，探索如何将计算表达、硬件映射与执行证据组织成可操作的决策过程。通过具体任务验证，逐步明确哪些硬件事实需要显性呈现、哪些应由系统自动处理，以及这些设计能为模型与算子开发带来什么帮助。

**依据与证据边界**

研究底稿第 10、11 节。优先级来自当前证据与可验证性，不是发生率或 ROI 排名。尚未完成用户测试与设备对照实验，不以原型存在证明任务收益。

### 3.2 保留在研究底稿的内容

- **七个案例及其原始数字、环境和修订记录**：容量、同步、有效预算、FIFO、HCA、serving、CSA 均保留。HCA 与 serving 用于收益范围及跨层责任的补充论证，不承担昇腾独特性的主要证明。
- **业界机制**：Ascend C、Gluon、Neuron Explorer、Nsight Compute、ROCm Compute Profiler、msprof 保留在底稿第 9 节。用于承载方式参考，不代替自身任务验证。
- **九域与六种承载形态**：作为覆盖检查和研发协作基础，不直接转成九个导航或六个页面。
- **1463 条归档口径**：保留方法说明，不转化成独立缺陷数、当前全量或 Hardware-Native 缺陷率。
- **HCA 与 CSA 收益边界**：HCA 旧整图收益主张已被复测修订；独立 CSA 改动的收益不能证明当前 UP_DOWN 候选有效。
- **研究与验证计划**：分别记录设计效果与技术效果，保留可以缩小或否定机会假设的条件。

## 四、正式汇报的证据表达

### 4.1 三种结论分别表达

- **已有证据**：“对应架构文档说明……”“该版本开发记录报告……”“当前编译产物显示……”。说明目标、版本和对象。
- **研究洞察**：“跨案例分析后，我们识别出……”。说明综合判断，不将困难归纳写成全量统计。
- **设计机会**：“因此我们探索……，希望改善……，后续通过……验证”。不把预期收益写成阶段成果。

### 4.2 必须保持的边界

| 不宜直接使用 | 建议表达 |
| --- | --- |
| 昇腾都采用同一核配比、容量和路径 | 指定目标架构具有这些机制，软件支持与实际生成结果另行核对 |
| AIV 没用满，说明性能有问题 | 当前有效分工提示实验方向，是否影响目标需要运行证据 |
| 增加 stage 就会增加有效并行 | 需核对槽位、资源、依赖与实际重叠，stage 不机械等于物理槽数 |
| 融合后数据自然留在片上 | 以目标能力、框架支持和本次生成路径确认中间数据流向 |
| 容量超限就缩小 Tile | 先区分计算、临时区、通信缓冲与预留，再选择责任层和操作 |
| 四个机会都已验证 | O1、O2、O4 有具体机制或案例；O3 仍需补充真实融合决策任务证据 |
| 原型完成即证明体验价值 | 原型表达、设备结果、用户任务效果分别验证 |

## 五、汇报收束段落

> 昇腾上的模型与算子实现，需要同时处理计算分工、专用存储、数据通路和异步协同。这些机制直接影响切分、分块、融合和流水选择。已有案例表明，开发者仍需跨越源码、编译产物和运行记录，才能理解一次选择的完整后果。因此，本阶段将 Hardware-Native 收敛为计算分工、Tile 资源、数据路径与融合、并行与同步四个体验机会，优先用 CSA 和容量任务验证。能够由系统可靠处理的复杂性继续自动承担，需要用户参与的决定则提供明确对象、作用范围与证据。
