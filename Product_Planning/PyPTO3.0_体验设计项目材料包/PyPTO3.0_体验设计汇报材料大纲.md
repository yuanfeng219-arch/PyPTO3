# PyPTO3.0 体验设计汇报材料大纲

> 版本：v0.1｜整理日期：2026-09-10  
> 本文只定义汇报材料的内容架构与论证关系，不拆分具体 PPT 页面。  
> 材料基于仓库内的产品规划、用户体验洞察、研究资料、数据快照和交互原型；“方案”“判断”“目标”需要在后续版本中继续区分，不直接等同于已上线能力或已验证效果。

## 一、材料总命题

### 1. 建议的总标题

**PyPTO3.0：面向 AI 时代的昇腾亲和、可观测、可解释的算子开发体验**

也可以保留更具传播性的表达作为副标题：

**从“能跑”到“可信交付”，重构复杂异构计算的开发体验。**

### 2. 核心判断

PyPTO3.0 的体验设计，不应只被理解为解决当前仓库中“错值、编译失败、性能回退、环境不一致、模型接入困难”等用户问题。

它还需要回应三个更大的产品变化：

1. **AI 正在改变算子开发的工作分工**：开发者从逐行编写和手工排查，转向表达意图、约束目标、审阅 AI 提案、组织验证和管理风险。
2. **昇腾亲和正在成为开发工具的核心价值**：工具不仅要让代码“能够运行在 NPU 上”，还要让用户理解并利用 AIC/AIV、内存层级、Tile、数据搬运、同步、通信和硬件约束，把硬件能力转化为可用性能。
3. **开发过程本身需要可观测、可解释**：用户不仅要看到最终结果，还要知道意图如何被编译、产物如何被执行、性能为何变化、结论基于哪些证据，以及当前还有哪些未知。

因此，PyPTO3.0 可以被定义为：

> **一个让开发者能够用 AI 表达和实现意图、用昇腾硬件知识做出更好决策、并在全过程中获得可观测和可解释反馈的算子开发与优化工作台。**

## 二、汇报材料要回答的四个问题

整份材料不以“我们做了多少页面”为主线，而是回答四个递进问题：

### 问题 1：为什么 PyPTO3.0 值得作为一个体验设计项目被关注？

回答项目的战略意义：它位于模型、算子、编译器、Runtime、硬件和服务之间，是昇腾硬件价值被开发者真正使用和放大的关键入口。

### 问题 2：用户今天到底在经历什么？

回答真实问题：用户面对的是跨层、跨仓库、跨角色、跨环境的可信迭代过程，而不是简单的代码编辑任务。

### 问题 3：体验设计改变了什么？

回答设计价值：体验设计重新定义了工作对象、信息关系、反馈机制、自动化边界和协作方式。

### 问题 4：这套设计如何转化为可落地的产品和业务结果？

回答落地逻辑：通过统一工作对象、证据图、硬件亲和的语义反馈、AI 协同和信任门禁，减少试错与定位成本，提升模型/算子从开发到服务交付的确定性。

## 四、模块 A：项目为什么重要——从工具项目到价值实现层

### 目标

让不熟悉业务的体验设计领导先理解 PyPTO3.0 的战略位置，也让业务领导知道它并非一个局部 IDE 或可视化项目。

### 需要讲清的内容

- PyPTO 位于模型语义与 NPU 实际执行之间；
- 算子开发结果会直接影响模型正确性、性能、资源利用率和服务稳定性；
- 昇腾的硬件能力只有通过编程模型、编译、运行时和开发工具才能变成用户可感知的业务价值；
- PyPTO3.0 的目标不是替代 pypto、PTOAS、pto-isa、simpler 或 pypto-serving，而是把它们组织成统一的开发控制面。

### 建议形成的战略表达

**PyPTO3.0 是昇腾硬件能力向开发者和业务结果转化的体验入口。**

## 五、模块 B：AI、昇腾和复杂系统正在带来的三重变化

这一模块是现有汇报材料最需要补充的背景层，但不能泛泛讲 AI 趋势，应直接落到算子开发工作方式的变化。

### B1. AI 让算子开发从“写代码”转向“管理意图与证据”

#### 要回答的问题

- AI 可以替代哪些重复劳动？
- 哪些判断仍需要开发者负责？
- 为什么普通 Coding Agent 不足以解决算子开发问题？

#### 内容要点

- AI 可以帮助理解源码、检索相似算子、生成实现骨架、补测试、解释编译变化、提出调优假设和生成复现包；
- 但算子开发的难点不只在代码生成，还在 Shape、dtype、layout、scope、依赖、内存、同步、硬件能力和性能正确性之间的联合约束；
- 因此，AI Agent 必须嵌入工程现场，读取真实上下文并绑定证据，不能只依赖聊天上下文；
- 开发者角色从“亲自完成每一步”转向“定义目标、审阅提案、确认风险、授权执行、验收证据”。

#### 关键设计判断

**AI 原生开发体验的核心不是让 AI 写更多代码，而是让 AI 能够提出可解释、可验证、可回退的工程动作。**

### B2. 昇腾亲和从“兼容硬件”升级为“帮助用户利用硬件”

#### 要回答的问题

- 什么是 PyPTO 语境下的昇腾亲和？
- 亲和如何成为用户体验，而不仅是底层技术属性？
- 为什么不能只展示抽象的模型图或通用性能数字？

#### 内容要点

昇腾亲和至少包含四层：

1. **表达亲和**：用户能够用接近计算意图的方式表达 Shape、Layout、Tile、并行、内存和依赖，而不必大量用字节计算或 workaround 暗示编译器。
2. **编译亲和**：工具能够解释源码如何经过 Pass、IR、PTOAS 和 ISA 约束，哪些结构适合 AIC/AIV，哪些变换会影响内存、同步和执行效率。
3. **执行亲和**：用户能看到 GM/L2/UB/L0、数据搬运、Pipeline、Barrier、Task、通信和多 Rank 的真实关系。
4. **优化亲和**：性能建议不是通用规则，而是结合具体昇腾硬件、Shape、内存余量、核心类型、通信拓扑和运行证据给出。

#### 关键设计判断

**昇腾亲和不是把硬件细节全部暴露给用户，而是把硬件约束转化为开发过程中及时、可理解、可行动的反馈。**

### B3. 系统复杂度让“开发过程可观测、可解释”成为基础体验

#### 要回答的问题

- 为什么运行时 Observability 还不够？
- 开发过程哪些状态需要被观察？
- 可观测与可解释的边界是什么？

#### 内容要点

开发过程可观测，指的是用户能够持续看到：

- 当前目标和约束是否完整；
- 当前环境和基线是否可信；
- 源码意图在编译过程中发生了什么变化；
- 运行时任务、内存、同步、通信和数据流如何执行；
- 正确性、性能和资源门禁处于什么状态；
- 当前结论是事实、推断、建议，还是仍缺证据；
- 某次判断如何沉淀为复现包、回归用例、Recipe 或服务准入资产。

可解释则要求：

- 结果能够回到来源；
- 系统明确说明“为什么这样判断”；
- 不确定性和证据缺口可见；
- 用户可以反向验证或推翻系统结论；
- 自动动作有影响范围、授权点和回退路径。

#### 关键设计判断

**可观测回答“现在发生了什么”，可解释回答“为什么发生、凭什么判断、还能否验证”。二者共同构成复杂开发系统的信任基础。**

## 六、模块 C：用户真实工作与体验断层

这一模块保留现有仓库关于用户问题的内容，但不再作为整份材料的唯一主线，而是作为三重变化的现实依据。

### C1. 真实工作流

`定义契约 → 固化环境 → 编写算子 → 编译生成 → 仿真/Golden → 真机/分布式 → 正确性定位 → 性能调优 → Serving 集成 → CI/协作 → 知识沉淀`

### C2. 现有体验断层

建议归纳成四类，而不是罗列大量 Issue：

| 断层 | 用户表现 | 需要被设计的能力 |
|---|---|---|
| 意图断层 | 用户想表达动态 Shape、依赖、内存或精度意图，代码只能靠隐式写法或 workaround 表达 | 意图式 DSL、契约检查、硬件语义反馈 |
| 证据断层 | 日志、IR、trace、tensor、性能数据和版本信息彼此割裂 | 统一 Run、Manifest、Evidence Graph |
| 协作断层 | 问题跨仓库流转，专家承担人工路由器角色 | 责任域定界、证据包、可交接产物 |
| 自动化断层 | Bot/Agent 产生很多信号，但人不知道如何分级、验证和决策 | 证据化 Agent、假设、验证计划、人类确认 |

### C3. 用户问题的最终表达

不要只说“用户不会用”或“工具不够友好”，而应表达为：

> **用户缺少一套把意图、硬件、编译、运行和验证连接起来的工作机制，因此只能用专家经验完成跨层判断。**

## 七、模块 D：体验设计命题与原则

### D1. 总体验命题

**让开发者能够表达意图、理解昇腾执行、观察全过程、验证每个结论，并把结果沉淀为可交付资产。**

### D2. 六项体验原则

1. **意图优先**：用户表达目标、约束和语义，系统辅助补全底层实现。
2. **昇腾亲和**：关键硬件约束和优化机会在恰当时机被解释，不隐藏也不倾倒。
3. **过程可观测**：从目标、环境、编译、运行到服务准入都能看到状态变化。
4. **结论可解释**：结论绑定来源、证据、可信度、影响和验证边界。
5. **AI 可协作**：Agent 提案可审阅、可验证、可授权、可回退。
6. **结果可复用**：一次运行沉淀为基线、复现包、回归用例、Recipe 或准入报告。

## 八、模块 E：三条核心设计主线

这三条主线是材料的主体，但不应被讲成三个孤立功能模块，而应说明它们共同改变了“用户如何完成算子开发”。

### E1. AI 原生算子开发

#### 需要定义的体验对象

- 任务意图；
- 算子契约；
- 当前源码和选区；
- 编译/运行上下文；
- 候选假设；
- 验证计划；
- Patch/Recipe/回归资产。

#### 需要覆盖的 AI 工作方式

- 理解：解释算子、数据流、硬件映射和当前风险；
- 生成：生成实现骨架、测试、配置和最小 Patch；
- 检查：发现契约、编译、正确性、性能和资源问题；
- 推理：基于证据提出责任域和性能假设；
- 执行：在用户授权下编译、测试、Profile 和生成报告；
- 学习：将成功/失败经验沉淀为规则、Recipe 和知识资产。

#### 需要明确的边界

- AI 不能把概率性回答伪装成事实；
- AI 不能绕过正确性和资源门禁；
- AI 不能默认修改关键工程状态；
- AI 必须说明证据来源与证据缺口。

### E2. 昇腾亲和的开发体验

#### 需要设计的内容层

- 模型/算子语义层；
- Tile、Layout、Shape、dtype、scope 和依赖层；
- AIC/AIV、内存层级、Pipeline 和同步层；
- Pass/IR/PTOAS/ISA 编译层；
- Task、通信、Rank 和 Runtime 执行层；
- 性能、资源和服务 SLO 结果层。

#### 需要形成的体验机制

- 编码时约束提示；
- 编译前风险预览；
- Pass 前后语义 Diff；
- 源码到硬件执行的双向追踪；
- Tile/内存/同步/通信的可视化；
- 结合具体硬件和运行数据的性能归因。

### E3. 开发过程可观测、可解释

#### 需要观察的过程状态

```text
目标与契约
  → 环境与基线
  → 源码意图
  → 编译变换
  → 生成产物
  → Runtime 执行
  → 正确性/性能/资源结果
  → 复现、回归与准入
```

#### 统一诊断结构

`严重度 / 一句话结论 / 影响 / 证据 / 可信度 / 建议动作 / 责任域 / 验证边界 / 可继续下钻内容`

#### 关键设计方向

- 以 Run/Experiment 作为全过程锚点；
- 以 Evidence Graph 连接不同工具和层级；
- 以三层信息密度服务不同角色；
- 以“首个异常”优先于“最后报错”；
- 以事实、推断、建议、未验证项分层呈现；
- 以低干扰采集、数据脱敏和可审计性控制风险。

## 九、模块 F：三条主线如何合成为一个工作台

### F1. 统一的中心对象

建议围绕以下对象组织整个产品体验：

| 对象 | 代表什么 | 连接的体验价值 |
|---|---|---|
| Intent/Contract | 用户要完成什么，以及约束是什么 | AI 理解、硬件约束、前置检查 |
| Operator Object | Tensor、Tile、ComputeOp、依赖、内存和任务等开发对象 | 对象化编辑、解释和协作 |
| Run/Experiment | 一次编译、运行、验证或性能实验 | 可比较、可复现、可协作 |
| Evidence Graph | 事实、推断、来源、关系和证据缺口 | 可观测、可解释、可追溯 |
| Trusted Artifact | 基线、复现包、回归用例、Recipe、准入报告 | 结果沉淀与业务交付 |

### F2. 统一的端到端闭环

`表达意图 → 生成/修改 → 编译解释 → 运行观测 → 正确性验证 → 性能归因 → 人类决策 → 形成可信资产`

AI 负责扩大理解、生成和搜索能力；昇腾亲和负责让优化方向与硬件真实执行一致；可观测可解释负责让每一步可验证、可交接、可复盘。

### F3. 统一的产品形态

- CLI：自动化、CI、远程和专家操作；
- IDE：编码时的意图反馈、Agent 协作和源码联动；
- Toolkit Studio：跨层证据、时间线、对比、调试、正确性、性能和服务可视分析；
- 共享底座：Manifest、Run ID、对象 Schema、诊断协议、规则、权限和脱敏机制。

## 十、模块 G：价值表达——三种价值要分别成立

### G1. 用户价值

- 更早知道环境、能力和约束是否成立；
- 更快定位错值、hang、编译失败和性能回退的首个异常；
- 更少依赖个人经验完成跨层排查；
- 更容易理解昇腾硬件为什么这样执行，以及如何优化；
- 更放心使用 AI，因为每个提案都有证据、边界和验证动作；
- 更容易把一次实验变成可复现、可回归、可交付的资产。

### G2. 业务价值

- 降低模型/算子开发和问题定位的时间成本；
- 缩短从模型接入到首个正确生成和开发服务响应的路径；
- 减少性能优化中的无效实验和错误归因；
- 提高跨团队问题交接和复现效率；
- 将高质量经验沉淀为组织可复用的规则、Recipe 和基线；
- 提升昇腾硬件能力在真实模型和服务场景中的转化效率。

### G3. 体验设计组织价值

- 从界面设计进入复杂技术产品的对象、关系、反馈和决策机制设计；
- 建立面向 AI 工具的可解释、可控、可回退交互范式；
- 建立面向 NPU 的硬件亲和体验语言；
- 形成复杂开发过程的可观测性与证据化设计方法；
- 将设计资产沉淀为对象模型、组件模式、诊断模板和 Agent 交互规范。

## 十一、模块 H：验证、路线图与协同

### H1. 不把原型数量当作成果标准

原型的作用是验证不同设计假设：

- `Toolkit Studio`：从模型子图到可信 Kernel 的工作流；
- `operator-coding-agent`：AI 原生算子开发；
- `compile-failure-diagnosis`：证据化诊断与人类决策；
- `operator-object-workbench`：面向智能体的算子对象化；
- `operator-run-overview`：Run 对象和信任门禁；
- `pass-atlas` / `pass-decision-studio`：编译变换和硬件决策可视化；
- `deepseek-csa-execution-atlas`：真实快照的源码—编译—执行跨层追踪；
- `memory-viz-demo` / `flash-attention-sync-replay`：资源与性能因果解释。

### H2. 需要补充的验证类型

- 可理解性：不同角色能否解释当前状态和下一步动作；
- 可定位性：能否减少从症状到责任域的时间；
- 可验证性：AI 结论和性能建议是否能被证据和实验验证；
- 可控性：用户是否清楚自动化的授权点、影响范围和回退方式；
- 硬件亲和性：用户是否能据此做出更符合昇腾执行特征的实现选择；
- 复用性：一次问题是否能沉淀成规则、测试、Recipe 或基线。

### H3. 建议的落地顺序

1. **先建立统一对象和证据底座**：Run、Manifest、source span、Evidence Graph、诊断协议。
2. **再建立可观测与可解释的核心链路**：环境、编译、Runtime、正确性和性能的最小闭环。
3. **在证据底座上引入 AI 协同**：让 Agent 基于真实上下文提出假设、生成动作和验证计划。
4. **逐步增强昇腾亲和能力**：把 AIC/AIV、内存、Tile、同步、通信和硬件约束转成可理解的开发反馈。
5. **最后扩展到模型推理、Serving 和组织级知识闭环**。

### H4. 建议的度量框架

暂不填写具体目标数值，先确定指标类别：

| 指标类别 | 关注什么 |
|---|---|
| 可信度 | 高危静默错误是否被提前发现，结论是否有证据 |
| 效率 | 从首次运行到可信产物的时间，异常定位时间，实验次数 |
| AI 协作 | Agent 提案采纳率、验证通过率、人工回退率、证据完整度 |
| 昇腾亲和 | 硬件约束被理解和利用的程度，性能归因和资源越界拦截情况 |
| 可观测性 | 过程状态覆盖率、跨层关联完整度、未验证项可见性 |
| 交付性 | 复现包、回归资产、Recipe 和服务准入报告的生成与复用情况 |

## 十三、后续补材清单

在进入逐页设计前，建议先补齐以下材料，不必一次全部完成：

1. **AI 变化材料**：一个算子从人工开发到 AI 协同开发的前后工作流对比；明确 AI 介入点和人类决策点。
2. **昇腾亲和材料**：用一个真实算子说明 Shape/Tile/内存/AIC-AIV/同步/通信如何共同影响结果，以及工具如何把这些因素解释给用户。
3. **过程可观测材料**：用一个 Run 展示从意图、环境、Pass、Runtime 到正确性/性能结论的状态变化。
4. **可解释材料**：用一个编译失败或性能回退案例，展示事实、推断、证据缺口和最小验证动作。
5. **业务结果材料**：选定一个真实试点，建立 TTTT、MTTI、实验次数、复现完整度或模型接入时长的前测基线。
6. **体验设计资产材料**：整理对象模型、信息分层、诊断卡片、证据状态、Agent 状态和硬件语义反馈等可复用模式。

## 十四、当前阶段的结论

当前不宜直接进入“15 页 PPT 怎么排”的阶段。更合适的工作顺序是：

1. 先确认总命题是否接受；
2. 再确认 AI 原生、昇腾亲和、可观测可解释三条主线是否构成完整的设计价值框架；
3. 再补齐三条主线各自的真实案例和原型证据；
4. 再决定哪些内容进入主汇报，哪些放入案例或附录；
5. 最后才拆成页面、演示和讲稿。

现阶段最重要的不是证明“我们做了很多原型”，而是建立一个清晰判断：

> **PyPTO3.0 体验设计正在把 AI 能力、昇腾硬件能力和复杂开发过程组织成一种可理解、可验证、可协作、可交付的新型算子开发体验。**
