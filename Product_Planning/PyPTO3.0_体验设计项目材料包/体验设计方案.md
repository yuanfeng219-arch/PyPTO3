# PyPTO3.0 体验设计方案

> 版本：v1.0｜整理日期：2026-08-17  
> 适用对象：产品、设计、架构、算法、开发、测试与平台团队

## 1. 设计命题

PyPTO 现阶段的关键体验问题不是“功能缺失”本身，而是系统在编译、运行和优化过程中缺少可见的因果解释：用户看到的是全零、错值、hang 或性能回退，却不知道首个异常发生在哪里、影响什么、应该把问题交给哪个责任域。

因此，PyPTO3.0 的体验设计命题是：

> **让每一次开发、运行和优化，都留下可比较、可解释、可验证、可回归的证据。**

## 2. 产品定位与体验目标

### 2.1 定位

PyPTO3.0 Toolkit 是面向 NPU 模型与算子开发者的“意图驱动、证据贯通、默认安全”的开发与优化平台；PyPTO Studio 是其中面向推理场景的“比较优先、证据贯通、专家在环”的工程诊断与准入工作台。

### 2.2 体验目标

| 目标 | 用户感知 |
|---|---|
| 更早发现风险 | 编译时就知道约束、能力和潜在错误，不等到真机结果才暴露 |
| 更快完成定界 | 从服务指标一路下钻到请求阶段、模块、rank、算子和硬件证据 |
| 更敢采用自动化 | Agent 的结论绑定证据、可信度和最小验证动作，用户始终保留控制权 |
| 更容易复盘协作 | 一次运行可以分享、比较、复现、回归和交接，而不是依赖截图和口头描述 |

## 3. 目标用户与关键任务

| 角色 | 关键任务 | 当前阻力 | 设计回应 |
|---|---|---|---|
| 算子开发者 | 表达意图、实现 kernel、理解硬件映射 | DSL/编译/硬件知识断裂 | Intent Studio + Coding Agent + 源码到硬件的解释链 |
| 编译与底层工程师 | 定位 lowering、IR、约束和内存问题 | 错误晚暴露，日志分散 | Compile Guardian + Provenance Explorer |
| 正确性/测试工程师 | 定位首个错误 tensor，沉淀回归用例 | 只能看最终 diff | Correctness Lab + Tensor Diff + 回归资产 |
| 性能/Infra 工程师 | 对比版本、定位服务回退和多卡异常 | 采集工具彼此割裂 | Experiment & Diff Hub + Multi-Rank Aligner |
| 模型/服务工程师 | 模型接入、推理验证、服务准入 | 模型级目标和底层证据断层 | Model Inference Studio + Serving/Admission Pipeline |

## 4. 端到端体验主线

### 4.1 统一工作流

目标不是增加一组独立工具，而是建立一个贯穿工作上下文的闭环：

`定义目标 → 建立基线 → 表达意图 → 编译与检查 → 运行与观测 → 比较与归因 → 验证与复现 → 准入与回归`

### 4.2 统一中心对象：Run / Experiment

每次关键运行都应绑定统一 Manifest，至少包含：模型/算子、源码与 commit、框架/CANN/编译器版本、硬件拓扑、输入与 shape、采样方式、指标、trace、日志和结论状态。

这使“比较”成为默认入口，也让后续诊断、复现和 CI 回归有稳定的对象基础。

## 5. 核心体验架构

### 5.1 一个底座、三个入口、七个能力中心

- 一个底座：Workspace / Manifest / Run ID / 证据图 / 版本与权限。
- 三个入口：源码与意图、模型与推理、实验与服务。
- 七个能力中心：编译可信、跨层追踪、正确性验证、性能解释、分布式对齐、运行观测、知识与准入。

### 5.2 三层信息密度

| 层级 | 面向对象 | 默认回答的问题 |
|---|---|---|
| L1 结论层 | 模型工程师、测试、首次使用者 | 发生了什么？影响是什么？下一步做什么？ |
| L2 工程层 | Infra、性能、RL 工程师 | 哪个请求阶段、batch、模块或 rank 出现了差异？ |
| L3 专家层 | 算子、编译、底层专家 | 哪个 Pass、tensor、指令、通信事件或约束产生了证据？ |

### 5.3 诊断输出标准

所有诊断结果统一采用：

`严重度 / 一句话结论 / 影响 / 证据 / 可信度 / 建议动作 / 责任域 / 可继续下钻内容`

事实、推断和建议必须显式区分；AI 不能仅凭日志文本生成不可追溯的结论。

## 6. 关键场景设计

### 场景 A：从模型子图到首个可信 kernel

用户导入模型或子图，系统展示算子覆盖、能力缺口和实现骨架；Coding Agent 在源码上下文中解释 tensor 契约、shape/layout、数据精度流、chunk/tile 与硬件映射；编译前给出风险和验证计划。

### 场景 B：从“能跑”到性能达标

用户将新旧实验放入 Diff Hub，系统以相同 Manifest 约束可比性，按服务指标 → 请求阶段 → 模块 → rank → 算子 → kernel 下钻，自动标出关键路径、首个偏离点和可复现证据。

### 场景 C：wrong output / hang / 性能回退

系统先判断环境和版本是否可信，再定位首个异常 Pass、tensor 或 rank；用户可以打开源码、IR、trace、日志和版本 Diff，生成最小复现包并将问题路由到责任团队。

### 场景 D：模型接入到推理服务

Model Inference Studio 负责架构识别、算子覆盖、精度/量化分析和 Recipe；Inference Runner 贯通 prompt → token → text；Serving Studio 继续完成流式 API 联调、基础容量估算、准入门禁和可重放请求。

### 场景 E：证据化 Agent 协作

Agent 不按名称割裂界面，而是嵌入源码、编译结果、运行详情和实验 Diff 中。它输出“结论—证据—影响—可信度—最小验证动作”，并支持追问、反证和人工确认。

## 8. MVP 建议

### 8.1 MVP 用户故事

一名工程师升级 CANN 与推理引擎后发现线上 P99 TTFT 回退。他把新旧实验拖入 Diff Hub，在同一屏看到 decode 阶段的 attention kernel 变慢和某张卡的 HCCL 等待；系统指出首个偏离 rank，排除环境问题，并生成脱敏复现包。该 Diff 可直接作为准入门禁的回退证据。

### 8.2 MVP 功能包

1. Experiment Manifest、Run ID、版本锚点。
2. Experiment & Diff Hub：TTFT/TPOT/吞吐/显存/热点算子等多维 Diff。
3. Multi-Rank Aligner：慢卡、首个偏离 rank、通信等待识别。
4. Accuracy Lab：同 token 锚点与首个偏差定位。
5. 错误与日志归因 v1：Python、CANN、算子与 plog 的因果链。
6. Admission Pipeline：精度、性能、可复现四类门禁。
7. 现有采集工具导入适配器：msprof、MindStudio Insight、Perfetto、vLLM-Ascend bench 等。

### 8.3 首版不纳入

完整 RL 训推链路诊断、大规模集群吊卡自愈、自主修改代码的 AI Agent、生产运维与计费告警平台。

## 9. 路线图与验收

| 阶段 | 时间 | 体验重点 | 关键出口 |
|---|---:|---|---|
| Phase 0 | 0–3 个月 | 比较与责任域定界底座 | 版本变化可生成改进/回退/责任域/证据 Diff |
| Phase 1 | 3–9 个月 | 服务到算子的端到端诊断 | 典型线上异常可定位到首个异常阶段或偏差点 |
| Phase 2 | 9–18 个月 | RL 一致性与规模化智能诊断 | 训推一致性、性能归因和准入回归进入同一工作台 |

建议北极星指标：

- Toolkit：从首次运行到可信达标产物的中位时间（TTTT）。
- Studio：从发现性能/精度异常到责任域定界的中位时间（MTTI）。

## 10. 设计原则与风险控制

1. 先证据底座，再扩展 UI：没有统一 Manifest、Run ID 和证据 schema，页面会变成静态大屏。
2. 比较优先：任何结论都要说明相对于哪个基线、在什么条件下成立。
3. 默认安全：采集开销、数据脱敏、权限与可审计性在启用前可见。
4. 自动化可回退：Agent 给建议和验证动作，不绕过用户直接修改关键工程状态。
5. 与现有工具共存：以导入适配器和证据增强为主，不重做采集器与推理引擎。
6. 明确边界：事实、推断、建议和未验证项必须分层呈现。
