# PyPTO3.0 体验设计汇报讲稿与页面大纲

> 版本：v1.0｜整理日期：2026-09-10  
> 适用场景：体验设计部门领导汇报、业务侧领导汇报、项目立项与阶段评审  
> 材料性质：基于仓库现有产品规划、用户体验洞察、研究资料、数据快照与交互原型整理；文中的“方案”“目标”“建议”不等同于已上线能力或已验证效果。

## 一、汇报定位

### 1. 推荐的总标题

**从“能跑”到“可信交付”：PyPTO3.0 的体验设计价值**

副标题可用：**面向 NPU 模型与算子开发的意图驱动、证据贯通、默认安全工作台**

### 2. 只讲一个核心命题

PyPTO3.0 的体验设计，不是给复杂技术增加一层漂亮界面，而是把分散在源码、编译 Pass、运行时、硬件、正确性和性能工具中的信息，组织成一条用户可以理解、验证、协作和复用的工作链路。

> **让每一次开发、运行和优化，都留下可比较、可解释、可验证、可回归的证据。**

### 3. 两类领导分别要带走什么

| 汇报对象 | 他们最关心的问题 | 需要留下的判断 |
|---|---|---|
| 体验设计部门领导 | 这个项目的战略意义是什么？体验设计的独特价值在哪里？方案有什么创新？ | 我们正在把“复杂异构系统的可理解性与可信度”变成产品竞争力；体验设计参与了产品对象、信息架构、决策机制和人机协作边界的定义。 |
| 业务侧领导 | 用户遇到了什么问题？我们做了什么方案？能帮助业务产生什么结果？ | 我们围绕错值、编译失败、性能回退、环境不一致和模型服务接入等高成本问题，设计了可定位、可验证、可复现、可交付的闭环。 |

### 4. 建议的讲法切换

- 面向体验设计领导：按“行业/项目战略 → 体验命题 → 设计创新 → 体验价值护城河 → 设计治理与度量”讲。
- 面向业务领导：按“用户任务 → 关键阻力 → 方案动作 → 解决的问题 → 业务结果与落地节奏”讲。
- 不建议拆成两套完全不同的材料。保留同一套核心页面，只切换每页的讲解重点和案例深度。

## 二、汇报开场：两种 90 秒版本

### A. 面向体验设计部门领导

PyPTO 面对的是 NPU 模型和算子开发中最复杂的一类体验问题：用户面对的不是一个页面，而是一条跨越模型语义、DSL、编译器、指令、运行时、硬件和服务的链路。过去产品更多是在提供工具和日志，用户需要依靠专家经验把这些信息重新拼起来。

PyPTO3.0 的体验设计抓住的不是“再做一个 IDE”，而是重新定义用户工作的基本单位：一次可追踪的 Run、一个可解释的算子对象、一条从意图到执行的证据链，以及一个始终保留人类决策权的 Agent 协作过程。设计因此进入了产品底座，而不只是界面表现层。

### B. 面向业务侧领导

用户现在经常能看到“错了、慢了、挂了”，但不能快速知道“最早在哪里出问题、影响了什么、应该找谁、下一步怎么验证”。这会把时间消耗在读日志、对版本、猜原因和重复试错上。

PyPTO3.0 通过统一工作台、Run/Manifest、跨层证据图、正确性与性能联合门禁，以及证据化 Agent，把用户从“收集更多信息”带到“得到可行动结论”：能更早发现风险，更快定位责任域，更稳地完成模型接入与服务准入，并把一次问题沉淀为后续可复用的工程资产。

## 三、推荐主汇报结构（15 页）

### 第 1 页｜封面：从“能跑”到“可信交付”

**页面信息**

- PyPTO3.0 体验设计汇报
- 一句话副标题：让开发、运行和优化都留下可追踪的证据
- 页面视觉：模型/算子 → 编译 → 运行 → 正确性 → 性能 → 服务的连续链路

**体验设计领导重点**：复杂技术产品的体验竞争，不只是降低学习成本，更是降低“不敢采用、不敢修改、不敢发布”的信任成本。

**业务领导重点**：项目目标是把“能运行的技术产物”推进为“可以验证、解释、复现和交付的工程产物”。

### 第 2 页｜为什么现在必须做体验升级

**页面结论**：PyPTO 的主要体验问题不是缺少更多功能，而是缺少跨层因果解释。

用户看到的结果通常是：全零、错值、hang、性能回退或服务不稳定；但根因可能发生在模型契约、DSL、编译 Pass、内存/同步、Runtime、分布式状态或版本组合中的任一层。

**建议展示**：一张“症状 → 可能责任域 → 当前人工排查方式”的断层图。

**体验设计领导重点**：这是典型的复杂系统可解释性问题，设计对象从页面扩展到信息关系、证据结构和决策路径。

**业务领导重点**：用户把大量时间花在排除错误层，而不是解决问题；专家经验成为人工路由器，难以规模化复制。

### 第 3 页｜用户真实工作：一个不断回环的可信迭代环

**页面结论**：用户不是完成一次“写代码”，而是在持续完成一条可信迭代链。

`定义目标与契约 → 固化环境 → 编写 Kernel → 编译/生成 → 仿真/Golden → 真机/分布式 → 精度定位 → 性能归因 → Serving 集成 → PR/CI → 知识沉淀`

可将角色归纳为：模型/算子开发者、性能工程师、Serving/集成工程师、编译器/Runtime 协作者，以及正在出现的 Coding Agent。

**体验设计领导重点**：设计面对的是多角色交接与多层语义转换，而不是单一用户画像。

**业务领导重点**：一个局部问题会在后续模型、服务或回归阶段放大，因此需要端到端的体验闭环。

### 第 4 页｜设计命题：把“信息堆”变成“证据链”

**页面主句**：

> 用户不缺日志，缺的是能回答“发生了什么、为什么、影响什么、下一步怎么做”的证据链。

**方案框架**：

1. 统一中心对象：`Run / Experiment / Manifest`；
2. 统一关联关系：`source → DSL → IR/Pass → PTOAS/ISA → task → tensor/metric`；
3. 统一诊断表达：`结论 / 影响 / 证据 / 可信度 / 建议动作 / 责任域 / 下钻`；
4. 统一产物出口：可信基线、复现包、回归用例、准入报告。

**体验设计领导重点**：这是体验设计对产品模型的重构，不是对既有工具的简单包装。

**业务领导重点**：用户最终拿到的是可行动的判断和可交接的工程产物，而不是一堆互不关联的输出文件。

### 第 5 页｜产品形态：一个底座、三个入口、七个能力中心

**页面结论**：PyPTO3.0 不是更多命令的集合，而是一个统一的开发与优化控制面。

| 层级 | 内容 |
|---|---|
| 一个底座 | Workspace、Manifest、Run ID、证据图、版本与权限 |
| 三个入口 | CLI、IDE Extension、Toolkit Studio |
| 七个能力中心 | 环境；意图与编译安全；追踪与调试；正确性；性能；模型推理；服务工程 |

**讲解提醒**：强调“统一协议、统一对象、统一证据”，而不是逐个念能力中心名称。

**体验设计领导重点**：设计将多个技术域组织为一套一致的信息架构，让用户按任务进入，而不是先理解仓库边界。

**业务领导重点**：已有采集器、编译器、Runtime 和服务组件可以共存，3.0 重点补齐统一工作流、诊断协议和交互体验。

### 第 6 页｜创新一：把一次运行设计成可追踪的 Run 对象

**页面主句**：从“目录和日志”升级为“可比较、可分享、可复现的运行对象”。

一次 Run 绑定源码与 commit、模型/算子、Python/CANN/编译器/Runtime、硬件拓扑、输入 Shape、trace、日志、oracle、指标、结论状态和采集边界。

**用户动作**：选择 Run → 查看五道信任门禁 → 查看首要结论 → 下钻证据 → 比较基线 → 导出复现包或准入报告。

**可展示原型**：`Design/operator-run-overview/`、`Design/Toolkit Studio/`。

**体验设计领导重点**：Run 是新的产品基本对象；它把可视化、协作、复现和治理连接在一起。

**业务领导重点**：减少“你本地能不能复现”的来回沟通，让结果具备交接和回归条件。

### 第 7 页｜创新二：三层信息密度，让不同角色看懂同一份事实

**页面结论**：不是把复杂信息全部展示出来，而是让不同角色沿同一条证据链看到合适的深度。

| 信息层 | 默认回答 | 典型用户 |
|---|---|---|
| L1 结论层 | 发生了什么？影响是什么？下一步做什么？ | 模型工程师、测试、首次使用者 |
| L2 工程层 | 哪个阶段、模块、rank 或指标发生了差异？ | 算子、性能、Infra 工程师 |
| L3 专家层 | 哪个 Pass、tensor、指令、通信事件或约束提供了证据？ | 编译、ISA、Runtime 专家 |

**可展示原型**：`Design/operator-object-workbench/` 的图、内存/Tile、Pipeline、验证与证据链视图。

**体验设计领导重点**：渐进披露既避免专家信息被隐藏，也避免非专家被原始 IR 和硬件细节淹没。

**业务领导重点**：同一问题可以从一句结论一路下钻到源代码和运行证据，减少跨角色翻译成本。

### 第 8 页｜创新三：证据化 Agent，而不是黑盒自动化

**页面主句**：Agent 的价值不是替人做所有决策，而是把上下文、候选假设和最小验证动作组织好。

Agent 输出固定采用：

`结论 → 证据 → 影响 → 可信度 → 候选假设 → 最小验证计划`

默认行为：读取当前源码、配置、编译产物和运行证据；给出可追溯建议；生成 diff 和验证计划；在修改代码、重编译、真机实验和发布动作前保留人类确认。

**可展示原型**：`Design/compile-failure-diagnosis/`、`Design/operator-coding-agent/`。

**体验设计领导重点**：人机协作的关键创新是“可解释、可反证、可回退”，体验设计定义了自动化的信任边界。

**业务领导重点**：把专家排查方法转成可复用的诊断流程，减少盲目试错，同时避免 Agent 直接修改关键工程状态带来的风险。

### 第 9 页｜场景一：从模型子图到首个可信 Kernel

**用户问题**：模型子图落到 NPU 后，算子覆盖、Shape/Layout、硬件约束、编译变化和测试证据分散，开发者很难知道“这段代码是否真正可信”。

**设计方案**：

1. 导入模型子图或选择算子配方；
2. 展示算子覆盖、能力缺口和实现骨架；
3. Coding Agent 解释输入输出契约、Shape/Layout、精度和硬件映射；
4. 编译卫士在 Pass 过程中校验不变量；
5. Correctness Lab 通过多 Oracle 与分层 Diff 定位首个分歧；
6. 签发带环境指纹和证据链的可信基线。

**用户收益**：从“写完再跑、跑错再猜”转为“编码时理解、编译时发现、运行后验证”。

**可展示原型**：`Design/Toolkit Studio/`、`Design/model-inference-studio/`。

### 第 10 页｜场景二：从编译失败到首个可验证原因

**用户问题**：编译失败通常跨越源码、类型/Shape、Layout、Lowering 和硬件约束；最终错误不一定是首个错误。

**设计方案**：

- 聚合工程现场、环境快照、最近成功基线和相关测试；
- 以 Pass 时间线显示通过、警告、失败和未执行阶段；
- 将“源码事实 → IR Diff → 约束违反 → 失败结果”串成错误因果链；
- 给出多个候选假设及置信度；
- 用户选择假设后生成最小验证计划，而不是直接自动改代码。

**原型中的示例**：`rmsnorm.py` 在 Vector Lowering 前因 Layout 约束未满足而失败；界面显示“Layout / Vector CodeGen”疑似责任域，Agent 置信度 82%，并明确真实设备指令和 UB 分配尚未验证。

**用户收益**：更快完成责任域定界；即便当前无法确认，也能清楚知道“还缺什么证据”。

### 第 11 页｜场景三：从“感觉变慢”到性能可归因

**用户问题**：性能数据经常存在口径不一致，等待、同步、搬运、计算和内存复用互相影响，用户能看到慢却解释不了慢。

**设计方案**：

- 以相同 Manifest 锁定新旧实验可比条件；
- 从服务指标/请求阶段下钻到模块、rank、算子和 kernel；
- 将耗时拆解为计算、数据搬运、同步、内存和调度原因；
- 对每个优化候选同时执行正确性、资源和性能门禁；
- 将验证通过的方案保存为 tuning recipe 和回归基线。

**可展示原型**：`Design/pypto-studio-v2/`、`Design/operator-debug-tuning-lab/`、`Design/flash-attention-sync-replay/`、`Design/memory-viz-demo/`。

**用户收益**：从“反复试参数”变成“提出假设—做对照实验—获得归因—沉淀方案”。

### 第 12 页｜场景四：从模型接入到可交付服务

**用户问题**：单个 Kernel 能跑，不代表完整模型能正确生成；单次请求通过，也不代表长序列、复用 Cache、多 Rank 和并发服务稳定。

**设计方案**：

- 模型导入时识别架构、算子覆盖、fallback、精度和硬件限制；
- 用 Inference Runner 串起 prompt → token → text；
- 将 logits、token、decode step、KV Cache 和 Runtime 证据关联；
- 通过容量、正确性、性能、稳定性和兼容性门禁；
- 输出带边界、配置、回滚信息和完整证据的服务就绪报告。

**可展示原型**：`Design/model-inference-studio/`、`Design/deepseek-csa-execution-atlas/`、`Design/architecture/deepseek_v4_flash_csa/`。

**补充案例**：DeepSeek V4 CSA 快照原型展示了从源码、52 个 Pass、PTO/CPP/O/BIN、Host 编排、双 rank 任务 DAG 到性能和 Shape 证据的跨层链路；原型同时明确标注当前快照缺少真实 Tensor 输入/输出 dump，避免把元数据误说成数值验证结果。

### 第 13 页｜体验设计带来的独特价值

**页面建议做成四列价值图**：

| 体验设计介入点 | 解决的产品问题 | 形成的独特资产 |
|---|---|---|
| 对象化 | 用户面对文件、日志和工具，不知道工作的基本单位是什么 | Run、Experiment、Operator Object、Evidence Chain |
| 关系化 | 多层产物彼此割裂，无法解释因果 | source ↔ IR ↔ task ↔ tensor ↔ metric |
| 分层化 | 同一份复杂信息无法同时服务不同角色 | L1/L2/L3 渐进披露体系 |
| 决策化 | 自动化要么太弱，要么不可控 | 假设、置信度、验证计划、人类确认、可回退 |

**面向体验设计领导的结论**：体验设计的独特价值，是把复杂技术能力转化为用户可以建立信任的产品机制。

**面向业务领导的结论**：体验设计不是“做界面”，而是在减少定位成本、验证成本、交接成本和发布风险。

### 第 14 页｜落地节奏与度量方式

**路线图**

| 阶段 | 时间 | 体验重点 | 关键出口 |
|---|---:|---|---|
| Phase 0 | 0–3 个月 | Run/Manifest、环境健康、统一诊断、编译安全 | 结果可识别、环境可复现、高危静默错误可提前拦截 |
| Phase 1 | 3–9 个月 | Evidence Graph、首个异常、正确性与调试闭环 | 典型错值/hang 可定位并生成复现包 |
| Phase 2 | 9–18 个月 | 性能归因、模型推理、服务准入与智能诊断 | 从模型产物到服务就绪形成统一工作流 |

**建议度量**

- TTTT：从首次运行到可信达标产物的中位时间；
- MTTI：从发现异常到责任域定界的中位时间；
- 高危静默错误被门禁捕获比例；
- 性能回退可归因比例；
- 首次提交即具备完整环境与证据的问题比例；
- 从模型导入到首个正确生成、从 Inference Bundle 到开发服务首次响应的中位时间。

**重要说明**：当前这些是建议指标和目标值，不应在汇报中表述为已经取得的业务效果；后续需要通过可用性测试、工程试点和真实运行数据建立基线。

### 第 15 页｜结论与需要业务支持的事项

**结论**

PyPTO3.0 的核心升级，是把“专家才能完成的跨层排查和优化”转化为“用户可以理解、系统可以验证、团队可以复用”的工作流。体验设计的价值，最终体现在三件事上：

1. 让复杂技术更容易被采用：用户知道能力边界和风险边界；
2. 让问题更快被解决：用户能从症状走到首个异常和责任域；
3. 让结果更容易被交付：每次运行都能形成基线、证据、回归和准入资产。

**建议在汇报最后提出的支持事项**

- 确认一个真实模型/算子场景作为端到端试点；
- 指定编译、Runtime、性能、模型和服务侧的联合接口人；
- 允许建立统一 Manifest、诊断规则和证据 Schema 的最小共建机制；
- 用一个真实 wrong output、性能回退或模型接入问题验证 MTTI/TTTT 的基线和收益。

## 四、按汇报对象准备的重点页

### 1. 体验设计部门领导：建议重点展开

建议重点讲第 4、6、7、8、13、14 页，强调以下判断：

- 设计对象从“界面”扩展到“产品基本对象、信息关系和决策机制”；
- 体验创新不是视觉创新，而是把证据链、渐进披露和人机协作做成默认产品行为；
- 在复杂系统中，可信度、可解释性和可回退性本身就是体验指标；
- 体验设计可以沉淀为可复用的对象模型、诊断模式、信息分层和 Agent 交互规范；
- 设计部门的长期价值，是建立复杂技术产品的统一体验语言和治理能力。

### 2. 业务侧领导：建议重点展开

建议重点讲第 2、3、9、10、11、12、15 页，强调以下判断：

- 业务侧最直接的损失是排查时间长、责任边界不清、问题重复发生和发布风险高；
- 方案不是增加一个展示层，而是把环境、编译、正确性、性能和服务验证串成闭环；
- 业务结果应通过真实场景验证：减少定位时间、提升首次复现完整度、减少无效实验、提升模型接入和服务准入效率；
- MVP 应从一个高价值场景切入，优先选择“wrong output/hang/性能回退/模型接入”中的一个真实案例做前后对照。

## 五、建议的 8 分钟原型演示顺序

1. **启动页**：从 `launch.html` 进入 PyPTO3 Design Lab，说明项目不是一个单页面，而是一组围绕同一体验命题的设计验证。
2. **Toolkit Studio**：展示从模型子图到可信 Kernel 的 Build、Explain、Observe、Correctness、Performance 五段主线。
3. **编译失败诊断**：展示证据聚合、首个失败 Pass、候选假设、置信度和最小验证计划。
4. **算子对象工作台**：展示 OperatorSpec、Tensor、Tile、ComputeOp、Run、Metric 的对象化关系，以及内存/Tile/Pipeline/验证/证据链切换。
5. **性能调优工作台**：展示基线对比、同步/搬运/计算归因和正确性门禁。
6. **DeepSeek V4 CSA Execution Atlas**：展示一个真实 JIT 快照如何从源码走到编译产物、任务 DAG 和运行证据，并主动指出证据缺口。
7. **回到一句话**：我们交付的不是更多页面，而是一套让复杂开发结果变得可信、可解释、可复用的体验机制。

## 六、材料边界与表述禁区

### 可以直接使用的表述

- “基于仓库 Issue、用户体验洞察、产品规划和原型，我们识别出……”
- “当前提出的设计方案是……”
- “原型验证了信息结构和关键交互路径……”
- “下一阶段通过真实试点验证 MTTI/TTTT 等指标……”
- “系统会明确区分事实、推断、建议和未验证项。”

### 暂不应直接说成事实的表述

- “已经为业务节省了 X% 时间”；
- “Agent 已经自动解决了问题”；
- “所有错值/hang 都可以自动定位”；
- “DeepSeek V4 的数值正确性已经被当前原型证明”；
- “当前原型就是已经上线的产品能力”。

### 证据状态标识

| 标识 | 含义 | 汇报中建议说法 |
|---|---|---|
| 事实 | 已存在于仓库材料、Issue、数据或代码中的内容 | “现状显示……” |
| 方案 | 产品规划或体验设计提出的方向 | “我们设计为……” |
| 原型 | 已制作的交互验证资产 | “原型验证了……” |
| 目标 | 尚待真实试点验证的指标或效果 | “计划通过……验证” |
