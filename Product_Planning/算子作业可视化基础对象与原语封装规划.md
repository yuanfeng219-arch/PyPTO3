# 模型 / 算子开发全流程 · 可视化基础作业对象与原语封装规划

> 文档版本：v2.0
> 更新时间：2026-09-09
> 适用范围：从场景定义、方案选型、模型接入、算子开发编译调试调优、分布式编排、服务化，到基线回归、在线治理与知识沉淀的完整链路
> 目的：**从作业流程本身**推导出可视化的基础作业对象与原语，形成一套可封装、可被各智能体调用的公共能力
>
> v2.0 变更：v1.0 是从 `Design/` 已有原型归纳，覆盖面受限于已做过的 demo。本版改为**先按全流程推导应有的对象，再回头标注现状**，因此新增了立项选型、分布式编排、服务化容量、基线回归、在线治理、知识沉淀六段，以及由此带来的一批新对象和 4 个新原语。

---

## 1. 方法说明

有两种推导路径，结论差别很大：

- **自下而上（v1.0）**：看已有 demo 画了什么 → 归纳共性。问题是只能覆盖已经做过的场景，缺失的部分永远看不见。
- **自上而下（本版）**：把模型/算子开发的完整作业流程铺开 → 每个阶段问「开发者在这一步要做什么判断」→ 判断需要哪些对象 → 对象需要什么图元 → 最后才回头看现状。

本版采用后者。判断标准是：

> 一个东西值得成为**基础作业对象**，当且仅当：① 它在 ≥2 个阶段被引用；② 它有稳定的字段结构；③ 它能被锚定回源码/产物/运行；④ 智能体可以对它下结论。

一个东西值得成为**可视化原语**，当且仅当：① 它在 ≥3 个阶段复用；② 它的版式由数据结构决定而非由某个业务场景决定；③ 换一批数据仍然成立。

## 2. 全流程分层

模型/算子开发不是一条直线，而是三层嵌套：

```
外循环（模型与服务）  S1 目标 → S2 选型 → S3 模型接入 → ……… → S11 服务化 → S12 上线
                                              ↓                  ↑
内循环（算子）              S4 意图 → S5 Coding → S6 编译 → S7 正确性 → S8 调试 → S9 调优 → S10 分布式
                                              ↓                  ↑
贯穿层（治理与沉淀）        S13 在线监控与异常回流  ·  S14 知识沉淀与复用
```

- **外循环**决定「该不该做、做到什么程度算够」；
- **内循环**决定「怎么做对、怎么做快」；
- **贯穿层**决定「这次的结论下次还能不能用」。

**三层共用同一套对象与原语，是这套封装成立的前提。** 例如 `Breakdown` 在外循环拆 TTFT、在内循环拆 kernel 耗时、在贯穿层拆成本构成，是同一个图元。

## 3. 逐阶段推导

每张表的「现状」列：`已实现` = `Design/` 下有可用实现；`部分` = 有雏形但不完整；`空白` = 尚无原型。

### S1 场景与目标定义

| 项 | 内容 |
|---|---|
| 开发者要判断 | 优化哪个指标？什么流量结构下？质量红线在哪？ |
| 作业对象 | `Workload` 工作负载画像、`Objective` SLO/质量红线/资源预算、`Dataset` 评测集 |
| 需要的可视化 | 输入/输出长度分布与 QPS 分布（**Distribution**）、目标与当前差距（**Metric**，门禁形态）、多目标权衡（**Scatter** 平行坐标） |
| 现状 | 空白 |

> 这一段现在完全没有产品承载，但它决定了后面所有阶段「达标」的判定基准。缺了它，性能 Lab 里的"快了 12%"没有意义。

### S2 理论估算与方案选型

| 项 | 内容 |
|---|---|
| 开发者要判断 | 显存装得下吗？瓶颈偏 Prefill 还是 Decode？选哪套精度/并行/引擎组合？ |
| 作业对象 | `Estimate` 理论估算（权重/激活/KV Cache/算力/通信/算术强度）、`Plan` 候选方案、`Constraint` 兼容性与风险清单 |
| 需要的可视化 | 显存预算分解 vs 容量线（**Breakdown** 预算模式）、算术强度定位（**Scatter** Roofline）、方案多维对比（**Scatter** 平行坐标）、候选×指标（**Table** 矩阵态） |
| 现状 | 部分（`inference-memory.js` 有显存构成；Roofline 在 `inference-profiler.js`，但服务于实测而非估算） |

> 关键点：估算与实测**必须用同一个图元、不同的 `origin`**，这样后面才能做"估算 vs 实测"的直接对照。

### S3 模型接入与算子覆盖盘点

| 项 | 内容 |
|---|---|
| 开发者要判断 | 这个模型有哪些算子？哪些有 PyPTO 实现、哪些走库、哪些 fallback、哪些缺失？先做哪个？ |
| 作业对象 | `Model`/`Layer`/`ModuleNode` 模型结构、`OpInventory` 算子覆盖清单、`Fallback` 回退点、`QuantScheme` 量化策略、`Fingerprint` 权重/tokenizer/config 指纹 |
| 需要的可视化 | 模型图 + 覆盖着色（**Graph** 覆盖叠加）、算子清单与优先级排序（**Table** 排行态）、缺口分布（**Metric**）、精度策略沿模型的分布（**Graph** 精度图层） |
| 现状 | 部分（`model-inference-studio`、`qwen3-model-viz.js`、`deepseek-v4-model-viz.js` 有模型图；覆盖/fallback 清单只在融合目录里有雏形） |

### S4 算子选型与意图表达

| 项 | 内容 |
|---|---|
| 开发者要判断 | 这个算子的数学语义是什么？有没有可复用的样例/配方？契约怎么定？ |
| 作业对象 | `OpSpec` 算子规格（数学语义 + In/Out/InOut 契约 + shape/dtype/layout）、`Recipe` 配方、`Sample` 参考样例、`FusionRule` 融合规则与匹配结果 |
| 需要的可视化 | 数学语义到计算阶段的映射（**Graph**）、可选实现/样例对比（**Table** 排行态 + **Diff**）、融合规则匹配位置（**Graph** 规则图层） |
| 现状 | 部分（`fusion-rules-data.js` / `fusion-catalog-*` 有规则目录与匹配；`Intent Studio` 只有原型雏形） |

### S5 算子 Coding

| 项 | 内容 |
|---|---|
| 开发者要判断 | 代码表达了什么？数据怎么走？切分对不对？有什么风险？ |
| 作业对象 | `Operator`、`OpNode`、`Tensor`、`Tile`/`Chunk`、`Scope`、`Risk`/`Guard` |
| 需要的可视化 | 计算图（**Graph**，含精度/风险/覆盖图层）、契约与 shape 流（**Table**）、Chunk/Tile 映射（**Tiling**）、Scope 与并行域（**Tree**）、硬件执行路径（**Topology** 芯片内底图）、静态容量预警（**Occupancy**） |
| 现状 | 已实现（Toolkit Studio 算子面板最完整的一段） |

### S6 编译与 Lowering

| 项 | 内容 |
|---|---|
| 开发者要判断 | 为什么编不过？哪个 Pass 改了什么？改得合法吗？编译为什么变慢？ |
| 作业对象 | `Pass`、`IRNode`、`Diagnostic` 诊断、`Invariant` 不变量/Verifier 规则、`MemBlock`、`Kernel`/`CodegenArtifact`、`SourceMap` 源码—IR—产物映射 |
| 需要的可视化 | Pass 顺序轴与首个失败（**Sequence**）、结构化 IR Diff（**Diff**）、Verifier 面板（**Finding** + **Table**）、地址分配与冲突（**Occupancy**）、编译耗时构成（**Breakdown**）、源码↔IR↔产物三向定位（**SourceCanvas**） |
| 现状 | 已实现（`ir-compile-guard.js`、`ir-pipeline-data.js`、`ir-pass-visuals.js`、`compile-failure-diagnosis`） |

### S7 正确性与精度验证

| 项 | 内容 |
|---|---|
| 开发者要判断 | 结果可信吗？误差从哪进来？容差定得合理吗？边界覆盖够吗？ |
| 作业对象 | `Golden` 参考、`Oracle` 验证层（Torch / 原始 Program / Pass 后 IR / Device / 库实现）、`TensorDump`、`Deviation` 偏差、`TestCase`/`Coverage`、`Tolerance` |
| 需要的可视化 | Oracle 状态矩阵（**Table** 矩阵态）、误差空间分布（**Heatmap**）、误差分布与容差线（**Distribution**）、逐 Pass 数值二分（**Sequence** 带 pass/fail 徽标）、精度路径（**Graph** 精度图层）、边界覆盖（**Table** 矩阵态） |
| 现状 | 部分（`renderOracles`、`renderTensorCompare`、`renderHistogram` 有；误差热图与逐 Pass 二分较弱） |

### S8 调试与根因定位

| 项 | 内容 |
|---|---|
| 开发者要判断 | 第一个异常出现在哪？为什么这个 Task 没跑？谁在等谁？ |
| 作业对象 | `Symptom` 症状入口、`Task`/`Event`/`Fence`、`DepEdge` 依赖边（自动/显式/未满足）、`Lifetime` 生命周期、`FirstAnomaly` 首个异常点、`Repro` 最小复现包 |
| 需要的可视化 | **EvidenceChain 跨层证据链**（源码→IR→Kernel→Task→Tensor→症状）、动态任务图与阻塞链（**Graph** 状态叠加）、依赖 Fan-in（**Graph**）、Runtime 泳道与等待原因（**Timeline**）、Tensor 生命周期与地址重叠（**Occupancy**）、Tensor 逐元素对比（**Heatmap** + **Table**） |
| 现状 | 部分（`run-timeline.js`、`run-fan.js`、`flash-attention-sync-replay` 有；**跨层证据链没有统一载体**，是当前最大缺口之一） |

### S9 性能调优与实验

| 项 | 内容 |
|---|---|
| 开发者要判断 | 瓶颈是什么？改什么最有价值？收益从哪来、代价是什么？ |

### S10 分布式与多卡编排

### S11 模型集成、服务化与容量规划

| 项 | 内容 |

## 4. 作业对象总表（6 族 · 32 类）

对象是智能体的输出物，也是跨视图联动的唯一凭据。

### 族 1 · 意图与目标（S1–S2）
`Workload` · `Objective`（SLO/质量红线/预算）· `Dataset` · `Estimate` · `Plan` · `Constraint`

### 族 2 · 模型与资产（S3–S4、S14）
`Model`/`Layer`/`ModuleNode` · `OpInventory`（覆盖/fallback/缺失）· `OpSpec` · `QuantScheme` · `FusionRule` · `Recipe`/`Sample`/`Knowledge`

### 族 3 · 源码与编译（S5–S6）
`Operator` · `OpNode` · `Tensor` · `Tile`/`Chunk` · `Scope` · `Pass` · `IRNode` · `Diagnostic` · `MemBlock` · `Kernel`/`CodegenArtifact` · `SourceMap`

### 族 4 · 执行与证据（S7–S8、S10–S11）
`Run` · `Task`/`Event`/`Fence` · `DepEdge` · `TensorDump`/`Golden`/`Deviation` · `Counter`(PMU) · `CommOp`/`CommDomain`/`Device` · `Request`/`BatchSchedule`/`KVCache`

### 族 5 · 判断与实验（S9、S12）
`Finding` · `Symptom`/`FirstAnomaly` · `Bottleneck` · `Experiment`/`Candidate`/`SweepAxis` · `Gate` · `Baseline`/`Regression`

### 族 6 · 治理与沉淀（S12–S14）
`Manifest`/`Artifact`/`Version` · `Environment` 指纹 · `Lineage` · `Incident`/`Alert` · `Cost`/`Capacity`

### 4.1 四个横切契约（所有对象强制）

| 契约 | 形态 | 作用 |
|---|---|---|
| **Anchor 锚点** | `{ file, span, objectId, runId }` | 所有交互只广播 anchor，联动复杂度从 N² 降到 N |
| **Provenance 可信度** | `fact / resolved / compiled / estimated / measured` | 杜绝把估算画成实测；也是"估算 vs 实测"对照的基础 |
| **Action 动作** | `{ kind, payload, needsConfirm }` | 图上每条结论都可执行；高开销采集与改代码需确认 |
| **Scope 适用边界** | `{ platform, dtype, shape, backend, version }` | v2 新增。跨阶段复用（尤其 Recipe/Knowledge/Baseline）必须携带边界，否则经验会被错误套用 |

`Provenance` 已在 `operator-inspector.js` 中落地为 5 档，直接沿用。

## 5. 可视化原语总表（3 载体 + 17 图元）

标 **NEW** 的是 v2 从全流程推导中新增或显著泛化的。

### 载体（不是图，是图元的挂载面与叙事骨架）

| # | 原语 | 职责 | 服务阶段 |
|---|---|---|---|
| L1 | **TextCanvas** 文本锚面 **NEW（泛化）** | 源码 / IR 文本 / 日志三种文本面统一：行高亮、区段条、sticky 段落指示、行内标注 | S5–S9、S13 |
| L2 | **FindingCard** 结论证据卡 | 结论句 + 触发条件 + 折叠证据 + 动作 + provenance 角标 | 全部 |
| L3 | **EvidenceChain** 跨层证据链 **NEW** | 固定语义层带（源码→IR→Kernel→Task→Tensor→症状），高亮单条因果路径，标记首个异常点 | S6–S9、S13 |

> `EvidenceChain` 是三份规划文档反复要求、但至今没有统一载体的对象。它不是普通 DAG：**层带是固定的、路径是唯一的、每层节点必须能下钻到对应图元**。是本次最重要的新增。

### A 组 · 结构类

| # | 原语 | 回答 | 关键变体 |
|---|---|---|---|
| A1 | **GraphView** 有向图 | 数据怎么流？谁依赖谁？哪断了？ | 计算图 / 依赖图 / 模型图 / 状态机 / **血缘 lineage 版式 NEW**；图层开关（精度·风险·覆盖·规则匹配·动态状态） |
| A2 | **TreeView** 层级树 | 怎么嵌套？哪层是并行域？ | Scope 树 / 循环树 / 产物树；带指标列的树形表 |
| A3 | **TopologyView** 固定底图拓扑 | 数据在硬件上走哪条路？ | **芯片内底图**（Cluster/Cube/Vector/存储层级）+ **卡间集群底图 NEW**（Device/Interconnect/放置）；静态映射与实测路径必须视觉区分 |
| A4 | **TilingView** 分块映射 | `8192 = 16 × 512` 怎么切的？尾块在哪？ | Chunk/Tile 切分、M/N/K 三视图、**并行切分模式 NEW**（TP/PP/EP 的张量切分与 rank 映射） |
| A5 | **FlowView** 流量分配（桑基）**NEW** | 这些量流去了哪里？各占多少？ | 带宽去向、MoE 专家路由与负载、PD 分离分流、KV 命中/未命中、请求路由 |

> `FlowView` 的判据是**守恒量的分配**——总带宽/总 token/总请求按路径分流。用堆叠条表达会丢失"从哪来到哪去"，用 Graph 表达会丢失量的比例。

### B 组 · 时间类

| # | 原语 | 回答 | 与相邻原语的边界 |
|---|---|---|---|
| B1 | **TimelineView** 并发泳道 | 谁和谁重叠？谁在等？ | 表**并发**。多轨（多 Rank/多 Core/多 Ring）、等待原因着色、关键路径描边、区间刷选 |
| B2 | **SequenceView** 顺序阶段轴 | 按什么顺序？哪步失败？ | 表**强顺序 + 前后状态增量**。无变化步骤可折叠；支持逐步 pass/fail 徽标（逐 Pass 数值二分） |
| B3 | **BreakdownView** 构成/瀑布 | 总量由什么构成？谁贡献最大？ | 表**构成**（总量 = 分项之和）。瀑布 / 堆叠 / 旭日；**预算模式 NEW**（分项 vs 容量线，用于显存与容量规划） |
| B4 | **TrendView** 趋势与回归 **NEW** | 相比上一版是进步还是回退？何时引入的？ | 横轴是**版本或日历时间**，纵轴是指标，带基线带、门禁线、回归标记与变更点标注 |

> B1/B2/B3/B4 四者常被混做一个"时间图"，但语义完全不同：**并发 / 顺序 / 构成 / 演化**。这是 v1 里 `run-timeline.js`、`qwen3-performance-swimlane.js`、`inference-timeline.js` 三份代码互相不能复用的根源。

### C 组 · 数值类

| # | 原语 | 回答 | 关键变体 |
|---|---|---|---|
| C1 | **MetricView** 指标卡/仪表/门禁 | 多少？相对基线如何？过没过？ | KPI 行 / 仪表 / 评分条 / 门禁徽标 |
| C2 | **DistributionView** 分布 | 集中还是弥散？容差合理吗？ | 误差直方图 / ULP / 耗时分布 / **输入输出长度分布 NEW** / Rank 间不均衡 |
| C3 | **HeatmapView** 二维热图 | 局部还是系统性？甜点在哪？ | Tensor 误差空间图（含 Padding 遮罩、Top-K 定位）/ 参数二维扫描（含合法区·越界区·数值失败区）/ Rank×Layer 不均衡 |
| C4 | **ScatterView** 散点 / 前沿 | 受限于算力还是带宽？哪些候选值得留？ | Roofline（含屋顶包络）/ Pareto 前沿 / 单参数敏感性曲线 / **平行坐标 NEW**（多维方案与候选对比，优于雷达图）/ 容量曲线 |
| C5 | **OccupancyView** 空间占用 | 装得下吗？谁和谁重叠？何时释放？ | 地址打包（地址区间 × 生命周期矩形）/ 容量包络随时间 / Ring Slot / **KV Cache 分页占用与碎片 NEW** |

> `OccupancyView` 是这条工具链最不可替代的图元，通用图表库没有对应物；从算子 UB 地址一直复用到服务侧 KV Cache 分页，跨度最大。

### D 组 · 对照与凭据类

| # | 原语 | 回答 | 关键变体 |
|---|---|---|---|
| D1 | **DiffView** 对照 | 变了什么？和基线差在哪？ | 源码 Diff / IR 结构化 Diff（op 增删移改 + shape·dtype·layout·attrs）/ 契约 Diff / **基线因果 Diff**（参数变化→指标变化+归因列）/ 灰度批次对照 |
| D2 | **TableView** 表格 **NEW（泛化）** | 谁最值得先看？哪格不通过？ | 三态：**矩阵态**（Oracle / 覆盖 / 支持度 / 门禁看板）· **排行态**（Top-N 归因，格内条形）· **明细态**（Tensor 清单、算子清单、候选清单）；统一支持排序、筛选、锚点跳转 |

> v1 把它叫 `MatrixView` 是窄了。全流程扫下来，「排行归因表」（算子耗时 Top-N、缺口优先级、规则匹配排序）出现频次不低于状态矩阵，应该是同一个组件的三种模式。

## 7. 智能体调用契约

### 7.1 统一调用形态

智能体不调用 20 个 API，只产出一种「可视化作业单元」：

```jsonc
{
  "id": "vb-kv-frag-01",
  "stage": "S11",
  "primitive": "OccupancyView",
  "variant": "paged",
  "title": "KV Cache 分页碎片率 23%，长上下文请求被迫抢占",
  "origin": "measured",                    // 强制
  "anchor": { "runId": "run-8842", "objectId": "kvcache:pool-0" },
  "scope": { "platform": "A3", "seqLen": "8k-32k", "concurrency": 64 },
  "data": { /* 该原语的契约 */ },
  "finding": {
    "verdict": "碎片来自 block 大小与平均请求长度不匹配",
    "trigger": "并发 > 48 且序列长度方差 > 2x",
    "evidence": ["counter:kv_alloc_fail", "request:top-20-preempted"],
    "actions": [
      { "kind": "compare", "payload": { "blockSize": [16, 32] } },
      { "kind": "apply", "payload": { "blockSize": 32 }, "needsConfirm": true }
    ]
  }
}
```

前端只需一个 registry：`render(container, block)` 按 `primitive` + `variant` 分发。新增图元不改调用方。

### 7.2 四条硬约束

1. **智能体不产出 HTML/SVG**，只产出上述 payload。当前原型里大量 `renderXxx` 直接拼 HTML 字符串，是复用的最大障碍。
2. **`origin` 不可缺省**，缺省按 `estimated` 降级渲染并显示警示。
3. **所有交互只广播 `anchor`**，不直接操作其他视图。
4. **跨阶段复用的对象必须带 `scope`**（适用边界）。一条在 A3/BF16/8k 上成立的调优结论，不能无声地出现在 A5/FP8/128k 的场景里。

### 7.3 分层封装

```
@pto-viz/schema      // JSON Schema + TS 类型；同时作为智能体的 tool schema 直接下发
@pto-viz/core        // anchor 总线、provenance 渲染、action 分发、scope 校验、主题令牌
@pto-viz/primitives  // 17 个图元，纯函数：(container, data) => dispose()
@pto-viz/carriers    // TextCanvas / FindingCard / EvidenceChain
```

把 `schema` 直接当作智能体的工具定义下发，Agent 输出天然合法，省掉后处理校验层。

## 8. 现状盘点

| 覆盖度 | 阶段 | 说明 |
|---|---|---|
| **已实现** | S5 Coding、S6 编译 | Toolkit Studio 最成熟的两段，可直接作为原语抽取的样本 |
| **部分** | S2 选型、S3 接入、S4 意图、S7 正确性、S8 调试、S9 调优、S10 分布式、S11 服务、S12 基线、S14 沉淀 | 有图但缺对象化；多为一次性实现，换个算子/模型就不能复用 |
| **空白** | S1 目标、S13 在线治理 | 两端各缺一块：前端缺"达标基准"，后端缺"结论回流" |

**四个最值得补的缺口：**

1. **EvidenceChain 载体**（S8 主场，横跨 S6–S13）——三份规划文档都要求，至今没有统一实现。
2. **TrendView + Baseline/Regression 对象**（S12）——没有它，性能 Lab 的结论无法沉淀成回归防线。
3. **Experiment/Candidate/Gate 对象化**（S9）——目前候选对比是硬编码，无法支撑"受约束的参数搜索"。
4. **S1 Objective 对象**——所有"达标/未达标"判定的基准，缺失导致下游指标失去意义。

## 9. 落地优先级

| 批次 | 内容 | 依据 |
|---|---|---|
| **P0** | `schema` + `core`（anchor/provenance/scope）· `FindingCard` · `TableView` · `MetricView` | 14/14 与 12/14 覆盖，且是其他图元的挂载前提 |
| **P1** | `GraphView`（含图层与 lineage）· `TextCanvas` · `DiffView` · `SequenceView` · `OccupancyView` | 支撑 S5–S7 已成熟场景的复用化改造，投入产出比最高 |
| **P2** | `EvidenceChain` · `TimelineView` · `BreakdownView` · `TopologyView` · `TrendView` | 补齐调试、调优、治理三条主链 |
| **P3** | `TilingView` · `FlowView` · `HeatmapView` · `ScatterView` · `DistributionView` · `TreeView` | 深度分析与新场景（分布式、服务、选型） |

**迁移策略（不建议重写）：**

1. 先抽 schema 不动实现——给现有 `renderXxx` 补输入契约，验证 17 个图元的字段能否覆盖全部现存调用。
2. 先统一 anchor 总线——当前联动是点对点的，换成广播后可先收敛一批联动缺陷。
3. 按 P0→P3 逐个替换，每替换一个就下线对应的重复实现（如三份泳道合一）。
4. 以 Toolkit Studio 为首个宿主验证，再回迁其余原型。

## 10. 明确不抽象的部分

- **一次性叙事插画**：IR Pass 快照里的定制示意图、白皮书架构图。价值在人工编排的版式，抽象后即失效。
- **页面框架与信息架构**：左侧资源管理器 / 中间工作区 / 右侧面板 / 底部证据区，属于工作台外壳。
- **领域计算逻辑**：关键路径求解、IR 结构化 Diff 算法、瓶颈排序、Pareto 筛选——属于智能体或后端能力，图元只画算好的结果。
- **模型/算子特有的定制视图**：`renderPagedAttentionInspector` 这类，应拆成「通用图元 + 该算子的数据装配」，装配留在业务侧。
- **交互录制与回放编排**：融合前后的分步动画属于叙事编排，可作为 `TopologyView` 的一个可选控制器，但不进核心契约。
