# PyPTO 2027 UX 规划：从「能生成」到「能采信」

> 战略讨论稿｜2026-11-09 撰写｜规划年度：2027 自然年
> 口径：五看（市场与趋势、客户、竞争、自己、机会）→ 三定（方向、目标、路径）
> 性质：面向产品、UX、技术与业务决策者的方向性讨论材料，不代表已交付能力、已确定产品边界或研发承诺。
> 证据标注：**【外·一手】** 公开一手资料（官方页面、论文摘要、官方调研页）；**【外·二手】** 媒体或分析机构转述；**【内】** 本仓库已有研究材料；**【推断】** 作者判断；**【建议】** 行动提议。外部资料核实于 2026-11-09。

## 一、核心结论（一页）

**2027 年 PyPTO 的 UX 主命题，不是「让 Agent 把算子写出来」，而是「让人和组织敢把 Agent 写出来的东西用到生产里」。**

理由是三条已经成立的外部事实叠加：

1. **Agent 写算子在 2026 年已被正式纳入昇腾官方路线**。华为在 HUAWEI CONNECT 2026（2026-09-19，上海）把「从人工算子编程到 Agent 编程与调优」列为智能体时代五个转变之一，并开源了 CANNBot（算子生成）、Model Agent（模型适配）、MindStudio Agent（精度调优）、Solution Agent（行业部署）四类端到端 Agent 工具。**【外·一手】**[1] 这意味着「有没有 Agent」在 2027 不再是差异点。
2. **同期学术界已经证明「生成」这一环的可信度远低于其表观数字**。KernelBench-Verified 在修正基线并引入隐藏测试分布后，最优模型的几何平均加速从 1.43× 降到 **0.88×**，即不再快于 PyTorch，且该模型生成的 kernel 有 **28%** 抬高了峰值显存；原因包括针对窄测试分布硬编码绕过计算。**【外·一手】**[5] KernelBenchX 进一步给出：**46.6%** 的「正确」kernel 慢于 eager 基线，72% 的 Fusion 任务在全部五种方法下失败，量化类任务 0/30 成功。**【外·一手】**[6]
3. **开发者的信任模式已经稳定在「可验证才采信」**。Stack Overflow 2026 开发者调查：编码助手与 Agent 以 66% 成为第一大 AI 用例、73% 的受访者每日使用，但只有 **48%** 表示「在能轻易验证答案时才信任 AI」，仅 16% 把信任扩展到非重要决策；官方结论是 human-in-the-loop 仍是主导工作模式。**【外·一手】**[7]

**【推断】** 2027 年的竞争位置因此发生了位移：生成能力会迅速商品化，**稀缺的是「验收面」**——把一次 Agent 产出的正确性、性能、硬件约束与资源代价，组织成一个人能在几分钟内判断「收不收」的界面。而这恰好落在 PyPTO 的结构优势上：Tile 编程模型 + 多级 IR（Tensor→Tile→Block→Execution Graph）+ MPMD 调度 + 分层抽象，使它比纯 kernel DSL 掌握更长的、可追溯的语义链路。**【内】**[9]

**【建议】** 2027 年聚焦两个重点方向，外加一个条件启动方向：

| | 方向 | 一句话 | 优先级 |
|---|---|---|---|
| **方向一** | **可采信的 Agent 作业面** | 把「Agent 交付一个算子」变成一次有契约、有独立验收、有接管出口的工程作业 | P0，2027 全年主线 |
| **方向二** | **代际迁移与硬件约束工作台** | 一年一代的硬件节奏下，让「源码可移植」的承诺在体验上被兑现 | P0，跟随 960 系列节奏 |
| **方向三** | **服务目标到算子的证据链** | SuperPoD/SuperCluster 规模下，从服务结果归因到算子与通信 | P1，条件启动 |

两个 P0 共享同一套对象模型（任务契约 → 候选 → 证据 → 决策），因此不是两个产品，而是同一体验底座的两个入口。

## 二、五看

### 1. 看市场与趋势：2027 的四个硬时间点

| 趋势与公开依据 | 2027 年的具体形态 | 对 PyPTO UX 的直接含义 |
|---|---|---|
| **硬件一年一代，且 2027 年内有两次代际事件**。Ascend 960DT 定于 2027 Q1（比原计划提前三个季度）、960PR 定于 2027 Q3；970/980 分别在 2028/2029。**【外·二手】**[2] | 2027 年开发者会在同一年里面对两次新代际适配，而不是一次 | 迁移体验从「偶发项目」变成**常态工作流**，必须有常设入口，而非一次性迁移指南 |
| **PTO ISA 对外开放，并把「跨代兼容、算子源码可移植」作为公开承诺**；现含 8 类、120+ 条虚拟指令，支持 Auto 与 Manual 两种优化模式。**【外·一手】**[1] | 承诺已经公开，2027 是被开发者实际检验的一年 | **「可移植」是一个体验承诺，不只是编译器承诺**：移植后性能掉多少、哪一行需要改、Auto 退回 Manual 的代价，必须可见 |
| **Agent 编程与调优进入官方工具链**，CANNBot/Model Agent/MindStudio Agent/Solution Agent 均已开源；Ascend 社区开放万卡级算力并推出「100 NPU-Hour 计划」，未来三年投入 50 亿元人民币生态建设。**【外·一手】**[1] | 2027 年开发者手上同时有多个 Agent 工具，算力门槛显著降低 | 竞争从「Agent 能力」转向**「谁的产出可被采信、谁能承接别家 Agent 的产出」**；也意味着 Agent 跑实验的算力约束在减弱，**验证成本成为新瓶颈** |
| **评测口径本身正在成为基础设施**。CANN Bench 已作为昇腾侧开放基准进入官方 CANN 仓，覆盖 53 个算子、1060 个用例、四个难度层与 FP16/BF16/FP32/INT8，采用编译、功能正确性、性能三轴加权评分，并以真机硬件锚定性能上限（HAP）作为性能刻度，明确设计为抵抗 reward hacking。**【外·一手】**[3] | 2027 年「我的算子好不好」有了社区公认刻度 | **产品应当对齐这把尺子而不是自造一把**；三轴评分可以直接作为验收界面的信息结构 |

**【推断】** 四条合起来给出 2027 的市场结构：算力不缺、生成不缺、评测刻度开始统一，**缺的是把这三者接起来让人做决定的那一层**。这是本规划把「验收面」而不是「生成能力」作为主命题的全部依据。

**边界说明**：以上公开材料证明方向正在被产品化或研究，不证明任何能力已在 PyPTO 上实现；960 系列时间表来自对 HC 2026 的媒体转述，未见独立确认。

### 2. 看客户：决策内容变了，决策人没变

**【内】** 仓库既有研究已经刻画出五类角色（算子开发者、编译器 Pass 开发者、后端与 ISA 工程师、运行时与系统工程师、服务与部署工程师）及三条贯穿主线：自动化的信任赤字、抽象是一道单向门、工具在最需要的时候失效。[10] **【推断】** Agent 介入后，这三条主线不是被解决，而是被放大——因为生成速度上升而验证速度没有同步上升。

2027 年各角色的**决策内容**变化：

| 角色 | 2026 的典型问题 | 2027 的典型问题 | 由此产生的体验诉求 |
|---|---|---|---|
| 算子工程师 | 「这个算子怎么写出来、怎么调快」 | 「这三个候选里哪个我敢签字，依据是什么」 | 候选对比 + 独立验收 + 可下钻到 IR 与 trace 的证据 |
| 模型／推理工程师 | 「这个算子在我的模型里快了多少」 | 「跨代硬件上我的模型还跑不跑得动、要改哪里」 | 迁移影响面清单、按模型而非按算子组织的回归 |
| 编译／后端工程师 | 「编译器为什么这么选」 | 「Agent 绕过了编译器的哪个假设，是 bug 还是我的启发式该改」 | Agent 决策与编译器决策的对照、可回灌的反例 |
| 平台／性能团队 | 「谁在占设备」 | 「Agent 跑掉的算力换回了什么，哪些结果可复用」 | 实验预算、产出留存、跨团队证据交接 |
| 技术负责人／评审者 | 「这个优化有效吗」 | 「这批 Agent 产出的质量门槛在哪，谁担责」 | 一页式验收摘要 + 明确的未覆盖项与责任边界 |

**【外·一手】** 外部调研与这组推演一致：开发者使用 AI 最集中的场景是熟悉代码的生成（69%）、调试与重构（64%）、写测试（58%），都属于「答案可核验」的技术任务；一旦任务转向难以核验的领域，使用率显著下降。[7]

**【推断】** 共同诉求可以压成一句：**用户要的不是更强的 Agent，而是更便宜的「不信」**——快速否掉一个坏候选的成本，决定了他们是否愿意让 Agent 批量产出。目前这个成本极高，因为否掉一个候选往往要人手工复现一遍。

**局限**：上表角色与诉求基于仓库既有研究与场景推演，不是 2027 年的新一轮实证用研；方向一的第一阶段应当补一轮针对「验收行为」的专项访谈。

### 3. 看竞争：2027 的竞争面是「验收」与「迁移」，不是 DSL 语法

| 对标层次 | 代表参照与公开事实 | 可借鉴／可被追问的体验问题 | PyPTO 在 2027 的位置 |
|---|---|---|---|
| **昇腾官方 Agent 工具链** | CANNBot、Model Agent、MindStudio Agent、Solution Agent 已开源。**【外·一手】**[1] | 生成能力官方化之后，用户如何判断产出可用 | 不与之争生成，**争验收与承接**；应能消费这些工具的产出并给出独立结论 |
| **昇腾侧 Agent 算子研究** | AgenticCANN 在 Ascend 910B 六个算子上：elementwise/normalization 可行率 90–100%，**fusion 仅 56%**；盘古 1B 推理 kernel 最高 6.65× 加速；知识注入把 elementwise 可行率从 57% 提到 86%。**【外·一手】**[4] | 「越难的算子越不行」是结构性现象，不是模型问题 | **融合与跨层编排正是 PyPTO 多级 IR 与 MPMD 的主场**，这是差异化的真实落点 |
| **社区评测刻度** | CANN Bench 三轴评分 + 真机 HAP 上限 + 抗 reward hacking 设计，已版本化进入官方 CANN 仓。**【外·一手】**[3] | 谁定义「好」，谁就定义了产品的界面 | **对齐而非另立**：把三轴与 HAP 作为验收界面的信息骨架 |
| **上游生态的收敛动作** | Helion 由 Meta 捐入并于 2026-04-07 被 PyTorch Foundation 接纳，采用 AOT autotuning（约 10 分钟搜索 1200 个候选），后端路线图含 TileIR/Pallas/CuTe DSL。**【外·二手，press-release 级】**[8] | 「一次搜很多候选」正在成为标准动作 | 候选规模化之后，**对比与采信界面**成为瓶颈，与本规划结论一致 |
| **头部模型侧的硬件协同** | DeepSeek 于 2026-09-30 发布 Ascend 版 TileLang、DeepGEMM、DeepEP、TileKernels、FlashMLA、DeepSelect；分析指出其中仅 TileLang 当时可用，其余依赖 CANN 9.2.0 与 C++20；co-design 案例包括为 Ascend 重排 FlashMLA 的 KV-cache 布局（量化值与 scale 同区存放以减少搬运请求）、以及因 Cube L0C 无法原地 rescale 而把累加器留在 Vector UB。**【外·二手】**[11] | **真实的昇腾优化全部发生在「硬件事实 → 实现决策」这一层** | 这正是 Hardware-Native 体验要服务的决策类型；**把这类决策显式化，是 PyPTO 可防御的叙事** |

**【推断】** 2027 年 PyPTO 不应把差异化押在「tile DSL 更好用」上——这一层已高度同质。可防御的位置有两个：**(a) 融合与跨层编排场景下的 Agent 可采信性**（外部数据显示这是公认难区）；**(b) 跨代迁移的体验兑现**（官方承诺已公开，谁先做出体验谁就定义标准）。

### 4. 看自己：结构优势真实，但兑现依赖三件事

**【内】** PyPTO 的结构性资产可从仓库材料确认：Tile 为核心的编程模型、Tensor→Tile→Block→Execution Graph 的多级 IR 与 pass 体系、CodeGen 到 PTO 虚拟指令、设备侧 MPMD 调度、以及面向不同人群的分层抽象（算法开发者用 Tensor 级、性能专家用 Tile 级、系统开发者用 Block 级）。[9] 同时，仓库已有大量可直接复用的研究沉淀：开发者体验洞察、基于 1463 条 Issue 的 Hardware-Native 失效类型、性能调优真实案例、Agent 强参与下的流程与体验变化推演、以及 Hardware-Native 全流程体验问题地图。[10][12][13][14][15]

| 真实优势 | 2027 年兑现它所依赖的前提 |
|---|---|
| 语义链路比纯 kernel DSL 更长（DSL → 多级 IR → 虚拟指令 → 执行） | **链路末端必须能接回用户写的那一行源码**。诊断只定位到 IR 文本位置时，对人价值有限，对 Agent 价值更低——Agent 无法用一个指向 IR 行的提示去改用户代码 |
| MPMD 与跨 kernel 编排在架构上有位置 | 需要有与之匹配的**作业级（而非 kernel 级）验收对象**，否则优势无法进入用户感知 |
| 已有丰富的真实案例与失效类型分类 | 需要把这些分类**转成验收界面上的检查项**，而不是停留在报告里 |
| 分层抽象 | **降级路径（逃生舱）的迁移成本必须低**。若从自动层降到手动层等于重写数据流，分层在真实压力下不会被使用 |

**【推断】** 这四条前提中，前两条决定方向一能否成立，第四条决定方向二能否成立。它们都属于**体验与架构的交界**，无法只靠 UX 侧交付，必须进入 2027 的联合排期。

### 5. 看机会：三个机会的价值与首要不确定性

| 机会 | 用户价值假设 | 战略价值假设 | 首要不确定性 |
|---|---|---|---|
| **可采信的 Agent 作业面** | 把「否掉一个坏候选」的成本从小时级降到分钟级，让专家敢于让 Agent 批量产出 | 在生成能力商品化后占住验收位；对齐 CANN Bench 刻度即进入社区默认路径 | 独立验收能否做到足够强（反例生成、隐藏分布、显存与数值同时看），以及验证本身的算力成本 |
| **代际迁移与硬件约束工作台** | 一年两次代际事件下，把迁移从项目变成例行作业 | 兑现 PTO ISA 的公开可移植承诺，形成官方叙事的体验载体 | 960 系列真机与工具链的可得时间；跨代性能回归的数据来源 |
| **服务目标到算子的证据链** | 让团队知道该优化哪一层、改了是否对真实负载有效 | 把底层性能与服务价值连接 | 跨系统数据权限、代表性负载、与服务平台的边界 |

## 三、三定之一：定方向（2 个重点 + 1 个条件启动）

### 方向一｜可采信的 Agent 作业面（P0，2027 全年主线）

**问题判断。** 2027 年的瓶颈不在生成。外部证据显示：表观加速在修正基线后可能归零甚至为负（0.88× 几何平均）、正确的 kernel 近半数慢于基线、迭代修复会抬高编译通过率但拉低平均加速（1.58×→1.44×）、融合类任务是系统性难区（昇腾侧 fusion 可行率 56%，GPU 侧 Fusion 任务 72% 全失败）。**【外·一手】**[4][5][6] **【推断】** 这些数字的共同含义是：**任何「Agent 自称成功」的信号都不可直接采信，产品必须提供与生成过程解耦的独立验收。**

**目标体验。** 开发者给出一个有边界的目标（算子语义、设备、workload、精度要求、可改范围、算力预算、停止条件），Agent 在授权内探索；最终开发者看到的不是一段对话，而是**一张可签字的验收页**：哪些候选通过了什么检查、在什么硬件上离上限多远、哪些输入没覆盖、花了多少设备时间、哪一步是 Agent 的假设而不是工具的结论。

**关键设计对象。**

1. **任务契约（Task Contract）**：目标、数值语义、设备与代际、workload 形状分布、精度门槛、可修改文件范围、算力预算、停止条件。可编辑、可复用、保留来源。**它同时是 Agent 的输入和验收的判据**——没有契约就没有「通过」的定义。
2. **独立验收面（Acceptance Panel）**：对齐 CANN Bench 的三轴结构——**编译、功能正确性、性能**分别独立呈现，性能以真机硬件锚定上限（HAP 式刻度）而非相对基线倍数作为主刻度。**【外·一手】**[3] 追加两条本仓库证据支持的必查项：**峰值显存／内存占用变化**（外部数据显示 28% 的生成 kernel 抬高峰值显存[5]）与**数值精度口径**（量化路径在外部评测中 0/30 成功[6]）。
3. **反例与覆盖（Counterexamples & Coverage）**：显式呈现测试分布、隐藏分布结果、以及「哪些输入形状／数值范围未被覆盖」。**【推断】** 这一项是抗 reward hacking 的用户侧对应物：用户不需要理解 reward hacking，但需要看到「这个候选只在测过的那几个 shape 上成立」。
4. **证据与归因（Evidence Trail）**：每个候选绑定代码版本、编译产物、IR 与 pass 决策、trace、测量条件；区分三类来源——Agent 的假设、工具的结果、人的决定。**【推断】** 这是 PyPTO 多级 IR 的体验兑现点，也是它与纯 kernel DSL 的真实分野。
5. **预算与接管（Budget & Handover）**：设备时间与调用成本实时可见；支持暂停、接管、从任意候选分叉继续。**【外·一手】** 外部调研显示 human-in-the-loop 是主导模式[7]，接管不是降级路径而是常态路径。

**首个设计交付物。** 三段式交互原型：**(a) 契约起草**（含缺失项提示与预算设定）→ **(b) 执行与接管**（计划、当前动作、预算消耗、失败与分叉）→ **(c) 验收与签字**（三轴 + 覆盖 + 证据下钻 + 一页摘要）。配套一份**验收数据契约草案**：Agent 工具结果、测量条件、覆盖信息的最小字段集。

**成功信号（待验证）。** 在同一批真实任务上，用户**否掉一个坏候选的平均时间**显著下降，且采信的候选在后续真机回归中不出现翻盘。

**失败即停（kill criteria）。** 若独立验收无法在不显著增加算力成本的前提下稳定识别出「表观有效但实际无效」的候选，则本方向的核心假设不成立，应退回到「证据组织工具」的较小定位。

### 方向二｜代际迁移与硬件约束工作台（P0，跟随 960 系列节奏）

**问题判断。** 2027 年内存在两次代际事件（960DT 定于 Q1、960PR 定于 Q3）**【外·二手】**[2]，而 PTO ISA 已公开承诺「tile 级抽象实现跨代兼容、算子源码可跨代迁移」并提供 Auto／Manual 两种优化模式。**【外·一手】**[1] **【推断】** 承诺公开意味着它会被检验：**源码能编过不等于迁移完成**——性能是否保持、哪些手工优化在新代际上失效、Auto 模式够不够、不够时降到 Manual 要改多少，都是真实的用户工作。这正是仓库 Hardware-Native 研究一直在描述的那类决策，只是被代际节奏放大了。**【内】**[12][14]

外部 co-design 案例佐证了这类决策的真实形态：为 Ascend 调整 FlashMLA 的 KV-cache 布局以减少搬运请求、因 Cube L0C 无法原地 rescale 而把累加器留在 Vector UB。**【外·二手】**[11] **【推断】** 这些都不是「写得对不对」的问题，而是「硬件事实 → 实现决策」的问题；它们目前主要靠少数专家的头脑中的映射完成，没有产品承载。

**目标体验。** 开发者把一组已有算子或一个模型指向新代际，得到一张**迁移影响面**：哪些可直接复用、哪些能编过但性能回退、哪些依赖的硬件事实已改变、每一条对应要改的那一行源码与可选方案；Auto 模式达不到目标时，能在**同一套写法内**逐步接手控制权，而不是重写数据流。

**关键设计对象。**

1. **代际事实差异表（Generation Delta）**：把代际间与开发决策相关的硬件事实（存储层级容量、搬运与同步、精度格式如 HiF8 到 HiF4 的演进、SIMD 与 SIMT 的组合方式）组织成**可被引用的条目**，每条关联「会影响哪类实现决策」。**【外·一手】** HC 2026 明确列出 SIMD→SIMD+SIMT、HiF8→HiF4 两条转变[1]。
2. **迁移影响面（Migration Impact）**：以算子／模型为单位的分类清单——直接复用、需调参、需改实现、不支持；每条给出判据与证据，而非仅给结论。
3. **约束到源码的回指（Constraint → Source）**：硬件约束被破坏或被逼近时，提示指向**用户写的那一行**，而不是流水线后的 IR 位置。**【推断】** 这是方向一与方向二共用的地基；它不成立，两个方向都只能停在「IR 某处有问题」。
4. **渐进式逃生舱（Progressive Control）**：Auto → Manual 的控制权移交应是**同一套语法内的标注式降级**，而非切换到另一套数据流写法。**【推断】** 业界在这一点上已形成共识做法（在同一语言内提供低层控制面），**若 PyPTO 的降级等于重写，分层抽象在真实压力下不会被使用**——这是本方向上风险最高、也最值得在 2027 解决的一条。
5. **跨代回归（Cross-Gen Regression）**：同一套契约在两个代际上的结果并排呈现，测量条件差异显式标注，禁止跨条件直接比较。

**首个设计交付物。** 一个**代际迁移故事**的交互原型：选定一组真实算子（优先取仓库已有案例），走完「指向新代际 → 影响面 → 逐条处置 → 跨代回归 → 迁移摘要」；外加一份代际事实条目的结构定义（字段、来源、失效期）。

**成功信号（待验证）。** 一次代际迁移中，**需要专家从零排查的算子比例**下降，且迁移后性能回退能在上线前被发现而不是在生产中被发现。

**失败即停。** 若 960 系列真机与工具链在 2027 年内无法稳定获得，本方向降级为「代际事实知识库 + 迁移检查清单」，不投入完整工作台。

---

### 方向三｜服务目标到算子的证据链（P1，条件启动）

**问题判断。** 2027 年的运行环境是 SuperPoD 与 SuperCluster：单套 Atlas 960E SuperPoD 可支持 4096 NPU、8 EFLOPS FP8、至多 1PB HBM；SuperCluster 可互联至 512,000 NPU，多轨拓扑可扩展到百万级；华为并指出常规服务器集群中处理器间通信可占训练时间 **40% 以上**。**【外·二手】**[2] **【内】** 仓库既有研究亦指向同一结论：分析的最小单元在真实服务里是链路而不是算子。[13]

**【推断】** 在这个规模下，「算子快了 x 倍」与「服务目标达成」之间的距离进一步拉大。但这一层的体验建设**强依赖外部数据与边界**（服务平台、调度、框架、权限），因此 2027 年应作为条件启动项，而不是与两个 P0 并列投入。

**2027 年的最小动作。** 不建平台，先建**接口与一个故事**：选一个真实的推理或训练链路问题，走通「服务目标 → 分层下钻 → 定位到算子或通信 → 回到方向一的契约 → 验收后交回服务侧」的闭环，并在过程中明确三件事：数据从哪来、谁有权限、结论由谁负责。

**启动条件。** 具备一个愿意共建的服务或训练团队、可获得代表性负载与样本 trace、且方向一的契约与证据对象已稳定。三者缺一则本方向在 2027 保持为研究议题。

---

### 三个方向的关系

```text
用户目标：交付一个算子 / 迁移到新代际 / 达成服务目标
                        ↓
         人 + Agent：定义契约、探索候选、独立验收、签字
                        ↓
   共享对象：任务契约 → 候选 → 证据（IR/trace/测量条件）→ 决策
                        ↓
   既有执行层：PyPTO 编译与调度、CANN、官方 Agent 工具、服务与训练框架
```

**【建议】** 共享对象是设计提议，不预设统一平台已存在。方向一与方向二**必须共用**契约与证据对象，否则会产出两套不互通的界面；方向三在启动时复用同一套对象，不另建模型。PyPTO 的产品边界、与官方 Agent 工具链的分工、以及数据协议，需由产品与技术共同确认后固化。

## 四、三定之二：定目标

**总体目标（2027）**：把「一次 Agent 产出从交付到被采信」的周期与成本降到可规模化的水平，同时不降低质量门槛。**不以单一加速倍数作为价值陈述**——外部证据已显示该口径在修正基线后不成立。**【外·一手】**[5]

| 方向 | 用户价值指标 | 质量与成本护栏 | 待验证的成功信号 |
|---|---|---|---|
| 方向一 可采信的 Agent 作业面 | 否掉坏候选的时间；从契约到可签字候选的时间；人工介入的原因分布 | 三轴（编译／正确性／性能）达标率、覆盖缺口数、峰值内存变化、设备时间与调用成本 | 同批真实任务下用户更快形成可审查结论，且采信结果在真机回归中不翻盘 |
| 方向二 代际迁移工作台 | 迁移中需从零排查的算子比例；迁移影响面的判定准确率 | 跨代性能回退的发现时点（上线前／后）、降级改动量（行数或改动类型） | 代际事件前后，迁移从专项项目变为例行作业 |
| 方向三 服务证据链（条件） | 归因到正确层级的比例 | 测量口径一致性、负载代表性 | 团队能据此决定优化层级并在代表性负载上验证 |

**【建议】** 2027 Q1 先做基线测量：现有流程下**否掉一个候选、完成一次迁移判定**各需多长时间、失败原因分布如何。没有基线的量化目标会在复盘时无法解释。报告时必须区分离线实验、模拟负载与真实生产，并披露样本量与未完成任务。

**不承诺的三件事（期望管理）。** **【建议】**

1. 不承诺「Agent 自动写出高性能算子」。外部一手数据不支持，承诺会在第一次真实演示中被戳破；应承诺「每一步可验证、可接管」。
2. 不承诺跨厂商硬件可移植。应正面呈现这一取舍，并把它转化为「硬件专用深度」的论证前提。
3. 不承诺全算子覆盖。应公开覆盖范围与更新节奏，把口径诚实本身作为差异化资产。

## 五、三定之三：定路径

| 阶段 | 重点工作 | UX 与技术交付 | 退出条件／决策点 |
|---|---|---|---|
| **2027 Q1**：定义与基线 | 针对「验收行为」的专项访谈（算子、模型、评审三类角色）；盘点可用的真机与数据；确认与官方 Agent 工具链的分工 | 任务契约与验收面的对象定义；验收数据契约草案；现状基线报告 | 用户确认「否掉候选的成本」是真问题；契约字段可被至少一类真实任务填满 |
| **2027 Q2**：方向一首个闭环 | 选 1–2 个真实算子任务（优先取融合类，因其为公认难区）打通契约→执行→验收 | 三段式交互原型 + 可运行的验收面（对齐三轴与真机上限刻度） | 在真实任务上能稳定识别出「表观有效实际无效」的候选；否则触发方向一的 kill criteria |
| **2027 Q2–Q3**：方向二跟随代际 | 结合 960 系列可得性，做代际事实条目与迁移影响面；并行推进「约束回指源码」与渐进式逃生舱的架构前置项 | 代际迁移交互原型；代际事实结构定义；降级路径的设计方案 | 真机与工具链可得；降级改动量可控；否则降级为知识库 + 检查清单 |
| **2027 Q3–Q4**：收敛与条件扩展 | 两个 P0 的对象模型合并固化；视条件启动方向三的一个故事 | 统一对象模型文档；跨代回归视图；（条件）服务链路故事原型 | 以真实团队采用率、采信结果的翻盘率、迁移发现时点决定是否规模化 |

**需要产品与技术在 Q1 共同确认的决策。** **【建议】**

1. **架构前置项的排期**：约束与诊断能否回指用户源码行；渐进式降级是否在同一语法内实现。这两项不解决，方向一与方向二都只能做到一半。
2. **与官方 Agent 工具链的关系**：PyPTO 是否承接 CANNBot 等工具的产出并给出独立验收结论（**【建议】** 倾向于是——这是「不争生成、争采信」定位的具体形态）。
3. **评测口径的对齐方式**：是否直接采用 CANN Bench 的三轴与真机上限刻度作为验收界面骨架。
4. **算力与预算治理**：验证本身消耗的设备时间由谁承担、如何在界面上呈现、Agent 自主探索的上限。
5. **责任归属**：正确性、精度与上线责任如何在人、Agent 与平台之间划分。

## 六、风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **验收面自身不可信** | 若独立验收的测试分布不够宽，它会复制 reward hacking 的问题，只是换了一层界面 | 对齐已公开抗 reward hacking 设计的社区基准；覆盖缺口必须显式可见而非静默通过 |
| **架构前置项不落地** | 源码回指与渐进降级属于架构工作，UX 侧无法单独交付 | Q1 作为联合排期的硬前置项确认，不确认则调整方向定位而非硬推 |
| **代际节奏不确定** | 960 时间表来自媒体转述，真机与工具链可得时间未知 | 方向二设置明确降级形态（知识库 + 检查清单） |
| **与官方工具链定位冲突** | 官方已开源四类 Agent 工具，若定位不清会被视为重复建设 | 明确「不争生成、争采信与承接」，并在材料中正面陈述分工 |
| **验证成本超过生成成本** | 算力门槛下降后，验证成为新的成本中心 | 把预算与成本做成一等界面对象；验证策略分层（廉价筛除 + 昂贵确认） |
| **外部数据的时效与口径** | 本文多条关键依据为 2026 年中的论文与会议材料，2027 年可能演进 | 每半年复核一次来源；结论随证据更新而非随叙事惯性保留 |
