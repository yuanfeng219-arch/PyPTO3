# Agent 时代算子开发的 UX 设计机会：流程变化、新诉求与人-Agent-Toolkit 协同

> 日期：2026-11-04
> 范围：PyPTO / PTO 面向昇腾的算子生成、编译、调试、正确性验证、性能调优与集成
> 视角：**只分析能由 UX 设计改善的变化。** 纯技术带来的变化或限制（如编译速度、环境确定性、模型能力本身）不展开，只在第 5 节列出排除清单，说明未纳入的原因。
> 性质：设计推断。“事实”指仓库材料或公开研究已有的内容；机会点和优先级尚需通过开发者访谈与原型验证。
> 关联文档：流程细节、共享对象（Task → Candidate → Run → Evidence → Decision）与授权分级见 [Agent 强参与下的算子开发](./Agent强参与下的算子开发_流程开发者与UX变化.md) 和 [人、Agent 与 Toolkit 协作模式](./人-Agent-Toolkit协作模式_算子开发流程.md)。本文复用其中的术语，不重复展开。

---

## 0. 一页结论

1. **UX 的主战场从“帮人操作工具”转向“帮人委托、监督和判断 Agent”。** 编码和工具串联由 Agent 承担后，人留下的工作是定义目标、授权、看进展、审证据、做取舍、接管和沉淀。这些工作恰好都发生在界面上，因此都是 UX 问题。
2. **Agent 时代最大的体验风险不是“不会用”，而是“误信”和“失控”。** 生成变便宜、验证变昂贵之后，人容易被流畅的结论说服，也容易在大量候选和日志前放弃审查。设计的核心目标是**让信任与证据相匹配**。
3. **筛选后共得到 14 个 UX 机会点**，覆盖“发起与委托 → 执行中 → 审查与判断 → 交付与沉淀 → 长期协作”五个时刻（第 3 节）。
4. **三条协同关系中，人 ↔ Agent 和人 ↔ Toolkit 是 UX 主战场；Agent ↔ Toolkit 基本属于技术问题**，只有“Agent 的调用过程如何被人看见”这一面纳入 UX 分析（第 4 节）。
5. **建议优先做四件事：** 可编辑的任务契约、结论分级与证据下钻、候选对比、决策点与交接设计（第 6 节）。

## 1. 筛选标准：什么算 UX 机会点

对每一项变化或诉求问三个问题：

| 问题 | 判断要点 |
|---|---|
| Q1 是否存在人的触点？ | 人需要在此感知、理解、决策、操作，或与他人协作 |
| Q2 现状是否对人造成可感知的问题？ | 认知负担、误信、失控感、等待焦虑、返工、交接困难等 |
| Q3 能否通过设计改善？ | 能通过信息架构、交互流程、可视化、文案、控制方式或协作机制改善，而不是只能靠工程能力或模型能力解决 |

- **三项都满足**：纳入，作为 UX 机会点分析。
- **Q1 满足、Q3 不满足**：属于技术前提。不分析，但在机会点中注明依赖。
- **Q1 不满足**（只发生在 Agent 与工具之间）：排除。
- **混合项**：一项技术变化可能带来人能感知的后果。例如设备排队是技术问题，但“人在等待中不知道发生了什么”是 UX 问题。这类只保留人能感知的那一面。

## 2. 有 UX 机会的流程变化

原先梳理的七个结构性转变中，五个带来明确的 UX 机会，两个只有部分相关。

| 流程变化 | 人的处境发生了什么变化 | UX 相关性 |
|---|---|---|
| 瓶颈从编码迁移到验证与审查 | 人每天要看的不再是自己的代码，而是 Agent 的 Diff、测试和测量结果，审查量明显上升 | **强**：审查效率和审查质量取决于信息如何组织 |
| 探索方式从单次尝试变为候选群体 | 人要从多个候选中选择，且候选的条件和适用范围各不相同 | **强**：比较、筛选和淘汰原因的呈现 |
| 状态载体从“人脑”变为显式对象 | 人不再亲历每一步，需要靠界面重建“进行到哪、为什么” | **强**：任务状态、恢复和交接 |
| 出现 Agent 特有的失败模式 | 放宽容差、只针对测试 shape 特化、虚假归因等错误看起来“合理”，人难以察觉 | **强**：可疑信号的主动提示和信任校准 |
| 交付物变为“代码 + 证据 + 决策” | 评审者和团队负责人需要读懂一次委托的结果，而不是聊天记录 | **强**：结果包和决策记录的形态 |
| 迭代节拍由编译和设备排队决定 | 加快节拍本身是技术问题；但人在等待中需要知道状态和消耗 | **部分**：只保留进展与预算的可见性 |
| 知识需要结构化后注入 Agent | 知识库建设本身是技术与内容工程；但专家纠正 Agent 的那一刻是交互时刻 | **部分**：只保留“纠正即沉淀”的交互 |

各阶段中有 UX 机会的变化如下，纯技术项已删去。

| 阶段 | 有 UX 机会的变化 | 风险（人这一侧） |
|---|---|---|
| 需求与语义 | 目标由 Agent 整理成任务契约，人从“写需求”变为“确认契约” | 把 Agent 推断的约束当作已确认 |
| 实现 | 人从写代码变为审 Diff | Diff 过大或缺少设计意图，审查流于形式 |
| 编译迭代 | Agent 自动修错，人不再看到每次失败 | Agent 陷入重试循环，人不知道该何时介入 |
| 正确性 | 测试和比对由 Agent 生成 | 人没有意识到容差被改、覆盖不足 |
| 性能调优 | 候选批量产生，收益以表格呈现 | 噪声内的“提速”或局部收益被当作真实收益 |
| 集成交付 | Agent 汇总证据包 | 只覆盖部分 shape 却被当作普遍适用 |
| 维护 | 后来者要理解当初为何如此实现 | 决策理由只存在于已关闭的对话里 |

## 3. UX 机会点

按人在一次 Agent 协作中经历的五个时刻组织。每个机会点说明：由什么变化触发、人的问题、设计机会和可能的设计形态。

### 3.1 发起与委托

#### U1 任务契约的共建

- **触发**：Agent 把自然语言整理成任务，人从“写需求”变为“确认契约”。
- **问题**：自然语言目标常缺少 shape、dtype、精度、目标芯片和性能目标；Agent 补上的推断容易被默认接受。
- **机会**：把契约做成人与 Agent 共同编辑的对象，而不是一段对话。
- **形态**：结构化契约卡；每项约束标注“已确认 / Agent 推断 / 未知”三态；未知项阻塞启动或明确被豁免；可从源码、报错、Run 或模型入口带上下文预填。

#### U2 授权、预算与协作模式的设定

- **触发**：Agent 能自主执行，但操作的成本和风险差异很大（改源码 vs 占用设备 30 分钟 vs 覆盖共享基线）。
- **问题**：每步都确认令人厌烦，一次性全授权又令人不安；人很难预估一次委托会花多少设备时间。
- **机会**：让授权成为可理解、可调整的设置，而不是“Agent 模式开 / 关”。
- **形态**：按风险分级的授权面板；设备时间、实验次数和停止条件作为预算控件，并显示预估消耗；按任务选择协作模式（L0 人主导 / L1 结对 / L2 委托 / L3 批量自治，定义见 4.1）；授权附着在任务上，不自动延续到下一个任务。
- **技术依赖**：Toolkit 需提供操作的成本和副作用声明（第 5 节，A7）。

### 3.2 执行中

#### U3 进展可见与等待体验

- **触发**：内环自动运行，编译和设备排队决定节拍；人不再亲历每一步。
- **问题**：只有滚动日志时，人无法回答“现在在做什么、做到哪了、还要多久、是否需要我”，于是频繁打断或完全放手。
- **机会**：把任务状态作为一等界面，取代日志流。
- **形态**：任务时间线（已完成、进行中、排队中、被门禁拦下）；预算消耗条；顶部始终回答“是否需要我”；日志降为可下钻的第三层。

#### U4 打断时机与决策卡

- **触发**：内环中会出现必须由人决定的节点，如精度与性能的取舍、扩大修改范围、超出预算。
- **问题**：打断过频导致疲劳和盲目同意；打断过少导致越权或错过关键取舍。
- **机会**：设计“何时打断”和“打断时给什么”。
- **形态**：只在预定义的决策点打断；决策卡列出要决定的问题、可选项、各自的影响与成本、Agent 的建议及其依据；已授权的日常操作不再询问。

#### U5 卡住时的交接与接管

- **触发**：Agent 在复杂 hang、精度问题或全新算子上会反复失败；人需要随时接手，之后也可能再交回。
- **问题**：Agent 空转消耗预算；人接手时要从头阅读对话和日志，重新建立上下文。
- **机会**：把“委托”和“接管”设计成双向、低成本的切换。
- **形态**：失败计数与自动停止提示；Agent 交出交接包（目标回顾、已排除的假设、关键证据、建议的接管点）；人在 IDE 或 Studio 中直接打开同一任务、同一 Run 和同一证据继续工作；处理完一段后可把剩余部分再委托回去。

### 3.3 审查与判断

#### U6 结论分级与证据下钻

- **触发**：Agent 的陈述与 Toolkit 的实测混在同一段文字里。
- **问题**：人难以区分哪些是猜测、哪些已实测，容易误信。
- **机会**：让结论的可信等级一眼可辨，并且每条结论都能回到原始证据。
- **形态**：统一的可信度标记（源码推断 / 编译实测 / 设备实测 / 未验证）；结论旁的证据链接，一键跳转到对应的 Run、Tensor、Pass trace、泳道图或源码行；缺少证据的结论显式标为“待验证”。

#### U7 候选对比

- **触发**：调优从手工单次尝试变为一批候选。
- **问题**：候选的测量条件、覆盖范围和波动不同，直接按数字排名会误导；被淘汰的候选去向不明。
- **机会**：设计以“可比性”为前提的候选比较。
- **形态**：baseline 与候选并列，展示 Diff 摘要、各门禁状态、测量条件、收益与波动区间、适用的 shape 范围；不满足可比条件的不参与排名并说明原因；淘汰候选保留失败阶段和原因。

#### U8 验证充分性的审查

- **触发**：测试和比对由 Agent 生成，生成者与验证者可能是同一方。
- **问题**：人很难察觉容差被放宽、输出覆盖不足或测试被改写。
- **机会**：让“验证标准”成为人确认并锁定的对象，任何改动都醒目可见。
- **形态**：oracle、容差和用例集由人在契约中确认后锁定；Agent 试图修改时进入决策卡；审查视图中展示覆盖矩阵（shape × dtype × 边界情况），而不只显示“通过”。
- **技术依赖**：Toolkit 需提供独立于 Agent 的判定机制（第 5 节，A6）。

#### U9 可疑信号提示（信任校准）

- **触发**：Agent 特有的失败模式通常“看起来合理”。
- **问题**：自动化偏差会让人放松审查，新手尤甚；审查疲劳会让人退化为一路点“通过”。
- **机会**：在审查界面主动标出值得怀疑的地方，把有限的注意力引向高风险点。
- **形态**：风险提示，例如修改了测试文件、容差变化、只覆盖部分 shape、收益落在测量波动内、引用了未在当前 Run 中产生的结果、修复与报错位置无关；提示附依据，避免泛泛的“请仔细检查”。

#### U10 Agent 轨迹回放

- **触发**：人没有亲历内环，却要审查结果、理解失败或学习做法。
- **问题**：完整对话冗长；只看最终结果又不知道 Agent 是怎么得出的。
- **机会**：把 Agent 的工作过程变成可浏览的路径，而不是聊天记录。
- **形态**：按“假设 → 动作 → 证据 → 结论”组织的轨迹视图；标出关键转折（假设被推翻、被门禁拦下、改变方向）；可从任一步跳到当时的代码和证据。

### 3.4 交付与沉淀

#### U11 结果包与决策记录

- **触发**：交付物从代码扩展为“代码 + 证据 + 决策”；评审者和后来的维护者没有参与过程。
- **问题**：评审者面对的是长对话或零散截图；数月后没人知道当初为何这样实现。
- **机会**：为不同读者设计交付视图。
- **形态**：一页式结果包——目标是否达成、采用的候选、各门禁状态、收益及条件、适用范围与未覆盖项、人做出的关键决策及理由、复现入口；面向团队负责人的跨任务汇总视图。

#### U12 纠正即教学

- **触发**：Agent 不熟悉昇腾硬件和 PyPTO 惯用法，专家会反复纠正同类错误。
- **问题**：纠正只在当次对话生效，下次又犯；专家的知识没有被积累。
- **机会**：把专家纠正 Agent 的瞬间，变成沉淀知识的入口。
- **形态**：纠正时一键提议“记为规则”，确认适用范围后进入团队规则库；后续 Agent 引用该规则时显示来源；规则的命中与效果可查看和撤销。
- **技术依赖**：规则库与 Agent 上下文注入机制（第 5 节，A9）。

### 3.5 长期协作

#### U13 保持人的理解与成长

- **触发**：长期只审不写，人可能失去审查和接管所需的硬件与数值直觉。
- **问题**：新手难以判断 Agent 是否正确；团队整体的接管能力下降。
- **机会**：让协作过程同时成为理解过程，并按经验提供不同深度。
- **形态**：可按需展开的“为什么这样做”解释，关联源码到昇腾硬件的映射（内存层级、Cube/Vector 分工、流水）；新手默认引导模式，专家可直达原始 trace 和 IR；关键决策点可选择“让我先判断，再看 Agent 的建议”。

#### U14 多入口之间的连续

- **触发**：同一任务会在 IDE、CLI、Studio 和 Agent 面板之间流转。
- **问题**：换个入口就要重新交代背景；不同入口看到的结论不一致。
- **机会**：让“任务”而不是“工具”成为跨入口的连续单元。
- **形态**：任一入口都可打开同一任务并看到相同的状态和证据；从 Studio 的某段泳道图或某个 Tensor 直接发起对 Agent 的追问，上下文自动带入。

## 4. 协同关系变化中的 UX 机会

### 4.1 人 ↔ Agent：UX 主战场

关系从“使用工具”变为“委托与监督”，人的角色变为目标定义者、约束设计者、证据审查者、专家兜底者和最终责任人。这几个角色对应的界面需求都由第 3 节的机会点承接。

协作模式并非一成不变的产品等级，而是按任务风险和 Agent 可靠度选择的协作方式（U2）：

| 模式 | 分工 | 适用场景（推断） | 关键体验 |
|---|---|---|---|
| L0 人主导 | Agent 解释、检索，人亲自实现 | 新算子语义探索；复杂 hang 初期定位 | 解释的可信度标记（U6）、理解与成长（U13） |
| L1 结对 | Agent 小步提议，人逐步确认 | 领域判断较多的实现与重构 | Diff 审查、轻量确认 |
| L2 委托 | Agent 自动运行内环，人在决策点介入 | 编译修错、扩展 dtype 或 shape、目标明确的调优 | 进展可见（U3）、决策卡（U4）、交接（U5） |
| L3 批量自治 | Agent 批量处理，人抽检验收 | 批量迁移、回归修复、预算内的参数搜索 | 可疑信号（U9）、结果包（U11） |

需要设计应对的三个人因风险：

- **自动化偏差**：对应 U6、U9。
- **审查疲劳**：对应 U4、U7、U9。
- **技能空心化**：对应 U13。

**信任校准**是贯穿性的设计目标：授权范围应随该类任务的历史表现扩大或收缩。界面可以展示“此类任务的历史接受率与回退率”，帮助人决定给多大授权。

### 4.2 人 ↔ Toolkit：从亲手操作到审计与深潜

- **使用频率下降，单次深度上升**：日常的编译、运行和采集交给 Agent；人打开 Toolkit 主要为了核验结论，或在 Agent 失败时深入排查。
- **可视化目的改变**：从“帮我发现问题”扩展为“帮我判断 Agent 说得对不对”和“帮我从 Agent 停下的地方接手”。例如，泳道图不仅用于找瓶颈，也用于核实 Agent 声称的“消除了某段串行”是否真实发生。
- **专家深度不可被摘要取代**：原始 IR、Pass trace、泳道图和 profiling 数据仍需完整可达。

对应机会点：U6、U7、U10、U14。

### 4.3 Agent ↔ Toolkit：基本属于技术问题

接口结构化、输出精简、确定性、沙箱隔离、取证能力等属于工具契约和工程问题，不在本文分析范围内（见第 5 节）。

只保留一面纳入 UX：**Agent 对 Toolkit 的每次调用，人都能看见、能理解、能复跑。** 这由轨迹回放（U10）和证据下钻（U6）承接。

## 5. 排除清单：纯技术变化与限制

以下项目不满足第 1 节的标准，不展开分析。若其中有人能感知的一面，已并入相应的机会点。

| 变化或诉求 | 不纳入的原因 | 已并入的 UX 面 |
|---|---|---|
| 迭代速度：增量编译、编译缓存、上设备前的 cost model 预筛 | 属于工程性能问题 | 等待与预算可见（U3） |
| 结构化调用接口：CLI `--json`、API、MCP（A1） | 只发生在 Agent 与工具之间 | — |
| 面向 Agent 的低 token 输出（A2） | 只发生在 Agent 与工具之间 | — |
| 环境确定性与可复现（A3） | 属于工程可靠性 | 复现入口（U11） |

## 6. 优先级建议

以“Agent 时代特有程度 × 对信任与效率的影响”排序，属于设计建议。

| 优先级 | 机会点 | 理由 |
|---|---|---|
| **P0** | U1 任务契约、U6 结论分级与证据下钻、U7 候选对比、U4/U5 决策点与交接 | 构成可信委托的最小闭环：说清目标，看清证据，比得出结果，卡住能接手 |
| **P1** | U2 授权与预算、U3 进展可见、U8 验证充分性、U9 可疑信号 | 让委托规模可以扩大，同时控制误信与失控 |
| **P2** | U10 轨迹回放、U11 结果包、U12 纠正即教学、U13 理解与成长、U14 多入口连续 | 面向团队协作和长期能力，依赖 P0/P1 的对象与数据 |

## 7. 待验证的 UX 问题

| 问题 | 建议验证方式 |
|---|---|
| 开发者愿意委托哪些操作？在哪些节点希望被打断？ | 访谈 + 任务原型中观察授权设置、打断响应与接管行为 |
| 哪种证据呈现最能帮助人快速判断 Agent 结论的真伪？ | 在不同呈现方式下让开发者判断候选，统计判断准确率和用时 |
| 可疑信号提示能否降低误信，同时不引发提示疲劳？ | 对照试验：比较有无提示时漏判的错误候选数与审查时长 |
| 交接包能否显著缩短人接管所需的时间？ | 记录接管后定位到首个有效证据的时间 |
| 新手与专家对信息层次的需求差异有多大？ | 分层可用性测试，观察两类用户的首个下钻路径 |

衡量时应同时报告失败、未完成任务和人工审查时长，不只统计成功案例。
