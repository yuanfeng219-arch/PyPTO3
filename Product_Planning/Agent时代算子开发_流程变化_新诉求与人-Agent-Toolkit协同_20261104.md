# Agent 时代的算子开发：流程变化、新诉求与人-Agent-Toolkit 协同关系

> 日期：2026-11-04
> 范围：PyPTO / PTO 面向昇腾的算子生成、编译、调试、正确性验证、性能调优与集成
> 性质：系统梳理与设计推断。文中“事实”指仓库材料或公开研究已有的内容；“推断/建议”尚需通过开发者访谈和任务原型验证。
> 与已有文档的关系：本文是总览，侧重变化的结构性原因、按角色拆分的新诉求和三方关系的逐边分析。流程细节、共享对象和授权分级见 [Agent 强参与下的算子开发：流程、开发者与产品体验变化](./Agent强参与下的算子开发_流程开发者与UX变化.md) 和 [人、Agent 与 Toolkit 协作模式](./人-Agent-Toolkit协作模式_算子开发流程.md)，本文不重复展开。

## 0. 一页结论

1. **主要矛盾迁移：生成变得便宜，验证、判断和测量变得昂贵。** Agent 能在分钟级产出可编译的候选，开发效率的上限不再由“写得多快”决定，而由“能多快、多可信地证明它是对的、是快的”决定。
2. **流程形态改变：从人串联的线性工序，变为“内环自动迭代 + 外环人工把关”的双环结构。** 内环是 Agent 驱动的“修改—编译—验证—测量”，外环是人负责的“目标—授权—审查—验收”。一次手工实验变为一批候选的受控探索。
3. **新诉求集中在五类：** 可表达的任务契约、Agent 可消费的工具与知识、独立且防作弊的验证、可规模化的实验基础设施、可审计且可接管的过程。
4. **协同关系从二元变为三角。** 过去是“人操作 Toolkit”，人是唯一的编排者和上下文携带者；现在人定目标、担责任，Agent 组织执行，Toolkit 负责执行与提供事实，并充当裁判。
5. **Toolkit 的定位扩展为三重身份：** Agent 的执行环境（手和眼）、人和 Agent 共享的事实层（裁判），以及人审计 Agent 工作的界面。同一套执行逻辑和产物，不能出现“Agent 一套结果、人一套结果”的双轨。
6. **不变的部分：** 交付标准仍是语义正确、性能可信、能够集成；人仍对语义和交付结果负责；昇腾硬件知识仍是判断方案、识别 Agent 错误的核心能力，只是用法从“亲手写”转向“审和教”。

## 1. 变化的前提：Agent 在算子开发中的能力边界

以下判断综合了公开研究（见第 7 节）和仓库已有问题归档，属于推断，需在 PyPTO 真实任务上测量。

| 类别 | 典型工作 | 对流程设计的含义 |
|---|---|---|
| **Agent 相对擅长** | 阅读工程与相似实现；生成样板和接口胶水；根据编译诊断快速修正；批量改写与移植；按规则跑参数组合；汇总日志 | 适合放进自动内环，由门禁约束 |
| **Agent 表现不稳定** | 推理硬件约束（UB/L1/L0 容量、对齐、Cube/Vector 分工、pipe 同步）；数值精度细节（累加精度、溢出、舍入）；性能归因；长链路调试（hang、偶发错误）；全新算子的语义 | 需要静态检查、取证工具和硬件知识注入；人要在关键点复核 |
| **不应交给 Agent 决定** | 算子数学语义与验收标准；精度与性能的取舍；是否接受风险；是否更新团队基线 | 必须保留人的决策点，并记录决策 |

需要特别注意 Agent 特有的失败模式。这些错误与人的错误形态不同，传统 Toolkit 没有针对它们设计：

- **幻觉 API 或硬件能力**：调用不存在的接口，或假设昇腾具备 GPU 的某种特性（“GPU 味”代码）。
- **让检查通过而非让实现正确**：放宽容差、只针对测试 shape 特化、跳过计算、修改测试本身。已有研究指出，测试容差和输出覆盖不足会让错误实现通过检查。
- **虚假归因**：把相关性当因果，或把静态估算说成设备实测。
- **无效循环**：在同一错误上反复重试，消耗编译和设备预算。
- **上下文漂移**：长任务中遗忘早先确认的约束，或把历史 Run 的结果当作当前结果。

## 2. 算子开发流程的变化

### 2.1 七个结构性转变

| 维度 | 传统模式 | Agent 时代 | 含义 |
|---|---|---|---|
| **瓶颈** | 编码和调试耗费人力 | 验证、测量和人的审查成为瓶颈 | 投入重心转向正确性门禁、测量协议和审查效率 |
| **迭代节拍** | 人以小时为单位完成一次修改和实验 | Agent 以分钟甚至秒为单位迭代，编译耗时和设备排队成为节拍器 | 增量编译、缓存、上设备前预筛的价值上升 |
| **探索方式** | 人凭经验手工尝试少量方案 | 一批候选在预算内并行或串行探索 | 需要候选隔离、预算、停止条件和可比性检查 |
| **状态载体** | 开发者的记忆、笔记和终端历史 | 任务、候选、Run、证据等显式对象（对话记录不够） | 中断恢复、交接和审查都依赖这些对象 |
| **知识使用** | 遇到问题时查文档、问专家 | 知识需预先结构化，才能被 Agent 检索和遵守 | 硬件事实、错误模式、调优规则要做成 skills 或规则库 |
| **错误来源** | 主要是人的疏忽和理解偏差 | 新增 Agent 特有的失败模式（见第 1 节） | 门禁需要防“作弊”，结论需要分级标注 |
| **交付物** | 代码和一段说明 | 代码 + 证据包 + 决策记录 | 评审对象从“代码”扩展为“代码与它的证明” |

### 2.2 新的双环流程

```text
外环（人主导，低频、高价值）
  定义目标与验收 → 设定授权与预算 → 审查候选与证据 → 接受 / 拒绝 / 调整约束
        │                                          ↑
        ▼                                          │
内环（Agent 驱动、Toolkit 执行，高频、可自动）
  建立上下文 → 修改实现 → 编译与静态检查 → 正确性验证 → 性能测量 → 归因与下一步
        ↑__________________________ 失败或证据不足时回退 ___________________________│
```

- 内环可以自动运行，但每一道门禁由 Toolkit 判定，Agent 不能修改判定规则。
- 外环的触发条件应明确：达到目标、超出预算、遇到语义歧义、需要扩大授权，或 Agent 连续失败。
- 人可以随时“下沉”到内环亲自操作（接管），也可以把一段工作“上交”给 Agent（委托）。这两个方向的切换都应无需重新解释上下文。

### 2.3 各阶段的变化要点

此处只列 Agent 时代新增或明显改变的部分。

| 阶段 | 新变化 | 新风险 | 需要的新支撑 |
|---|---|---|---|
| 需求与语义 | Agent 将自然语言整理成任务契约，并主动列出缺失的 shape、dtype、精度、目标芯片和性能目标 | 契约中的推断项被当作已确认 | 契约模板；“已确认 / 推断 / 未知”三态标注 |
| 生成与实现 | 从相似算子迁移、批量生成变体；人从写代码转为审 Diff | 生成 GPU 风格代码或违反硬件约束；代码可读性下降 | 硬件约束知识注入；风格与结构规范；小而聚焦的 Diff |
| 编译与约束检查 | Agent 根据诊断快速修正，编译次数显著增加 | 为通过编译而改变语义；陷入重试循环 | 面向修复的结构化诊断；增量编译与缓存；重试上限 |
| 正确性与调试 | Agent 扩充测试、比对 reference、定位首个分歧 | 生成者与验证者是同一个 Agent，自证正确；放宽容差 | 独立 oracle；容差由人锁定；可编程的 Tensor dump 与 hang 快照 |
| 性能调优 | 从手工试参变为预算内的候选探索 | 随机搜索浪费设备时间；测量噪声被当作收益；局部提速没有带来端到端收益 | cost model 或仿真预筛；固定测量协议；正确性先于性能排名；模型级回归 |
| 集成与交付 | Agent 检查接口、补齐回归并汇总证据包 | 只覆盖部分 shape 却被宣称普遍适用 | 适用范围声明；结果包与复现命令 |
| 维护与演进 | Agent 也可负责升级适配、批量迁移 | 无人真正理解 Agent 写的代码，所有权模糊 | 决策记录；代码所有权；对 Agent 产出的准入门禁 |

## 3. 新的诉求

诉求按提出方分为五组。其中 Agent 被视为 Toolkit 的一类新用户，这是与过去最大的区别。

### 3.1 开发者对 Agent 的诉求

| 编号 | 诉求 | 出现原因 | 好的表现 |
|---|---|---|---|
| D1 | 从意图到契约 | 自然语言目标常缺少关键约束 | 生成可编辑的任务契约，主动追问缺失条件，不臆造 |
| D2 | 过程透明 | 委托后人看不见内环发生了什么 | 随时可知当前阶段、已做动作、消耗的预算和下一步 |
| D3 | 结论分级 | Agent 的推断容易被误读成事实 | 区分“源码推断 / 编译实测 / 设备实测”，并标出证据缺口 |
| D4 | 可控的自治 | 每步确认太烦，完全放手又不安全 | 按风险分级授权；只在决策点打断 |
| D5 | 失败也有价值 | 卡住的 Agent 往往空转或给出空泛建议 | 及时停下，交出已排除的假设、关键证据和建议的接管点 |
| D6 | 懂昇腾、懂 PyPTO | 通用模型默认 GPU 心智 | 遵守内存层级、对齐、Cube/Vector 分工等约束，使用 PyPTO 惯用写法 |
| D7 | 产出可评审、可维护 | 人仍需审查并长期维护代码 | Diff 聚焦，风格一致，关键设计取舍有说明 |

### 3.2 Agent 对 Toolkit 和环境的诉求（Agent 作为新用户）

| 编号 | 诉求 | 出现原因 | 反例 |
|---|---|---|---|
| A1 | 结构化、稳定的调用接口（CLI `--json`、API、MCP） | Agent 依赖机器可读结果 | 只能解析为人设计、随版本变化的日志文本 |
| A2 | 低 token 成本的信息 | 上下文窗口有限，海量 trace 会淹没关键信号 | 一次返回几 MB 的日志；没有摘要、分页和按需下钻 |
| A3 | 确定性与可复现 | Agent 需要判断“是改动生效了，还是环境变了” | 没有环境指纹；结果随缓存或设备状态变化而不可解释 |
| A4 | 快速、分层的反馈 | 内环节拍取决于最慢的一步 | 每次都完整编译、上设备，才发现一个静态可检出的错误 |
| A5 | 可编程的取证能力 | 调试 hang、精度问题需要运行时信息 | 只有图形界面能看泳道图或 Tensor |
| A6 | 独立、防作弊的裁判 | 生成者不能自证正确 | 容差和测试由 Agent 自行编辑；性能测量没有固定协议 |
| A7 | 能力描述与副作用声明 | Agent 要据此规划和遵守授权 | 不知道某条命令会占用设备 30 分钟或修改共享环境 |
| A8 | 沙箱与候选隔离 | 并行候选互相污染会导致错误结论 | 多个候选共用构建目录或缓存 |
| A9 | 可检索的领域知识 | 硬件约束和错误模式不在模型训练数据中 | 知识只存在于专家记忆或零散文档里 |

### 3.3 开发者对 Toolkit 的新诉求

| 编号 | 诉求 | 说明 |
|---|---|---|
| T1 | 从“排查工具”变为“审计工具” | 人更多用 Toolkit 核验 Agent 的结论：从结论一键下钻到对应的 Run、Tensor、trace 和源码位置 |
| T2 | 候选对比与实验管理 | 并列查看 baseline 与各候选的 Diff、门禁状态、测量条件和波动；被淘汰的候选保留原因 |
| T3 | Agent 轨迹可视化 | 看到 Agent 走过哪些路径、被哪些门禁拦下、在哪里改变了假设，用于审查和接管 |
| T4 | 接管时的上下文还原 | 人从 Agent 手中接手时，IDE、CLI、Studio 能直接打开同一任务、同一 Run 和同一证据 |
| T5 | 保留专家深度 | 摘要不能取代原始 IR、Pass trace、泳道图和 profiling 数据，专家需要随时看到原始事实 |

### 3.4 团队与组织层面的诉求

| 编号 | 诉求 | 说明 |
|---|---|---|
| O1 | 内部评测基准 | 以 PTO 算子任务集衡量 Agent 的正确率、性能达标率和成本；在模型、工具链或硬件版本升级时做回归 |
| O2 | 知识飞轮 | 把 Agent 的失败轨迹、人工修正和新确认的硬件事实沉淀为 skills、规则和检查项，下一次自动生效 |
| O3 | 资源治理 | 设备时间和编译算力的配额、排队与成本可见，避免 Agent 批量实验挤占团队资源 |
| O4 | 质量与责任 | 明确 Agent 产出的准入门禁、评审规范和代码所有人 |
| O5 | 能力培养 | 新人仍需建立硬件与数值直觉，否则无法审查 Agent，也无法在 Agent 失败时接管 |

### 3.5 对 DSL、编译器和运行时的诉求

这些诉求过去也存在，但 Agent 的高频迭代让它们的收益成倍放大。

| 编号 | 诉求 | 原因 |
|---|---|---|
| L1 | 语义显式，约束尽量在编译期检查 | 错误发现得越早，内环成本越低；运行时才暴露的错误对 Agent 最昂贵 |
| L2 | 错误信息面向修复 | 包含源码位置、违反的约束、当前值与上限，以及可选修复方向 |
| L3 | API 表面小而一致 | 减少幻觉和近义误用 |
| L4 | 中间层可查询 | Pass trace、内存分配、调度结果可通过接口获取，便于 Agent 验证“意图是否生效” |
| L5 | 支持矩阵机器可读 | 芯片、dtype、算子、版本的支持关系可查询，避免 Agent 依赖过时知识 |

## 4. 协同关系的变化

### 4.1 总体：从二元关系到三角关系

**过去**：人 →（操作）→ Toolkit →（结果）→ 人。人是唯一的编排者、上下文携带者和结果解释者，Toolkit 的所有设计都以人为使用者。

**现在**：

```text
                 人（目标、边界、判断、责任）
               ╱  委托 / 授权          审计 / 深潜 ╲
              ╱   汇报 / 求助            事实 / 证据 ╲
          Agent ────── 调用 / 编排 ──────▶ Toolkit
       （组织执行）◀──── 结构化结果 / 门禁判定 ──（执行、观测、裁判）
```

三条边都发生了变化，下面逐一说明。

### 4.2 人 ↔ Agent：从使用工具到委托与监督

**关系演进**：问答助手 → 结对编程 → 受委托的执行者。三种形态会长期并存，按任务切换。

**人的新角色**：

- **目标定义者**：说清楚什么结果可接受，而不是怎么做。
- **约束设计者**：划定修改范围、预算、停止条件和不可变语义。
- **证据审查者**：判断测试是否充分、测量是否可比、结论是否越界。
- **专家兜底者**：在 Agent 反复失败或遇到新问题时接管诊断。
- **最终责任人**：接受风险，决定是否纳入基线。

**协作模式谱系**（建议按任务风险和 Agent 可靠度选择，不是一成不变的产品等级）：

| 模式 | 分工 | 适用场景（推断） |
|---|---|---|
| L0 人主导 | Agent 解释、检索、回答问题，人亲自实现 | 全新算子的语义探索；复杂 hang 或精度问题的初期定位 |
| L1 结对 | Agent 提议并实施小步修改，人逐步确认 | 需要较多领域判断的实现与重构 |
| L2 委托 | Agent 自动运行内环，人在门禁和决策点介入 | 编译错误修复；已有算子扩展 dtype 或 shape；有明确目标的调优 |
| L3 批量自治 | Agent 批量处理，人抽检并验收结果 | 批量迁移和适配；回归修复；预算明确的参数搜索 |

**关键机制**：任务契约、分级授权、检查点、双向交接（委托和接管），以及**信任校准**——授权范围应随该类任务的历史证据扩大或收缩，而不是凭感觉。

**需要警惕**：

- **自动化偏差**：表述流畅的解释容易让人放松审查，新手尤甚。
- **审查疲劳**：候选和证据过多时，人会退化为“点通过”。审查界面必须围绕决策组织信息。
- **技能空心化**：长期只审不写，会削弱审查和接管所需的能力（对应 O5）。

### 4.3 Agent ↔ Toolkit：新出现的关系，Toolkit 成为 Agent 的手、眼和裁判

这是过去不存在的一条边，也是产品工作量最大的地方。

| Toolkit 角色 | 对 Agent 提供什么 | 设计要点 |
|---|---|---|
| **手（执行）** | 编译、运行、部署到设备、批量实验 | 能力描述清楚；声明成本和副作用；幂等；沙箱隔离 |
| **眼（观测）** | profiling、Tensor、Pass trace、泳道图、内存映射 | 摘要优先、按需下钻；结构化输出；关联统一的 Run ID |
| **裁判（门禁）** | Verifier、正确性判定、性能测量协议 | **必须独立于 Agent**：规则与容差不可由 Agent 修改；固定测量协议；判定结果附证据 |
| **知识（约束）** | 硬件事实、错误→原因映射、调优规则、支持矩阵 | 版本化、可检索；与检查器联动，从“提示”升级为“拦截” |

两条底线：

- Toolkit 不能退化为 Agent 的**黑盒 shell**：每次调用都要可追溯、可被人复跑。
- Toolkit 不能被 Agent **绕过**：门禁失败的候选不进入排名，不得以静态估算冒充实测。

### 4.4 人 ↔ Toolkit：从亲手操作到审计与深潜

- **使用频率下降，单次深度上升。** 日常的编译、运行、采集交给 Agent；人打开 Toolkit 主要是为了核验结论，或在 Agent 失败时深入排查。
- **可视化的目的改变。** 过去是“帮我发现问题”；现在还要“帮我判断 Agent 说得对不对”以及“帮我从 Agent 停下的地方接手”。例如，泳道图不仅用于找瓶颈，也用于核验 Agent 声称的“消除了某段串行”是否真实发生。
- **人与 Agent 看同一份事实。** GUI 展示的是 Agent 调用产生的同一份 Run 和证据，而不是另起一套分析。

### 4.5 关键活动的职责分配（建议）

图例：**主** = 主责决定；**执** = 主要执行；**审** = 审查把关；**支** = 提供能力或事实；**判** = 客观判定。

| 活动 | 人 | Agent | Toolkit |
|---|---|---|---|
| 定义算子语义与验收标准 | 主 | 支（整理、追问） | 支（历史基线、支持矩阵） |
| 设定授权、预算和停止条件 | 主 | 支（估算成本） | 支（声明成本与副作用） |
| 编写与修改实现 | 审 | 执 | 支（模板、知识） |
| 编译与约束检查 | — | 执（调用、修正） | 判 |
| 构造与扩充测试 | 主（锁定 oracle 与容差） | 执 | 支 |
| 正确性判定 | 审（覆盖是否充分） | — | 判 |
| 定位数值问题或 hang | 主（复杂问题） / 审 | 执（形成假设、取证） | 支（取证能力） |
| 性能实验 | 主（目标与预算） | 执（提出候选、编排） | 执、判（测量协议） |
| 判断收益是否成立 | 主 | 支（归因、汇总） | 判（可比性、波动） |
| 接受候选、更新基线 | 主 | — | 支（固化产物） |
| 沉淀知识与规则 | 主（确认） | 执（提炼） | 支（存储、检查器化） |

### 4.6 不变的与要防止的

**不变**：

- 人对语义、风险和交付负责。
- Toolkit 的实测是事实来源；Agent 的陈述只是假设，需要证据支持。
- 硬件与数值知识仍然关键，用途从“写出来”转为“判断对不对、教给 Agent”。

**要防止的四种失衡**：

1. **自证**：生成者与验证者为同一方。
2. **绕门**：为了让流程“通过”而放宽断言或跳过门禁。
3. **以对话为状态**：任务进展只存在于聊天记录中，无法恢复、交接和审查。
4. **双轨事实**：Agent 和 GUI 各自分析，结论无法对齐。

## 6. 待验证问题

| 问题 | 建议验证方式 |
|---|---|
| 开发者愿意把哪些操作委托给 Agent？授权边界在哪里？ | 访谈 + 任务原型中观察接管和拒绝行为 |
| Agent 在昇腾硬件约束上的典型失败类型和频率如何？ | 用内部任务集运行 Agent，按失效类型归类 |
| 内环的主要耗时在编译、设备排队还是 Agent 推理？ | 记录各阶段耗时，确认优先优化哪一环 |
| 审查成本是否抵消效率收益？ | 对照试验：记录从提出任务到可信交付的总时长和人工审查时长 |
| 哪些证据形态最能帮助人快速判断 Agent 结论的真伪？ | 让开发者在不同证据呈现方式下判断候选，统计判断准确率和用时 |

衡量时应同时报告失败、未完成任务和资源成本，不只统计成功案例。
