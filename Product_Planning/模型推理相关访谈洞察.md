# 模型推理相关访谈洞察

> 来源：`userResearch/盘古&GPU专家访谈信息整理_已补标签.xlsx`  
> 分析范围：工作簿「访谈信息整理」表的 1,535 条信息点  
> 说明：先以推理、部署、服务化、推理引擎、吞吐/时延、量化、KV Cache、训推对齐等词进行宽口径筛选，得到 391 条候选信息（GPU 161 条、NPU 230 条，涉及 38 位受访者），再结合场景标签与上下文人工去噪、归并。本文中的 `N10-030` 等编号均为源表「信息点编号」，可回溯原始总结和用户原声。

## 一、结论摘要

推理产品的核心矛盾已经不再是“有没有一个推理引擎”，而是如何让模型从适配、部署、上线验证，到运行、优化、诊断和迭代形成一条可观测、可比较、可回归的工程闭环。

本次访谈最值得优先关注的六个结论是：

1. **推理优化是系统工程，单看算子不足以解决问题。** 请求调度、资源调度、组 batch、并行策略、KV Cache、CPU/GPU 协同和底层算子共同决定 TTFT、TPOT 与吞吐；工具需要覆盖从服务指标到代码/算子的完整链路。
2. **真正阻塞交付的往往是精度和兼容性，而非性能优化本身。** 尤其在 NPU、低精度量化、框架升级和 RL 边训边推场景，精度问题难定界、难复现，常比性能劣化更容易阻塞发版。
3. **性能数据不缺，缺的是跨方案、跨卡、跨版本的自动对比。** 当前用户大量依赖肉眼叠图、手工 hover、切大 trace、对齐多卡数据；“自动 diff + 异常归因”比再做一个静态大盘更有价值。
4. **NPU 推理开发的主要成本集中在算子覆盖、文档、报错和版本链路。** shape/参数稍变就可能不支持，Python 层报错缺少根因，文档分散且不可直接运行；这些问题把大量时间耗在“确认能否用”和“找谁处理”上。
5. **RL 把推理从独立服务变成训练主链路。** RL 训练 70%–90% 的时间可能在推理侧；训推框架、算子和精度体系不一致，会直接拖慢版本迭代，现有工具只能看到框架边界，缺少向下穿透能力。
6. **最有机会的产品形态是“推理工程诊断工作台”，而不是单点工具。** 以统一任务/实验为中心，串联准入测试、运行监控、性能 profile、精度对齐、版本变更和故障闭环，并允许专家继续交互追问、回看证据。

## 二、推理端到端工作流与关键断点

访谈中较完整的推理流程可以归纳为：

1. **需求与方案输入**：接收模型架构、业务场景、并发/SLA、硬件与精度要求。
2. **理论拆解与技术选型**：估算计算量和显存，确定切分、并行、量化、KV Cache 与推理引擎方案。
3. **模型与算子适配**：复用现有算子；遇到融合算子、特定 shape 或新架构能力缺口时提需求或快速开发。
4. **镜像与集群部署**：构建推理引擎镜像，将模型加载到 worker，配置多机多卡和服务参数。
5. **上线前验证**：跑精度评测、性能 benchmark、正确性与故障注入；输出准入报告。
6. **在线服务与监控**：持续观察 TTFT、TPOT、TPS、RPM/TPM、SLA 成功率、错误码、GPU/网络健康及资源利用率。
7. **性能诊断与优化**：从服务异常下钻到调度、并行、通信、算子和代码，调整方案后再次对比验证。
8. **版本迭代与回归**：引擎、CANN、算子、模型或参数变更后重新验证性能与精度，拦截回退。

当前断点主要出现在四处：

- **方案到适配**：缺少可靠的算子/shape/版本能力查询和收益预估。
- **验证到上线**：精度、性能、故障用例分散，缺少统一准入基线。
- **监控到诊断**：线上 P99 指标与 profile、代码、算子之间无法自然关联。
- **变更到回归**：跨版本、跨硬件、跨配置的差异难自动解释，依赖专家经验。

## 三、核心洞察

### 洞察 1：推理性能优化的最小分析单元应从“算子”升级为“服务链路”

**现象**

- 推理不仅由底层算子决定，还受到请求/资源调度、组 batch、并行策略、CPU/GPU 协同和 KV Cache 管理影响。（G22-002、G22-003）
- 在线关注 TTFT、TPOT、TPS、RPM/TPM 与 SLA 成功率；性能目标是在满足时延约束下最大化吞吐，而不是追求单一算子最快。（G22-005、G22-038）
- 推理框架内部同时包含上层调度和下层模型/算法能力；仅提供算子视角会丢失大量系统性瓶颈。（N13-005）

**洞察**

用户需要的是从“业务请求为什么慢”出发，逐层回答服务入口、调度、batch、并行、通信、模型模块、算子和硬件哪个环节造成等待。工具如果只展示 kernel timeline 或静态模型结构，仍需要专家在脑中完成拼接。

**产品机会**

- 建立“服务指标 → 请求阶段 → 模型模块 → 算子/通信 → 代码”的下钻路径。
- 内置 TTFT、TPOT、吞吐、成功率、排队时间、prefill/decode 耗时、batch 利用率、KV Cache 命中/占用等推理专属指标。
- 支持 PD 分离、TP/DP/EP/PP/CP、连续批处理等场景的依赖与空泡视图。

### 洞察 2：精度问题比性能劣化更容易阻塞推理交付

**现象**

- 推理流程在定切分/量化后，必须做端到端精度与性能验证；定位精度问题仍主要依赖逐层 dump 与 golden torch 脚本比对，难度极高。（N10-030、N10-032）
- 量化算子、并行策略和 KV Cache 管理变化都可能导致线上 evaluation 掉分，即使算子已通过单点正确性测试。（G22-032）
- 测试侧明确认为精度问题比性能问题更容易阻塞发版，现有分析手段有限。（N28-012）
- RL 场景中，版本发布 70%–80% 的时间可能花在训推精度对齐；单轮完整定位从数天到数周。（N26-001、N26-015、G24-020）

**洞察**

精度不是上线前的一次性验收，而是伴随模型、算子、引擎、量化、硬件和版本变化持续发生的回归风险。精度诊断需要和版本变更、调用链、样本、张量及算子实现建立关联。

**产品机会**

- 以同一输入 token/样本为锚点，对比基线与候选版本的输出、logit/logprob、层级张量和算子结果。
- 支持“首个偏差点”定位，而不是只展示最终误差；自动区分正常浮点误差与异常放大。
- 将精度回归纳入 CI 准入，记录模型、权重、框架、算子包、硬件、量化参数和随机性配置。
- 为 RL 提供训练侧与推理侧双链路对齐，至少能定界到模型模块、框架接口或算子。

### 洞察 3：性能分析的最大低效来自“比较”，而非“采集”

**现象**

- FP8 与 BF16、优化前与优化后需要分别抓 trace，Perfetto 一次只能打开一个 profile，用户靠 hover 和人工记录做对比。（G22-015、G22-040）
- NPU 多卡 profile 信息量大，用户只能把多卡数据叠在一起肉眼比对，希望自动判断各卡是否对齐。（N10-024、N10-025）
- 在线十分钟 trace 可达数 GB，超过 1GB 可能无法直接打开，需要手工切分。（G22-019）
- 用户不会盲信 AI 结论，仍会用 timeline 做确定性事实核验，并要求建议能关联到代码和运行证据。（G22-022、G22-024、G22-025）

**洞察**

用户已经有 Torch Profiler、Perfetto、Nsight、MS Prof、MindStudio Insight 等采集工具。新产品的差异化价值应落在规范化、聚合、对齐、diff、异常检测和证据可追溯，而不是重复采集与画图。

**产品机会**

- 原生支持双实验/多实验 diff：耗时、调用次数、空泡、通信重叠、显存、吞吐和时延变化一屏比较。
- 自动做多 rank 对齐，识别慢卡、负载不均、异常等待与首个偏离 rank。
- 对大 trace 进行按请求/时间/模块的无损切片与摘要，保留跳回原始事件的证据链接。
- AI 诊断采用“结论—证据—置信度—建议实验”结构，并支持继续追问与反证。

### 洞察 4：NPU 推理体验的关键短板是算子可用性与可诊断性

**现象**

- 新模型常遇到融合算子或特定 shape 不支持；参数稍变即报错，FA 等算子会因 KV/Q 头数变化重新提需求。（N10-014、N10-031）
- Ascend C 开发周期可能需要 1–2 个月、代码数千行；Triton 简单算子可在半天完成，但昇腾上的性能调优能力仍不完整。（N10-006、N10-016、N10-017、N10-018）
- Python 层常只报 tuning 问题，有效信息藏在 plog，无法直接指出哪个参数或 shape 不支持。（N10-021、N10-036）
- 文档分散、搜索困难，部分内容错误或缺依赖、缺可运行示例；新算子甚至依赖口口相传。（N10-008、N10-011、N10-012、N30-003、N29-013）

**洞察**

NPU 用户最耗时的并非编写业务模型，而是确认“当前版本能不能支持这个调用”“为什么不支持”“应该改参数、换算子、换包还是提需求”。能力查询、错误解释和升级建议应成为推理工具链的一等能力。

**产品机会**

- 建立可机器读取的算子能力知识库：支持版本、硬件、dtype、shape、布局、量化方式和已知限制查询。
- 运行前做兼容性预检，明确指出不支持项及可选替代方案。
- 将 Python 报错、plog、CANN/算子日志自动归并成一条因果链，直接给出参数/shape/版本根因。
- 为快速实验提供 Triton Ascend/PyPTO 等路径，为生产交付提供向高性能实现的迁移与收益评估。

### 洞察 5：RL 场景使“训推一致性”成为新的推理基础能力

**现象**

- RL 训练 70%–90% 的时间可能在推理侧，训练进程长时间等待推理；常采用训推分离、PD 分离或边训边推。（N26-023、G24-018、N29-005）
- 训练系统与推理系统各自有算子和优化路径，RL 要求推理 logprob 与训练侧高一致，生产目标可达 0.99；实际可能长期卡在约 92%。（N26-005、N26-006）
- 推理侧为性能引入的新特性、融合算子或低精度优化更容易破坏一致性；精度与性能相互牵制。（N26-016、N26-021、N26-023）
- 现有自研工具最多定界到训练/推理框架边界，再往下需要跨团队人工接力。（N26-009、N26-014）

**洞察**

RL 中推理不再是训练完成后的部署环节，而是训练循环的关键路径。推理产品若只服务线上 endpoint，会遗漏权重同步、推理作业调度、训推一致性、推理等待和沙箱反馈等高价值场景。

**产品机会**

- 支持训练权重发布、推理加载、请求执行、结果回传的全链路时序与等待分析。
- 同时展示一致性、KL、reward、logprob 与推理性能，避免单指标“看起来正常”的假收敛。
- 对训练/推理框架 commit、算子清单、量化与确定性配置做变更追踪，异常时自动关联最近变化。
- 为推理作业提供 hang、回调失败、外部依赖/沙箱不可用等状态诊断。

### 洞察 6：上线能力应产品化为“可重复的准入流水线”

**现象**

- GPU 团队已将镜像构建、部署高度自动化，代码提交后约 1 小时可完成推理镜像与集群环境更新。（G22-004）
- 上线前会做通用精度评测、性能 benchmark、正确性验证；正式上线往往经过镜像构建、参数组合 benchmark、报告准入三阶段。（G22-030、G22-035）
- 盘古推理测试设置多条 CI 流水线，绑定不同 CANN 与推理框架版本，覆盖精度、性能与功能特性。（N28-002、N28-005、N28-006）
- 已有基于 vLLM benchmark serve 改造的统一性能测试工具及服务化故障注入/流量仿真工具。（N28-018）

**洞察**

成熟团队已经在自建准入体系，但能力分散在流水线、脚本、监控和文档中。产品应将“基线、环境、配置、用例、结果、门禁”标准化，让任何一次变更都可重复验证、可解释回退。

**产品机会**

- 统一管理模型/框架/CANN/算子/硬件的版本矩阵与准入结果。
- 提供精度、性能、稳定性、故障注入四类模板；允许按模型和服务 SLA 自定义阈值。
- 自动生成变更报告：相对基线哪些指标改善、哪些回退、是否达到上线门槛、建议复测项。
- 将线上异常样本和流量特征沉淀为回归用例，形成“线上问题 → 离线复现 → CI 防护”的闭环。

### 洞察 7：监控大盘只有与诊断和决策联动才有价值

**现象**

- 推理监控需要同时覆盖服务指标、引擎指标、GPU/网络健康和负载相关错误，并反推引擎参数与集群配置。（G22-005）
- 不同卡型、网络与并行策略下，健康度权重不同；固定的综合分数容易误导。（G22-020）
- GPU 吊卡、慢卡、通信中断仍靠脚本和人工补洞，难以保证完全稳定。（G22-033、G22-034）
- RL 看板需联合观察一致性、KL、reward 分布等多指标，单指标正常也可能是假收敛。（N26-011、N26-012）

**洞察**

用户不缺一块显示指标的大屏，而是缺从异常信号到定位假设、证据、建议动作和验证结果的闭环。健康度应按场景动态解释，并允许用户查看组成与调整权重。

**产品机会**

- 将告警自动关联对应请求、rank、profile 片段、版本变更和历史相似故障。
- 场景化健康模型：在线低时延、离线高吞吐、RL 边训边推、PD 分离分别配置指标权重。
- 每个异常给出“影响范围、最可能根因、需要补采的数据、建议实验和责任域”，减少跨团队扯皮。

## 四、不同用户群的需求差异

| 用户群 | 首要目标 | 主要痛点 | 更适合的产品入口 |
|---|---|---|---|
| 模型/推理开发 | 模型快速适配并达到精度、性能目标 | 算子覆盖、shape 不支持、文档与报错、精度定位 | 开发环境中的兼容性预检、错误诊断、精度/性能 diff |
| AI Infra / MaaS | 在 SLA 下最大化吞吐和资源利用率 | 调度、batch、并行、KV Cache、trace 对比、大规模集群稳定性 | 服务监控与性能诊断工作台、准入流水线 |
| RL Infra | 缩短训练迭代并确保训推一致 | logprob 对齐、权重同步、推理等待、作业调度、沙箱 | 训推一致性与 RL 全链路诊断 |
| 测试/质量 | 拦截版本回退并推动问题闭环 | 黑盒难下钻、版本矩阵复杂、精度防护不足 | 自动化准入、差异报告、故障复现与历史问题库 |
| 算子/底层专家 | 快速复现并判断是否为算子问题 | 上层信息不完整、收益目标不清、问题移交反复 | 标准问题包、算子级证据、理论/实测差异与调用上下文 |

## 五、产品规划建议

### P0：优先解决“比较与定界”

1. **推理实验/版本 Diff**  
   对比模型版本、框架版本、CANN/算子包、量化方案、并行策略与硬件配置；统一输出 TTFT、TPOT、吞吐、显存、精度、热点算子和回退项。
2. **多卡/多 rank 自动对齐**  
   自动识别慢卡、首个异常 rank、通信等待、负载不均与不同 profile 的关键差异。
3. **错误与日志归因**  
   聚合 Python、框架、CANN、算子、通信与系统日志，直接指出疑似责任域、参数/shape/版本限制和下一步动作。
4. **上线准入报告**  
   把精度、性能、功能与稳定性回归统一成可配置门禁，并留存可复现实验上下文。

### P1：形成端到端推理诊断闭环

1. **服务指标到代码/算子的下钻**：从 P99 TTFT/TPOT 或错误码定位到请求阶段、模型模块、rank 和原始事件。
2. **算子能力与兼容性知识库**：支持自然语言和结构化查询，并可被 Agent、IDE、CI 直接调用。
3. **大 trace 智能切片与证据导航**：面向 GB 级数据按请求/阶段/异常窗口分析，避免整包加载。
4. **线上问题回流 CI**：自动沉淀异常流量、输入和环境，形成可重复故障用例。

### P2：覆盖高价值的 RL 训推场景

1. **训推精度穿透对齐**：同 token、同层、同接口逐步定位首个偏差点。
2. **权重同步与推理等待分析**：展示训练、发布、加载、prefill/decode、回传的关键路径。
3. **RL 多指标联合诊断**：一致性、KL、reward、logprob 与推理性能联动，识别假收敛。
4. **推理作业与沙箱状态诊断**：覆盖 hang、回调、网络/安全限制、实例创建释放和外部工具依赖。

## 六、建议的核心指标

### 用户价值指标

- 首次完成模型推理适配的时间（Time to First Successful Inference）。
- 从发现性能/精度异常到完成责任域定界的时间（MTTI）。
- 从定界到修复并通过回归的时间（MTTR）。
- 人工 profile 对比、日志整理、逐层 dump 的工时下降比例。
- 版本发版因精度/性能问题阻塞的次数与时长。

### 产品效果指标

- 异常自动定界到正确责任域的 Top-1 / Top-3 命中率。
- 多 rank 异常与首个偏离点的检出率。
- 自动生成建议被采纳并验证有效的比例。
- 准入门禁拦截真实回退的比例及误报率。
- 从线上异常自动生成可复现回归用例的成功率。

## 七、设计原则

1. **证据优先**：AI 结论必须能跳回原始 trace、日志、指标、代码或版本变更，避免不可核验的“一次性报告”。
2. **比较优先**：所有性能与精度结果默认支持基线比较，而不是孤立展示绝对值。
3. **场景可配置**：不同硬件、模型、在线/离线、RL/非 RL 的权重和门槛应可调整。
4. **分层但不割裂**：允许从服务层逐级下钻，同时支持把标准证据包移交给框架、算子或硬件团队。
5. **专家在环**：自动分析用于缩小范围和给出验证实验，最终判断保留人工复核与交互追问。
6. **对 Agent 友好**：文档、算子能力、错误码、接口和实验数据需要结构化、可检索、可调用。

## 八、研究边界与后续建议

- 本报告基于访谈整理表中的摘要、原声及标签，候选条目通过关键词宽筛后人工归并；391 条是候选池规模，不等同于 391 条独立推理需求。
- 受访者同时包含 GPU、NPU、模型、Infra、测试、算子等角色，部分观点代表具体团队或项目阶段，不应直接外推为全行业比例。
- 建议下一轮围绕 P0 方向做 5–8 位定向验证：分别选择盘古推理开发、RL Infra、系统测试、MaaS Infra 和算子专家，使用真实的一次版本回退案例验证“实验 Diff—责任域定界—准入回归”完整流程。
