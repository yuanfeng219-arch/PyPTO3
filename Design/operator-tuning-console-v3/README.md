# Tuning Atlas（算子调优控制台 V3）

把 `operator-tuning-console` 的五层工作台压成**一屏一图**：页面主体是一张色块矩阵，
一个 AICore 执行块一格；除了两个浮层，页面上没有正文。

入口：[index.html](index.html) ·
数据：直接引用 `../operator-tuning-console/data.js`（不另存副本）

---

## 参考框架

结构照搬 The Visual Agency 的 **Codex Atlanticus**（达芬奇大西洋古抄本可视化）。
它的信息层次是这样的：

| 层 | Codex Atlanticus | Tuning Atlas |
|---|---|---|
| 1 | 两条可刷选的总览带：`NUMERICAL ORDER`（页码）/ `CHRONOLOGICAL ORDER`（年代） | **下发序** / **墙钟时间** |
| 2 | `Show [all\|active] in [numerical\|chronological] order` | `显示 [全部块\|仅关键路径] 按 [下发序\|时间序\|核序] 排列` |
| 3 | 主体：一页一格的色块矩阵，色 = 学科（5 类） | 主体：一块一格，色 = 单块耗时（5 档） |
| 4 | 右栏 `SUBJECTS` 图例，点击筛选 | 右栏两组筛选：耗时档 + scope |
| 5 | 底部唯一的大号文字：`1,119 SELECTED PAGES` | `4,038 个块被选中` |

配色不是凭印象仿的：底色 `#10141a` 和五个分类色是从原图上逐像素取样来的，
集中声明在 [atlas.css](atlas.css) 的 `:root` 里。排版、间距、字体仍走 PTO Design System 的语义令牌。

## 两条总览带必须是两个不同的轴

这是照搬框架时最容易做砸的一步。

第一版我把左边那条做成「发射序」——**按开始时间排序后的下标**。
它和右边的墙钟是单调对应的，所以两条带其实是同一个轴：
刷完左边再刷右边，交集几乎恒等于后者。实测左 30% ∩ 时间窗 1220–2196 us 只剩 **1 个块**，
不是因为它们在筛，是因为它们在互相抵消。

真正的第二个轴藏在 tag 里。任务 tag 形如 `rNtM`：`N` 是下发环，`M` 是环内的下发序号。
这是任务被**排进队列**的次序，和它实际**跑起来**的次序不是一回事：

```
decode_csa / rank0      84 个任务，21 处倒置
decode_fwd_layers      426 个任务，232 处倒置
```

倒置 = 一个任务跑在了比它先下发的任务前面。改成 `(ring, tIdx)` 之后，同样那两刷的交集是
**699 个块** —— 两条带终于各筛各的。这正是 Codex 里「页码」和「年代」的关系：
一个是内在编号，一个是实际发生的时刻。

网格的排列开关因此给了三个：`下发序 / 时间序` 正对着上面那两条带，换一个排法就能看见
调度把哪些块挪了位置；`核序` 是第三个物理轴，同一个核的块连在一起。

左边那条带的纵轴**开过方**。块时长跨三个数量级（1.x us 到 881 us），线性画出来是一条
平线加几根针，看不出形状也没法下手刷。纵轴因此不是等比的，只用来找位置，不用来读数。

## 为什么颜色给耗时，不给 scope

第一版颜色给了 scope：按 Σ core-time 取前五个，其余合并成灰。结果矩阵 **81.4% 是灰的** ——
本路有 62 个 scope，前五个只盖住 **18.6%** 的格子。主体大半是无信息的像素，
这和「页面主体都是可视化区域」正好相反。

换成按**单块耗时**分档，是完全划分，没有"其余"：

| 档 | 色 | 块数 | 占格子 | Σ core-time | 占时间 |
|---|---|---:|---:|---:|---:|
| `< 5 us` | 蓝 | 1,064 | 26.3% | 3,646 | 2.9% |
| `5 – 20` | 绿 | 2,235 | 55.3% | 22,244 | 17.7% |
| `20 – 100` | 琥珀 | 495 | 12.3% | 18,076 | 14.4% |
| `100 – 400` | 珊瑚 | 150 | 3.7% | 21,561 | 17.2% |
| `≥ 400 us` | 红 | **94** | **2.3%** | **60,044** | **47.8%** |

（decode_csa / rank0）

**2.3% 的格子吃掉 47.8% 的 core-time。** 这件事不需要写成一句话放在角落，
它就是这张图第一眼的样子：满屏蓝绿里散着几十颗红点。

scope 没有消失，它降级成右栏第二组筛选（前五 + 其余），不参与上色，
选中态只靠左边一道 accent，不跟矩阵的配色打架。点矩阵里的格子等同于点它所属的 scope 那一行。

## 白边 = 依赖关键路径

格子上的白边是第二重编码：这个块所属的任务在**依赖关键路径**上。
路径取自 `cpath.cpm`，是在 happens-before 过滤后的依赖图上算的最长链，
不是按耗时排序挑出来的。

| run | 路径上的任务 | 路径上的块 |
|---|---:|---:|
| decode_csa / rank0 | 14 | 884 |
| decode_csa / rank1 | 11 | 1,641 |
| decode_fwd_layers | 14 | 167 |

它只值一行说明，不值得再起一组图例，所以做在右栏底部一行。

这层编码在这张图里很重要，因为 **Σ core-time 大不等于拖慢墙钟**：一个 scope 可能摊在
72 个核上一次跑完。`qk_pv` 是 72 块、Σ 46,662 us（占 37.2%），但它跨的墙钟只有 886 us。
要判断值不值得动，看它在不在路径上，而不是看它的格子多不多、颜色深不深。

## 四层怎么互相过滤

```
下发序刷选  ─┐
墙钟刷选    ─┤
耗时档筛选  ─┼─→  矩阵（落选的压到 14% 不透明度）─→  大号数字 + 一行读数
scope 筛选  ─┤
仅关键路径  ─┘
```

五个条件取交集，读数实时重算。几个交叉验证过的例子（decode_csa / rank0）：

```
全部                      4,038 块   Σ 125,572 us   100.0%
仅关键路径                  884 块   Σ  64,180 us    51.1%   跨 3,253 us
≥ 400 us 这一档              94 块   Σ  60,044 us    47.8%
qk_pv                        72 块   Σ  46,662 us    37.2%   跨 886 us
qk_pv + 仅关键路径            72 块   ← qk_pv 的 72 个块全在路径上
```

`跨 3,253 us` 和 `cpath.cpm.len` 对得上；`Σ 46,662` 和 `scopes[0].coreTime` 对得上；
每一档的块数和 Σ 都是独立算过一遍核对的。

## 第二屏：KERNEL 详情（原 L1 / L0）

参考图的详情页顶栏写着 `< Return to General overview` —— 它和总览页是同一个产品的两屏。
所以原来 L1 / L0 页签下的内容做成了这里的第二屏，而不是另一个 demo：
在矩阵上点任意一格，进那个 kernel 的详情；`‹ 返回总览` 回去。

| Codex 详情页 | Tuning Atlas 详情页 |
|---|---|
| 顶部胶片条：选中的 99 页，当前页带 `●` | **顶部 kernel 条**：总览页筛剩下的 kernel，缩略图 = 它的块时长剖面 |
| `PAGE INFORMATION` + 竖直堆叠条（学科构成） | **KERNEL** + 竖直堆叠条（**三口径构成**） |
| `TOPICS PER SUBJECT` 分组列表 | **构成**：展开 / 离散 / 引擎 / 路径 / 来源 |
| 中央：手稿页大图 + `‹ ›` + `Recto / Verso` | 中央：**块分布** + `‹ ›` + `按核 / 按时长` |
| 右栏 `SIMILAR PAGES`，每行一个迷你堆叠条 | 右栏 **构成相近**，同样的迷你条，可直接比形状 |

### 胶片条就是总览页的筛选结果

这是两屏合成一个产品的关键：在矩阵上刷一段时间窗、点一档耗时、选一个 scope，
详情页的候选集跟着变，左上角写 `N 个 KERNEL 被选中`。没有筛选时就是全部。
点那个数字循环换排序：`Σ core-time / setup 占比 / hand-off 占比 / 下发序`。

缩略图的纵轴按**这个 kernel 自己的最长块**归一，不是全 rank 的上限。
试过用全 rank 上限：qk_pv 的 881 us 一压，绝大多数 kernel 的柱子只剩 5px，一条都读不出来。
所以高度画的是**形状**（平 = 均衡，陡 = 长尾），绝对大小交给颜色（还是那五档）和下面的 Σ。
右上角一小段 accent = 它在依赖关键路径上；整框白边留给"当前选中"。

### 左栏：一个块的三口径

`kernel`（真正在算）⊂ `+setup`（块内准备）⊂ `+hand-off`（派发到回收）
是对同一个块的**三次嵌套测量**，所以堆叠条画的是它们的**差分**，不是三次独立的量。
这一点在图上看不出来，只能写在 `怎么读` 里。

差分是精确的，不是近似：三份 dump 594 个 task 上，
`kernel 均值 + setup 均值 == 块均值` 和 `busySum == kdurSum + setupSum`
两个恒等式偏差都是 `0.000000`，防负的 `max(0, ·)` 一次都没触发。

这一栏值得看，是因为构成差得很开：

```
setup 占比      0.06%  →  78.5%   （qr_rms_norm_quant）
hand-off 占比   0.08%  →  75.8%   （weights_proj_reduce）
```

也就是说有的 kernel 绝大部分时间根本没在算。随手点开的 `hc_pre_linear` 就是
kernel 41.0% / setup 5.6% / **hand-off 53.3%** —— 一半以上花在派发和回收上。

### 中央：同一批块的两种摆法

`按核` 是这些块在它用到的核上的真实落位，横轴是这个 kernel 自己的 span，看得见错开和拖尾；
`按时长` 把同一批块降序排开并画一条中位线，柱顶和中位线的落差就是长尾。

参考图那个位置是 `Recto / Verso`（同一张纸的两面）。最贴切的类比本来是
**AIC 面 / AIV 面**，但本 run 只有 2 个 scope 是混合的，撑不起一个通用开关。
退而求其次没有编数据：`data.js` 里每个块只有 `[起始, 时长, task]`，
没有 per-block 的 kernel / setup 拆分，所以中央两面不是两次测量，是两种排法。

### 右栏：这是一个问题，还是一类问题

按三口径比例向量的 L1 距离排，取最近的 9 个。迷你条和左栏那根是同一种编码，
所以可以直接比形状。当前这个也在列表里并高亮 —— 和参考图一样，
**没有参照物的时候，形状本身看不出偏不偏**。

这一栏回答的是调优里最值钱的那个问题：右栏如果跟着一片同样形状的 kernel，
那就不是改一个算子的事，该去改编译或改框架。

搜索范围是**整个 rank**，不是胶片条里那些。第一版我拿筛选结果当搜索池，
错了：被自己的筛选条件限住，这一栏就答不了「是不是一类问题」。

代价是可以跳到一个不在候选集里的 kernel。这时候胶片条把它插在条首，
左上角写 `N 个 KERNEL 被选中 + 当前 1 个` —— 而不是把页面弹回候选集的第一个。
弹回去会让右栏点不动，不插进来又会让 `‹ ›` 因为找不到位置变成死的。
（点总览页里被压暗的格子也会走到这条路径上，是同一种处理。）

## 页面上的文字只有两处

`怎么读` 和 `关于这份 dump` 两个浮层。正文全在里面，其余位置只有极小号的标签和数字。

`关于这份 dump` 里写清了这张图**不能**单独回答什么：

- 单个 kernel 内部为什么慢 —— 要看核内流水的 MTE / Vector / Cube 占用（完整版控制台的 L1 页）
- Host 侧有没有贡献 —— 这份 dump 只有 STRACE span，没有 `BenchmarkStats`，
  给不出 rounds / warmup 的统计量（完整版控制台的 E2E 页）

以及那条一直要说的：**一次采集 = 一个样本**，这里所有数字都是这一次运行的观测值，
不是多次运行的统计量，不能当性能结论直接对外报。

## 和 V1 / V2 的关系

三个版本共用同一份数据，回答的问题不同：

- **V1 `operator-tuning-console`** —— 五层证据闭环（E2E / L2 / L1 / 编译 / ISA）+ 实验台账。查证用。
- **V2 `operator-tuning-console-v2`** —— 以 Investigation 组织基线、假设、证据、单变量实验。走流程用。
- **V3 本页** —— 一屏一图，看全貌和分布。找方向用。

数据来自 `../operator-tuning-console/data.js`，由那边的 `build-data.cjs` 生成。
本页不复制数据：那边重跑之后这边跟着变。新增 dump 也不用改这里，`window.TUNING_RUNS`
里多一个 rank，顶栏就自动多一个切换项。
