# Lab Tour 演讲稿

预计 5～6 分钟，适合边操作边讲。方括号内为操作提示，不用念出来。

## 开场与项目背景（约 1 分钟）

【打开 `intro.html`】

大家好，我们这个展台展示的是昇腾算子开发领域的 PyPTO 产品体验设计。今天会通过两个场景，介绍我们如何帮助开发者看懂算子代码、分析运行性能。

先简单说一下背景。开发者写算子时，先描述张量，也就是 Tensor 之间怎么计算。要让它在芯片上高效运行，还要把数据切成 Tile，也就是小块，再把任务分给不同的核。数据怎么切、任务怎么分、搬运和计算怎么配合，都会影响最终性能。

从写代码到上板运行，开发者通常会关注两个问题。

第一，AI 可以帮助开发者生成算子代码。但代码出来以后，开发者还要看懂它：算的是什么？任务怎么分？数据放在哪里？

第二，算子跑起来以后，会产生大量性能数据。但要从密密麻麻的执行记录中，找出拖慢整体运行的任务，还是很依赖经验。

下面以 DeepSeek 的稀疏注意力算子为例，来看一下开发者的开发过程。

## 场景一：开发时看懂计算（约 2 分钟）

【进入“算子开发”，展示 Agent 生成过程】

开发者先把需求交给 Agent，让它生成 qk_pv Kernel，也就是一段具体的算子计算代码。Agent 会读取相关代码，规划并生成 Kernel，再展示编译和精度对比的结果。

代码生成出来了。接下来，开发者要弄明白：这段代码做了什么？是不是符合预期？点进来看一下。

【进入 Operator Lens，展示整层计算图】

打开 Operator Lens，左边是源码，右边是计算图。现在看到的是模型的整层计算：数据从哪里来，经过哪些计算和通信，都可以在图上看到。如果想仔细看某个 Kernel，就可以从图里点进去。

【双击进入 `qk_pv` Kernel】

现在看到的是 qk_pv。上面这张图展示了处理一份任务要经过哪些计算。接下来看看，这些任务是怎么分给不同的核的。

【切换到“任务分配”】

切到任务分配，可以看到这批任务怎么生成、排序，再由各个核领取。开发者还可以对照不同的排序方案，看看各个核的工作量是否均衡，哪里还有优化空间。

看完任务怎么分，再看数据放在了哪里。

【切换到“存储落点”，悬停源码行或芯片区域】

这张图展示了数据在芯片上的存放位置。鼠标放到源码上，图中对应的计算和存储区域就会亮起来。这样开发者就能看到，代码用到了芯片上的哪些资源。

在这个例子里，图上提示一个向量计算单元，也就是 AIV，虽然分配了存储地址，却没有有效数据。开发者可以据此进一步检查资源使用情况。

了解了代码怎么工作，接下来就要看：它实际跑得怎么样？

## 场景二：运行后分析性能（约 1 分 40 秒）

【点击“编译并上板”，进入设备执行泳道】

【等待运行画面时】

现在模拟算子编译并上板。运行结束后，开发者会看到这张设备执行泳道图。每一行代表一个执行单元，横向是时间，方块是执行的任务。图里信息很多，要开始调优，该先看哪里？

接着进入性能分析。

【进入性能分析】

这里先标出影响整体耗时的关键路径。它是一条相互依赖的任务链，链上的任务变慢，可能拖长整体运行时间。页面还会提示路径上哪些任务值得关注。

【展示关键路径和优化候选】

这个例子里，页面提示一个任务的块负载不均：不同块完成工作的时间差别比较大。它又位于关键路径上，所以值得优先查看。

【指向关键路径中对应的任务，再查看泳道和读数】

开发者可以在关键路径上找到这个任务，再到泳道里查看执行情况，结合旁边的读数，判断提示是否有依据。页面也会给出可以尝试的优化方向。

这样一来，开发者可以先顺着提示找到可疑的地方，再查看数据，判断它是不是瓶颈。优化之后有没有效果，还要再跑一次来验证。

## 收尾（约 40 秒）

【回到场景总览，或停留在性能分析页】

从代码到运行数据，这两个场景分别帮助开发者看懂算子怎么工作，以及找到值得关注的性能问题。

在开发和运行之间，还有编译这一步。Demo 里也可以对照编译过程中各个步骤前后的结果，看看代码发生了哪些变化。

最后说明一下，今天看到的是设计原型。Agent 生成、编译和上板都是预置演示；任务分配的部分分析使用了模拟输入，优化效果还要实际上板验证。以上就是今天的分享，谢谢大家。

## 现场操作提示

- 重点走两条路径：整层图 → Kernel → 任务分配 → 存储落点；性能分析 → 关键路径 → 对应证据。
- 编译 Pass 作为收尾时的补充介绍即可；如果现场时间充裕，再进入页面展开。
- 演示停顿和页面切换已计入预计时间，建议现场试讲一次，根据操作速度调整。
