## 第一轮：LLVM Pass 和本地 DeepSeek V4 Pass 是一个概念吗？

### 用户

[LLVM’s Analysis and Transform Passes](https://llvm.org/docs/Passes.html) 和本地 DeepSeek V4 data 里面的 pass 是一个概念吗？

### Codex

结论：**上位概念相同，但不是同一套 Pass。**

两边的 `pass` 都表示编译器流水线中的一个处理阶段：读取某种 IR，进行分析或变换，再把结果交给后续阶段。LLVM 官方也是这样定义 Pass 的：遍历程序的一部分，收集信息或修改程序。

但本地 `Data/DeepseekV4` 里的 Pass：

- 不是 DeepSeek 模型本身的网络层或算法步骤；
- 不是直接运行 LLVM 官方 Pass；
- 而是 **PyPTO 编译器处理 DeepSeek V4 workload 时执行的 PyPTO IR Pass**。

证据是 PyPTO 的默认 PassManager 明确注册了这些阶段。而 `passes_dump/01_after_InlineFunctions.py` 这种文件，是每个 PyPTO Pass 执行后的 IR 快照。

大致对应关系如下：

| 本地 PyPTO Pass | LLVM 中相近的概念 | 是否相同实现 |
|---|---|---|
| `InlineFunctions` | `inline` / `always-inline` | 否。都是函数内联，但 PyPTO 专门展开 `FunctionType.Inline`，并删除这种函数定义 |
| `UnrollLoops` | `loop-unroll` | 否。变换思想非常接近，但本地针对显式的 `pl.unroll` 和编译期常量循环；LLVM 面向 LLVM IR 自然循环并结合规范化与收益判断 |
| `ConvertToSSA` | `mem2reg` 等 SSA 构造过程 | 不完全相同。PyPTO 把自己的非 SSA IR 整体转成 SSA；LLVM IR 本来就是寄存器 SSA，`mem2reg` 主要把合适的栈内存访问提升成 SSA 值 |
| `CtrlFlowTransform` | `simplifycfg`、各种 CFG lowering | 只有类别相近。PyPTO 主要把 `break/continue` 改成结构化控制流 |
| `Simplify` | `instcombine`、`simplifycfg`、常量传播 | 目标相近，但规则、IR 和边界不同 |
| `OutlineIncoreScopes` | outlining / function extraction | PyPTO 专用：把核内作用域抽成 `InCore` 函数 |
| `ConvertTensorToTileOps` | IR lowering / legalization | PyPTO/NPU 专用，LLVM Passes 页面里没有一一对应项；它把 InCore 中的 tensor 运算降低成 tile 运算 |

可以这样理解：

```text
DeepSeek V4 Python/PyPTO 程序
        ↓
PyPTO 前端 IR
        ↓
PyPTO Pass Pipeline
Inline → Unroll → SSA → Scope outlining → Tensor→Tile → 内存/流水线处理
        ↓
PTO / Ascend 后端代码
```

而 LLVM 是：

```text
C/C++ 等前端
        ↓
LLVM IR
        ↓
LLVM Pass Pipeline
inline → loop-unroll → instcombine → simplifycfg → …
        ↓
机器码
```

所以最准确的一句话是：

> **本地 DeepSeek V4 的 Pass 和 LLVM Pass 属于同一种编译器设计范式；其中少数变换语义相似，但它们处理不同 IR、由不同编译器实现，后半段大量 Pass 是 PyPTO/Ascend 专用的。**

截图里的 `diff` 也不是说“这是 LLVM Pass”，而是表示该 PyPTO Pass 执行前后的 IR 可以进行差异对比。

## 第二轮：开发者为什么要查看每个 Pass 的控制流和 Diff？

### 用户

开发者用这个工具的目的是什么，为什么要查看控制流在 pass 之间的 diff，为什么要看每个 pass 的控制流程？

### Codex

这个工具本质上是一个**编译器可观测与调试工具**。开发者用它回答：

> “这段 DeepSeek V4 的 PyPTO 程序，是在哪个 Pass 之后变成现在这个样子的？”

它查看的不是 DeepSeek 模型推理时的业务流程，而是**编译期间 IR 的演化过程**。

### 为什么看 Pass 之间的 Diff

每个 `xx_after_PassName.py` 都是一次编译快照：

```text
前端 IR
  ↓ InlineFunctions
内联后 IR
  ↓ UnrollLoops
循环展开后 IR
  ↓ ConvertToSSA
SSA IR
  ↓ OutlineIncoreScopes
编排与核内计算分离后的 IR
  ↓ ConvertTensorToTileOps
Tile 级 IR
```

比较相邻快照，可以精确判断某个 Pass：

- 增加了什么；
- 删除了什么；
- 重写了什么；
- 是否修改了本不该修改的结构；
- 是否为后续 Pass 制造了异常输入。

这在定位编译器问题时非常重要。最终错误可能在第 40 个 Pass 或 codegen 才暴露，但真正引入错误的可能是第 4 个 Pass。

例如：

```text
源程序结果正确
→ ConvertToSSA 后正确
→ Simplify 后正确
→ OutlineIncoreScopes 后正确
→ ConvertTensorToTileOps 后结果错误
```

那么排查范围就可以直接缩小到 `ConvertTensorToTileOps`，而不必从整个编译器和 DeepSeek 模型代码里盲查。

### 为什么特别关心控制流

控制流是程序的“骨架”，决定：

- 哪些语句会执行；
- 执行多少次；
- 在什么条件下执行；
- 循环之间如何传递状态；
- 分支汇合时选择哪个值；
- 任务、通信和计算之间的先后关系。

控制流一旦被错误改写，即使单个算子完全正确，最终结果也可能错误。

例如源程序是：

```python
for i in range(4):
    if valid(i):
        acc = acc + x[i]
```

经过 Pass 后如果变成：

```python
for i in range(4):
    acc = acc + x[i]
```

这里只少了一个条件，但可能造成越界访问、错误累加或读取无效 token。

在 PyPTO 里还会影响 NPU 特有行为：

- `pl.unroll` 是否被正确展开；
- `pl.pipeline` 的迭代和 stage 是否正确；
- `if/else` 中的 Tile 是否正确产生和消费；
- 循环携带值是否正确变成 `iter_args` / `yield`；
- `pl.spmd`、`pl.at` 是否被抽成正确的函数层级；
- AIC/AIV 任务是否保持正确依赖；
- 通信 `notify/wait` 是否仍处于正确分支和循环中；
- 内存复用是否跨越了不兼容的控制流生命周期。

### 为什么保留每个 Pass 后的控制流

因为不同 Pass 对控制流承担不同责任：

| Pass | 查看它后面的控制流，主要确认什么 |
|---|---|
| `InlineFunctions` | 调用是否被正确展开；局部变量有没有撞名 |
| `UnrollLoops` | 循环体复制次数是否正确；循环是否被意外放大 |
| `CtrlFlowTransform` | `break/continue` 是否被等价地结构化 |
| `ConvertToSSA` | 分支和循环中的值是否正确通过 phi、`iter_args`、`yield` 传递 |
| `Simplify` | 条件或循环是否被错误折叠；必要代码是否被删掉 |
| `OutlineHierarchyScopes` | 层级作用域抽取后，调用关系是否保持 |
| `OutlineIncoreScopes` | orchestration 和 InCore 的边界是否正确 |
| `OutlineClusterScopes` | Cluster/SPMD 的调用和执行范围是否正确 |
| `ConvertTensorToTileOps` | Tensor→Tile 后循环、边界、有效 shape 和写回位置是否保持语义 |

开发者通常**不会从头到尾逐个认真阅读所有 Pass**。更典型的使用方式是：

1. 先根据错误现象锁定一段范围。
2. 通过时间线快速浏览哪些 Pass 产生了 Diff。
3. 找到“第一次出现异常”的 Pass。
4. 详细查看该 Pass 前后控制流。
5. 再回到 Pass 实现源码定位原因。

因此，这个工具最核心的价值可以概括为：

> **把编译器从一个“输入代码、输出二进制的黑盒”，变成一条可以逐站检查的流水线。**

Pass Diff 用来确定“变化发生在哪里”，每个 Pass 后的控制流用来确认“变化是否仍保持原程序语义”。

## 第三轮：为什么 Pass Diff 不直接使用 IR Graph？

### 用户

为什么 pass diff 不用 ir graph 计算图来 diff？

### Codex

因为 **IR Graph 只是 IR 的一种投影，不是完整 IR 本身**。Pass Diff 的目标是精确判断“这个 Pass 到底改了什么”，所以文本/结构化 IR Diff 更适合作为主视图，Graph 更适合作为辅助视图。

### 1. PyPTO IR 不只是“计算图”

普通计算图主要表示：

```text
Tensor → Operator → Tensor
```

但 PyPTO Pass 还会处理：

- `for / if / break / continue`；
- SSA、`iter_args`、`yield`；
- 函数调用与内联；
- `Hierarchy / InCore / Cluster / SPMD` 作用域；
- Tensor 和 Tile 类型；
- shape、stride、layout、memory space；
- `notify / wait` 通信；
- Task ID 和依赖关系；
- pipeline stage；
- MemRef、地址和内存复用；
- source location、属性和参数方向。

如果只画计算图，很多变化根本看不见。例如：

```python
pl.tile.load(..., target_memory=pl.Mem.Vec)
```

变成：

```python
pl.tile.load(..., target_memory=pl.Mem.Mat)
```

计算图拓扑可能完全相同，但语义和硬件行为已经改变。文本 Diff 能直接显示 `Vec → Mat`。

### 2. Graph Diff 很难稳定匹配节点

Pass 经常会：

- 内联函数；
- 展开循环；
- 拆分算子；
- 合并表达式；
- 重命名 SSA 变量；
- 抽取新函数；
- 复制一整片子图。

例如 `UnrollLoops` 把一个循环体复制四次。Graph Diff 必须回答：展开后的四份节点，分别对应展开前的哪个节点？

如果没有跨 Pass 保持的稳定节点 ID，只能通过名称、拓扑和属性猜测。复杂 IR 中很容易配错。

文本 Diff 则有天然的上下文：

```diff
- for i in pl.unroll(4):
-     y = f(x, i)
+ y_inline0 = f(x, 0)
+ y_inline1 = f(x, 1)
+ y_inline2 = f(x, 2)
+ y_inline3 = f(x, 3)
```

### 3. Graph 布局变化会制造大量视觉噪声

即使只增加一个节点，自动布局也可能让整个图重新排列：

```text
Pass 前：A → B → C
Pass 后：A → X → B → C
```

新增的其实只有 `X`，但所有节点的位置和连线都可能移动。开发者看到的是“整张图都变了”，很难判断真正的变化。

### 4. 大型 Pass 的图会迅速爆炸

DeepSeek V4 里一个 Pass 后可能出现：

- 数千个 IR 节点；
- 大量循环展开副本；
- 多层嵌套 scope；
- AIC/AIV 并行分支；
- 跨核和跨卡依赖。

全部绘制成图后，会变成难以阅读的“意大利面图”。尤其是 `InlineFunctions` 和 `UnrollLoops`，恰好是最容易导致图规模爆炸的 Pass。

### 5. 不同 Pass 需要不同类型的图

并不存在一种“IR 计算图”能有效解释所有 Pass。

| Pass 类型 | 最合适的图 |
|---|---|
| `InlineFunctions` | 调用图 |
| `CtrlFlowTransform` | CFG 控制流图 |
| `ConvertToSSA` | CFG + def-use/phi |
| `OutlineIncoreScopes` | 函数与作用域层级图 |
| `ConvertTensorToTileOps` | Tensor/Tile 数据流图 |
| `MemoryReuse` | Buffer 生命周期/冲突图 |
| `AutoDeriveTaskDependencies` | Task DAG |
| 通信相关 Pass | 分布式通信图 |

如果强行都使用同一张计算图，必然会丢失每类 Pass 最关键的信息。

### 更好的方案：文本与 Graph 双视图

推荐的形态是：

```text
Pass 时间线
     │
     ├── IR Diff：精确、完整、作为事实来源
     │
     └── Graph Diff：帮助理解结构变化
          ├── CFG
          ├── Dataflow
          ├── Call/Scope
          ├── Task DAG
          └── Memory/Lifetime
```

Graph Diff 可以采用：

- 绿色：新增节点/边；
- 红色：删除节点/边；
- 紫色：属性被修改；
- 灰色：未变化；
- 折叠循环展开产生的重复节点；
- 点击图节点，跳到对应文本 Diff；
- 使用跨 Pass 的稳定语义 ID，而不是 SSA 名字匹配；
- 根据 Pass 类型自动选择合适的图。

例如查看 `OutlineIncoreScopes` 时，Graph 可以直观地展示：

```text
Pass 前
decode_csa
└── InCore Scope
    └── tensor operations

Pass 后
decode_csa_orchestration
└── call decode_csa_incore
             └── tensor operations
```

但参数方向、类型变化、动态 shape、属性变化，仍要回到文本 IR Diff 才能准确确认。

所以最准确的结论是：

> **不是 IR Graph 不能做 Pass Diff，而是它不能替代文本 IR Diff。文本 Diff 负责精确定位，Graph Diff 负责快速理解结构；最好的工具应该把两者同步起来。**
