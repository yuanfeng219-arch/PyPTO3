## 00 开场 · 先看硬件：PyPTO 在解决什么问题（约 70 秒）

**操作**：走到硬件模型前，指一次计算核区域，指一次片上存储与 HBM，然后放下手讲 PyPTO。

**口播**

> 先看这块芯片，两件事就够了。
>
> **计算核是分工的**：AIC 只做矩阵，AIV 只做向量，这款上面 24 个 AIC 配 48 个 AIV。**片上存储是几块各管各的空间**：从 HBM 进来先落 L1，再进 L0 给矩阵核，向量核用另一块 UB。
>
> 在这样一块芯片上写算子，难的不是算法，是三件事：**数据块怎么切**，切大了放不进 L1，切小了核跑不满；**活怎么分**，谁算哪一块、两边怎么交接；**搬运和计算怎么重叠**，不排流水就是算一下等一下。
>
> **PyPTO 要解决的，就是把这三件事变成能写在代码里的东西**：用 Tile 这种硬件感知的数据块编程，经多级 IR 编译成硬件指令；算法开发者停在 Tensor 层，性能专家下到 Tile 层。
>
> 但它留下一个问题：**我写的那一行代码，最后落在这块芯片的哪里？**

## 01 用户痛点 · 三个断点（约 40 秒）

**操作**：切到大屏，停在 Demo 首页。三幕卡片上各有一行灰字，就是下面这三个断点，可以直接指着念。

**口播**

> 从真实反馈里，我们归出三个断点。
>
> **写的时候看不见落点**：源码里是 shape 和 dtype，硬件上是地址和字节，对不上就先估一遍，编译失败再回头查。
>
> **编译器做了什么，源码上没有痕迹**：切分、内存复用、拆成两个核，这些决定只在编译产物里。
>
> **性能图看得懂数字，读不出结论**：一样长的两条，可能一条在算、一条在等。
>
> 三段分散在源码、编译产物和 profiling 里，我们要把它们接成一条闭环。

## 02 设计方案一 · 算子开发：代码旁边就能看见硬件（约 70 秒）

**操作**：点「算子开发」→ 打开 Lens（放大镜图标）→ 悬停 225 行 → 从硅片上的 `qk_kv` 反向悬停回来。

**口播**

> 这是 DeepSeek-V4 里的真实算子 `qk_pv`。
>
> 左边源码、中间算子逻辑、右边硅片落点，**悬停任意一处，三处一起亮**。我停在 225 行的 `create_l1`，逻辑图的「开 L1 缓冲」和硅片上那一块同时亮——**同一个计算对象，三种视角里是同一个身份**。
>
> 不用悬停也能读：标签就写在代码行里，左边说这层循环跑多少次，右边说数据落到 `L1`、`CUBE` 还是写回 `GM`。**编译器已经知道的事，不该等编译完才说。**

**操作**：点顶栏的面板图标展开右栏「问题分析」，第一条「AIV1 空转」默认已展开，指向「问题描述」里 `valid_shape=[0, 0]` 那段证据。

> 这个算子和另一个几乎同构，只差 208 行一个切分参数。后果是 **subblock 1 的每个 tile 都是 `valid_shape=[0, 0]`**——刚才那 48 个 AIV，有一半在空转。读源码看不到，编译没有警告，上板结果还完全正确。**记住这个参数，第三幕要回到它。**

**操作**：点 281 行的 `stage` 切到 1 再切回 2。

> 约束还能带进去推演：stage 点一下，占用跟着变，问题分析栏里多出一条 stage 的分析，推算出来的数一律标「推算」。

## 03 设计方案二 · 性能调优：从「哪里慢」到「改什么」（约 125 秒）

**操作**：回工作台点「编译并上板」，过渡页走完进入 Device Perf Lane。

**口播**

> 执行窗口 5.49 毫秒，**平均计算利用率 27.7%**。数字很清楚，难的是下一句：**接下来改什么？** 这里有三层体验问题。

**操作**：显示设置 → 着色从「默认着色」切到「Setup 占比」，再切「尾块浪费」。

> **第一层：一样长的条形，含义可能完全不同。** 占着时间的核，可能在算，也可能在等。真实反馈里就有人把「在等」读成了负载不均——误读直接导向错误的优化方向。
>
> 所以着色不只有一种：切到「Setup 占比」，`csa_merge` 的 Setup 占 58%，它不是算得慢，是起得太频；切到「尾块浪费」，切分没对齐的尾巴露出来。**同一条泳道，换一次着色就换一个问题。**

**操作**（时间紧可略）：泳道布局切「按物理核」→ 路径分析 → 点「低并行区」。

> **第二层（可略）：知道哪里慢，不知道这个慢是谁造成的。** 按 Task 排是「谁慢」，按物理核排是「哪些核在闲」：并行宽度只有 25%，这一段 0.663 毫秒里不超过两个核在跑。关键路径上的等待第一名挂着它的上游，依赖链也单独列出来——**等待有源头，链条能往回走。**

**操作**：底部切「特征」→ 勾「仅显示候选」→ 再切「优化」看优化候选。

> **第三层：一屏几十个任务，不知道从哪一个开始。** 页面先按特征归类——块负载不均、Setup 占比高、离散小 Task、尾波空置，还有 25 项未标记问题；再给一张排好序的候选：最慢块是平均块的 4.6 倍、3.0 倍、2.3 倍。**每一条都挂着判断依据，采集不到就标「未知」，不靠条形长度猜。**

**操作**：底部切「编译」，停在 `qk_pv` 的 P25 / P28。

> 最后是闭环。点开 `qk_pv` 的编译分析，页面直接指到两个 pass：**P25，Tensor 分片工作量不均**，32 × 128 沿列切成了 32 × 96 和 32 × 32；**P28，C2V 交接 slot 不匹配**，Push 和 Pop 不是同一个 slot。
>
> **这就回到第一幕那个切分参数**——泳道上的 2.3 倍，源头在源码里。

## 04 收尾 · 我们在设计什么（约 30 秒）

**操作**：回首页，停在三幕循环上。

**口播**

> 三条主线：**决策前可预判**、**失败后可追溯**、**优化后可复用**——写代码时看得到落点和代价，从泳道能走回源码，每个方案都带着它要补的证据。
>
> 边界说清楚：**这个 Demo 里编译和上板是模拟的**，数据来自一次真实编译产物和同一次运行的 trace。能证明的是这条路走得通，收益还要靠真实任务去验。

## 备用问答

| 可能的问题 | 回答要点 |
| --- | --- |
| 这些数据是真的吗？ | 地址与分配取自 `36_after_AllocateMemoryAddr` 真实编译产物，trace 是同一次运行的预置数据；页面上「真实」与「推算」分开标注。编译与上板为模拟。 |
| 为什么选 `qk_pv` 这个案例？ | 它一次命中三个断点：源码看不出后果、编译无警告、结果正确但算力没用满——正好要走完整条路才能判断。 |
| AIV 空转要不要改？ | Demo 不给结论。如果瓶颈在 AIC 的两次 K=512 matmul 和 L1 拼块，AIV 空着不影响端到端；要 profiling 才能回答。这正是「方案要带证据」的意思。 |
| 三种着色模式会不会太多？ | 三种对的是三个问题：默认看时长，Setup 占比看启动开销，尾块浪费看切分对不齐。默认只开一种，另两种按需切换。 |
| 优化候选那几个倍率分别是谁？ | 4.6× 是 `qr_hadamard_matmul`，3.0× 是 `indexer_topk_query_merge`，2.3× 是 `qk_pv_aic`；`tp_o_a_quant` 的 8 次短提交累计 0.021 ms 核时。 |
| 行内标签会不会太吵？ | 源码栏顶部有开关可一键关掉，回到纯代码；图例在 ⓘ 里。 |
| 和现有工具链是什么关系？ | 这是体验方案原型，不替代 Toolkit；要验证的是跨视角定位和证据链能否降低理解成本。 |
| 首页那个「可视化编译」入口呢？ | 本次不演示。它把 51 个 pass 摊成九段，是「编译器做了什么」这条线的延伸，留作追问时再开。 |

## 可裁剪与可加长

- **压到 3 分 30 秒**：开场三件难事只留「数据块怎么切」和「活怎么分」；痛点只留第一条和第三条；第三幕砍掉第二层（按物理核与依赖链），保留着色、候选和 P25／P28 闭环。
- **放到 6 分钟**：第三幕把优化候选逐条念出名字和倍率，并在第一幕打开问题分析栏、展开「AIV1 空转」的「修改建议」——选方案 A 后页面会列出重新编译要查哪几个 pass、上板要比对什么，这是「优化后可复用」最具体的一页。
- **有人追问编译过程**：再开首页第二个入口「可视化编译」，51 个 pass 分九段，停在 36 号 `AllocateMemoryAddr`，也就是刚才那些地址被定下来的地方。

## 本稿的事实边界

- **PyPTO 定义**：核心特性、分层抽象与目标用户的说法照 `repo/pto/README.zh-CN.md` 概述，未作引申。
- **开场「三件难事」**：切分、核间分工、搬运与计算重叠，是对 Tile 编程要处理的问题的机制层概述，用于铺垫，不是 README 的原文表述，也不含任何收益数字。
- **硬件数字**：24 AIC／48 AIV、UB 标称 192 KB 可用 184 KB，取自本 Demo 所用的 a2a3 编译产物口径；换设备需重新核对，不要泛化到所有昇腾型号。
- **页面事实**：联动方式、行内标签、`valid_shape=[0, 0]` 证据，以及第三幕引用的全部数值与控件——5.49 ms、27.7%、低并行 0.663 ms、并行宽度 25%、`csa_merge_pack_publish` Setup 58%、最慢块／平均块 4.6×／3.0×／2.3×、`tp_o_a_quant` 8 次短提交 0.021 ms 核时、25 项未标记问题、`qk_pv` 的 P25／P28——均取自 2026-11-09 `result.html` 的实际呈现。
- **已有反馈**：Vector 子块「等待被误读成计算」一类问题，来自问题地图引用的 pypto-lib #531；只引现象与排查过程，不引收益数字。
- **待验证**：「降低理解成本」「减少无效实验」属于设计假设，需按问题地图第 4 节的观察任务验证，不写成已证实结论。
